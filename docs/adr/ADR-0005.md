# ADR-0005 — Archetypes define topology; flags form independent dimensions

**Status:** accepted (2026-09-15) · **Scope:** the archetype catalogue and every
generated repository

## Decision

An archetype defines a repository's structural topology, its toolchain and its
release model. Flags select orthogonal capabilities, implementation libraries or
profiles *within* that shape.

The configuration space is the matrix of archetypes and supported flag values.
**Orthogonal means separately selectable, not universally compatible**: the spec
names the valid combinations, rejects incompatible ones, and distinguishes
shipped cells from deferred or untested ones.

A flag may vary generated fragments or implementation-specific files without
changing the archetype's structural identity. A choice that changes that
identity belongs in a different archetype. No two selectors may encode the same
choice.

## Consequences

- A capability is reused across archetypes without duplicating repository
  shapes.
- Every supported matrix cell needs its own validation. Adding a flag is not
  adding support for every combination of it.
- Names, defaults, dependency sets and shipped combinations are specifications,
  not further decisions — they change without an ADR.
- The catalogue grows by dimension rather than by product, so a new capability
  costs one flag instead of N archetypes.

## Alternatives considered

- **An archetype per framework and capability combination.** The catalogue grows
  as the product of every choice, and each cell carries its own template copy
  of the same shape.
- **One generic archetype driven entirely by flags.** The name then says nothing
  about the repository's structure or release model, so nobody can tell from
  `--archetype` what they are getting.
- **"Is it a monorepo" as the top-level axis.** Considered and rejected: it does
  not discriminate, because every archetype here can be one. *Publishing* does
  — per-package release tags and a per-package CI matrix, versus one version.

## Background

The catalogue was cut from a longer list to a small set of names plus
implementation flags (D53). Two findings forced the current shape: `python-app`
and `python-tool` differed by a name and one dependency line, which became the
`lifecycle` flag over a tool adapter (D59, D61); and the near-identical
`pyproject.toml` tool tables were examined for generation and left
repository-owned with a divergence warning instead, because generating them
would not have deduplicated anything (D60).

The rule that every shipped cell must be demonstrated by a rendered, runnable
golden repository came from the Phase C review, which found the policy being
broken by the templates it governed.
