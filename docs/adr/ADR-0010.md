# ADR-0010 — The canon carries an architecture baseline, as managed records

**Status:** proposed (2026-09-28) · **Scope:** the product code of every
generated repository

## Decision

kiln renders an architecture baseline into every generated repository: a small
set of decision records that fix the design of the product code, not only the
repository around it. They are managed artifacts under
`.rn-forge/kiln/baseline/`, hash-checked like any other kiln file.

A record belongs in the baseline only if it follows from the repository's
topology and stack, never from its domain. The test: it holds for a business API
and for a dashboard microsite alike. Auth schemes, storage engines and
domain-modelling styles fail that test and stay with each repository.

Records are composed from the configuration's dimensions, as the task vocabulary
is ([ADR-0007](ADR-0007.md)): each record says which archetypes and flags it
applies to, and a repository gets the union. A record enforceable by an import
contract is enforced by one, in the managed `.importlinter`.

A repository departs from a record through an ADR of its own that names the
record and the part it supersedes. It never edits the record.

## Consequences

- A new repository starts with a stated architecture, and an agent building its
  first feature has a design to follow and a contract that fails when it
  strays.
- A record is written once and reaches every repository it applies to. Changing
  one changes the architecture of every repository at its next
  `kiln config upgrade`, so a changed record ships as a noted, breaking
  release change.
- Record identifiers (`B-<nnnn>`) are global, so `B-0001` means the same thing
  in every repository. They are never renumbered or reused.
- The cost: a baseline must stay generic, so it says less than a repository's
  own design would. And the goldens keep their product code trivial, so they
  prove the contracts render and pass, not that the patterns are right.

## Influences

The records, the catalogue and the contracts are
[E12](../specs/epics/E12-architecture-baseline/index.md) and its
[design](../specs/epics/E12-architecture-baseline/design.md). The ownership
table in [the reference](../reference/standard-repo.md) gains
`.rn-forge/kiln/baseline/`.

## Alternatives considered

- **Seeded records.** The repository would own them after scaffolding, and
  doctor ignores seeded files ([ADR-0003](ADR-0003.md)). Each repository's
  copy would drift, and nothing would notice.
- **Seeded but drift-checked.** ADR-0003 rejected enforcing seeded files: a file
  doctor checks but the repository may edit has two owners, and neither can
  tell an intended change from drift.
- **One comprehensive record per archetype.** It would enumerate layers, names
  and patterns, which makes it a spec, not a decision. Every archetype × flag
  cell would also need its own copy of the shared parts.
- **Records under `docs/adr/`.** A repository with the `external` or `none` docs
  profile has no `docs/` tree, and managed files there would share a directory
  listing with the repository's own ADRs and their numbering.
- **Prose in `standard.md` only.** It carries no identifier a repository's ADR
  can cite and supersede.
