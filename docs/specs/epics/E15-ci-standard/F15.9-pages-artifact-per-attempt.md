The `docs` job names its Pages artifact after the run attempt, and
`deploy-pages` deploys that one. Re-running a failed `docs` job then deploys,
with no artifact to delete by hand first. When `deploy-pages` fails because the
run's artifact listing does not show the upload yet, the job waits and deploys
once more before failing.

## Context

`upload-pages-artifact` names its artifact `github-pages` by default, and
`deploy-pages` requires exactly one artifact of that name in the run. A re-run
is a new attempt of the same run, and it keeps the artifacts of every earlier
attempt. So once an attempt has uploaded the site, a re-run's deploy finds two
artifacts and fails. The only way out is to delete the old artifact through the
API, or to push a new commit.

pykit hit this on the merge of its Release 12 pull request. Attempt 1's
`deploy-pages` listed the run's artifacts less than a second after the upload
finalized and found 36 of 37, without `github-pages`. It failed with
`No artifacts named "github-pages" were found`, and its own message says to
re-run. Attempt 2 rebuilt and uploaded the site, then failed with
`Multiple artifacts named "github-pages" were unexpectedly found … Artifact count is 2`.
Every other job in the run had passed. The first failure was GitHub's; the
second is kiln's, because the template makes the re-run that message asks for
unable to succeed.

All three branches of `_docs.yml.j2` share the defect: `node-lib`, the Python
workspace, and the single-package archetypes.

The listing race is not rare. pykit's Release 12 shipped merge, CI run
45543671407, failed it on attempt 1: the upload finalized at 04:10:29.94 and
`deploy-pages` found 0 artifacts at 04:10:30.46. Attempt 2 failed on the
duplicate name. Before attempt 3 the owner deleted the old artifact, so the
re-run uploaded the run's only `github-pages` artifact, and `deploy-pages` still
found 0 artifacts 0.36 s after it finalized. Naming per attempt would have fixed
attempt 2 and not attempts 1 or 3. Upstream,
[actions/deploy-pages#451](https://github.com/actions/deploy-pages/issues/451)
reports the same race with the same pins (`upload-pages-artifact` `fc324d3`,
`deploy-pages` `368f825`). It has happened on most runs since about 2026-11-22.
A 2-second sleep fixed it for one reporter and stopped being enough on
2026-11-24. GitHub's status page showed Actions, Pages and API Requests as
operational, and the owner sees the failure in other repositories too. A re-run
is no remedy for a failure that happens on most runs.

## Design

**One artifact name per attempt.** In each branch of
`src/rn_forge/kiln/modules/cicd/templates/workflows/_docs.yml.j2`, the upload
step gains `name` and the deploy step gains `artifact_name`, the same value in
both:

```yaml
      - name: Upload Pages artifact
        uses: actions/upload-pages-artifact@<sha> # v5.0.0
        with:
          name: github-pages-${{ github.run_attempt }}
          path: ${{ runner.temp }}/site

      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@<sha> # v5.0.1
        with:
          artifact_name: github-pages-${{ github.run_attempt }}
```

`node-lib`'s upload keeps its `include-hidden-files: true`. Nothing else in the
job changes: not the environment name `github-pages`, not the concurrency group
or the permissions, and not the pins. The value is not used in a `run:` script,
so it raises no template-injection finding.

**A second deploy after a pause.** In each branch, the deploy step becomes three
steps in the same job. The first deploy carries `continue-on-error: true`. If it
fails, a wait step and a second deploy follow, and the second deploy's result is
the job's:

```yaml
      - name: Deploy to GitHub Pages
        id: deployment
        continue-on-error: true
        uses: actions/deploy-pages@<sha> # v5.0.1
        with:
          artifact_name: github-pages-${{ github.run_attempt }}

      - name: Wait for the artifact listing
        if: steps.deployment.outcome == 'failure'
        run: sleep 30

      - name: Deploy to GitHub Pages again
        id: deployment-retry
        if: steps.deployment.outcome == 'failure'
        uses: actions/deploy-pages@<sha> # v5.0.1
        with:
          artifact_name: github-pages-${{ github.run_attempt }}
```

The environment's `url` takes whichever deploy succeeded:
`${{ steps.deployment.outputs.page_url || steps.deployment-retry.outputs.page_url }}`.
`node-lib`'s two deploy steps keep having no `name:`; its wait step is named as
above. The retry adds no permission, no job and no output, so the concurrency
group, the environment and the permissions stay as they are. The pause is a
fixed 30 s, more than ten times the delay that stopped being enough upstream. It
is paid only on a failed first try.

The first deploy fails here before it creates a deployment, at the artifact
lookup. A first deploy that fails later, after it has created one, is a
different failure, and the second deploy may fail on it too. In that case the
second deploy's error is the job's error, as it is today.

## S15.9.2 — A failed deploy is tried once more after a pause

**State:** Closed (2026-11-25)

**Tests first.** Run them and show them failing.

- In `tests/modules/cicd/test_pages.py`, `test_docs_job_steps_in_order` (the
  `node-lib` docs job) expects the last three steps to be:

    - the first deploy, with `id: deployment`, `continue-on-error: true` and the
      per-attempt `artifact_name`;
    - the wait, with `if: steps.deployment.outcome == 'failure'` and
      `run: sleep 30`;
    - the second deploy, with `id: deployment-retry`, the same `if` and the same
      `artifact_name`.

- In the same file, `test_node_lib_renders_no_docs_yml_and_one_docs_job` expects
  the environment `url` to be the `||` of the two deploys' `page_url` outputs,
  and `test_docs_job_steps_have_no_id_env_or_if` allows `if` and `id` only on
  those last three steps: `id` is `deployment` or `deployment-retry`, and `if`
  is `steps.deployment.outcome == 'failure'`. Every other step still has no
  `env`, `if` or `id`.

- In `tests/modules/cicd/test_stages.py`,
  `test_docs_job_permissions_and_environment` (the single-package archetypes)
  and in `tests/modules/cicd/test_pipeline.py`, `test_python_lib_docs_job`
  (the workspace) assert the same three steps and the same `url`. The upload
  step is the one before them.
  `test_docs_hooks_run_in_order_before_pages_deploy` expects the last four
  step names to be the upload, `Deploy to GitHub Pages`,
  `Wait for the artifact listing` and `Deploy to GitHub Pages again`.

**Build.** In each of the three branches of `_docs.yml.j2`, replace the deploy
step with the three steps the design shows, and change the environment `url`.
Re-render kiln's own workflows and goldens the way the repository does for a
template change.

**Acceptance:**

- The updated tests pass, and failed before the template change.
- Every rendered `_docs.yml` has the three deploy steps and the `||` `url`.
  `test_actionlint_passes` and `test_actionlint_passes_on_the_docs_job` pass,
  and zizmor reports no new finding.
- `task validate`, `task lint KILN_DOCTOR_FULL=1` and
  `task self:golden:validate` pass.

## Acceptance

- Both stories' acceptance holds.
- pykit, the first consumer, moves its `[kiln] ref` to the commit that closes
  S15.9.2 and runs `task kiln:apply`. It then deploys Pages from a `main` run
  without a manual re-run, or with the first deploy failing and the second
  succeeding. That is pykit's work and is not written here.

## Considered and rejected

- **Delete the previous attempt's artifact before uploading.** It needs
  `actions: write` on the job and a `gh api` step, and it widens the
  permissions of a job that already holds `contents: write` and
  `id-token: write`. Naming per attempt needs no new permission.
- **A fixed wait before every deploy.** Every run would pay for it, even the
  runs that need no wait, and upstream a 2-second sleep stopped being enough.
  The second deploy waits only after a failure.
- **Deploy in its own job.** It adds a delay between upload and deploy, but a
  delay alone has stopped being enough (#451), and the second deploy covers
  the same failure. It would also have to take the artifact name from the
  build job's outputs; whether a re-run of only the deploy keeps those outputs
  is unverified. The `pages` concurrency group would have to move to the
  calling job in `ci.yml`, or one run's queued deploy could cancel another
  run's queued build. And the environment would move off the build job, taking
  its secrets and the OIDC token away from `hooks.docs`. Revisit it if the
  second deploy still fails, or to take the Pages and OIDC permissions away
  from docs hooks.
- **Name the artifact after the run ID.** Every attempt of a run shares its ID,
  so the names would still collide.
