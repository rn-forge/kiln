E7's scope items 1 and 3: tag an `rn-forge-kiln` release, then each repository
moves its kiln pin with `kiln upgrade` ([ADR-0006](../../../adr/ADR-0006.md))
and runs `kiln config upgrade --apply`. Added 2026-10-17 by S6.1.14, so that
E7's `Active` state has a feature to agree with.

Since [F7.4](F7.4-kiln-runs-beside-the-repository.md), a repository's kiln pin
is `[kiln] ref` in `.rn-forge/kiln/config.toml`, not a dev dependency. "Moving
the pin" therefore means:

1. set that ref to the new tag;
1. run `kiln apply`, which re-renders the `KILN` var in `tasks/kiln.yml` and
   `tasks/docs.yml`.

The cut also sets `archetypes.KILN_REF` from `feature/v1` to `v<version>`, so
`kiln new` pins the release.

## Context

**The version (owner decision, 2026-10-31).** The tag is `v0.1.0`, the version
in `pyproject.toml`. "Release 1" names the scope and is not a version number.

**Distribution.** kiln stays on git, through `uvx --from git+…@<ref>`.
Publishing it to PyPI stays the idea `kiln-on-pypi`.

**Order matters.** `KILN_REF` names a tag that does not exist until the commit
that names it reaches `main` and `release` runs, so that commit is the last one
before the merge. Nothing renders from it before the tag exists.

## S7.2.4 — Run the cutover SOP on pykit, then ngkit

**State:** New · **Depends on:** S7.2.1, S16.1.4, S16.2.3, S16.3.1, S15.2.3,
S15.3.3, S15.4.2, S15.5.2, S15.6.1 · **Owner's story:** a decision, not code

Rewritten 2026-11-04 (owner). The earlier text asked for throwaway rehearsals
that classified losses as covered, dropped or gap, and ran the repository's own
cutover story. The owner settled the approach in
[E16](../E16-init-adopts-by-overwrite/index.md): `init` is opinionated, and one
runbook,
[the cutover SOP](../E16-init-adopts-by-overwrite/F16.3-cutover-sop.md), is
followed for each repository. This story runs it.

**Absorb first.** pykit's cutover pull request declares no `[[ci.jobs]]` for a
check [E15](../E15-ci-standard/index.md) covers: licences, the secret scan,
internal ranges, the umbrella release and Scorecard. Only `broker-profile.yml`
stays pykit's, as a repository-owned scheduled workflow
([F15.7](../E15-ci-standard/F15.7-repo-owned-workflows.md)). The pull request
deletes `main.yml` in the same change that adds `ci.yml`: both share the
concurrency group, and the ruleset requires the context `ci-ok`.

**Build:** none in kiln, unless a verdict is **absorb**. For pykit, then for
ngkit, in a fresh clone on a branch, with kiln run from this checkout's
`feature/v1` commit and not a tag (`tests/e2e/ngkit_shape.sh` shows how to point
`[kiln] ref` at a local one):

1. Follow `docs/runbooks/cutover.md` steps 1 to 7. The branches are never pushed
   or merged: the real cutovers stay pykit's
   [F16.3](https://github.com/rn-forge/pykit/blob/main/docs/specs/epics/E16-kiln-adoption/F16.3-cutover.md)
   and ngkit's
   [F17.2](https://github.com/rn-forge/ngkit/blob/main/docs/specs/epics/E17-kiln-adoption/F17.2-cutover.md),
   on the tag ([ADR-0009](../../../adr/ADR-0009.md)).
1. Record the verdict table under this story, one per repository, in the
   runbook's format, with the kiln commit, the repository commit, and the exit
   status of `task setup` and `task validate` after the second `init`.

**Acceptance:**

- One verdict table per repository, in this story. Not scriptable.
- Every **absorb** row is a release-1 story, closed before S7.2.2, or an idea
  the owner moved out of release 1.
- After the second `init`, `task validate` exits `0` in each clone.
- The owner records that kiln needs nothing more for release 1.
