A release run on the default branch writes `security-evidence.json`: for each
security control, its result on the pushed commit and a link to the evidence. An
`evidence` job of `ci.yml` writes it once `release` and `verify-release` are
done. The job uploads it as a run artifact and writes it to the job summary as a
table.

## Design

The controls come from kiln's check registry, so a control is added or retired
in one place. Each control has a name, its effect (fails the build, or only
reports) and a source for its result:

| Control | Result from | Evidence |
| -- | -- | -- |
| Dependency audit (`pip-audit`, `pnpm-audit`) | the conclusion of the job that runs `task lint` | that job's URL and the step name |
| Licence inventory (`licenses`) | the same job | the same, with the deny list in force |
| Source scan (ruff's `S` rules; `node-lib`: its lint) | the same job | the same |
| Secret scan (`secret-scan`) | the `secret-scan` job's conclusion | the job's URL |
| Push protection | not read by CI: recorded `not checked`, and filled by `evidence render` ([F21.2](F21.2-evidence-page.md)) | the API call and its date |
| SBOM | a `*.cdx.json` asset on each package's GitHub release | the release URL and the asset names |
| Attestation | `gh attestation verify` on each released artifact; with `[ci] release = "pypi"`, the PyPI integrity API returns provenance for each wheel | the HTTP status per file |
| `SECURITY.md` | the file exists at the repository root at the pushed commit | its path |
| Scorecard (`scorecard`) | the newest `scorecard.yml` run on the default branch | its run URL, score, version and the commit it scored |

A control the repository does not run, such as Scorecard when
`[ci.checks] scorecard` is off, is recorded as `not run`, never left out. The
record names the commit, the run ID and the attempt, and each released package
with its version and tag.

## S21.1.1 — The control catalog

**State:** Closed (2026-11-24)

**Acceptance:**

- Each control in the design table has a registry entry giving its name, its
  effect and where its result comes from, and the catalog is rendered into
  `.rn-forge/kiln/standard.md` beside the CI checks.
- A test asserts that every security check in the registry has a catalog entry,
  so a new check without one fails `task test`.

The catalog is `CONTROLS` in `rn_forge.kiln.modules.cicd.controls`, each control
with an `Effect` and a `Source`; a registry check is a security check when its
`security` flag is set.

## S21.1.2 — `kiln-devops evidence collect`

**State:** Closed (2026-11-24) · **Depends on:** S21.1.1

**Acceptance:**

- `kiln-devops evidence collect --run <id> --sha <sha>` writes
  `security-evidence.json` with one entry per catalog control: `name`,
  `effect`, `result` (`passed`, `failed`, `not run` or `not checked`),
  `evidence`, and the commit, run, attempt and released packages.
- It reads only the GitHub API and the registry's public API, and never writes
  to either.
- Tests cover a run where every control passed, a run with a failed job, a
  package with no SBOM asset, a repository with Scorecard off, and a Scorecard
  run on an earlier commit than the pushed one, whose row names that commit.
  They use recorded API responses, not the network.

The catalog reaches it as a controls file, `--controls FILE` (owner decision,
2026-11-24, since `kiln-devops` imports no other kiln code): a `release` mode
and one `{name, effect, source, runs, job?, step?}` entry per control. Each
record entry's `evidence` is `{url, detail}`, and the command prints the record
as a Markdown table.

## S21.1.3 — An `evidence` job runs it

**State:** New · **Depends on:** S21.1.2

**Acceptance:**

- With `[ci.checks] release-evidence = true`, `ci.yml` has an `evidence` job,
  run on a push to the default branch after `release` and `verify-release`,
  that runs `task ci:release:evidence`. The task uploads
  `security-evidence.json` as the artifact `security-evidence` and appends the
  table to `$GITHUB_STEP_SUMMARY`.
- The check is off by default, and `release-evidence = true` with
  `[ci] release = "none"` is an error, as it is for `umbrella-release`.
- `ci-ok` waits for `evidence`. A control that failed does not fail the
  `evidence` job, because the job that ran the control already failed.
- `zizmor` and `actionlint` accept the rendered workflow, and the job's token
  has `contents: read`, `actions: read` and `attestations: read` only.

## Acceptance

```bash
set -euo pipefail
task test -- -k "s21_1_1 or s21_1_2 or s21_1_3"   # S21.1.1, S21.1.2, S21.1.3
task validate                                      # S21.1.3: the rendered ci.yml passes zizmor and actionlint
```

Not scriptable: a real release run uploads `security-evidence` and shows the
table in its summary (S21.1.3).
