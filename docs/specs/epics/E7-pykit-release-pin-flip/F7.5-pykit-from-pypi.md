pykit publishes every `rn-forge-*` package to pypi.org. kiln stops declaring
pykit's GitHub Pages index in what it renders, takes its own pykit dependencies
by range from PyPI, and tells a repository that still declares the index to
delete it.

## Context

**Why.** [ADR-0018](../../../adr/ADR-0018.md) renders a
`[[tool.uv.index]] name = "rn-forge"` table in every Python root with an
rn-forge requirement, pointing at `https://rn-forge.github.io/pykit/simple/`.
Under uv's default `first-index` strategy, uv asks that host about every
package, third-party ones included. GitHub Pages throttles it, and
[S6.4.5](../E6-rebuild-the-repos/F6.4-workspace-pipeline.md#s645-the-pykit-shaped-repository-runs-it)'s
reruns failed on `429 Too Many Requests`. With the packages on PyPI, the default
index serves them and the table is not needed.

**Why release 1 (owner decision, 2026-10-31).** This feature was planned for
release 2. pykit's Release 7 published to PyPI first, so nothing is waiting on
kiln's tag any more, and it removes the 429 that holds up
[S6.4.5](../E6-rebuild-the-repos/F6.4-workspace-pipeline.md#s645-the-pykit-shaped-repository-runs-it)
and F6.7's acceptance.

**PyPI has only the newest versions.** Each package's Release 7 version is its
first on pypi.org: `rn-forge-commons` 0.8.1 is the only commons there. A range
with a ceiling of `<0.8` has no solution, so the floors move first (S7.5.6). A
scratch copy of kiln at these floors, on 2026-10-31, locked from PyPI and passed
its suite apart from the literals S7.5.6 names, and a rendered `python-web-api`
passed its tests on `rn-forge-fastapi` 0.4.0.

**What does not change.** The requirements stay ranges, from
`archetypes.requirement`, with floors read from `RN_FORGE_TAGS`. pykit keeps
creating `<name>-v<version>` tags, so the table and its name stay as they are.
The `rn-forge-devops` git pin in `modules/tasks/artifacts.py` is
[F6.7](../E6-rebuild-the-repos/F6.7-kiln-devops.md)'s to remove, not this
feature's.

**Ordering with pykit.** pykit keeps the index until its F21.5, whose entry
criterion is "a kiln release whose archetypes emit no pykit index". This
feature's release is that kiln release. Locks written before it still name the
index, and they keep resolving until F21.5.

**What a repository sees.** After its kiln pin moves to the release with this
feature, `task lint` fails on `deps.pykit-index` until the table is deleted. The
next `task setup` (`uv sync`) re-locks, and moves each `rn-forge-*` package's
source to pypi.org. That one-time lock diff is the upgrade.

**Out of scope.** Publishing kiln itself to PyPI (idea `kiln-on-pypi`).

## S7.5.1 — ADR-0018 revised: rn-forge packages come from PyPI

**State:** Closed (2026-10-31)

**Build:** revise [ADR-0018](../../../adr/ADR-0018.md) in place, status
`revision proposed (<date>)`.

- **Decision:** rn-forge requirements are ranges resolved from PyPI. No
  repository declares an index for them. A `[[tool.uv.index]]` entry with
  pykit's Pages URL is a finding.
- **Consequences:** add "the index-first lookups that throttled CI (F6.4) stop";
  remove the consequences about declaring the index.
- **Background:** a dated line naming pykit E21 and this feature.
- `docs/adr/index.md`: the 0018 row's title follows the ADR's.

**Acceptance:**

- The owner flips the status to `accepted (<date>)`. Not scriptable.

**What the build settled that the story did not say:**

- **The owner accepted the revision in advance**, 2026-10-31, so the status
  reads `revised and accepted (2026-10-31)` and not `revision proposed`.
- **The ADR's title** drops "pykit's package index" and reads "from PyPI", and
  the Background section sits before the Decision.
