# S18.10.13 — The config refuses what it cannot render

Brief for
[S18.10.13](../F18.10-review-defects.md#s181013-the-config-refuses-what-it-cannot-render),
at `feature/v1` after `7d4abbd`.

## Goal

Four inputs the config accepts today but cannot render are refused with an
`AppException` that names the offender: an archetype spelled `python_tool`, a
`ci.release` the archetype cannot take, a malformed `docs/_areas.yml`, and (the
fourth) a `python-app` with `lifecycle = true` gets the tool starter.

## Settled

- **Archetype name.** In `archetypes.load`
  (`src/rn_forge/kiln/archetypes/__init__.py`), refuse a name that is not in
  `shipped()` with the existing `Unknown archetype {!r} — this kiln ships {}`
  message. The `name.replace("-", "_")` stays only to find the directory.
- **Release.** `ConfigManager.validate`
  (`src/rn_forge/kiln/modules/core/config/manager.py`) builds the
  `KilnConfig`, then reads `config.release` once inside `try`, and turns a
  `ValueError` into `AppException("{}: {}", source, error)`. The message
  already starts `ci.release = 'pypi' needs a library workspace`, so it names
  the key.
- **Areas manifest.** In `src/rn_forge/kiln/modules/docs/areas.py`, `Area`
  becomes a frozen `StrictModel` (from `rn_forge.commons.lang.models`) with
  `key: str`, `title: str`,
  `nav: Literal["children", "index-only", "include", "work"] = "children"`,
  `optional: bool = False`, `generated: bool = False`. A
  `model_validator(mode="before")` sets `title` from `key.title()` when `key`
  is a string and `title` is absent. A new `AreasManifest(StrictModel)` holds
  `areas: list[Area] = []`. `load_areas` keeps its three early refusals (file
  absent, top level not a mapping) and then returns
  `AreasManifest.parse(raw, source=str(manifest)).areas`;
  `ModelValidationError` is an `AppException` and names the dotted key.
  `NAV_VALUES` and the dataclass imports go. `nav.py` and `structure.py` read
  only attributes, and `PACKAGES_AREA = Area(key=..., title=..., nav=...)`
  still constructs.
- **Lifecycle starter.** `python/starter.py` `render` picks the tool starter
  when `config.lifecycle` is true: `tool = config.lifecycle` (that property is
  true for `python-tool` too). Evidence it is the right one, so no owner
  decision: the archetype manifest says `python-tool` is "python-app with
  `lifecycle = true`" (ADR-0005), `AGENTS.md` already shows such a repo as
  `python-tool` (`_display_archetype` in `instructions/artifacts.py`),
  `cli.toml` and the `rn-forge-tooling` requirement already follow
  `lifecycle`, and the app starter's `main.py` has no `[lifecycle]` product to
  mount. The other option (show `python-app` in `AGENTS.md`) is rejected: it
  would contradict ADR-0005.
- Rejected (do not build): a pydantic validator on `CiConfig` (it cannot see the
  archetype), and keeping `Area` a dataclass with a second model beside it.

## Current behaviour

Probed on a `python-app` repo made with the `repo` fixture:

- `archetype = "python_app"` loads (`KilnConfig.load` returns a config);
  `archetypes.load("python_tool")` finds the `python_tool` directory.
- `[ci] release = "pypi"` loads; `.release` then raises a bare `ValueError`
  (`ci.release = 'pypi' needs a library workspace`).
- `load_areas` on `areas:\n  - just a string` raises `ValueError`
  (`dictionary update sequence element #0 has length 1`); on `areas: 3` raises
  `TypeError`; on an entry with an unknown key (`bogus: 1`) returns the area
  and drops the key.
- `starter.render` for `python-app` with `lifecycle = true` returns the three
  app files (no `product.py`, no `tests/test_product.py`).

## Change

- **Change:** the four files above.
- **Overlap:** none with `devops/requirements.py`, `cicd/config.py`,
  `tasks/config.py`, `tasks/checks/layout.py`, `docs/site.py` or
  `docs/structure.py`.
- **Leave alone:** templates, `cicd/config.py`'s `resolve_release`, and
  `structure.py` (it already catches `AppException` from `load_areas`).
