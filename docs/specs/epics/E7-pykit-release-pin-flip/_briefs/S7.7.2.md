# S7.7.2 — Generated `python-tool` repositories install the same way

Brief for
[S7.7.2](../F7.7-kiln-installs-as-a-tool.md#s772-generated-python-tool-repositories-install-the-same-way),
at `b4801b2`.

## Goal

The `product.py` kiln renders for every `python-tool` repository subclasses
pykit's `PythonTool`, as kiln's own does since S7.7.1, so a generated tool
installs itself from an archive and its `bin/<tool>` runs.

## Settled

- **The template**
  `src/rn_forge/kiln/modules/python/templates/starter/product.py.j2`:
  `class Tool(PythonTool)` instead of `Tool(ToolProduct)`; drop its
  `artifacts()` (`PythonTool.artifacts()` returns
  `(Link("bin/<name>", "bin/<name>"),)` for the product's `name`, the same
  link); keep `check_home` and `checks()`; keep
  `PRODUCT = Tool(name=…, version=version("{{ name }}"), repo=…)`. Imports:
  `from rn_forge.tooling.install import Check, PythonTool, ToolHome`. Update
  the class docstring the way S7.7.1 did kiln's (see
  `src/rn_forge/kiln/product.py`).
- **The generated test** `templates/starter/test_product.py.j2` (it renders as
  the repository's `tests/test_product.py`) is unchanged: its
  `test_the_one_artifact_is_the_command_on_path` still holds.
- **The floor already matches.** S7.7.5 set `RN_FORGE_TAGS`'s tooling tag to
  `rn-forge-tooling-v0.3.3`, the rendered and kiln's own floor. Change nothing
  there.
- **The self-install test needs the network**, as S7.7.1's does: `uv` resolves
  the generated tool's dependencies from pypi.org. It carries `requires("uv")`
  from `tests.conftest`, and passes an absolute `UV_CACHE_DIR` (kiln's
  `.uv-cache`, resolved against the kiln repository root) to every `uv`
  subprocess. No `UV_OFFLINE`.
- Tests are named for behaviour, `test_<subject>_<behaviour>`, with no spec ID
  in a name, docstring or comment.

## Current behaviour

At the base commit:

- `product.py.j2` renders `class Tool(ToolProduct)`, whose default `build`
  copies the release tree and leaves no `bin/<tool>`. S7.7.1 observed the same
  defect on kiln: the install exits 0, but `bin/<tool>` is a broken link and
  `<tool> self doctor` reports `install.link-broken`. The new test below fails
  on its `--help` run (the link target does not exist). Record what you see.
- `tests/modules/python/test_starter.py` checks the rendered starter files
  (`by_path["src/python_tool/product.py"]`); copy its shape for the template
  assertion.
- `tests/commands/test_lifecycle.py` holds S7.7.1's `installed` fixture (git
  archive, absolute `UV_CACHE_DIR`, `RNF_HOME` under `tmp_path`); copy its
  environment handling.
- `tests/conftest.py`'s `rendered_copy("python-tool")` gives a writable copy of
  a `kiln new --archetype python-tool` repository (tool name `python-tool`,
  package `python_tool`), with no `.git`; `uv sync` gives it its `.venv`.

   `test_tool_product_is_a_python_tool`: the rendered
   `src/python_tool/product.py` contains `class Tool(PythonTool)` and no

1. In a new `tests/commands/test_tool_install.py`:
   `test_a_generated_tool_installs_itself_from_an_archive`, `requires("uv")`:
    - `root = rendered_copy("python-tool")`;
    - `uv sync` in `root` (subprocess, `cwd=root`, the absolute `UV_CACHE_DIR`,
      `VIRTUAL_ENV` removed from the environment);
    - write `python-tool-0.1.0.tar.gz` under `tmp_path` with `tarfile`, every
      file of `root` under the prefix `python-tool-0.1.0/`, excluding `.venv`,
      `.uv-cache`, `.git` and `__pycache__`;
    - run
      `root/.venv/bin/python-tool self install --archive <tarball> --version 0.1.0`
      with `RNF_HOME=<tmp_path>/home`; it exits 0;
    - `<tmp_path>/home/bin/python-tool --help` exits 0;
    - `root/.venv/bin/python-tool self doctor` (same `RNF_HOME`) exits 0 and its
      output holds `install.ok`.

Both fail before the template change: the first on the class line, the second on
the `--help` run.
