# F4.3 — The concern modules, with templates

Epic: [E4](index.md) · Phase step: D.3 · Design:
[template inventory](design.md#template-inventory),
[apply sequence](design.md#apply-sequence) · **Depends on:**
[F4.2](F4.2-core-module.md); the [E3](../E3-realign-goldens-and-canon/index.md)
goldens, which the templates are written from

In apply order, one at a time, each with its config model, options, Jinja
templates written from the E3 goldens, and `checks()` = its checks functions +
its render-dependent checks (`artifact.stale`, `block.stale`).

**Every story in this feature is done only when, for its module, tests show
that:**

1. Rendering a small config for each Python archetype produces exactly the
   module's rows of the template inventory.
1. Into an empty directory, the module's artifacts classify only `CREATE`,
   `INSERT` or `SKIP`.
1. A second apply is all `UNCHANGED`.
1. Each rendered file equals its counterpart in the E3 goldens, apart from name
   and provenance-version lines.
1. Each of the module's checks fails on a fixture that breaks its rule, and
   passes on the rendered output.

The story-specific acceptance below is in addition to these.

## S4.3.1 — `python`

**Status:** planned

`uv init` + reconcile, `.importlinter`, pyproject check 8a including `[project]`
identity ([ADR-0005](../../../adr/ADR-0005.md)), rn-forge dependency set incl.
`lifecycle`.

**Acceptance:**

- The scaffold step runs `uv init` into an empty directory, and the reconcile
  leaves a `pyproject.toml` that check 8a passes.
- Check 8a *warns*, and does not error, when a `[tool.ruff]` value or
  `[project] name` differs from the expected value. kiln never writes either.
- `lint-imports` passes on the rendered `.importlinter` in each archetype.
- The dependency check refuses a render missing a required rn-forge package.
  `lifecycle = true` adds `rn-forge-tooling` to the required set.

## S4.3.2 — `docs`

**Status:** planned

Tree, `_areas.yml`, `_structure.md`, `mkdocs.yml` nav block.

**Acceptance:**

- `docs.profile = "none"` and `"external"` render no docs artifacts. `"mkdocs"`
  renders the tree, and `mkdocs build --strict` passes on it.
- An edited `_areas.yml` survives apply (`SKIP`), and the docs structure check
  validates against the edited copy.
- Adding a page and re-applying updates only the nav block. The body of
  `mkdocs.yml` keeps its bytes.

## S4.3.3 — `tasks`

**Status:** planned

`Taskfile.yml`, `tasks/*.yml`, repo-owned includes, `extra_refs`.

**Acceptance:**

- `task --list` in a rendered repo shows exactly the ten root verbs. Only an
  `mkdocs` repo also shows `docs:build docs:serve docs:nav docs:structure`.
- A repo-owned include is seeded once, and an edit to it survives apply.
- An `extra_refs` entry is reachable from `validate`, and
  `kiln doctor --only task-layout` passes on the result.

## S4.3.4 — `cicd`

**Status:** planned

Workflows, `.github/actions/setup`, pin set
([ADR-0003](../../../adr/ADR-0003.md)).

**Acceptance:**

- `actionlint` passes on every rendered workflow.
- Every `uses:` is SHA-pinned with a version comment, and every job declares
  `permissions:`.
- `ci.sonar = false` renders neither the Sonar job nor
  `sonar-project.properties`.
- `kiln doctor --only ci-entrypoint` passes, and fails on a workflow that calls
  a forbidden tool directly.
- **The two Sonar questions below are answered** — as an ADR or a rejected
  option — before this story is done.

### Parked: Sonar

Sonar is a `cicd` concern, parked here until this story is elaborated: the
`sonar-project.properties` template, the Sonar job and its quality-gate wait,
the fork-PR skip, and the `ci.sonar` toggle. The goldens carry the current
shape, and the reference's §8 states it; nothing about Sonar is decided beyond
that.

- **Is Sonar on by default (`ci.sonar = true`) for every archetype, or opt-in?**
  The golden repos assume default on.
- **Are these repos public or private?** SHA-pinning and `permissions:` are
  generated regardless; confirm there is no reason to relax, and whether Sonar
  hosting differs by visibility.

## S4.3.5 — `instructions`

**Status:** planned

`README.md`/`CLAUDE.md`/`AGENTS.md` seeds, the kiln block.

**Acceptance:**

- An edit to the body of `README.md`, `CLAUDE.md` or `AGENTS.md` survives apply.
- A config change updates the kiln block in `CLAUDE.md` and `AGENTS.md`. Bytes
  outside the block are unchanged.
- `.rn-forge/kiln/standard.md` is managed: a hand edit classifies `DRIFT`.
