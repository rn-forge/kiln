kiln deletes the plumbing it wrote beside pykit, and reads, renders and parses
through the kit:

- YAML through `YamlUtils`, which drops kiln's undeclared PyYAML import.
- TOML and JSON through `DocumentUtils`, with no direct `tomllib`, `tomlkit` or
  `json` reads.
- Typed reads through `DictUtils` and `ListUtils`, which deletes
  `rn_forge.kiln.documents`.
- The generation engine and `StateStore` from `rn_forge.commons`, where pykit
  moved them from tooling.
- Templates through `rn_forge.commons.text.templates`, `TemplateEngine.cached`
  and `render_artifacts`.
- `kiln diff` through `generation.diff`.
- Markdown through `MarkdownUtils`, which deletes
  `rn_forge.kiln.modules.docs.markdown`.
- Generated repositories take pykit by version range from its package index, and
  `rn-forge-deps` accepts a range with a ceiling
  ([ADR-0018](../../../adr/ADR-0018.md)).

## Context

**The defect this fixes.** Three render-free checks import PyYAML: `ci-pins`,
`ci-hooks` and `task-layout`. PyYAML is only in kiln's `dev` group, so
`rn-forge-kiln`'s wheel does not require it. A repository works today only
because kiln's scaffolder also puts `pyyaml` in that repository's `dev` group,
and an `mkdocs` repository gets it through MkDocs. Installed any other way,
`kiln doctor` fails with `ModuleNotFoundError: yaml`. kiln switched to
`yaml.CSafeLoader` for test-suite speed, because pykit's YAML and TOML reads
were 14 and 7 times slower. pykit's release fixes that. The measurements are in
pykit's E18.

**Two pin sets, moved separately.** Since
[F7.4](F7.4-kiln-runs-beside-the-repository.md), kiln runs in its own
environment, so its own pykit pins (`pyproject.toml`) and the pins it renders
into repositories (`RN_FORGE_TAGS`) are independent:

- S7.3.1 moves kiln's own pins, which every other story here needs.
- S7.3.6 moves the rendered pins, and turns them from tag URLs into version
  ranges on pykit's index ([ADR-0018](../../../adr/ADR-0018.md)). That is a
  standard change for every generated repository, reviewed through the
  goldens. After it, an additive pykit release needs no kiln change.

S7.3.7 lets `rn-forge-deps` accept a range first. pykit's own members already
declare each other by range, so the check needs it for pykit's adoption whatever
S7.3.6 renders.

**What `kiln doctor` must keep out, once the engine is in commons.**
[ADR-0006](../../../adr/ADR-0006.md) runs `kiln doctor` on every CI run, so
importing the render-free checks (`rn_forge.kiln.checks`) must not load Jinja or
the generation engine. Two guards enforce this today:

- `.importlinter`'s `render-free-checks` contract forbids `jinja2`.
- `tests/test_checks_are_render_free.py` imports the checks in a clean
  interpreter and fails if `jinja2` or `rn_forge.tooling.generation` is in
  `sys.modules`. A test is needed because import-linter cannot name a
  subpackage of an installed package as a forbidden module.

pykit moves the engine to `rn_forge.commons.generation`, and that changes two
things:

1. **The probe goes blind.** Once kiln imports `rn_forge.commons.generation`,
   nothing ever loads a module named `rn_forge.tooling.generation`. The test
   would keep passing while checking nothing, even if a check started loading
   the engine. It must watch the new names, `rn_forge.commons.generation` and
   `rn_forge.commons.text.templates`, in the same story that moves the
   imports.
1. **The checks' every import now sits next to the engine.** The checks import
   `rn_forge.commons.findings` and friends, and Python runs
   `rn_forge/commons/__init__.py` first, which imports its modules eagerly.
   Had pykit re-exported anything from `generation` there, every `kiln doctor`
   run would load the engine, and kiln could not avoid it. pykit rules that
   out: the facade does not import `generation` or `text`, and a pykit test
   asserts it. kiln's probe is the second line, catching a kiln check that
   imports the engine itself.

This also fixes how the checks read `state.json`. `StateStore` moves to
`rn_forge.commons.fs.state`, outside `generation`. But kiln's store is typed by
`StateEntry`, which lives in `rn_forge.commons.generation.artifacts`, so a check
that built a `StateStore` would load the engine. The checks keep reading the
file as a plain document (S7.3.2), and only the apply cycle uses `StateStore`.

**The release (2026-10-25).** pykit's Release 6 tagged every package from pykit
`main` `9557668`. Read there, it has every name this page uses: `DocumentUtils`,
`DocumentError` and `ConfigFormat` in `rn_forge.commons.fs.documents`;
`DictUtils` and `ListUtils`; `YamlUtils.load` and `read_file`;
`TemplateEngine.cached`; `TemplateArtifact` and `render_artifacts` in
`rn_forge.commons.generation.templated`; `diff` on the `generation` facade;
`StateStore` in `rn_forge.commons.fs.state`; and `MarkdownUtils`. The commons
facade does not import `generation` or `text`. Tooling 0.3.0 keeps only `cli`
(with `build_tool_app`) and `install`. The commons extras `pydantic`, `markdown`
and `templates` exist.

**Iteration.** Release 1, because kiln's wheel ships the PyYAML defect
otherwise. Moving the feature to Release 2 is a one-cell change, if the owner
would rather cut release-1 first and require PyYAML in the wheel meanwhile.

## Considered and rejected

- **Declare PyYAML as a runtime dependency instead.** It fixes the wheel, but
  leaves kiln on a second YAML library with YAML 1.1 rules beside the one
  pykit uses. The `on`-is-`True` workaround in `ci-hooks` is the symptom.
- **Move kiln's docs-site checks or spec-board reader to pykit.** They are
  MkDocs policy and kiln's spec model, and kiln is their only consumer.
- **Keep rendering tag URLs, and accept ranges only in the check.** It keeps
  every additive pykit release a standard change for every generated
  repository, which the index was published to end (ADR-0018).
- **Move kiln's own pins and `RN_FORGE_TAGS` in one story.** The two were bound
  while kiln sat in each repository's lock. Since F7.4 they are not, and
  splitting them lets kiln adopt pykit's helpers without changing any
  generated repository.
