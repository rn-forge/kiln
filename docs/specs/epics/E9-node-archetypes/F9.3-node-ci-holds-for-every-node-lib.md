A new `node-lib` repository can release its first library, or fails before
anything is pushed. Every Pages deploy keeps the API and Storybook sites. A
repository declares its own Sonar exclusions. A `node-lib` says in its standard
what it must declare. ngkit's adoption of kiln gates release-1, so this is
release-1 work.

## Context

A review of the rendered `node-lib` cell on 2026-10-31, at commit `181b34a` with
[F9.2](F9.2-one-node-scaffold.md) built, asked what ngkit would meet on the day
it adopts kiln, and what a new `node-lib` repository would meet on the day it
adds its first library. It was prompted by the owner finding the ngkit diff hard
to review. The session that ran it is gone, so this page carries everything it
found. What it found falls into five groups:

- A new library does not release: no `release` block, no `pack` or `verify-dist`
  defaults, and nothing in the generated documents says what a library must
  declare
  ([S9.3.5](#s935-a-new-library-releases-or-fails-before-anything-is-pushed),
  [S9.3.6](#s936-a-node-lib-repository-says-what-it-must-declare)).
- The Pages deploy can delete the API and Storybook sites
  ([S9.3.1](#s931-every-deploy-carries-compodoc-and-storybook)).
- ngkit's Sonar exclusions have no home
  ([S9.3.2](#s932-a-repository-declares-its-sonar-exclusions)).
- The `validate` job repeats the whole Nx workload that `ci-cloud` or `ci-local`
  runs next ([S9.3.3](#s933-decide-what-node-libs-validate-job-runs),
  [S9.3.4](#s934-validate-runs-only-the-checks-that-do-not-run-nx)).
- Small wording and pin corrections
  ([S9.3.7](#s937-small-corrections-to-the-node-files)), and a compare that is
  hard to read ([S9.3.8](#s938-the-ngkit-compare-leaves-files-to-read)).

Closed text that this feature replaces keeps its words, and a note says so here:

- [S9.1.11](F9.1-node-lib-hosts-ngkit-ci.md#s9111-one-pages-site-mkdocs-with-compodoc-and-storybook-under-it)
  says "Assembly runs only when `BUILD=true`". S9.3.1 replaces that: assembly
  always runs.
- [S9.1.5](F9.1-node-lib-hosts-ngkit-ci.md#s915-dispatch-release) says each
  `ci:release:*` task body is ngkit's step body verbatim. S9.3.5 adds one
  guard to `ci:release:verify`, and so is no longer verbatim there.

[F9.1](F9.1-node-lib-hosts-ngkit-ci.md)'s S9.1.12 waits on the stories here that
change its diff. The owner's read of that diff on 2026-10-31 held its approval
because of this feature.

Each story is sized for one session on a Sonnet-class model. Every decision a
story needs is made on this page, except the one that is its own story, S9.3.3.
S9.3.1, S9.3.4 and S9.3.7 each edit `ci.yml.j2`, so build them one at a time.

## Design

### What was proved

These were run on 2026-10-31 on a throwaway copy of the rendered `node-lib` cell
at `181b34a` (the committed baseline), with kiln from this checkout.

**Dependabot and drift**

| Check | Result |
| -- | -- |
| The rendered `dependabot.yml` | has only `uv` and `npm`. A `github-actions` block renders only for `[ci] hooks` directories (`dependabot.yml.j2`), so Dependabot does not touch kiln-rendered workflow SHAs. ngkit's own `github-actions` block goes away on adoption |
| A SHA edited in `ci.yml`, then `kiln doctor .` | exits 1: `managed artifact has drifted from the committed state` |
| The same, then `kiln apply` | exits 1 and refuses: `Refusing to apply: 1 unapproved change(s): .github/workflows/ci.yml (drift)` |
| The same, then `kiln apply --force .github/workflows/ci.yml` | exits 0, restores kiln's SHA and writes a backup under `.rn-forge/kiln/backups`. kiln never overwrites silently |
| `package.json`, `pnpm-lock.yaml` or `pyproject.toml` edited, then `kiln doctor .` | exits 0. They are not `state.json` entries, so `npm` and `uv` Dependabot pull requests do not drift |

Consequence: action SHAs move only when kiln's `cicd/pins.toml` changes and a
repository moves `[kiln] ref` and applies. Dependabot cannot read `pins.toml`;
the idea `kiln-pins-freshness` covers that. ngkit gives up automatic action
updates until it is built.

**Checked and fine**

- None of the ten files in `NGKIT_FILES` (`scripts/golden_matrix.py`) nor
  `tasks/ci.yml` names ngkit or its packages (grep).
- The release scripts match ngkit's. Under go-task: `ci:release:state` gives
  `mode=new`, `mode=resume` with a tag, and
  `::error::More than one v* tag at HEAD` with two; `ci:release:tag` gives
  `name=v1.0.0`; `ci:release:gate` refuses off `main`
  (`::error::Release runs from main, not feature`); `ci:release:version`'s dry
  run passes with a generated library.
- An empty workspace: `ci:has-e2e` prints `has-e2e=false`, `ci:coverage` prints
  `reports=`, `ci:affected` and `ci:package` print "No tasks were run" and
  exit 0, `ci:docs:affected` gives `build=false`, `ci:docs:site` with
  `BUILD=false` exits 0. `nx release` with no projects fails cleanly, before
  anything is pushed: `Release group "__default__" matches no projects`.
- Job-level permissions are narrower than ngkit's, an improvement.
- `assemble-site.mjs .tmpsite` with no project declaring `compodoc`, and an
  `index.html` already there, exits 0, keeps the file, adds `.nojekyll` and
  creates neither `api/` nor `storybook/`.

### What a library author adds

Checked while writing this page, on a throwaway copy of the rendered cell, with
`nx.json` carrying the `release` block and the two `targetDefaults` that S9.3.5
writes. A library from the generator above, with the dry run of
`ci:release:version` (`DRY_RUN=true VERSION_SPEC=1.0.0 FIRST_RELEASE=true`),
then `ci:release:verify`:

| `project.json` | `ci:release:version` | `ci:release:verify` |
| -- | -- | -- |
| as generated (`tags: []`) | fails: `Release group "__default__" matches no projects` | not reached |
| `tags: ["publishable"]`, no `pack` | passes | passes "No tasks were run", writes no tarball |
| `tags: ["publishable"]`, `"pack": {}` and `"verify-dist": {}` | passes | writes `dist/tarballs/rn-forge-foo-1.0.0.tgz`, whose `package.json` says `1.0.0` |

The generator already writes `release.version` into the project
(`manifestRootsToUpdate: ["dist/{projectRoot}"]`,
`currentVersionResolver: "git-tag"`, `fallbackCurrentVersionResolver: "disk"`),
so the author adds three things: the tag `publishable`, `"pack": {}` and
`"verify-dist": {}`. The generator does not write `nx-release-publish`'s
`dryRun: true`, which ngkit sets while npm publishing is off; without it a real
release publishes to npm (reasoned from `release.yml`, not run), so S9.3.6 says
to add it until publishing is set up.

`nx run-many -t build patch-package-exports -p tag:publishable` (ngkit's
`preVersionCommand`) exits 0 in a workspace whose projects do not declare
`patch-package-exports`, so S9.3.5 keeps it verbatim.

### Decisions

1. **Every deploy builds Compodoc and Storybook.** `deploy-pages` replaces the
   whole site, so a deploy that skips them deletes them. The doc builds run on
   every `main` push, and that cost is accepted: the job has no Nx cache to
   lean on, because it restores no cache and carries no
   `NX_CLOUD_ACCESS_TOKEN`. ngkit's whole `docs` job took 74 s on run
   40634448355\. The affected-gate step, its output and the step that only it
   used go.
1. **Sonar exclusions are `[ci]` config, not a seeded file.** Two keys,
   `sonar_exclusions` and `sonar_coverage_exclusions`, for every archetype.
   The file stays `managed`, so kiln keeps owning `projectKey` and the
   organization, and a repository's paths are the repository's. With both
   empty the rendered file does not change.
1. **`validate` for `node-lib`** is the owner's, in S9.3.3. S9.3.4 is written
   against the recommendation.
1. **A release with nothing to upload fails in the verify step.**
   `ci:release:verify` fails in both modes when `dist/tarballs/` holds no
   tarball, so a dry run catches it before `ci:release:push`. `ci:package`
   gets no such guard: an empty workspace must keep passing it.
1. **`nx.json` is written by the scaffold, for both cells.** It is in
   `PARITY_FILES`, and the owner's rule is one scaffold. The `release` block
   and the two `targetDefaults` are ngkit's, with `patch-package-exports` kept
   in `preVersionCommand`. In a `python-web-app` they stay unused until a
   project there is tagged `publishable`; the helper scripts the `pack`
   command names are rendered for `node-lib` only.
1. **Action SHAs stay kiln's.** Generated workflows carry `pins.toml`'s SHAs,
   and an edit is drift. S9.3.6 says so in the standard.

### What ngkit does when it adopts

A checklist, not a story. Each item is ngkit's, except where a kiln story is
named.

- Set the repository variable `USE_NX_CLOUD=true`.
  `gh variable list -R rn-forge/ngkit` showed none on 2026-10-31, and without
  it ngkit silently moves from `ci-cloud` to `ci-local` (T12). Its `nxCloudId`
  is in `nx.json`.
- Set the two Sonar keys in `.rn-forge/kiln/config.toml`, after S9.3.2:
  `sonar_exclusions = ["apps/ng-demo-api/**", "apps/ng-demo-api-fastapi/**"]`
  and
  `sonar_coverage_exclusions = ["tools/scripts/patch-package-exports.mjs", "apps/*-e2e/**", "apps/*/src/environments/**", "apps/*/src/app/app.config.ts"]`.
- Delete `tools/ci/check-template.mjs` and `docs/architecture/ci-template.md`:
  the `template` job is gone (T6), T1 replaces the marker, and kiln's standard
  now holds the declarations (S9.3.6). Update ngkit's documents that link
  them.
- Keep ngkit's own `nx.json` and `project.json` files: they are repository-owned
  and kiln writes `nx.json` only at `kiln new`.
- Its `dependabot.yml` `github-actions` block goes away; action SHAs now follow
  kiln's `pins.toml`, with no automatic update until the idea
  `kiln-pins-freshness` is built.
- ngkit has no `release/**` branch (verified: `main`, `docs/release-2-shipped`,
  `feature/release-1`, `feature/release-2`), and S9.1.7 made releases
  `main`-only.
- Its documentation failures under S9.1.6 remain ngkit's to fix.

## S9.3.2 — A repository declares its Sonar exclusions

**State:** New

**Build — tests first** in `tests/modules/cicd/test_artifacts.py`, named
`test_s9_3_2_<n>_…`. Copy the shape of `test_s9_1_3_3_…` (the properties) and
`test_s9_2_6_4_…` (the web-app lines), and use `_with_ci(root, extra)` to add
keys to `[ci]`. Before editing any template, render `sonar-project.properties`
for `python-app`, `python-lib`, `python-web-api`, `python-web-app` and
`node-lib` and paste each into the test file as a literal (`SONAR_BEFORE`), the
header line's version replaced by `{version}`, as S9.2.4 did with
`NODE_LIB_ACTION_BEFORE`.

1. `CiConfig` accepts `sonar_exclusions` and `sonar_coverage_exclusions`, each a
   list of strings defaulting to `[]`, under every archetype.
1. An entry that is empty, holds a comma, or holds a newline is refused with a
   `ModelValidationError` naming `ci.sonar_exclusions` (or
   `ci.sonar_coverage_exclusions`).
1. `node-lib` with
   `sonar_exclusions = ["apps/ng-demo-api/**", "apps/ng-demo-api-fastapi/**"]`
   renders
   `sonar.exclusions=**/node_modules/**,**/dist/**,**/*.stories.ts,**/.storybook/**,**/.venv/**,apps/ng-demo-api/**,apps/ng-demo-api-fastapi/**`:
   the archetype's own, then the repository's, in the order given.
1. `sonar_coverage_exclusions = ["tools/scripts/patch-package-exports.mjs", "apps/*-e2e/**", "apps/*/src/environments/**", "apps/*/src/app/app.config.ts"]`
   renders `sonar.coverage.exclusions=` with those four, comma-joined, in
   `node-lib` and in every other archetype. With the list empty no such line
   renders.
1. With both keys empty, each of the five renders in `SONAR_BEFORE` is
   byte-identical to its literal.
1. `python-app` with `sonar_exclusions = ["docs/**"]` renders
   `sonar.exclusions=docs/**` on the line after `sonar.tests=`.
   `python-web-app` with the same renders
   `sonar.exclusions=**/node_modules/**,**/dist/**,**/*.spec.ts,docs/**`.
1. `docs/reference/standard-repo.md` names both keys in its `[ci]` example.

**Build:**

- `modules/cicd/config.py`, `CiConfig`: after `doctor_full`,
  `sonar_exclusions: list[str] = Field(default_factory=list[str])` and
  `sonar_coverage_exclusions`, each with a one-line docstring, and one
  `@field_validator("sonar_exclusions", "sonar_coverage_exclusions")` that
  refuses an empty entry or one holding `,` or `\n`, in the style of
  `CiHooks._entries_are_valid` (the field name from `info.field_name`).
- `modules/cicd/artifacts.py`: two constants beside `_NODE_HELPERS`,
  `_NODE_LIB_EXCLUSIONS = ("**/node_modules/**", "**/dist/**", "**/*.stories.ts", "**/.storybook/**", "**/.venv/**")`
  and
  `_WEB_APP_EXCLUSIONS = ("**/node_modules/**", "**/dist/**", "**/*.spec.ts")`.
  Context keys `sonar_exclusions` (the archetype's constant, empty for the
  others, then `ci.sonar_exclusions`) and `sonar_coverage_exclusions`
  (`list(ci.sonar_coverage_exclusions)`).
- `modules/cicd/templates/sonar-project.properties.j2`: the two literal
  `sonar.exclusions=` lines (`node_lib`, `web_app`) become
  `sonar.exclusions=[[ sonar_exclusions | join(",") ]]`. The `workspace`,
  `web` and plain branches render that line after `sonar.tests=` only when
  `sonar_exclusions` is non-empty.
  `sonar.coverage.exclusions=[[ sonar_coverage_exclusions | join(",") ]]`
  renders last in the source block when that list is non-empty. Item 5 decides
  the whitespace.
- `docs/reference/standard-repo.md`, §9's `[ci]` example: after `sonar = true`,
  `sonar_exclusions = []` and `sonar_coverage_exclusions = []`, each with a
  comment saying the paths are added to the archetype's own and that coverage
  exclusions are counted by Sonar but not expected to have coverage.
- Run `kiln apply` here and `task lint KILN_DOCTOR_FULL=1`.

## Considered and rejected

- **Deploying the site only when a doc project is affected.** A change to MkDocs
  alone would never publish. The cost of building everything is doc builds on
  every `main` push.
- **Fetching the previous site and merging into it.** A second download step,
  and a stale `api/` could outlive the project it documents.
- **A seeded `sonar-project.properties`.** kiln would stop owning `projectKey`
  and the organization, and the file would drift from the other archetypes'.
- **Hardcoding ngkit's exclusions in the template.** They name ngkit's
  applications.
- **The tarball guard in `ci:package`.** An empty workspace must keep passing
  it, and the release is where an unpacked library does harm.
- **A `github-actions` Dependabot block for generated workflows.** Its pull
  requests would edit managed files, and every one would be drift.
- **Dropping `patch-package-exports` from `preVersionCommand`.**
  `release:verify` packs with `--excludeTaskDependencies`, so a library that
  declares the target would lose its patched exports in a release. Keeping it
  costs nothing: the command exits 0 when no project declares it.
