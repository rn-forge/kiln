Added 2026-10-13. pykit (its S14.2.x and S14.4.x) and ngkit both hardened their
CI after kiln's cicd templates were written
([F4.3](../E4-generator/F4.3-concern-modules.md), S4.3.4). Some of their
patterns are already rendered: SHA pins with version comments, least-privilege
`permissions:` per job, `concurrency:` per ref that cancels only pull requests,
the Pages concurrency group, the fork guard on the Sonar job,
`sonar.qualitygate.wait`, `UV_LOCKED`, and the published release as the record.
This feature adds the patterns both repos have and kiln does not. Without it,
adopting kiln would take features out of their CI. The changes apply to every
archetype. pykit's workspace-specific jobs are
[F6.4](F6.4-workspace-pipeline.md), and ngkit's Nx pipeline is
[E9](../E9-node-archetypes/F9.1-node-lib-hosts-ngkit-ci.md).

Evidence, read on 2026-10-13: pykit `.github/workflows/main.yml` and
`.github/actions/setup/action.yml`; ngkit `.github/workflows/ci.yml` and
`release.yml`, and `docs/architecture/ci-template.md` (its rules 3, 5 and 8).

**Rejected: Dependabot in generated repositories.** Both upstream repositories
ship `.github/dependabot.yml` with weekly grouped `github-actions` updates. In a
kiln repository the workflows are generated, so a Dependabot pull request edits
a generated file, and `task lint` fails on it as drift. The pins stay in
`modules/cicd/pins.toml` and reach a repository through a kiln upgrade (D21,
[E4 design](../E4-generator/design.md)). When pykit or ngkit adopts kiln, it
deletes its `dependabot.yml`, or keeps one that watches only its own
non-generated workflows. That is the repository's choice.

**Build each story by the
[board's procedure](../../index.md#building-a-story).** The tests go in
`tests/modules/cicd/test_artifacts.py`. Copy the shape of the S4.3.4 and S5.1.2
tests already in that file. Every template change is reviewed through
`task self:golden:render` (F4.4's risk guard). kiln's own `.github/` is
re-rendered with `kiln apply` and committed with the story.

## S6.3.2 — One required check: `ci-ok`

**State:** Closed (2026-10-14)

Branch protection requires one check that holds across job and matrix renames.
pykit (`main.yml:394-401`) and ngkit (`ci.yml:239-258`) both name it `ci-ok`.

**Build — tests first:**

- `test_s6_3_2_ci_ok_needs_every_other_job`: in each rendered `ci.yml`, a
  `ci-ok` job exists. Its `needs` is the set of every other job key in the
  file, and its `if` is `always()`.
- `test_s6_3_2_ci_ok_has_no_permissions`: its `permissions` is `{}`.
- `test_s6_3_2_ci_ok_fails_on_failure_or_cancel`: its single `run` step contains
  `contains(needs.*.result, 'failure')` and
  `contains(needs.*.result, 'cancelled')`.

**Build:** append this job to `templates/ci.yml.j2` as the last job. Build its
`needs` list the same way `release` builds its own: `validate`, then `sonar` if
`sonar`, then `release` if `release == "tag-exists"`.

```yaml
  # The only check branch protection requires. Job and matrix names change as
  # the repo grows; this one does not. A skipped job (the fork-guarded scan, a
  # release on a pull request) is not a failure.
  ci-ok:
    needs: [validate, sonar, release]   # rendered per the flags above
    if: always()
    runs-on: ubuntu-latest
    timeout-minutes: 5
    permissions: {}
    steps:
      - name: Every job passed or was skipped
        if: contains(needs.*.result, 'failure') || contains(needs.*.result, 'cancelled')
        run: exit 1
```

The step has no `uses:`, so `ci-pins` and `ci-entrypoint` have nothing to check.

**Acceptance:**

- Every rendered `ci.yml` ends with `ci-ok`, built as above.
- The rendered standard says that `ci-ok` is the only required check.
  `modules/instructions/templates/standard.md.j2` §5 ("What CI checks, and
  what it does not") gains one sentence: *Branch protection requires `ci-ok`
  and nothing else.*

**What the build settled that the story did not say:**

- The tests run over the five archetype cells plus a Sonar-off and a
  release-none `python-tool`. `ci-ok`'s `if` is asserted as `always()`, the
  step's `if` carries the two `contains(...)` tests, and its `run` is
  `exit 1`.
- Two S4.3.4 tests that listed the job set or compared the Sonar-off render byte
  for byte now include `ci-ok` (`{"validate", "release", "ci-ok"}`,
  `{"validate", "sonar", "ci-ok"}`, and `ci-ok`'s `needs` rewritten in the
  expected text).
- kiln's own `.github/workflows/ci.yml` was hand-copied, not applied. Its

## S6.3.3 — Sonar analyses the branch that triggered the run

**State:** Closed (2026-10-14)

pykit S14.4.2 (`main.yml:280-300`). A push or a manual dispatch passes
`sonar.branch.name` from the ref. A pull request leaves the scanner's own
detection in place. A dispatch on a tag fails before the tests run. The ref
reaches the shell only through `env`, never through `${{ }}` inside `run`.

**Build — tests first:**

- `test_s6_3_3_scan_passes_the_target_branch_arg`: the rendered `sonar` job has
  a step with `id: target` before `Test with coverage`. The scan's `args`
  contains `${{ steps.target.outputs.branch-arg }}`.
- `test_s6_3_3_ref_text_reaches_run_only_through_env`: no `run:` in the `sonar`
  job contains `github.ref_name` or `github.head_ref`.

**Build:** in `templates/ci.yml.j2`, inside `{% if sonar %}`, insert this step
after `Install dependencies`. Change the scan's `args` to the folded block
below.

```yaml
      # A push or dispatch names its branch, so the analysis lands on that
      # branch rather than the project's main. A pull request keeps the
      # scanner's own detection. A tag has no branch to analyse.
      - name: Resolve the analysis target
        id: target
        env:
          EVENT_NAME: ${{ github.event_name }}
          REF_TYPE: ${{ github.ref_type }}
          REF_NAME: ${{ github.ref_name }}
        run: |
          set -euo pipefail
          if [ "$EVENT_NAME" = pull_request ]; then
            printf 'branch-arg=\n' >> "$GITHUB_OUTPUT"
          elif [ "$REF_TYPE" = tag ]; then
            printf '%s\n' "Sonar analyses branches, not tags: $REF_NAME" >&2
            exit 1
          else
            printf 'branch-arg=-Dsonar.branch.name=%s\n' "$REF_NAME" >> "$GITHUB_OUTPUT"
          fi
```

```yaml
        with:
          args: >
            -Dsonar.qualitygate.wait=true
            ${{ steps.target.outputs.branch-arg }}
```

**Not in this story:** pykit's local branch scan

verb, which is a vocabulary change under [ADR-0007](../../../adr/ADR-0007.md).
It is parked in the [ideas list](../../ideas.md).

**Acceptance:**

## S6.3.4 — A release resumes from its tagged source

**State:** Closed (2026-10-14)

pykit S14.2.5 (`main.yml:236-262`) and ngkit (`release.yml:86-101`, 170-182).
Today's template already skips a published release. It does not handle two other
cases. A tag can exist without a published release, and today the job rebuilds
from the pushed `HEAD` and not from the tagged commit. A leftover draft release
is also not replaced.

**Build — tests first:**

- `test_s6_3_4_check_step_outputs_the_tag_state`: the step `id: check` writes
  `tagged=` and `draft=` to `$GITHUB_OUTPUT`, as well as `should-release=`.
- `test_s6_3_4_checkout_of_the_tag_precedes_build`: there is a step named
  `Check out the tagged source`, with
  `if: steps.check.outputs.tagged == 'true'`, between `check` and `Build`.
- `test_s6_3_4_draft_is_deleted_before_publish`: there is a step named
  `Delete the leftover draft`, with `if: steps.check.outputs.draft == 'true'`,
  between `Build` and `Publish GitHub Release`.
- `test_s6_3_4_publish_targets_the_source_commit`: `target_commitish` is
  `${{ steps.source.outputs.sha }}`.

**Build** in `templates/ci.yml.j2`, release job only:

- Rewrite the `check` step's `run` as follows. Keep the `tag=` line and its
  workspace prefix exactly as they are today.

    ```bash
    tag="…as today…"
    draft=$(gh release view "$tag" --json isDraft --jq .isDraft 2>/dev/null || true)
    if [ "$draft" = false ]; then
      printf '%s\n' "Release $tag already published; nothing to do."
      printf 'should-release=false\n' >> "$GITHUB_OUTPUT"
      exit 0
    fi
    printf 'should-release=true\n' >> "$GITHUB_OUTPUT"
    printf 'draft=%s\n' "$([ "$draft" = true ] && echo true || echo false)" >> "$GITHUB_OUTPUT"
    if [ -n "$(git ls-remote --tags origin "refs/tags/$tag")" ]; then
      printf 'tagged=true\n' >> "$GITHUB_OUTPUT"
    else
      printf 'tagged=false\n' >> "$GITHUB_OUTPUT"
    fi
    printf 'tag=%s\n' "$tag" >> "$GITHUB_OUTPUT"
    ```

- After `check`, add `Check out the tagged source` with
  `if: steps.check.outputs.tagged == 'true'`. It passes the tag through `env`
  as `TAG: ${{ steps.check.outputs.tag }}` and runs
  `git fetch --no-tags origin "refs/tags/$TAG:refs/tags/$TAG" && git checkout --detach "$TAG"`.
  Put this comment on it: *a tag without a published release is a release
  that failed after tagging; rebuilding from `HEAD` would ship a different
  commit under that version.*

- Then add `id: source`, guarded by `should-release`, which runs
  `printf 'sha=%s\n' "$(git rev-parse HEAD)" >> "$GITHUB_OUTPUT"`.

- Between `Build` and `Publish GitHub Release`, add `Delete the leftover draft`.
  It runs `gh release delete "$TAG" --yes`, with `GH_TOKEN` and `TAG` in
  `env`.

- In `Publish GitHub Release`, set `target_commitish` to
  `${{ steps.source.outputs.sha }}`.

- Keep the existing comment about action-gh-release creating the tag. Add one
  line to it: *on a resumed release the tag already exists and is reused.*

**Do not** add a `workflow_dispatch` release input or change the tag format. Do
not move the release into its own workflow.

**Acceptance:**

- In every cell with `release = "tag-exists"`, the release job is built as
  above, and `actionlint` passes.
- The rendered `python-lib` matrix (`test_s4_3_4_5_…`) still passes.
- **Not scriptable:** the owner reruns a throwaway repository's release with a
  tag and no release, and links the run here.

## S6.3.7 — `ci-pins` reads `.yaml` as well as `.yml`

**State:** Closed (2026-10-19)

Added 2026-10-19. GitHub runs a workflow or an action whether its file ends in
`.yml` or `.yaml`. `ci-pins` globs `*.yml` only (S4.3.4's spec said so), so a
repository-owned `.github/workflows/release.yaml` with a tag-pinned `uses:` or a
job with no `permissions:` passes the check. `ci-entrypoint`
(`checks/entrypoint.py`) already reads both suffixes. kiln still renders `.yml`
only, because that is each consuming tool's default name; this story changes
what the check reads, not what kiln writes.

**Build — tests first,** in `tests/modules/cicd/checks/test_pins.py`. Copy the
shape of the `test_s4_3_4_…` tests in that file, and its `PINNED` constant:

- `test_s6_3_7_a_yaml_workflow_is_checked_for_pins`: a fixture
  `.github__workflows__release.yaml` with
  `jobs:\n  a:\n    permissions: {}\n    steps:\n      - uses: actions/checkout@v4 # v4\n`
  reports exactly `["ci.unpinned"]`.
- `test_s6_3_7_a_yaml_workflow_is_checked_for_permissions`: a fixture
  `.github__workflows__release.yaml` with a job that uses `PINNED` and has no
  `permissions:` key reports exactly `["ci.permissions"]`.
- `test_s6_3_7_a_yaml_action_is_checked_for_pins`: a fixture
  `.github__actions__setup__action.yaml` with
  `runs:\n  using: composite\n  steps:\n    - uses: astral-sh/setup-uv@main\n`
  reports exactly `["ci.unpinned"]`.
- `test_s6_3_7_yml_and_yaml_are_both_read`: one fixture with
  `.github__workflows__ci.yml` and `.github__workflows__release.yaml`, each
  with one tag-pinned `uses:` and `permissions: {}`, reports
  `["ci.unpinned", "ci.unpinned"]`.

**Build:**

- In `src/rn_forge/kiln/modules/cicd/checks/pins.py`, replace `rglob("*.yml")`
  with `rglob("*")` filtered by
  `path.is_file() and path.suffix in {".yml", ".yaml"}`, as `entrypoint.py`'s
  `check` does. Keep the `sorted(...)`. Change nothing else in `check`.
- In the module docstring, change "over every `*.yml`" to "over every `*.yml`
  and `*.yaml`".

**Do not:** rename any template or rendered file; change `entrypoint.py`; add a
finding for a `.yaml` suffix; change the actionlint globs in the specs or in
`test_s4_4_5_3_…` (they read only files kiln renders, which are all `.yml`). No
golden, no `.github/` file and no `state.json` hash changes.

**Acceptance:**

- The four tests pass.
- `ci-pins` still passes on every cell (`test_s4_3_4_2_…`,
  `test_s5_1_2_ci_pins_…`), and the `test_s4_3_4_…` tests in `test_pins.py`
  are unchanged and pass.
- `task validate` passes.

**What the build settled that the story did not say:**

- The suffix filter is a `continue` guard at the top of the loop body rather
  than a comprehension in the `sorted(...)` call, which keeps the `rglob("*")`
  line the same shape as `entrypoint.py`'s.
- The module docstring line is re-wrapped to stay inside the line length.
