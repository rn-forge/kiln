## S16.9.1 — A local `--config` file is not recorded as `[source]`

**State:** Closed (2026-11-10) · **Depends on:** —

`kiln new --config <file>` writes the file's path into the new repository's
`config.toml` as `[source] location`. When the file is a scratch file the path
is machine-local, and a generated repository must not carry one. A `git+` URL is
portable and stays recorded (it is what `kiln config-update` re-reads).

**Design.** Only a git source is recorded. A local path is read as a layer and
not recorded; `[source]` stays hand-writable, so `kiln config-update` still
works on a repository whose owner writes one. The simplest alternative, a
relative path, is not stable either.

## S16.9.2 — `generate package` and a `new` with `packages` write the commented `config.toml`

**State:** Closed (2026-11-10) · **Depends on:** —

`kiln new` writes `config.toml` through `catalog.render`
(`src/rn_forge/kiln/modules/core/config/catalog.py:61`), one array element per
line, each key under its description. But `_add_package`
(`src/rn_forge/kiln/commands.py:919`) adds a package with
`DocumentUtils.update(root / CONFIG_PATH, {"archetype": {"python-lib": section}})`
(line 927), a tomlkit round trip. Reproduced on 2026-11-09 with kiln's own
library code: after the update
`packages = ["packages/a", "packages/b", "packages/c"]` is one line, and the new
`modules` entry lands after the comment of the *next* table
(`# How the repo publishes its documentation.` sits above
`"packages/c" = "rn_forge.c"` and `[docs]` follows with no blank line). `new`
calls `_add_package` for every entry of a `python-lib` config's `packages`
(`commands.py:314`, the `for member in members` loop), so a `new` with
`packages` is affected too. `taplo fmt --check` accepts this text (checked
2026-11-09: exit 0), so the defect is that it is not the form `kiln new` and
`config-update` write (S16.4.7), not a taplo failure.

**Design.** `_add_package` keeps `DocumentUtils.update` to change the values,
then re-renders the file with `_write_config` (`commands.py:1223`), as
`config-update` already does. A hand-written comment in `config.toml` does not
survive `generate package`; the file is kiln's commented form by contract
(S16.4.7.6).

**Tests first.** In `tests/test_new.py`, with `_lib_layer`, `TWO_PACKAGES`,

1. `test_s16_9_2_2_new_with_packages_writes_the_commented_form`: `_new_lib` with
   `TWO_PACKAGES + MODULES`; the same equality. It fails today.

   `python-app` (no layer) and the `python-lib` layer above; run the
   repository's own check on the output:
   `TAPLO = Path(sys.executable).parent / "taplo"` (as

## S16.9.3 — The overlay takes `mkdocs.yml` whole and regenerates its nav

**State:** Closed (2026-11-10) · **Depends on:** S16.8.2

A managed `mkdocs.yml` cannot be byte-copied between repositories as the
runbook's step 3 says: about 150 lines of it, the `nav`, are derived from the
repository's own pages. This is already the contract of
[F16.2](F16.2-kiln-owns-mkdocs.md): the nav is a derived region, the recorded
hash covers the file with the fence's body emptied
(`test_s16_2_2_1b_nav_edit_is_not_drift`), and `task docs:generate` writes the
body.

**Design.** No code change; the runbook says so. The overlay copies the
reference's `mkdocs.yml` like any managed file, then runs `task docs:generate`,
which rewrites the nav from the repository's pages; the nav lines of the first
diff are expected and are not a verdict row. Making the nav a second kind of
region in the overlay would add a rule for a case the engine already handles.

1. `test_s16_9_3_1_runbook_regenerates_the_nav`: the runbook's step "Bring the

"`mkdocs.yml` is copied whole like any managed file; its `nav` is a derived

Add the same sentence, with `task docs:generate`, to the "Classify the files"

## S16.9.4 — `config_hash` follows the parsed config, not its bytes

**State:** Closed (2026-11-10) · **Depends on:** —

`state.json` metadata `config_hash` is the SHA-256 of `config.toml`'s bytes
(`src/rn_forge/kiln/modules/core/cycle.py:174`, in `_prepare`). A byte-different
but equivalent config (a comment moved, the layout reformatted) therefore
rewrites `state.json` on the first `kiln apply`, a diff with no meaning. Nothing
compares the hash (the standard's "input" row says so).

**Design.** Hash the parsed document, serialised with sorted keys and compact
separators. Comments and layout no longer count; any value does. The
alternative, documenting the churn, leaves a one-line diff in every cutover.
Existing repositories' `state.json` changes once, on their next apply.

**Tests first.** In `tests/modules/core/test_cycle.py` (fixtures `root`, `home`;
constant `CONFIG`, line 24):

1. `test_s16_9_4_1_config_hash_ignores_comments_and_layout`:
   `cycle.apply(root, home=home)`; read `root / STATE` bytes; rewrite the
   config as
   `"# a comment\n\n" + CONFIG.replace('[repository]\n', '[repository]\n# moved\n')`
   plus a trailing blank line; `cycle.apply` again; `state.json` bytes
   equal.
1. `test_s16_9_4_2_config_hash_follows_a_value`: apply; change
   `owner = "rn-forge"` to `owner = "other"`; apply; the two `config_hash`
   values differ.

**Build.** In `cycle.py` add `import json` and
`from rn_forge.commons.fs.documents import DocumentUtils`; line 174 becomes
`"config_hash": ContentHash.of(json.dumps(DocumentUtils.read(root / CONFIG_PATH), sort_keys=True, separators=(",", ":"))),`.
In `src/rn_forge/kiln/modules/instructions/templates/standard.md.j2` (line 81)
and `docs/reference/standard-repo.md` (line 96) the cell "its hash, as
`config_hash`" becomes "the hash of its parsed content, as `config_hash`". Run
`task kiln:apply` here (this repository's `state.json` changes once).

**Acceptance:**

- Both tests pass; `task validate` passes; a second `task kiln:apply` reports
  nothing to change.

**What the build settled that the story did not say:**

- The code is at `_prepare` in `cycle.py`, near line 150 rather than 174.
- Test 1 failed before the change. Test 2 passed before it too, since a changed
  value changed the byte hash as well; it guards the new hash against ignoring
  values.
- `task kiln:apply` changed this repository's `state.json` and `standard.md`
  once; a second apply reported nothing to change.

## S16.9.6 — `state.json` records the scaffolded files

**State:** Closed (2026-11-10) · **Depends on:** —

A cutover must tell kiln-owned, seeded, scaffolded and repository-owned files
apart from the reference alone. `state.json` already records the 16 seeded
files, with `kind: "seeded"` and no hash (checked in a `node-lib` reference on
2026-11-09). What it omits are the **scaffolded** files: the bodies of
`README.md`, `CLAUDE.md` and `AGENTS.md`
(`modules/instructions/scaffold.py:18`), `pyproject.toml`, `uv.lock` and
`.python-version`, and for a node cell `package.json`, `nx.json`, `.nvmrc` and
the lockfile. The standard says they are recorded as "nothing"
(`standard.md.j2:79`).

**Design.** `kiln new` records the scaffolded paths as a sorted list under
`metadata.scaffolded` in `state.json`: every file the finished repository holds
that git would add (`git ls-files --others --exclude-standard`, which honours

`kiln doctor` reports `does not resolve` and `broken link` twice each, and
`mkdocs build --strict` aborts with two warnings. The epic pages themselves are

**Design.** When the board writes a Deferred row, rewrite every inline Markdown
link target in the copied cell. Leave a target alone if it has a URL scheme
(`https:`, `mailto:`) or starts with `/`. A target that is only an anchor (`#x`)
becomes `epics/<dir>/index.md#x`. Any other target `t` becomes
`posixpath.normpath(f"epics/{dir}/{t}")`, with its anchor kept. The link text
and the rest of the cell are unchanged. The rule lives in one helper,
`_rebase_links`, beside the board writer. No other derived region copies text
from a page, so nothing else changes.
