## Where the records live

- **Paths.** `.rn-forge/kiln/baseline/<id>.md` for each record, plus
  `.rn-forge/kiln/baseline/index.md`. All are **managed**. They are rendered
  for every docs profile, because they sit in kiln's namespace, not under
  `docs/`.
- **Module.** A new module, `baseline` (`src/rn_forge/kiln/modules/baseline/`).
  It has no config section, no options and no checks of its own. Drift is
  caught by `core`'s `generated` check, as for every managed file. It is
  registered between `cicd` and `instructions`, and every archetype manifest
  lists it in the same place.
- **Provenance.** The first line of every baseline file is the one the
  `CLAUDE.md` block uses:
  `<!-- Generated by kiln {{ kiln_version }} from .rn-forge/kiln/config.toml — do not edit; run 'kiln apply' -->`,
  followed by one blank line.
- **Formatting.** The seeded `.mdformat.toml` does not exclude
  `.rn-forge/kiln/baseline/`, and a repository that already exists would never
  receive a new exclude, because the file is seeded. So every rendered
  baseline file must already be mdformat-clean under the goldens'
  `.mdformat.toml`. The record texts below have been checked with
  `mdformat --check` under that file. The index's only variable part is its
  table rows, which mdformat does not wrap.
- **Who reads them.** `standard.md` gains a section that points at the index,
  and the `CLAUDE.md` block gains an **Architecture** bullet. Both are static
  text. `instructions` does not import `baseline`, so the planned
  [F4.7](../E4-generator/F4.7-import-contracts.md) rule — a concern module
  imports `core` and not its siblings — still holds.

## The tiers and their contracts

B-0001 names the tiers. The `layers` contract encodes them, top to bottom:

| Line | Layers | Meaning |
| -- | -- | -- |
| 1 | `(main) : (commands) : (product) : (app) : (http)` | entry points; `:` lets them import each other |
| 2 | `(services) \| (adapters)` | `\|` makes them independent of each other |
| 3 | `(domain)` | imports nothing above it |

Parentheses make every layer optional, so the contract holds on a package that
has none of them yet. It was checked against import-linter 2.15: a missing
optional layer passes, and `services` importing `adapters` breaks the contract.

**Single-package archetypes** (`python-app`, and the web archetypes' API
member). The rendered `.importlinter` gains this contract after
`frameworks-come-from-rn-forge`, with one blank line between them. For the
`python-tool` golden, whose package is `golden_tool`, the text is exactly:

```ini
; The architecture baseline's B-0001 (.rn-forge/kiln/baseline/B-0001.md):
; imports point inward. Every layer is optional, because a tier exists only once
; code needs it, so this holds on a fresh repo and fails on the first import
; that points upward.
[importlinter:contract:dependencies-point-inward]
name = Imports in golden_tool point inward (baseline B-0001)
type = layers
containers =
    golden_tool
layers =
    (main) : (commands) : (product) : (app) : (http)
    (services) | (adapters)
    (domain)
```

With this appended, `lint-imports` against the golden's own `src/` reports
`Contracts: 2 kept, 0 broken`. The workspace archetype, `python-lib`, gets no
`layers` contract. B-0003 governs it, and its `packages-are-independent`
contract is unchanged.

**FastAPI** (`config.backend == "fastapi"`) also gains this contract, after
`dependencies-point-inward`, with one blank line between them. For a package
`demo_api` the text is exactly:

```ini
; The architecture baseline's B-0004 (.rn-forge/kiln/baseline/B-0004.md): the
; web framework stops at the entry points. `.**` matches the modules below each
; package, so this holds before the package exists.
[importlinter:contract:framework-stays-at-the-edge]
name = demo_api's domain and services import no web framework (baseline B-0004)
type = forbidden
source_modules =
    demo_api.domain.**
    demo_api.services.**
forbidden_modules =
    fastapi
    starlette
allow_indirect_imports = False
```

**The known gap.** `demo_api.domain.**` does not match the package
`demo_api.domain` itself, so an import in `domain/__init__.py` is not caught.
Naming `demo_api.domain` in `source_modules` would close the gap, but
import-linter then fails with `Module 'demo_api.domain' does not exist` on every
repository that has not created the package yet. A render cannot know which
packages exist ([ADR-0004](../../../adr/ADR-0004.md)), so the gap stays open and
is left to review.

## Changing a record

- Record IDs are global and permanent. A retired record stops rendering, and its
  ID is listed on this page as retired, never reused.
- A record's text changes in a golden first, while goldens are in git; after
  [F4.4](../E4-generator/F4.4-render-matrix.md), it changes through the render
  matrix's approval. A changed record changes the architecture of every
  repository it applies to, so the release that carries it says so.
- A new record is an owner's story that approves its text, followed by a build
  story, exactly as F12.1 and F12.2 are structured.

### B-0001

`templates/B-0001.md.j2`: the provenance line, a blank line, then exactly:

```markdown
# B-0001 — Dependencies point inward; I/O lives at the edges

**Status:** accepted · **Scope:** every module under this repository's root
package

## Decision

Product code is arranged in three tiers, directly under the root package, and
imports point only downward:

1. **Entry points** — `main`, `commands`, `product`, `app` and `http`: where a
   process, a command line or a web server comes in. They parse input, build
   what the request needs, call a service and present its result. They hold no
   business rule.
1. **`services` and `adapters`**, side by side and independent of each other. A
   service is one use case, written against protocols that `domain` defines.
   An adapter is the only code that touches the outside world — a database, a
   file, a subprocess, another API, a queue — and implements one of those
   protocols.
1. **`domain`** — the types, rules and protocols the product is about. It does
   no I/O and imports nothing above it.

Entry points choose which adapter a service gets; nothing else does. A tier is
created when the first code needs it: a repository with one command and no I/O
has only `commands`.

## Consequences

- `domain` and `services` are tested without a network, a disk or a framework. A
  fake adapter is a small class that implements the protocol.
- Replacing a storage engine or an upstream API is a new adapter and one changed
  line of wiring.
- The cost is indirection: a protocol and an adapter where a direct call would
  do. A repository pays it only for the I/O it actually has.
- A module outside these names, such as `utils`, is not constrained.

## Influences

The `dependencies-point-inward` contract in `.importlinter` enforces the order.
Each tier in it is optional, so the contract holds on a repository that has not
created a tier yet and bites the first import that points upward.
[B-0002](B-0002.md) says what crosses the entry-point boundary.

## Alternatives considered

- **Layering by technical kind** (`models`, `views`, `controllers`). It shapes
  the product around its framework, and the rules cannot be tested without
  that framework.
- **No prescribed structure.** Each repository would re-decide it, and no import
  contract could say when code landed in the wrong place.
- **Full domain-driven design** — aggregates, repositories, a unit of work. It
  presumes a domain rich enough to need them. A dashboard does not have one,
  and this record has to hold for both.
```

### B-0002

`templates/B-0002.md.j2`: the provenance line, a blank line, then exactly:

```markdown
# B-0002 — Errors, settings and logs each cross one boundary

**Status:** accepted · **Scope:** every module under this repository's root
package

## Decision

- **Errors.** Product code raises `AppException` from `rn-forge-commons`, or a
  subclass of it for a failure a caller can act on, with an `error_code` and
  its context as keyword data. Code does not catch an exception only to log
  and re-raise it. An entry point is the one place an exception becomes an
  outcome: an exit code, which `rn-forge-cli` maps, or an HTTP response.
- **Settings.** Configuration is read once, at startup, by an entry point, into
  one typed and immutable settings object, which is passed down. Nothing below
  the entry points reads an environment variable or a configuration file.
- **Logs.** Code logs through `AppLogger` from `rn-forge-commons`, with context
  as structured fields rather than interpolated text. Logging is configured
  once, by an entry point. Output meant for a user is the entry point's to
  write; everything else is a log line.

## Consequences

- A test sets configuration by constructing the settings object. It never
  patches the environment.
- A caller branches on an exception's type or `error_code`, never on its
  message.
- Every failure is reported once, where it is handled, with the context it was
  raised with.
- The cost is plumbing: settings and collaborators are passed through
  constructors instead of imported from wherever they are needed.

## Influences

[B-0001](B-0001.md) defines the entry points. No import contract can see an
environment read or a stray `print`; this record is enforced by review.

## Alternatives considered

- **A settings module imported wherever a value is needed.** Every importer
  gains a hidden dependency on the process environment, and tests start to
  depend on the order they run in.
- **Result types instead of exceptions.** They are foreign to the Python
  libraries this code calls, so every boundary would convert between the two.
- **Each module choosing its own logger and format.** Logs from one request
  could no longer be correlated or filtered by field.
```

### B-0003

`templates/B-0003.md.j2`: the provenance line, a blank line, then exactly:

```markdown
# B-0003 — A library's surface is explicit and inert

**Status:** accepted · **Scope:** every package in this workspace

## Decision

- **Explicit.** Each package declares its public API in its `__init__.py`,
  listed in `__all__`. Every other name is private, and internal modules take
  a leading underscore.
- **Inert.** Importing a package does nothing but define names: no I/O, no
  environment reads, no logging configuration, no global registration.
- **Configured by its caller.** A library never reads configuration itself.
  Values arrive as arguments. It logs through `AppLogger` from
  `rn-forge-commons` and never installs a handler; that is the application's
  job.
- **Its own errors.** Each package raises exceptions from one hierarchy rooted
  in `AppException`, so a caller can catch everything the package raises with
  one type.
- **Versioned surface.** Removing or changing a public name is a breaking change
  under the package's version. A name is deprecated for at least one minor
  release before it is removed.

## Consequences

- A caller can depend on exactly what `__all__` lists, and on nothing else.
- Importing a package in a test, a script or an application costs nothing and
  changes nothing.
- The cost is ceremony: a public name is declared twice, once where it is
  defined and once in `__all__`.

## Influences

pyright strict reports use of a private name from outside its module. The
`packages-are-independent` contract in `.importlinter` keeps the workspace's
packages from depending on each other silently. The rest is enforced by review.

## Alternatives considered

- **Everything importable is public.** Then every internal rename is a breaking
  change, and the version stops meaning anything.
- **A library that reads its own settings from the environment.** Two
  applications that use it differently cannot share a process, and its tests
  depend on the machine they run on.
```

### B-0004

`templates/B-0004.md.j2`: the provenance line, a blank line, then exactly:

```markdown
# B-0004 — HTTP is an adapter at the edge

**Status:** accepted · **Scope:** the API service's root package

## Decision

- **`app` builds the application.** It loads settings, and registers the
  routers, the exception handlers and the middleware. Routers live in `http`,
  one module per resource.
- **Handlers are thin.** A route handler parses the request, calls one service
  and maps the result to a response model. No business rule, query or outbound
  call lives in a handler.
- **The wire format is its own.** Request and response models are defined in
  `http`, separately from `domain` types, and converted at the handler.
- **The framework stops at `http`.** Services and adapters reach handlers
  through FastAPI's `Depends`, declared only in `http`. `domain` and
  `services` never import FastAPI or Starlette.
- **One error shape.** Exception handlers registered in `app` translate
  `AppException`, by its `error_code`, into one error response body that every
  route shares. A handler never builds an error response itself.
- **The event loop never blocks.** Handlers are `async def`, and a blocking call
  runs in a worker thread, not on the loop.

## Consequences

- A service is tested without the application. An API test drives the real
  application through the test client and checks the wire format.
- A domain type can be renamed or reshaped without changing the public API.
- Clients see one error format, whichever route failed.
- The cost is a second set of models, and a conversion in each handler.

## Influences

The `dependencies-point-inward` contract in `.importlinter` places `app` and
`http` among the entry points ([B-0001](B-0001.md)). The
`framework-stays-at-the-edge` contract forbids FastAPI and Starlette in `domain`
and `services`. Errors follow [B-0002](B-0002.md).

## Alternatives considered

- **Logic in route handlers.** Every test of a rule needs the whole application,
  and two routes that share a rule copy it.
- **Domain types as response models.** Every internal rename becomes a breaking
  change to the API.
- **Error responses built per route.** Clients meet several error shapes, and
  status codes drift between routes.
```

### B-0005

`templates/B-0005.md.j2`: the provenance line, a blank line, then exactly:

```markdown
# B-0005 — The API schema is the contract between backend and frontend

**Status:** accepted · **Scope:** the API service and the frontend workspace

## Decision

- **One definition.** The backend's OpenAPI document is the only definition of
  the API. The frontend's API client, and its request and response types, are
  generated from it and never written by hand.
- **Backend first.** An API change is made in the backend. Regenerating the
  client then shows, at compile time, every frontend call it broke.
- **Rules live in the backend.** The frontend owns presentation and interaction
  state. Business rules and authorization decisions are the backend's. The
  frontend repeats a validation only to give the user earlier feedback, never
  as the check that counts.

## Consequences

- The two halves cannot silently disagree about a field's name or type.
- A frontend change never needs a backend rule copied into it.
- The cost is a generation step between an API change and the frontend work that
  uses it.

## Influences

kiln renders no client-generation task yet. Until it does, the repository adds
its own, and this record is enforced by review. The API's shape is
[B-0004](B-0004.md).

## Alternatives considered

- **Hand-written client types.** They drift from the API one field at a time,
  and nothing notices until a request fails at runtime.
- **Business rules duplicated in the frontend.** The two copies diverge, and the
  one the user sees is not the one that is enforced.
```
