`kiln self install` puts a working `kiln` on PATH from a branch, a tag or a
commit, with no GitHub release needed. `kiln self` then manages the installed
versions, the install state and a repository's pinned kiln correctly. This is
the first real test of pykit's `rn-forge-cli` and `rn-forge-tooling` as a
standalone tool's runtime, and every `python-tool` repository kiln generates
gets the same install.

## Context

**Found 2026-11-14,** running kiln from `feature/v1` with
`uvx --from git+…@feature/v1 kiln`. That route works: `kiln new` of a
`python-tool` repository and its `task validate` pass. The install route does
not:

- `kiln self install` resolves `releases/latest` on GitHub. kiln has no release,
  and `--version` names a tag `v<version>`, so a branch cannot be installed.
  The version is also the directory name under `versions/`, and `feature/v1`
  is not a single path segment.
- The default `ToolProduct.build` copies the release's source tree, which holds
  no `bin/kiln`. Even from a tag, the install has nothing for
  `Link("bin/kiln", "bin/kiln")` to point at. The `ToolProduct` that kiln
  renders for every `python-tool` repository (`src/<pkg>/product.py`) has the
  same gap.
- S4.5.5 proved only the wiring: `kiln self --help` lists the six verbs.

**Not gated on the tag.** This feature needs no `v0.1.0` and no GitHub release:
it installs from `feature/v1` and from a commit. It is release-1 work, so
[F7.2](F7.2-kiln-release-and-config-upgrade.md)'s tag waits on it, as the
owner's 2026-11-14 condition says ("the CLI/tool side is tested").

**What pykit owns.** Installing from a ref, the Python-tool build and the
help-text defects are generic, so they are pykit's: pykit
[E23](https://github.com/rn-forge/pykit/blob/main/docs/specs/epics/E23-standalone-tool-findings/index.md),
F23.1 (help text) and F23.2 (ref installs and the Python-tool build). kiln takes
them through the [upstream pin](../../index.md#upstream-pins) and changes only
its own product, its template and its pin check. kiln gets no hand-written
lifecycle: a kiln-only installer is the special case D61 rejected.

**Relation to
[F18.14](../E18-kiln-simplification/F18.14-a-pin-is-a-commit.md).** A repository
pins kiln as a tag, or as a commit plus the branch it tracks. An install records
the same pair (`ref` as asked, `commit` as resolved), so the pin check compares
like with like.

## Design

- **Install sources.** Taken from pykit F23.2:

    - `kiln self install --ref <branch|tag|sha>` resolves the ref to a commit and
      installs that commit's tree;
    - `--version <v>` keeps meaning the tag `v<v>`;
    - `--archive <file> --version <v>` keeps meaning a local archive.

    A ref install's version directory is named for its commit, and `state.json`
    records `version` (the package version, from the tree), `ref` and `commit`.

- **The build.** kiln's `Kiln` product subclasses pykit's Python-tool product,
  which builds a uv tool environment inside the version directory with `bin/`
  beside it. `Link("bin/kiln", "bin/kiln")` stays as it is.

- **`kiln self upgrade`.** A ref install re-resolves its recorded ref, and a tag
  install moves to the newest release. When the commit has not moved, the
  install is already current.

- **An installed kiln knows its ref.** When `kiln` runs from an install,
  `kiln version` prints `<version> (<ref> @ <commit 12>)`, which it reads from
  the install's `state.json`. Run from `uvx` or a checkout, it prints only
  `<version>`, as it does now.

- **The pin check** (`modules/core/checks/pin.py`) compares a repository's pin
  with the running kiln:

    - a tag pin compares versions, as it does now;
    - a SHA pin (F18.14) compares commits when the running kiln is an install;
    - a branch pin is not compared.

    An error's message says to run kiln through `task`, as it does now.

## S7.7.1 — kiln installs from a branch, a tag or a commit

**State:** Closed (2026-11-18) · **Depends on:** the pykit F23.2 pin

**Acceptance:**

- `pyproject.toml`'s `rn-forge-tooling` floor is the release that carries pykit
  F23.2, and `product.py`'s `Kiln` subclasses its Python-tool product.
- Under a temporary `RNF_HOME`,
  `kiln self install --archive <git archive of HEAD> --version 0.1.0` leaves
  `$RNF_HOME/bin/kiln` on a link through `current`, and
  `$RNF_HOME/bin/kiln version` prints `0.1.0`. This is a test. It needs the
  network: `task setup` caches wheels but not index metadata, so
  `uv tool install` cannot resolve offline.
- `kiln self install --ref feature/v1` and `--ref <a commit SHA>` install from
  GitHub with no release. This is in the feature's acceptance block, not a
  unit test, because it needs GitHub.
- `kiln self doctor` after an install reports `install.ok` and no error.

Outcome: before the change the install exited 0 with `bin/kiln` a broken link
(`install.link-broken`); `Kiln(PythonTool)` fixes it.

## S7.7.6 — An installed tool reads its CLI declaration from its package

**State:** Closed (2026-11-18) · **Depends on:** S7.7.1

*Found 2026-11-18 by S7.7.2; owner decision the same day.* A generated
`python-tool`'s `main.py` reads `.rn-forge/kiln/config.toml` relative to
`__file__`, which exists only in an editable checkout, so an installed tool
fails on start with `DocumentError: Document does not exist`. kiln avoids it
with a hand-kept `src/rn_forge/kiln/cli.toml`, held equal to its config by a
test. kiln now renders that file for every repository with lifecycle verbs, kiln
included, and the generated `main.py` reads it from the package.

**Acceptance:**

- For a repository whose config turns lifecycle on (`python-tool` always),
  `kiln apply` renders `src/<package path>/cli.toml` as a managed file: the
  provenance header, then the config's `[cli]` and `[lifecycle]` tables. A
  repository without lifecycle gets no such file.
- The seeded `main.py` of a new `python-tool` builds its app from that packaged
  file, the way kiln's `main.py` does.
- kiln's own `src/rn_forge/kiln/cli.toml` is that rendered file, and the two
  equality tests in `tests/commands/test_cli_surface.py` are gone.
- `task kiln:apply` runs here, and `task lint KILN_DOCTOR_FULL=1` passes.
- An existing `python-tool` repository's `main.py` is seeded, so `kiln apply`
  does not change it; such a repository edits `main.py` once by hand.

Outcome: `modules/python/artifacts.py` renders the file with
`DocumentUtils.dumps(..., multiline_arrays=True)`, which taplo accepts; the
first apply of kiln's own copy needs `--force`, as will any adopter's hand-kept
one.

## S7.7.3 — An installed kiln knows its ref, and the pin check uses it

**State:** Closed (2026-11-18) · **Depends on:** S7.7.1

**Acceptance:**

- Run from an install, `kiln version` prints `0.1.0 (feature/v1 @ <commit 12>)`.
  Run from `uvx` or a checkout, it prints `0.1.0`. Both are tests, with a fake
  `state.json` under a temporary `RNF_HOME`.
- `kiln.pin-mismatch` is reported for a SHA pin when the installed commit
  differs, and for a tag pin when the version differs. It is not reported for
  a branch pin, or when kiln is not running from an install. There is one test
  for each case.

Outcome: `product.running_install()` reads `state.json` only when `sys.prefix`
is under the active version directory. A branch pin never reaches the check:
`KilnPin` refuses a branch (F18.14).

Outcome: a generated tool mounts the lifecycle verbs at its root (kiln alone
uses `self`), so the test runs `install` and `doctor`. The run found the
start-up defect S7.7.6 fixed.

## S7.7.4 — The standalone run

**State:** New · **Depends on:** S7.7.1, S7.7.2, S7.7.3, the pykit F23.1 pin ·
**Owner's story:** a run, not code

This is the main test. kiln runs only as an installed tool, in a clean shell
with a temporary `RNF_HOME` and nothing from `uvx` or a checkout on PATH. The
run checks how the install manages its home, its versions, its state and a
repository's config. The owner runs the feature's acceptance block below, reads
each step's output and records the run under this story. A wrong result becomes
a kiln story in this feature, or a pykit story when the result comes from pykit.

**Acceptance:**

- The feature's acceptance block passes, end to end.
- Not scriptable: the owner reads each step's output and records that:
    - the home layout is what the pykit lifecycle guide describes;
    - `state.json` names the ref and commit;
    - `kiln self` never writes a repository's `.rn-forge/kiln/config.toml`, and
      `kiln pin` is the only command that does;
    - the help text reads as written.

## S7.7.5 — The rendered floors admit pykit's Release 9

**State:** Closed (2026-11-18)

pykit's Release 9 (pykit `dc5336e`, on pypi.org 2026-11-18) published
`rn-forge-commons` 0.10.0, `rn-forge-cli` 0.2.0 and `rn-forge-tooling` 0.3.3.
kiln's rendered ranges, `rn-forge-commons>=0.9.0,<0.10` and
`rn-forge-cli>=0.1.3,<0.2` (from `RN_FORGE_TAGS`, read at pykit's `release-8`),
exclude the first two, and so do kiln's own ranges in `pyproject.toml`. S7.7.1
and S7.7.4 need those releases, so a rendered repository must be able to resolve
them. Release 8's web packages cap `rn-forge-commons<0.10`, so the whole table
moves to `release-9`'s tags, not commons alone.

**Acceptance:**

- `RN_FORGE_TAGS` and kiln's own `pyproject.toml` ranges admit
  `rn-forge-commons` 0.10.0, `rn-forge-cli` 0.2.0 and `rn-forge-tooling`
  0.3.3, and the standard's rendered examples,
  [ADR-0018](../../../adr/ADR-0018.md)'s example and the tests' expected
  values show the same ranges.
- A repository rendered for each archetype that carries these packages resolves
  them with `task setup`, and `task validate` passes.
- `task kiln:apply` runs here, the goldens are re-seeded, and
  `task lint KILN_DOCTOR_FULL=1` passes.

Outcome: `uv.lock` moved only commons 0.10.0, cli 0.2.0 and tooling 0.3.3; all
six golden cells pass `task self:golden:validate` on the new ranges.

## Acceptance

Run in a clean shell with the network on, from an empty scratch directory. `$K`
is kiln's GitHub repository, and `$SHA` is a commit on `feature/v1` older than
its head.

```bash
set -euo pipefail
absent() { local rc=0; rg -q --hidden --glob '!.git' "$@" </dev/null || rc=$?; [ "$rc" -eq 1 ]; }
fails_with() { local out rc=0; out=$("${@:2}" 2>&1) || rc=$?; [ "$rc" -ne 0 ] && grep -qF -- "$1" <<<"$out"; }
export RNF_HOME="$PWD/home" PATH="$PWD/home/bin:$PATH"
K=rn-forge/kiln

# S7.7.1 — bootstrap once through uvx, then only the installed kiln runs
uvx --from "git+https://github.com/$K@feature/v1" kiln self install --ref feature/v1
command -v kiln | grep -qF "$RNF_HOME/bin/kiln"
kiln version | grep -qE '^0\.1\.0 \(feature/v1 @ [0-9a-f]{12}\)$'           # S7.7.3
kiln self doctor | grep -qF install.ok
jq -e '.ref == "feature/v1" and (.commit | length == 40)' "$RNF_HOME/kiln/state.json"

# S7.7.1 — a second install, from a commit; status shows both, current moves
kiln self install --ref "$SHA"
[ "$(kiln self status --json | jq '.versions | length')" -eq 2 ]
kiln self install --ref feature/v1                     # back to the branch head
kiln self upgrade | grep -qF 'already active'          # the ref has not moved
kiln self cleanup --yes
[ "$(kiln self status --json | jq '.versions | length')" -eq 1 ]

# S7.7.2 — a python-tool repository made by the installed kiln installs itself
kiln new demo --archetype python-tool --owner rn-forge --yes
(cd demo && task validate)
git -C demo archive --prefix=demo/ -o ../demo.tar.gz HEAD
(cd demo && .venv/bin/demo install --archive ../demo.tar.gz --version 0.1.0)
"$RNF_HOME/bin/demo" --help >/dev/null

# S7.7.3 — the pin check against the installed commit
(cd demo && kiln pin "$SHA" && fails_with kiln.pin-mismatch kiln doctor .)
(cd demo && kiln pin feature/v1 && kiln doctor .)

# pykit F23.1 — help text reads as written
kiln pin --help | grep -qF '[kiln] ref'
absent -F 'App Logger Configured' <(kiln version 2>&1)
absent -F 'Raises:' <(kiln new --help)

# S7.7.1 — uninstall leaves nothing behind
kiln self uninstall --yes
[ ! -e "$RNF_HOME/kiln" ] && [ ! -e "$RNF_HOME/bin/kiln" ]
```

`kiln pin` writes a SHA directly only after
[F18.14](../E18-kiln-simplification/F18.14-a-pin-is-a-commit.md). Before it, the
S7.7.3 lines edit `[kiln] ref` by hand.

## Considered and rejected

- **Install only from a GitHub release.** It needs `v0.1.0` before the tool side
  can be tested, and the tag waits on that test.
- **`uv tool install git+…@<ref>` as kiln's install.** It works, but it bypasses
  `rn-forge-tooling`, so `kiln self` would manage nothing and pykit's
  lifecycle would stay untested.
- **A kiln-only `build` and release source.** Every generated `python-tool` has
  the same gap, so the fix belongs to pykit (D61: no kiln special case).
