# ADR-0018 — rn-forge dependencies are version ranges from PyPI

**Status:** accepted (2026-10-25), revised and accepted (2026-10-31) ·
**Scope:** the rn-forge requirements kiln renders, and the `rn-forge-deps` check
in every Python repository

## Background

- 2026-10-31: revised for pykit's E21. Every `rn-forge-*` package is on pypi.org
  from pykit's Release 7, and kiln stops declaring pykit's index
  ([F7.5](../specs/epics/E7-pykit-release-pin-flip/F7.5-pykit-from-pypi.md)).

## Decision

rn-forge packages resolve from PyPI. kiln renders every rn-forge requirement by
name and version range. No repository declares an index for them, and a
`[[tool.uv.index]]` entry with pykit's retired Pages URL,
`https://rn-forge.github.io/pykit/simple/`, is a finding:

- **The range.** The floor is the version kiln's pin table names. The ceiling is
  that version's next breaking release: the next minor before 1.0, the next
  major from 1.0. An example is `rn-forge-commons>=0.8.1,<0.9`. This is
  pykit's rule for its own packages.
- **The lock pins.** `uv.lock` records the exact version and hash, so a build is
  as reproducible as a tag pin.

`rn-forge-deps` accepts two forms for an rn-forge requirement in `dependencies`:
a pinned git direct URL, as before, or a version range with a ceiling. It
rejects a bare name and a range with no ceiling. Inside a library workspace, a
member may depend on a sibling by range ([ADR-0014](ADR-0014.md), as revised):
the wheel carries the range, and a consumer resolves it from PyPI.

kiln's own dependencies on pykit are ranges too. kiln runs from git through
`uvx` ([ADR-0006](ADR-0006.md)), and its wheel's ranges resolve from PyPI.

## Consequences

- An additive pykit release needs no kiln change and no change in a generated
  repository. `uv lock --upgrade` takes it.
- A breaking pykit release still needs a kiln pin-table change, which moves
  floors and ceilings in a standard change, reviewed through the goldens.
- A consumer can take two pykit packages released at different times. Before
  this, uv refused two URLs for one distribution, so the set moved together or
  not at all.
- The index-first lookups that throttled CI (F6.4) stop: uv asks pypi.org, and
  nothing asks GitHub Pages for a package.
- A repository scaffolded before this keeps passing with its tag URLs. It moves
  to ranges by rewriting the requirements, and deletes any `[[tool.uv.index]]`
  entry for pykit.

## Influences

- pykit's E19 (version ranges between packages) and its revised ADR-0004.
- [F7.3](../specs/epics/E7-pykit-release-pin-flip/F7.3-adopt-pykit-extraction.md):
  S7.3.7 (the check) and S7.3.6 (the rendered requirements).
- D46 ([context](../plans/context.md)): rn-forge requirements were pinned direct
  URLs because a wheel's `Requires-Dist` needed a resolvable source, and pykit
  had no index. The index removes that reason; the rejection of
  `[tool.uv.sources]` overrides stands.

## Alternatives considered

- **Keep exact tag URLs.** Every pykit release that a repository wants forces
  the whole rendered set to move together. That costs a standard change for
  each additive release.
- **Floors only (`>=0.7.0`).** A breaking pykit release would install under a
  repository never tested against it. pykit rejected it for the same reason.
- **`~=0.7.0`.** It is right before 1.0, but it changes meaning at 1.0
  (`~=1.0.0` is `<1.1`). The explicit pair stays correct across the boundary.
- **Render ranges, but keep the git URL rule in the check.** The check would
  then fail every repository kiln renders.
