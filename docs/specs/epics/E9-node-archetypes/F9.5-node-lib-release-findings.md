Five gaps between `node-lib` and what `python-lib` already does, found while
ngkit adopted kiln. None blocks the adoption: ngkit releases as one fixed group
today. Each story records the finding and the files it would change; none is
scheduled.

## Context

`node-lib` releases every publishable project as one fixed Nx release group
under a single `v<version>` tag ([ADR-0015](../../../adr/ADR-0015.md)).
`python-lib` releases each package under its own `<package>-v<version>` tag,
with its own version, GitHub release and, under `[ci] release = "pypi"`, its own
upload. The node path already creates the GitHub release as a draft, publishes
to npm, and only then publishes the release, but it passes no npm token and the
standard tells the owner to keep `"dryRun": true`, so nothing reaches npm.

## S9.5.1 — `node-lib` releases packages independently

**State:** New

An independent mode for `node-lib`, chosen in `config.toml`, beside today's
fixed group.

**Build:**

1. `nx.json` renders `release.projectsRelationship: "independent"` in this mode
   and `"fixed"` otherwise; `release.version` and the changelog follow.
1. Each package is tagged `<package>-v<version>`, the python spelling, with the
   scope stripped from an npm name (`@s/a` gives `a-v1.2.0`), and gets its own
   GitHub release, tarball asset and notes.
1. Internal dependencies are caret ranges (`workspace:^`), which S15.4.3 already
   enforces.
1. A push releases the packages whose version is not yet tagged, in dependency
   order, as the python release job does; `task ci:release:state` reports per
   package.

**Acceptance:**

- A rendered independent `node-lib` has `projectsRelationship: independent`, and
  two packages at different versions produce two tags and two releases.
- A fixed `node-lib`'s rendering is unchanged (`task self:golden:compare`).
- `task validate` passes.

**Files:** `modules/tasks/templates/tasks/ci.yml.j2` (`release:*` tasks),
`modules/cicd/templates/workflows/_release.yml.j2` and `ci.yml.j2`,
`modules/instructions/templates/standard.md.j2` (Releasing), the `nx.json`
template, `devops/` release-state.

## S9.5.2 — `[ci] release = "npm"`

**State:** New · **Depends on:** S9.5.1

The npm counterpart of `[ci] release = "pypi"`.

**Build:**

1. Publish to npm by trusted publishing (OIDC), with provenance
   (`--provenance`), and no `NODE_AUTH_TOKEN` or other npm secret.
1. Publish before the GitHub release is published, as today's
   draft-then-finalize order already does, so a published release implies the
   version is on npm.
1. The standard stops telling the owner to add `"dryRun": true` to
   `nx-release-publish`; the setting is rendered from the mode.
1. The owner creates GitHub environments as for pypi (`npm`, deployment branch
   `main`), and one trusted publisher per package on npmjs.com.

**To verify before building:** which workflow file the npm trusted publisher
must name when the publish runs in a called workflow (`_release.yml`) rather
than the caller (`ci.yml`). PyPI requires the caller; confirm whether npm
validates the caller or the called file, and record the answer in the standard.

**Acceptance:**

- A `node-lib` with `release = "npm"` renders a publish step with
  `id-token: write`, no token variable, and `--provenance`; one without it
  renders as today.
- The standard names the workflow and environment the trusted publisher takes.
- `task validate` passes.

**Files:** `modules/cicd/templates/ci.yml.j2` and `workflows/_release.yml.j2`,
`modules/tasks/templates/tasks/ci.yml.j2` (`release:publish`), the config schema
for `[ci] release`, `standard.md.j2` (Releasing and the variables table).

## S9.5.3 — `node-lib` ships an SBOM and an attestation per package

**State:** New · **Depends on:** S9.5.2

`python-lib` generates a CycloneDX SBOM per package and attests its
distributions; `node-lib` does neither.

**Build:**

1. A CycloneDX SBOM (`<package>.cdx.json`) is generated per package from its
   lockfile entries.
1. `actions/attest-build-provenance` (the pinned `attest` action) attests each
   tarball and SBOM before anything is published.
1. Both are release assets, and the verify step fails when one is missing.

**Acceptance:**

- A rendered `node-lib` release job has the SBOM and attest steps, and its
  release asset list includes `*.cdx.json`.
- `task validate` passes.

**Files:** `modules/cicd/templates/ci.yml.j2` and `workflows/_release.yml.j2`,
`modules/tasks/templates/tasks/ci.yml.j2`, `devops/` (`release-publish` asset
list and verification), `modules/cicd/pins.toml`.

## S9.5.4 — `workspace:*` in a fixed group

**State:** New · **Depends on:** S9.5.1

Low priority. `kiln-devops requirements --stack node` rejects `workspace:*`
because it publishes as an exact pin. In a fixed release group an exact pin is a
legitimate choice, since the members always release together. ngkit has moved to
`workspace:^`, so nothing waits on this.

**Build:** either (recommended) accept `workspace:*` when `nx.json`'s
`release.projectsRelationship` is `fixed`, or keep the check and state in the
standard that `node-lib` requires caret ranges, and why.

**Acceptance:**

- With the first option, a fixed workspace using `workspace:*` exits `0` and an
  independent one still fails; with the second, `standard.md` carries the
  rule.
- `task validate` passes.

**Files:** `devops/requirements.py` (`check_node`),
`tests/devops/test_requirements_node.py`, or `standard.md.j2`.

## S9.5.5 — The one-entrypoint rule allows project-scoped native commands

**State:** New

`standard.md.j2` §1 says nobody invokes `pnpm`, `npx`, `nx` or `ng` directly,
but the ten verbs cannot cover project-level commands: `nx serve <app>`,
`nx g …`, `nx show project`, `nx run-many -t pack`. No check enforces §1 in
documents today; only workflow steps are checked.

**Build:** narrow §1 to workflows and the gate verbs: a workflow step and a gate
(`validate`, `lint`, `test`, `build`) go through `task`, while a document may
name a native command that is project-scoped and documented. The alternative, a
pass-through verb (`task nx -- …`), adds a verb to the ten and is not
recommended.

**Acceptance:**

- A rendered standard states the narrowed rule, and the `AGENTS.md` block
  repeats no wider claim.
- The workflow check that rejects a wrapped tool is unchanged.
- `task validate` passes.

**Files:** `modules/instructions/templates/standard.md.j2` (§1),
`modules/instructions/` AGENTS block template,
`docs/reference/standard-repo.md`.
