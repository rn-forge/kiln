# F13.2 — The board and Scope regions, and metadata checks

**Status:** planned

Epic: [E13](index.md) · Design: [E13 design](design.md#the-work-model) ·
**Depends on:**
[S13.1.1](F13.1-derived-regions.md#s1311-the-nav-is-a-derived-region)

This feature is code in `rn_forge.kiln.modules.docs`, tested on trees built
under `tmp_path`. It changes no golden and no template; F13.3 does that.
Everything here applies only to a repository whose `docs/specs/index.md` carries
the board fence, so kiln's own tree (no fence until S13.3.2) and the goldens (no
fence until S13.3.1) pass unchanged.

**Build each story by the
[board's procedure](../../index.md#building-a-story).**

## S13.2.1 — Read and validate work-item metadata

**Status:** planned

**Build:**

- New `modules/docs/work.py`, with this public surface:
    - Constants, verbatim from the design: `EPIC_KEYS`, `FEATURE_KEYS`,
      `RELEASE_KEYS` (tuples, in the design's order),
      `STATES = ("New", "Active", "Closed", "Removed")` and
      `RELEASE_STATUSES = ("planned", "in progress", "shipped")`.
    - `read_metadata(text: str) -> list[tuple[str, str]] | None` reads the
      metadata table exactly as the design's
      [Page metadata](design.md#page-metadata) says, returning the
      `(key, value)` pairs in file order with both sides stripped. It returns
      `None` when there is no such table.
    - Frozen dataclasses:
      `Page(path: Path, title: str, meta: tuple[tuple[str, str], ...])`, with a
      `get(key) -> str | None` method;
      `FeatureRow(id: str, file: str | None, state: str, tags: str)`;
      `Epic(page: Page, number: int, dir: str, rows: tuple[FeatureRow, ...], has_state_column: bool)`;
      `Feature(page: Page, id: str, epic_number: int, epic_dir: str)`, where
      `id` is the file name's prefix (`F13.2`) and `iteration` is a property
      returning the `release-<n>` name its `Iteration` value links to, or
      `None`; `Release(page: Page, number: int, dir: str)`;
      `Work(epics: tuple[Epic, ...], features: tuple[Feature, ...], releases: tuple[Release, ...])`.
    - `load_work(docs_root: Path) -> Work` globs `specs/epics/*/index.md`,
      `specs/epics/*/F*.md` and `releases/release-*/index.md`, sorted by number.
      A page without metadata is still loaded, with an empty `meta`, so that
      `validate` can report it.
    - `validate(work: Work, repo_root: Path) -> list[Finding]` applies every rule
      in the design's
      [Rules and finding codes](design.md#rules-and-finding-codes) table except
      `docs.board-markers` and `docs.scope-markers`, which S13.2.2 owns. It uses
      those codes verbatim. Each message names the page, the key and the
      offending value, for example `has Closed Date but its State is Active`.
- No wiring in this story: `generate.py` and the check do not call `work.py`
  yet.

**Do not:** validate stories; validate a feature's `Start Date` (the design says
why); read `Source` or `Predecessors` values beyond their presence.

**Tests:** new `tests/modules/docs/test_work.py`. Build each tree under
`tmp_path` with a small helper that writes `{relative path: text}`. Copy the
helper shape from `tests/modules/docs/test_docs.py`'s `repo` fixture usage.

**Acceptance:**

- `read_metadata` returns the same pairs for a table written with `| | |` /
  `| --- | --- |` and for the same table after mdformat (`|  |  |` /
  `| -- | -- |`). It returns `None` when a paragraph sits between the title
  and the table.
- A valid tree with one epic (`Active`), two features (one `Active` with an
  `Iteration` linking `release-1`, one `New` tagged `deferred` with
  `Entry criteria`) and `releases/release-1/index.md` (`in progress`) gives no
  finding.
- Each code in the design's table, except the two marker codes, has a test that
  breaks exactly one rule in that valid tree and asserts exactly that one
  finding code.
- Two broken pages give two findings: reporting does not stop at the first.
- An epic table row that links `F1.1-x.md` with the State cell `New`, while the
  file has `State` `Active` gives `docs.work-state-mismatch`. A bare-ID row is
  never compared.

## S13.2.2 — Generate the board and Scope regions

**Status:** planned · **Depends on:** S13.2.1

**Build:**

- `modules/docs/work.py` gains:
    - `BOARD_BLOCK = ManagedBlock("derived board", comment=HTML_COMMENT)` and
      `SCOPE_BLOCK = ManagedBlock("derived scope", comment=HTML_COMMENT)`,
      importing `ManagedBlock` and `HTML_COMMENT` from
      `rn_forge.commons.fs.blocks`.
    - `render_board(work: Work) -> str` and
      `render_scope(work: Work, release: Release) -> str`. Each returns the
      region body exactly as the design's
      [board region](design.md#the-board-region) and
      [Scope region](design.md#the-scope-region) give it, including the leading
      and trailing blank lines. Titles are page H1s.
- `modules/docs/generate.py`:
    - `generate(root)` and `stale(root)` also handle the board and Scope regions
      when `docs/specs/index.md` contains `BOARD_BLOCK.begin`. The board's body
      comes from `render_board`, and each release page's Scope from
      `render_scope`. Write with `BLOCK.render(text, body)`.
    - In that case `stale` also returns `validate(load_work(...))`, and
      `docs.board-stale` (`docs/specs/index.md`) or `docs.scope-stale` (that
      release page) when a region differs. Each stale message ends `— run \`task
      docs:generate\`\`.
    - `docs.board-markers`: only one of the board's two markers is present.
      `docs.scope-markers`: the board fence exists, but a release page has no
      complete scope fence. Neither page is written.
    - `generate` writes the regions even when `validate` finds errors, and returns
      those findings as a second value:
      `generate(root) -> tuple[list[Path], list[Finding]]`. Update the S13.1.1
      callers.
- `commands.docs_generate` prints each finding with `console.error`, as `doctor`
  does, and raises `AppException` when any is an error, after writing.

**Do not:** generate a board for a tree without the fence; insert a missing
fence; write a release page's `Status`; add a task (`task docs:generate` already
runs `kiln docs-generate`).

**Tests:** `tests/modules/docs/test_work.py` for rendering, and
`tests/modules/docs/checks/test_derived.py` for the check. Import `mdformat` at
the top of the test module. It is in the `docs` dependency group, which
`task setup` installs (`uv sync --group dev --group docs`); do not add it to
`dev`.

**Acceptance:**

- For the valid tree of S13.2.1 plus a `release-2` page (`planned`, no
  features), `render_board` returns the design's shape. Release 2 is listed
  first with `—`, release 1 shows `1 Active`, and the backlog has a
  `### Deferred` row for the deferred feature with its epic's link.
- With no epics and no releases, `render_board` returns a Releases table with no
  rows and `Every feature is on a release or Removed.`.
- `render_scope` lists features numerically: `F2.1` before `F10.1`.
- `mdformat.text(<region inside its fence>, options={"wrap": 80, "compact_tables": True}, extensions={"gfm", "tables", "mkdocs"})`
  returns its input unchanged, for every region the tests render.
- A tree with the board fence and a hand-edited board row reports
  `docs.board-stale`. After `generate`, `stale` reports nothing.
- A tree without the board fence reports no board, scope or work finding,
  whatever its spec pages contain.
- A release page without a scope fence, under a fenced board, reports
  `docs.scope-markers`, and `generate` leaves that page byte-identical.
- In kiln, `uv run kiln doctor . --only docs-generate` passes (no fence yet).
