# S7.8.4 — Preview and apply share a plan

Brief for
[S7.8.4](../F7.8-existing-repos-take-the-pin-table.md#s784-preview-and-apply-share-a-plan),
at `871e2b1`.

## Goal

Prepare the managed changes once and use that plan for preview, execution and
upgrade. Keep ownership checks and required docs finalization inside the apply
recovery boundary.

## Current behaviour

- `commands/apply.py:33` plans to validate force paths, then calls
  `cycle.apply`, which plans again.
- `modules/core/cycle.py:208` applies starter policy, but the separate preview
  at line 307 renders all artifacts directly.
- `commands/config.py:90` writes the candidate config before invoking apply.
- `commands/new.py:118` finalizes derived docs after rendering. Existing-repo
  apply does not, so enabling MkDocs can leave an incomplete first render.

## Change

- Consolidate artifact preparation in `modules/core/cycle.py`. Reuse the
  existing engine for classification and writes. Allow the committed config or
  an already validated candidate. Keep force, provenance and starter policy in
  the shared preparation and execution path.
- Route ordinary apply, diff and config preview through that preparation. Pass a
  prepared plan into execution so the classification checked and displayed is
  the one used. Keep explicit starter creation for `new` and package
  generation. Preserve their sequencing for package docs.
- For config update and upgrade, include the pending config write with the
  apply, so a refused or failed apply leaves the previous config and state.
- Use the existing derived-docs implementation to initialize the required
  regions when apply enables MkDocs. Include those writes and the ownership
  checks in the apply recovery boundary. Account for the candidate state in
  post-write checks. Preserve the read-only behavior of ordinary doctor.
- Expose the prepared artifact changes and all paths the apply can write to the
  upgrade coordinator. Keep pin resolution, range edits, clean Git checks and
  the full task gate in S7.8.2.

## Tests first

- Through the normal commands, compare config preview, dry-run and the apply
  result for the same candidate, including a missing starter. Assert the
  preview and dry-run leave the tree byte-for-byte unchanged.
- Verify ordinary apply reuses its plan after checking force paths. Cover drift
  refusal and an explicitly forced path.
- Enable MkDocs on an existing repo, apply once, and run doctor. Inject a docs
  finalization or ownership-check failure and assert restoration of the
  candidate config, managed files, derived docs and state.
- Keep existing coverage for new and package starter behavior.

## Validation

Run the relevant apply, config lifecycle, diff, doctor and scaffold tests
through `task test -- <paths>`. Run `task validate KILN_DOCTOR_FULL=1`. Use
`task kiln:apply` for any required changes to generated files.
