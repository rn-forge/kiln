With `[ci] release = "pypi"`, PyPI rejects every upload from the generated
pipeline. The cause is the reusable `_release.yml` that
[S15.8.9](../E15-ci-standard/F15.8-one-workflow-contract.md#s1589-reusable-stage-workflows)
introduced. This feature moves the library workspace's release job back into
`ci.yml`, where the [standard](../../../reference/standard-repo.md) already says
it runs: "adds a trusted publisher per package … naming workflow `ci.yml`".

## Context

pykit's first run on `main` after its cutover, run 43510893434:

1. **Attempt 1**, with trusted publishers naming `ci.yml`: the token exchange
   failed with `422 invalid-publisher`. PyPI matches a GitHub publisher on the
   OIDC token's `job_workflow_ref`, which for a called workflow is the callee,
   `rn-forge/pykit/.github/workflows/_release.yml@refs/heads/main`.
1. **Attempt 2**, with the publishers changed to `_release.yml`: the token
   exchange passed, then the upload failed with `400 Invalid attestations`.
   PyPI checks a PEP 740 attestation's Sigstore certificate by its Build
   Config URI (OID 1.3.6.1.4.1.57264.1.18), which is the caller,
   `.github/workflows/ci.yml@refs/heads/main`, against the publisher's
   workflow, `_release.yml`.

No publisher satisfies both checks while the upload runs in a called workflow.
Only a job in the top-level workflow gives the same file for both
`job_workflow_ref` and the Build Config URI. pykit's Release 7 passed because
`main.yml` ran the upload inline. Nothing was published: PyPI and GitHub have no
Release 8 version.

Dropping `ci:release:sign` would also make the upload pass, but it removes the
attestations
[S6.8.3](F6.8-pykit-release-7-ci.md#s683-release-pypi-uploads-pep-740-attestations)
added, so it is rejected (see below).

**Scope: the whole workspace body, not only `pypi`.** `_release.yml.j2` has
three bodies: `node_lib`, `workspace` (both `tag-exists` and `pypi`) and
single-package. Moving the `workspace` body for every mode leaves it in one
place. Moving it only for `pypi` would mean keeping two copies of the same body
or adding a shared partial. `tag-exists` loses nothing by being inline, because
`actions/attest` provenance verifies from a called workflow too (by signer
workflow). The `node_lib` and single-package bodies stay in `_release.yml`.

## S6.11.1 — `python-lib` renders its release job inline in `ci.yml`

**State:** Closed (2026-11-13)

**Build:**

- `modules/cicd/templates/ci.yml.j2`: when `workspace`, the `release` job is the
  `workspace` body of `_release.yml.j2`, moved in place of the
  `uses: ./.github/workflows/_release.yml` caller. It keeps the caller's
  `needs`, `if` and `permissions` (`contents: write`, `id-token: write`,
  `attestations: write`). Its steps, `environment`, `env`, `timeout-minutes`

- `tests/modules/cicd/test_reusable.py`: `_expected("python-lib")` drops

**Acceptance:**

## S6.11.2 — The docs say why the workspace release job is not a reusable workflow

## Acceptance

Not scriptable, judged by the owner on pykit, after `task kiln:apply` there on
`[kiln] ref = "feature/v1"`:

- The rendered `ci.yml` has an inline `release` job, and `_release.yml` is
  deleted.
- pykit's trusted publishers on pypi.org and test.pypi.org name `ci.yml` again,
  and the `_release.yml` ones are removed.
- The next push to `main` publishes Release 8: every selected package is on PyPI
  with its attestations, and `verify-release` passes.

## Considered and rejected

- **Drop `ci:release:sign` (the PEP 740 attestations).** The upload passes from
  `_release.yml`, but PyPI shows no provenance, and S6.8.3 is undone. The
  `actions/attest` provenance stays on GitHub only.
- **Move only the `pypi` body.** That needs two copies of the workspace body, or
  a shared partial, for no gain. See *Context*.
- **Register both `ci.yml` and `_release.yml` publishers.** The token is minted
  for `_release.yml`, and the attestation is still checked against that
  publisher, so it fails the same way.
