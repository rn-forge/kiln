[E11 design](index.md#design)

Split from F11.2 on 2026-09-27 so that each feature belongs to one release.
F11.2 builds the package sites; this feature deploys them. S11.5.1 replaces the
retired S11.2.4.

## Context

Moved to release-1 on 2026-10-18. The entry criterion it began with, that
pykit's default branch publishes versioned package sites, was circular: pykit
publishes them only through its hand-written `main.yml`, which this story exists
to retire. The pin is removed from the [board](../../index.md#upstream-pins).
What S11.5.1 needs from outside is nothing observable beyond the
`rn-forge-devops` pin F6.4 already holds.

It is also the last blocker to deleting that `main.yml`. Today a pykit push to
`main` would run two Pages deploys in the `pages` concurrency group, kiln's
root-only `docs.yml` and `main.yml`'s `docs` job, and a root-only deploy that
lands last removes the package sites from the live site. Rendering the deploy
inside `ci.yml` for `python-lib`, and no separate `docs.yml`, leaves exactly one
job that deploys Pages.

## Design

Settled 2026-10-18.

- **The task.** `ci:docs-publish`, an internal CI-only task in `python-lib`'s
  `tasks/ci.yml`. Like the other `ci:*` tasks it is public, not
  `internal: true`, because go-task refuses an internal task from the command
  line
  ([F6.4 Design, "The `ci` namespace"](../E6-rebuild-the-repos/F6.4-workspace-pipeline.md#design)).
  It adds no root verb; [ADR-0007](../../../adr/ADR-0007.md)'s vocabulary is
  unchanged.
- **What it does,** ported from pykit's `main.yml` `docs` job (pykit `8cc7b69`,
  `git -C ../pykit show 8cc7b69:.github/workflows/main.yml`, lines about
  337-397): for each package `rn-forge-devops released` reports,
  `mike deploy --deploy-prefix <dir> -F <dir>/mkdocs.yml --alias-type copy --update-aliases --push <major.minor> latest`
  onto `gh-pages` (plus `mike set-default` the first time); then the root
  site, strict; then `gh-pages`' `packages/` tree extracted into the root
  site.
- **The job.** For `python-lib`, `ci.yml` gains a `docs` job after `release`:
  needs `validate`, `plan` and `release`; runs when `release` did not fail,
  the plan's `docs` output is `'true'`, and the event is a push to `main`;
  `concurrency: pages`; permissions `pages: write`, `id-token: write` and
  `contents: write`. It runs `task ci:docs-publish`, then uploads and deploys
  the Pages artifact. `ci-ok` needs `docs` too.
- **No `docs.yml` for `python-lib`.** Every other archetype keeps its `docs.yml`
  unchanged.

## Considered and rejected

- A public `docs:publish` root verb: a compatibility surface under
  [ADR-0007](../../../adr/ADR-0007.md) for a step only CI runs.
- Keeping a separate `docs.yml` for `python-lib` beside the new job: two Pages
  deploys per push, with the race described in Context.

## S11.5.1 — CI deploys versioned package sites

**State:** Closed (2026-10-18) · **Depends on:** S6.4.4

The `python-lib` CI template gains the docs deploy and drops `docs.yml`, as the
Design says.

**Build — tests first.** Tests go in `tests/modules/tasks/test_artifacts.py` and
`tests/modules/cicd/test_artifacts.py`, named `test_s11_5_1_<n>_…`, in the shape
of the S6.4 tests there.

1. `tasks/ci.yml` has a `docs-publish` task with a `desc` and no `internal` key;
   its commands run `mike` per released package, build the root site, and
   merge `gh-pages`' `packages/` tree.
1. The `python-lib` `ci.yml` has a `docs` job after `release` with the needs,
   `if`, `concurrency`, permissions and steps in the Design, and `ci-ok` needs
   it. It is present only when docs are on.
1. `python-lib` renders no `docs.yml`.
1. Every other archetype's `docs.yml` and `ci.yml` render as before.

**Acceptance:**

- The rendered `python-lib` `ci.yml` has the `docs` job and no `docs.yml` is
  rendered; `actionlint` passes on it, and `ci-entrypoint` passes.
- The rendered `docs.yml` of every other archetype is unchanged.
- A throwaway `python-lib` repository's run, or pykit's, publishes
  `packages/<pkg>/latest/`, and the run is linked here.

**What the build settled that the story did not say.**

- The root site is built by `task docs:build -- "$SITE_DIR"`, reached from the
  task as `{{.TASK_EXE}}`, with `SITE_DIR` passed through `env:`
  (`${{ runner.temp }}/site`, as `docs.yml` did). pykit's separate
  `mkdocs build --strict` is that task's first command, so every package site
  is also strict-built once more.
- `docs-publish` is rendered only when docs are on, as `docs:build` is. The job
  also checks `needs.validate.result == 'success'`, as pykit's did, and runs
  `task setup` before the task, as the other jobs do.
- With `release = "none"` there is no `release` job, so `docs` then needs only
  `validate` and `plan` and its `if` drops the `release` clause.
- The `github.ref_name == 'main'` test is the literal `external-install` uses.
  The merge extracts gh-pages' `packages/` tree as the Design says, while
  `mike` deploys under each package's own `dir`; a member outside `packages/`
  is deployed but not merged into the site.
- The job has no `actions/configure-pages` step: `docs.yml` never had one and
  the repo pins none.
