# ADR-0007 — Compose a declared public task vocabulary from modules

**Status:** accepted (2026-09-15) · **Scope:** the task surface of every
repository kiln generates

## Decision

A repository exposes a declared public task vocabulary, appropriate to its
archetype and its selected capabilities. `task` is the only entrypoint; nothing
— human, agent or CI — invokes the underlying tools directly.

The implementation is composed from concern-specific task modules. Root tasks
delegate to modules; a module keeps its implementation tasks internal and
exposes only its declared public surface.

A task file belongs to whatever owns its tasks. A language toolchain's file
holds every primitive of that toolchain: install, lint, format, typecheck, test
and build. A concern's file (docs, CI) holds the checks on the files that
concern generates. A service's file holds only how to run the service. Checks on
the repository as a whole share one file. When a public namespace exposes its
checks, it does so through a single `<namespace>:lint`, named after the root
verb it feeds, and not through one public verb per check.

The vocabulary is extended through explicit module or capability configuration,
never by editing a generated task file. Composition is checked: a repository
whose required validation is no longer reachable from the aggregate gate does
not pass.

## Consequences

- Callers get a stable interface while modules change their implementation
  underneath it.
- A new capability adds a namespaced public surface without flattening the task
  architecture into one file.
- An extension must declare its interface, so the public surface is always
  knowable without reading the task files.
- The public vocabulary is a compatibility surface: renaming a verb is a
  breaking change to every caller, agent and workflow.
- Renaming an internal task breaks no caller, but it does rename that task's
  `command_overrides` key. A repository that sets the old key has to update
  its config.
- A new toolchain adds one file, and a new archetype composes the files for its
  stacks rather than splitting a stack's commands across the shared ones.

## Alternatives considered

- **Let every repository invent its own public interface.** A caller then has to
  discover how to build and validate each repository, which is the state
  agents cope with worst.
- **Keep every command in one root task file.** Unrelated concerns become
  coupled, and a capability cannot add tasks without editing shared lines.
- **Freeze every repository to one universal command list.** A new capability
  then cannot expose the operations its users need, so the list gets bypassed.
- **Split the files by verb**, with one quality file for every lint, format,
  typecheck and test primitive. This was the layout until 2026-10-21. It
  spread each toolchain's commands over several files, and no module could add
  a check without editing the shared one.
- **One file per formatter** (TOML, Markdown). Each would hold two tasks. The
  checks cover the whole tree, so they stay with the other repository-wide
  checks.
- **A dedicated task-running tool of our own.** Built as taskkit and retired
  (D23): go-task already does this, and the wrapper was maintenance without a
  requirement.

## Background

The idea of writing the vocabulary down, rather than leaving it implicit in the
task files, came from a donor repository's task-vocabulary guide. The verbs
themselves were reconciled across two donor repositories that had drifted —
`format-check`, `dev` and `docs` on one side against the set now in the
reference.

- 2026-10-21: revised, by owner decision. The task files are split by owner: a
  file per toolchain (`python`, `node`), a file per concern for that concern's
  checks (`docs`, `ci`), and the repository-wide checks in `quality`.
  `docs:structure` gives way to `docs:lint`, and the frontend's
  lint/test/build leave the public `web:*` surface. The layout and the renames
  are [F4.12](../specs/epics/E4-generator/F4.12-task-files-by-owner.md).
