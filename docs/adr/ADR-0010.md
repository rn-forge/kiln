# ADR-0010 — kiln is a pinned dev dependency, and CI runs it read-only

**Status:** accepted

*Revised 2026-09-13. Until then this ADR split the checks into a separate
package; what it said and why it changed are under [History](#history).*

## Context

Before this decision a generated repo carried **1,454 lines** of committed
checker scripts, identical in every repo except for lists already present in
`.rn-forge/kiln/config.toml` (the breakdown is under History). That was
[ADR-0003](ADR-0003.md)'s rule read literally: CI runs committed code and never
installs kiln, so the checkers had to be committed. The question is what CI
installs to run the checks instead.

ADR-0003's case against CI installing kiln was that a generator bug becomes a
build failure in ten repos at once. That holds for an unpinned install. With
kiln locked, a kiln release changes nothing in a repo until that repo's lock
moves, and the lock moves in a pull request whose CI runs the new kiln against
that repo.

The open risk was resolution. pykit's workspace contains `rn-forge-tooling`, and
kiln depends on it. The spike recorded on
[S4.1.4](../specs/epics/E4-generator/F4.1-checks-by-module.md#s414-the-ci-shape-is-decided)
found that `uv lock` fails in pykit with conflicting URLs for
`rn-forge-tooling`, whether kiln names tooling by direct URL or by a bare name
with its own git source. One `override-dependencies` entry in pykit resolves it,
to pykit's own workspace copy. A consumer repo resolves with no change.

### Alternatives considered

- **Two distributions: `rn-forge-kiln` and a render-free
  `rn-forge-kiln-checks`** — this ADR's original decision, organized by module
  in D74. Keeps Jinja, the generation engine and the templates out of CI's
  environment. Rejected: two distributions to version and keep in schema step,
  a skew check that exists only because of the split, and CI still cannot run
  the render-dependent checks. What it saves is a dev-group install.
- **Two distributions, plus a non-gating regression workflow** that installs
  kiln at a ref on a schedule and opens a pull request with the rendered diff
  (option C on F4.1). Rejected: the pinned dependency gives the same signal on
  an ordinary dependency pull request, without a second install path, a
  write-scoped token or a new task verb.
- **kiln unpinned in CI, rendering on the fly.** Rejected, for ADR-0003's
  reason.
- **Keep committing every checker.** Rejected: a fix to a checker is ten commits
  instead of a version bump, and the byte-identical test that guards the
  copies is F2 — four forks of one script — reproduced deliberately at ten
  times the scale.
- **Put the checkers in `rn-forge-commons` or `rn-forge-tooling`.** Rejected on
  [ADR-0002](ADR-0002.md)'s table: "every managed artifact matches the
  committed state baseline" is rn-forge repository policy, and policy in a
  runtime-neutral library is how `forge-core` went wrong. The docs checkers
  are the exception, because they are mechanism (below).
- **Dodging the pykit conflict from kiln's side**, with a path source or a git
  source in kiln's own `[tool.uv.sources]`. Rejected: a path source is not
  CI-capable, and the spike showed the git source conflicts exactly as the
  direct URL does.

## Decision

**kiln is a dev dependency of every kiln-generated repo, pinned like any other
rn-forge dependency ([ADR-0005](ADR-0005.md)), and CI runs that pinned kiln
through `task`. CI only checks: it never runs `apply` and never writes a
generated file.**

- **One distribution.** `rn-forge-kiln` carries the generator, the templates and
  every check. The render-free checks live in the module that owns each rule
  and are reached as `kiln check`; the render-dependent ones are
  `kiln doctor`. An import contract keeps `kiln check` render-free, so it
  stays cheap.
- **Two gates.** `task validate` runs `kiln check` on every CI run.
  `kiln doctor`, a full render and diff, runs where the workflow asks for it:
  by default, pushes to the default branch and manual dispatch. It is not a
  new verb — `lint` runs it when the `KILN_DOCTOR` task variable is set, so
  [ADR-0007](ADR-0007.md)'s vocabulary is unchanged.
- **Upgrading is a dependency bump.** Inside a repo, `kiln upgrade` moves the
  `rn-forge-kiln` pin and the lock, and `uv sync` installs the new kiln; the
  new kiln then runs `kiln config upgrade --apply`. Nothing is rendered by the
  kiln that was running before the bump. Outside a repo, `kiln upgrade` is the
  lifecycle verb that upgrades the installed tool `kiln new` runs from.
- **What stays committed** is what CI must trust without re-deriving it:
  `.rn-forge/kiln/state.json` (carrying `schema_version`),
  `.rn-forge/kiln/config.toml` and `.rn-forge/kiln/standard.md`. The checker
  logic is not committed, and `scripts/` leaves a generated repo.
- **The docs checkers live in `rn-forge-tooling`** (`check_docs`,
  `check_structure`, `gen_nav`): validating a docs tree against a declared
  area model is generic mechanism, and kiln supplies the policy object. The
  four policy checks — generated state, the rn-forge dependency set, the task
  layout, the CI entrypoint rule — are kiln's.
- **A pykit workspace that takes kiln overrides every pykit member kiln
  reaches**, with `[tool.uv] override-dependencies`, so kiln resolves to the
  workspace copies.

## Consequences

- A generated repo loses 1,454 lines it never reads. `scripts/` exists only for
  a repo's own lints, wired through `[tasks.extra_refs]`, and
  `tests/support/assert_generated_bodies.py` loses its subject.
- Jinja, pydantic, the generation engine and the templates enter every repo's
  dev lock. That is the accepted price of one kiln everywhere.
- Which kiln rendered a repo is recorded in its lock. Doctor check 8b is
  `kiln.pin`: kiln is a pinned dev dependency, and the running kiln is the
  locked one.
- A bad kiln release breaks no repo until someone moves that repo's pin, and
  then it fails that pull request's CI.
- A cold clone still builds without `$RNF_HOME` or a bootstrap script. It needs
  `uv sync`, which it needed anyway, and kiln's git source must be reachable,
  like every other rn-forge dependency.
- kiln's own repo stays `python-tool`: it ships one distribution.
- In pykit, kiln runs against pykit's own tooling rather than the tooling kiln
  locked, so a tooling change that breaks kiln fails in pykit's CI first.
- ADR-0003's rule narrows to: CI never writes generated files and never runs an
  unpinned kiln.

## History

### 2026-09-13 — one pinned kiln replaces the separate checks package

Reopened by the owner on
[F4.1](../specs/epics/E4-generator/F4.1-checks-by-module.md) on 2026-09-12 and
decided by S4.1.4. The original decision (below) never shipped: no checks
package was built. What changed the answer:

- Pinning removes ADR-0003's objection. The original reasoning assumed that CI
  installing kiln meant CI installing it unpinned.
- Two distributions bought one thing, a CI environment without the generator, at
  the cost of a second version line, a schema skew check, and CI still being
  unable to run the render-dependent checks.
- The pykit spike showed the one-distribution shape resolves, with one override
  line in pykit and none in consumer repos.

Kept from the original: the checker logic leaves generated repos; only
`state.json`, `config.toml` and `standard.md` stay committed; the docs checkers
belong to tooling. Dropped: `rn-forge-kiln-checks`, the `checks.version` skew
check, and kiln becoming a two-distribution `python-lib` workspace. D74's checks
organized by module survive as `kiln check`. The title and slug were *The
checkers become a versioned package; only their inputs stay committed*
(`0010-checkers-are-a-package.md`).

### Original decision (D51) — the checkers become a versioned package

*Accepted before Phase C, because it changed where Phase C put the docs
checkers.*

**Context then.** ADR-0003 was read as *the checkers themselves are committed*,
so a generated repo was about to carry:

| Script | Lines | Per-repo variation |
| -- | -- | -- |
| `scripts/docs/check_structure.py` | 291 | none |
| `scripts/docs/_common.py` | 172 | none |
| `scripts/docs/check_docs.py` | 158 | none |
| `scripts/docs/gen_nav.py` | 154 | none |
| `scripts/task/check_task_layout.py` | 198 | a list of task names |
| `scripts/standards/check_rn_forge_deps.py` | 191 | three lists |
| `scripts/standards/check_generated.py` | 151 | none |
| `scripts/ci/check_ci_entrypoint.py` | 139 | two lists |

The distinction ADR-0003 was protecting was argued to be *generation*, not
verification: a checker renders nothing, so CI could install one without
installing a generator.

**Decision then.** Split verification from generation into two distributions in
the kiln repo: `rn-forge-kiln` (CLI, templates, rendering; never installed in
CI) and `rn-forge-kiln-checks` (the checkers only, no Jinja, a pinned dev
dependency with one console script per check), with an `.importlinter` contract
forbidding `rn_forge.kiln.checks` from importing `rn_forge.kiln`. kiln would
become a two-distribution `python-lib` workspace.

**Alternatives rejected then, and still rejected:**

- **One distribution, `rn-forge-kiln[checks]`.** Extras add dependencies and
  cannot subtract modules, so CI would have the generator importable. (The
  2026-09-13 revision accepts exactly that, deliberately and pinned.)
- **Name the package `rn-forge-kiln-devops`.** `checks` names a role that can be
  falsified — a checker renders nothing — while `devops` names a domain that
  excludes nothing. [ADR-0003](ADR-0003.md) and D65 rely on this naming
  argument for the `cicd` module.
- **Config headers stay, bodies move** — a ten-line generated shim per checker.
  The lists are already in `config.toml`, so the shim would restate config.
