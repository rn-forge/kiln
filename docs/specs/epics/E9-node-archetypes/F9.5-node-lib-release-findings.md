Five gaps between `node-lib` and what `python-lib` already does, found while
ngkit adopted kiln. None blocks the adoption: ngkit releases as one fixed group
today. Each story records the finding and the files it changes. The owner moved
the feature into release 1 on 2026-11-17.

## Context

`node-lib` releases every publishable project as one fixed Nx release group
under a single `v<version>` tag ([ADR-0015](../../../adr/ADR-0015.md)).
`python-lib` releases each package under its own `<package>-v<version>` tag,
with its own version, GitHub release and, under `[ci] release = "pypi"`, its own
upload. The node path already creates the GitHub release as a draft, publishes
to npm, and only then publishes the release, but it passes no npm token and the
standard tells the owner to keep `"dryRun": true`, so nothing reaches npm.

## S9.5.1 — `node-lib` releases packages independently

**State:** New

An independent mode for `node-lib`, chosen in `config.toml`, beside today's
fixed group. This story is the mode and the versioning; the release job that
publishes it is [S9.5.6](#s956-the-independent-release-job).

**Settled (owner, 2026-11-17):**

- The key is `[archetype.node-lib] release_group`, `"fixed"` (the default) or
  `"independent"`.
- Independent is Nx-native: `nx.json`'s seeded `release` block gains
  `projectsRelationship: "independent"` and the tag pattern
  `{projectName}-v{version}`, and changelogs are per project. `nx.json` is
  seeded, so the key shapes a new repository; an existing one edits `nx.json`.
- `task version -- <bump> <project>` bumps and changelogs one project;
  `task version` prints each publishable project's version.
- A fixed `node-lib` renders as today.

**Acceptance:**

- A `node-lib` with `release_group = "independent"` scaffolds `nx.json` with
  `projectsRelationship: independent` and the tag pattern, and its
  `task version` takes a project.
- A fixed `node-lib`'s rendering is unchanged (`task self:golden:compare`).
- `task validate` passes.

**Files:** the `[archetype.node-lib]` config table, `modules/node/scaffold.py`
(`nx.json`'s `release` block), `modules/tasks/templates/tasks/node.yml.j2`
(`version`), the root `version` task's `desc:`,
`modules/instructions/templates/standard.md.j2` (Releasing).

## S9.5.2 — `[ci] release = "npm"`

**State:** New · **Depends on:** S9.5.1, S9.5.6

The npm counterpart of `[ci] release = "pypi"`.

**Settled (owner, 2026-11-17):** `nx-dispatch` becomes a GitHub-only release: it
tags and publishes the GitHub Release and renders no npm Publish step, so the
standard's `"dryRun": true` advice goes. `npm` adds the Publish step. ngkit, on
`nx-dispatch` with `dryRun`, releases as before.

**Build:**

1. Publish to npm by trusted publishing (OIDC), with provenance, and no
   `NODE_AUTH_TOKEN` or other npm secret. npm generates provenance itself
   under trusted publishing, with npm 11.5.1 or later.
1. Publish before the GitHub release is published, as today's
   draft-then-finalize order already does, so a published release implies the
   version is on npm.
1. The standard stops telling the owner to add `"dryRun": true` to
   `nx-release-publish`; the setting is rendered from the mode.
1. The owner creates GitHub environments as for pypi (`npm`, deployment branch
   `main`), and one trusted publisher per package on npmjs.com.

**Verified, 2026-11-17:** npm's trusted-publisher validation checks the calling
workflow, so the publisher names `ci.yml`, not `_release.yml`, and both the
caller and the called workflow grant `id-token: write`
([npm docs](https://docs.npmjs.com/trusted-publishers)). The standard records
it.

**Acceptance:**

- A `node-lib` with `release = "npm"` renders a publish step with
  `id-token: write`, no token variable, and `--provenance`; one without it
  renders as today.
- The standard names the workflow and environment the trusted publisher takes.
- `task validate` passes.

**Files:** `modules/cicd/templates/ci.yml.j2` and `workflows/_release.yml.j2`,
`modules/tasks/templates/tasks/ci.yml.j2` (`release:publish`), the config schema
for `[ci] release`, `standard.md.j2` (Releasing and the variables table).

## S9.5.3 — `node-lib` ships an SBOM and an attestation per package

**State:** New · **Depends on:** S9.5.2

`python-lib` generates a CycloneDX SBOM per package and attests its
distributions; `node-lib` does neither.

**Build:**

1. A CycloneDX SBOM (`<package>.cdx.json`) is generated per package from its
   lockfile entries.
1. `actions/attest-build-provenance` (the pinned `attest` action) attests each
   tarball and SBOM before anything is published.
1. Both are release assets, and the verify step fails when one is missing.

**Acceptance:**

- A rendered `node-lib` release job has the SBOM and attest steps, and its
  release asset list includes `*.cdx.json`.
- `task validate` passes.

**Files:** `modules/cicd/templates/ci.yml.j2` and `workflows/_release.yml.j2`,
`modules/tasks/templates/tasks/ci.yml.j2`, `devops/` (`release-publish` asset
list and verification), `modules/cicd/pins.toml`.

## S9.5.4 — `workspace:*` in a fixed group

**State:** Closed (2026-11-17)

Low priority. `kiln-devops requirements --stack node` rejects `workspace:*`
because it publishes as an exact pin. In a fixed release group an exact pin is a
legitimate choice, since the members always release together. ngkit has moved to
`workspace:^`, so nothing waits on this.

**Build:** accept `workspace:*` when `nx.json`'s `release.projectsRelationship`
is `fixed` (owner, 2026-11-17). Nx's default, when the key is missing, is fixed.

**Acceptance:**

- A fixed workspace using `workspace:*` exits `0` and an independent one still
  fails. `requirements.release_is_fixed(root)` reads `nx.json` under `--root`;
  `check_node(members, *, fixed=False)` takes the group. Tests:
  `test_workspace_star_passes_in_a_fixed_group`,
  `test_workspace_star_fails_in_an_independent_group`,
  `test_release_is_fixed_reads_nx_json`,
  `test_cli_reads_the_group_from_nx_json`.
- `task validate` passes.

**Files:** `devops/requirements.py` (`check_node`),
`tests/devops/test_requirements_node.py`, or `standard.md.j2`.

## S9.5.5 — The one-entrypoint rule allows project-scoped native commands

**State:** Closed (2026-11-17)

`standard.md.j2` §1 says nobody invokes `pnpm`, `npx`, `nx` or `ng` directly,
but the ten verbs cannot cover project-level commands: `nx serve <app>`,
`nx g …`, `nx show project`, `nx run-many -t pack`. No check enforces §1 in
documents today; only workflow steps are checked.

**Build:** narrow §1, for `node-lib`, to workflows and the gate verbs: a
workflow step and a gate (`validate`, `lint`, `test`, `build`) go through
`task`, while a document may name a native command that is project-scoped and
documented (owner, 2026-11-17). A pass-through verb (`task nx -- …`) was
rejected: it adds a verb to the ten.

**Acceptance:**

- A rendered standard states the narrowed rule, and the `AGENTS.md` block
  repeats no wider claim.
- The workflow check that rejects a wrapped tool is unchanged.
- Tests: `test_node_lib_standard_allows_project_scoped_commands`,
  `test_node_lib_agents_bullet_allows_project_scoped_commands`, and the guards
  `test_python_standard_keeps_the_whole_entrypoint_rule` and
  `test_python_agents_bullet_is_unchanged`. Only the `node-lib` cell's
  `standard.md` and `AGENTS.md` block change.
- `task validate` passes.

**Files:** `modules/instructions/templates/standard.md.j2` (§1),
`modules/instructions/` AGENTS block template,
`docs/reference/standard-repo.md`.

## S9.5.6 — The independent release job

**State:** New · **Depends on:** S9.5.1

Split from S9.5.1 on 2026-11-17. A push to the default branch releases each
publishable project of an independent `node-lib` whose version is not yet
released: its own `<project>-v<version>` tag, its own draft-then-published
GitHub Release with only its tarball and its notes, in dependency order, and the
same new, resume and released modes the fixed job has. There is no rolling
`latest` release in independent mode. `verify-release` installs every tag the
run released.

**Acceptance:**

- A rendered independent `node-lib`'s release job tags, releases and finalizes
  per project, and its `verify-release` takes the run's tags.
- A fixed `node-lib`'s rendering is unchanged (`task self:golden:compare`).
- `task validate` passes.

**Files:** `modules/tasks/templates/tasks/ci.yml.j2` (`release:*`),
`modules/cicd/templates/workflows/_release.yml.j2`, `_verify-release.yml.j2` and
`ci.yml.j2`, `devops/` (release state per project),
`modules/instructions/templates/standard.md.j2` (Releasing).
