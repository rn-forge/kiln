# S7.7.1 — kiln installs from a branch, a tag or a commit

Brief for
[S7.7.1](../F7.7-kiln-installs-as-a-tool.md#s771-kiln-installs-from-a-branch-a-tag-or-a-commit),
at `c7a0923`.

## Goal

kiln's `Kiln` product subclasses pykit's `PythonTool`, so
`kiln self install --archive <tarball> --version <v>` (and, through pykit,
`--ref <branch|tag|sha>`) builds a uv tool environment in the version directory
and puts a working `bin/kiln` on `$RNF_HOME/bin`.

## Settled

- **The floor is already met.** S7.7.5 moved `pyproject.toml` to
  `rn-forge-tooling>=0.3.3,<0.4`; 0.3.3 is the release that carries pykit
  F23.2 (`PythonTool`, `--ref`, `ref`/`commit` in `state.json`). Do not change
  `pyproject.toml`.
- **`product.py`:** `Kiln` subclasses `rn_forge.tooling.install.PythonTool`
  instead of `ToolProduct`. It drops its own `artifacts()`:
  `PythonTool.artifacts()` already returns `(Link("bin/kiln", "bin/kiln"),)`
  for `name="kiln"`, so the link is unchanged. It keeps `checks()` returning
  `(check_home,)`. `PRODUCT` keeps
  `Kiln(name="kiln", version=__version__, repo="rn-forge/kiln")`. Update the
  imports (drop `Link` and `ToolProduct` if unused) and the class docstring to
  say it is installed with `uv tool install`.
- `PythonTool` is a frozen dataclass; subclassing it without re-decorating is
  fine because `Kiln` adds no fields.
- **The install test runs offline.** It sets `UV_OFFLINE=1` and an absolute
  `UV_CACHE_DIR` (the repository's `UV_CACHE_DIR` from the environment, or
  `<repo root>/.uv-cache`, resolved to an absolute path) for the
  `uv tool install` subprocess that pykit's `PythonTool.build` runs, so the
  dependencies come from the cache `task setup` filled. It carries
  `requires("uv", "git")` from `tests.conftest`.
- `--ref` installs need the network, so they are in the feature's acceptance
  block, not a test.
- Tests are named for behaviour, `test_<subject>_<behaviour>`, with no spec ID
  in a name, docstring or comment.

## Current behaviour

At the base commit:

- `src/rn_forge/kiln/product.py`: `class Kiln(ToolProduct)` with `artifacts()`
  returning `Link("bin/kiln", "bin/kiln")` and `checks()` returning
  `(check_home,)`. `ToolProduct.build` copies the release tree into the
  version directory, which has no `bin/kiln`, so activation fails on the link:
  an install from an archive of kiln ends with a non-zero exit and no
  `$RNF_HOME/bin/kiln`. Run the first test below before the change and record
  the exact error in `## Result`.
- `tests/commands/test_lifecycle.py` builds kiln's CLI with
  `build_tool_app(ROOT / "src" / "rn_forge" / "kiln" / "cli.toml")` and an
  autouse `RNF_HOME` under `tmp_path`; copy that fixture shape.
- pykit's own test of the same build is
  `packages/rn-forge-tooling/tests/install/test_python.py` in the pykit repo
  (`../../pykit` from the kiln checkout's parent); read it, do not copy it in.

## Tests first

In `tests/commands/test_lifecycle.py`:

1. `test_self_install_from_an_archive_puts_kiln_on_path`:
   `git archive --prefix=kiln-0.1.0/ -o <tmp>/kiln-0.1.0.tar.gz HEAD` of the
   repository root;
   `kiln_cli.run(["self", "install", "--archive", <tarball>, "--version", "0.1.0"])`
   returns 0; `$RNF_HOME/bin/kiln` is a symlink whose resolved path runs
   through `$RNF_HOME/kiln/current`; running `$RNF_HOME/bin/kiln version` as a
   subprocess exits 0 and prints `0.1.0`. Before the change it fails at the
   install's link step.
1. `test_self_doctor_after_an_install_reports_install_ok`: after the same
   install, `kiln_cli.run(["self", "doctor"])` returns 0 and its output holds
   `install.ok` and no `ERROR`.

Both share one module-scoped or function-scoped install fixture, whichever keeps
them correct under `pytest -n auto`. Check the home layout names
(`kiln/current`, `kiln/versions/`) against pykit's `ToolHome` in
`rn_forge/tooling/install/home.py` (in the installed `rn-forge-tooling`), and
use what it defines rather than hard-coding a guess.
