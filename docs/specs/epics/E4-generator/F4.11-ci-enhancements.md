kiln's generated CI keeps improving after it matches the upstream CI
([F6.3](../E6-rebuild-the-repos/F6.3-hardened-ci.md)): what a repository may add
to it, and what the checks enforce on it, under one CI contract
([ADR-0016](../../../adr/ADR-0016.md)). Each story here is one such change.

[S4.11.1](#s4111-repositories-extend-the-generated-ci-by-reference) lets a
repository extend the generated CI only through files it owns: hooks at named
anchors, and declared jobs that call reusable workflows. kiln never guesses a
repository's needs and no repository hand-maintains its CI. kiln's own
self-hosting ([S4.8.1](F4.8-self-hosting.md#s481-kiln-generates-itself)) is the
first consumer; pykit retiring its hand-written `main.yml` is a likely next one.

## Design

### Extension by reference (S4.11.1)

- **`[ci.hooks]`.** A closed set of anchors; this story ships `setup`, a list of
  local composite actions the generated setup action runs as its last steps.
  Each entry matches `^\./\.github/actions/[a-z0-9][a-z0-9-]*$`, is not
  `./.github/actions/setup` (kiln's own), and is unique. Default: none, and
  the setup action is then byte-identical to before.
- **`[[ci.jobs]]`.** `uses` replaces `task`: a path
  `./.github/workflows/<file>.yml` (or `.yaml`), not `ci.yml`. The job renders
  as a reusable-workflow call after `validate`, and `ci-ok` needs it. `name`
  and `events` are as S4.8.3 settled them.
- **No `runs-on`, `timeout-minutes` or `steps`** on a call: GitHub refuses them.
  The called workflow's jobs carry their own timeouts, and S6.3.1's rule
  applies to them as authored. No `secrets:`: a job that needs secrets is a
  later ADR revision.
- **`ci.node` is removed.** `python-web-app` keeps its Node steps, gated on the
  archetype alone as before S4.8.3.
- **The repository's files are held to the same standard.** `ci-pins` reads what
  the repository owns under `.github/`, and `ci-entrypoint` its workflows (not
  its composite actions); the new `ci-hooks` checks that each hook and
  declared job names a file that exists and that a declared job's workflow can
  be called.

### Workflow security, dependency hygiene and release provenance (S4.11.3–S4.11.6)

- **One contract, no switches.** The four stories add checks to every
  repository's CI ([ADR-0016](../../../adr/ADR-0016.md)). None has a config
  flag to turn it off; the one config surface is the audit ignore list
  (`[[tasks.audit.ignore]]`, `id` and `reason` required), which records
  accepted vulnerabilities. Repositories are public (owner decision,
  2026-10-20), so `dependency-review` and attestations render unconditionally.
- **Scope.** The Python archetypes the cicd and tasks modules render today.
  `node-lib` ([E9](../E9-node-archetypes/index.md), ADR-0015) is out of scope;
  its equivalents are a row in [ideas](../../ideas/index.md).
- **Tools are dev-group packages.** `zizmor`, `actionlint-py` and `pip-audit`
  are added to the generated scaffold's `dev` group (bare names, as `taplo`)
  and to kiln's own `pyproject.toml`, so they are locked and run through `uv`,
  never installed by a workflow step.
- **Findings are fixed, not hidden.** A zizmor finding on the rendered templates
  is fixed in the template; a false positive is suppressed inline with a
  reason. No repository-wide ignore file.
- **The audit's failure mode.** `pip-audit` fails the gate. It needs the
  network. Git-sourced `rn-forge-*` dependencies are excluded from the export
  because they have no PyPI advisories and no hash; they stay in the SBOM.
- **Dependabot covers only what the repository owns.** The generated
  `dependabot.yml` has a `uv` entry and a `github-actions` entry whose
  directories are exactly the `[ci.hooks]` action directories (none, none
  rendered). Generated files are pinned by kiln's `pins.toml` and move only in
  kiln; a Dependabot bump of a generated file would fail `lint:generated`.
  Repo-owned called workflows share `.github/workflows/` with `ci.yml` and are
  not covered (S4.11.4's known gap).
- **The release record.** Attestation is made before the release is created,
  because the release, not the tag, is the record (S6.3.4); a failed
  attestation must leave nothing published. The SBOM comes from `task build`,
  not from a workflow step, so the workflow still calls only `task`.

### Not adopted

- **CodeQL.** Sonar already covers static analysis in the generated CI.
- **gitleaks.** GitHub secret scanning and push protection are repository
  settings, not workflow content.
- **`step-security/harden-runner`.** Not a default; a repository can add it
  through a hook or a declared job.

## S4.11.1 — Repositories extend the generated CI by reference

**State:** Closed (2026-10-20) · **Depends on:** S4.8.3

S4.8.3's build recorded the risk: the setup action's Node steps carry no pnpm
`version:` and no `node-version:`, because `python-web-app` has `packageManager`
and a lockfile to supply them, and kiln has neither a `package.json` nor a
lockfile. The hand-copied `golden-render` job passes `version: 12` and
`node-version: 24`; no key in `[ci] node` can say that, and a key that did would
have kiln guess a repository's Node needs. [ADR-0016](../../../adr/ADR-0016.md)
is revised (2026-10-19) to extend the generated CI by reference to files the
repository owns: hooks at named anchors, and declared jobs that call reusable
workflows. This story builds that, and supersedes S4.8.3's `ci.node` and the
`task` field of `[[ci.jobs]]`. Nothing here changes kiln's own `ci.yml`, which
stays hand-copied until S4.8.1.

### What the build settled that the story did not say

- **`actionlint` does not lint an action file (departure from the Acceptance and
  from `test_s4_11_1_8_*`).** `actionlint` 1.7.12 treats every file it is
  given as a workflow: `actionlint .github/actions/setup-node/action.yml`
  exits 1 with `"jobs" section is missing in workflow` and
  `unexpected key "runs"`, and the same happens for the generated setup
  action. The story's acceptance command and its test both name an action
  file, so neither can hold as written. The test runs `actionlint` on `ci.yml`
  and the called `golden-render.yml` instead (exit 0, which also proves the
  `uses:` call and the hook references resolve); the acceptance run is
  `actionlint .github/workflows/golden-render.yml` (exit 0). The `setup-node`
  action is checked by `ci-pins` and `ci-hooks` only. The story stays open for
  the owner to amend the acceptance line.
- **`ci-hooks` reads `[ci]` itself.** `checks/hooks.py` repeats the two-line
  `getattr(config.document, "ci", None)` read of `artifacts._ci_config` rather
  than importing that private function (pyright strict rejects the import).
- **Hook step placement.** The hook steps are separated by a blank line, as the
  generated steps are; the template ends `{% endfor -%}` so the no-hook output
  keeps its single trailing newline.
- **A non-mapping workflow file** in `ci-hooks` counts as not callable; a file
  that is not valid YAML raises as `ci-pins` does (no special handling).
- **`ci-pins` and `ci-entrypoint` were not changed.** `ci-pins` already walks
  `.github/workflows` and `.github/actions` recursively, and `ci-entrypoint`
  reads `.github/workflows` only, so the design's "repository's files are held
  to the same standard" needed no edit; the two direct runs below prove it on
  kiln's new files.
- **Config example in `standard-repo.md` §9** shows `[ci.hooks]` and
  `[[ci.jobs]]` as tables after the `[ci]` keys, not inline, so the comments
  sit beside the keys they describe.
- **Not verified here (needs S4.8.1 or CI):** the pull-request run of

## S4.11.2 — Pull requests run `ci-pins` and `ci-hooks`

**State:** Closed (2026-10-21) · **Depends on:** S4.11.1

`task validate` reaches `kiln doctor` only through `lint`'s internal tasks, each
of which runs `kiln doctor . --only <check>`: `generated`, `rn-forge-deps`,
`task-layout`, `ci-entrypoint` and the docs checks. `ci-pins` has no lint task,
and `ci-hooks` (S4.11.1) will have none. Both are `ownership` checks in
`CHECKS`, so a bare `kiln doctor` runs them, and `lint:generated` runs a bare
`kiln doctor . --full` only when `KILN_DOCTOR_FULL` is set; the generated
`ci.yml` sets it only for a push to the default branch and for
`workflow_dispatch`. So an unpinned action, a job without `permissions:`, or a
hook or declared job whose file is missing passes a pull request and fails only
after the merge. [ADR-0016](../../../adr/ADR-0016.md) holds a repository's own
files to these checks; this story makes a pull request enforce them, by giving
each its own lint task, shaped as `lint:ci-entrypoint` is, that `lint` runs.

## S4.11.5 — Dependency vulnerability audit

**State:** Closed (2026-10-21) · **Depends on:** S4.11.3

Nothing in the generated CI checks the locked dependencies for known
vulnerabilities. Sonar's dependency risk analysis is a quality-gate matter, not
a `task lint` one, and a pull request that adds a vulnerable pin passes. This
story adds two checks: `pip-audit` of the lock in `task lint`, and GitHub's
dependency review on pull requests.

The audit works against PyPI's advisory service, so it **needs the network**:
`task lint` offline fails on it. A repository that must run offline replaces the
command with `[tasks.command_overrides] "quality:lint:audit"`.

Checked on 2026-10-20 against kiln's own `uv.lock` with `pip-audit` 2.10.1 and
`uv` 0.13.3:

```bash
uv export --frozen --all-packages --all-groups --no-emit-workspace --no-header \
  --no-emit-package rn-forge-commons --no-emit-package rn-forge-cli --no-emit-package rn-forge-tooling \
  | uv run pip-audit --disable-pip --no-deps --strict -r /dev/stdin
```

- `uv export` writes pinned `name==version` lines with hashes, which is what
  `--disable-pip --no-deps` requires; no virtualenv is installed or read, so
  the audit needs no `pip` and cannot drift from the lock. `--frozen` reads
  `uv.lock` without re-resolving; `--all-groups` audits the dev and docs tools
  too, which run in CI with its token. `--no-emit-workspace` drops workspace
  members (local, not on PyPI). `--all-packages` covers every member of a
  workspace and is a no-op otherwise.
- A git-sourced dependency
  (`rn-forge-cli @ git+https://github.com/rn-forge/pykit@…`) is emitted as a
  direct reference with no hash, and `pip-audit` stops with
  `requirement … does not contain a hash`. `--no-emit-package` drops it. It
  cannot be audited against PyPI advisories anyway: the name is a PyPI project
  kiln does not publish to. An unknown name given to `--no-emit-package` is
  accepted (checked), so the command may list every `rn-forge-*` distribution.
- `--strict` makes `pip-audit` fail when it cannot collect a dependency, rather
  than skip it, so a dropped package is a failure, not a silent gap.
- The same run on kiln's own lock finds one vulnerability today: `certifi`
  2026.7.22, `PYSEC-2026-4320`, fixed in 2026.10.19. The builder updates the
  lock (`uv lock --upgrade-package certifi`), and does not add it to the
  ignore list.

## S4.11.6 — Releases carry build provenance and an SBOM

**State:** Closed (2026-10-21) · **Depends on:** S4.11.3

A published release is a wheel and an sdist, with no record of which commit and
workflow built them and no list of what they bring. This story makes the release
job attest the built distributions (GitHub's build provenance) and attach a
CycloneDX SBOM of each shipped package's runtime dependencies, also attested. It
builds on S4.11.3, which replaced the release action with `gh release create`
(the SBOM is one more file in that command).

**The SBOM.** `uv export --format cyclonedx1.5` exists in the installed `uv`
(0.13.3, `--format` accepts `requirements.txt`, `pylock.toml`, `cyclonedx1.5`).
Run on kiln's lock with `--frozen --no-default-groups` it writes a CycloneDX 1.5
document with the project as the root component, its 24 runtime dependencies as
components, and the git-sourced `rn-forge-*` ones as components with a
`pkg:pypi/…?vcs_url=…` purl. So the git-sourced packages stay in the SBOM
(unlike the audit, where they are excluded: an SBOM should list what ships).
CI's `uv` is whatever `astral-sh/setup-uv` installs; `action.yml.j2` sets no
`version:`, so it installs the latest. The builder verifies that the `uv` CI
resolves supports `cyclonedx1.5` (the first CI run after S4.8.1 proves it; if it
does not, add `version:` to the setup action's `Install uv` step, as a pin in
`pins.toml`-adjacent config, and record the version) and falls back to
`cyclonedx-py` only if no `uv` supports it. Not adopted: `cyclonedx-py`, as the
default.

**Released files.** The amended rule for S6.3.6: *the release uploads the built
distributions (`*.whl`, `*.tar.gz`) and their SBOM (`*.cdx.json`), and nothing
else; never `dist/.gitignore`.* S6.3.6's record gains a "superseded in part by
S4.11.6" note at build (its Build and tests are not edited, except as below).

**Where the files are.** The SBOM is written by the build, so `task build` stays
the only thing the workflow calls for it, and every `dist/` has one:
`workspace:build` writes `dist/<package>.cdx.json` after `uv build`. `uv build`
only needs the lock to be current; the export is offline.

**Provenance.** One `actions/attest-build-provenance` step per release job. Its
`subject-path` lists the globs of the files that job shipped.

**`python-lib` ordering.** `ci:release` today builds and publishes each package
in one loop, so an attestation placed after it would run after the release is
the record; if attestation then failed, a rerun would see the release published
and skip, and the provenance would never exist. So `ci:release` is split into
`ci:release-build` (skip what is published, build and write the SBOM into
`dist/<package>/`) and `ci:release-publish` (create each release from
`dist/<package>/`), with the attestation step between them. A failure before
publishing leaves nothing published.
