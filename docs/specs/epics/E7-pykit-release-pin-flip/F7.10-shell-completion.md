kiln takes `rn-forge-tooling` 0.4.0, whose install writes the rn-forge home's
`env.sh` and links a zsh completion script for every `PythonTool`
([pykit F28.1](https://github.com/rn-forge/pykit/blob/main/docs/specs/epics/E28-rn-forge-home/F28.1-home-contract-and-completions.md)).
kiln, and every `python-tool` repository kiln renders, then completes on `<TAB>`
in a zsh that has sourced only `env.sh`.

## Context

Found 2026-11-20: in a new terminal, `kiln <TAB>` completed nothing. kiln's CLI
answers zsh completion requests (`_KILN_COMPLETE=complete_zsh` lists its
commands), but nothing linked a completion script into the home, and nothing
outside macsetup's personal profile put the home on `PATH` or `fpath`. That is
generic install behaviour, so it is pykit's
([pykit ADR-0017](https://github.com/rn-forge/pykit/blob/main/docs/adr/ADR-0017.md)).
kiln changes only its pins, its template and its tests, the same split as
[F7.7](F7.7-kiln-installs-as-a-tool.md).

`Kiln(PythonTool)` and the starter's `Tool(PythonTool)` do not override
`artifacts()`, so both get the completion link from pykit's default. The
starter's `test_product.py` asserts the exact links, so it has to change with
the pin.

## S7.10.1 — kiln and the starter take `rn-forge-tooling` 0.4.0

**State:** Closed (2026-11-20) · **Depends on:** the pykit F28.1 pin

**Acceptance:**

- `RN_FORGE_TAGS["rn-forge-tooling"]` is `rn-forge-tooling-v0.4.0`. kiln's
  `pyproject.toml` and `standard.md.j2` require
  `rn-forge-tooling>=0.4.0,<0.5`. `tests/test_archetypes.py` follows.
- The starter's `test_product.py.j2` asserts both links: `bin/<name>` and
  `completions/_<name>`. Its test name says that the artifacts are the command
  and its completion.
- `task kiln:apply` here leaves no diff that `task lint KILN_DOCTOR_FULL=1`
  rejects, and the `python-tool` golden cell validates.
- The upstream pin row for pykit F28.1 on
  [the board](../../index.md#upstream-pins) reads `yes`, with the date and the
  pypi.org version.

Outcome: kiln's pins are pykit's Release 11 (`rn-forge-tooling` 0.4.0,
`rn-forge-commons` 0.10.1, `rn-forge-cli` 0.2.1, `rn-forge-web` 0.3.3,
`rn-forge-auth` 0.2.1, `rn-forge-fastapi` 0.5.2, `rn-forge-data` 0.1.6).

## S7.10.2 — The completion run

**State:** Closed (2026-11-20) · **Depends on:** S7.10.1

**Acceptance:**

- From a fresh `RNF_HOME`, `kiln self install --ref feature/v1` leaves `env.sh`,
  `bin/kiln` and `completions/_kiln`, and prints the `source` hint because the
  home is not on `PATH`.
- In a new `zsh -f` that runs only
  `source "$RNF_HOME/env.sh"; autoload -Uz compinit; compinit`, `kiln <TAB>`
  lists kiln's commands and `kiln self <TAB>` lists the six lifecycle verbs.
- `kiln self doctor` reports none of `home.env-missing`, `home.env-stale` or
  `home.not-on-path` in that shell.
- The same holds for a `python-tool` repository rendered by `kiln new` and
  installed from a commit.
- `kiln self uninstall` removes `bin/kiln` and `completions/_kiln`, and leaves
  `env.sh`.

Outcome (2026-11-20, a scratch `RNF_HOME`, kiln `09b0f5f`): every item holds.
The install printed the `source` hint. In `env -i … zsh -f` with only `env.sh`
sourced and `compinit` run, `_comps[kiln]` is `_kiln`, `kiln` resolves to the
home's `bin/kiln`, and the completion request for `kiln ` offers the 13 commands
and for `kiln self ` the six lifecycle verbs; the keystroke itself was not
driven (no terminal). `kiln self doctor` exits 0 with none of the three `home.*`
codes. A `kiln new` `python-tool` was installed from its commit with
`install --archive`, since it has no GitHub remote for `--ref`, and completes
the same way.
