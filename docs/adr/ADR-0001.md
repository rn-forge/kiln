# ADR-0001 — Ship kiln as one pinned distribution of modules

**Status:** accepted (2026-09-13) · **Scope:** kiln, and every repository it
generates

## Decision

Kiln is one Python distribution, `rn-forge-kiln`. It carries the generator, the
templates, the archetypes and every check, and `kiln doctor` reaches them all.

Concerns are modules inside that distribution — `core`, `python`, `docs`,
`tasks`, `cicd`, `instructions` — composed through one internal contract: each
module owns its configuration section, its `kiln new` options, its `artifacts()`
and its `checks()`, and kiln owns only composition. No module has a published
API, a separate version or a compatibility promise. Boundaries between them are
enforced by executable import contracts rather than convention.

Every generated repository takes `rn-forge-kiln` as a pinned development
dependency, so generation and verification are the same pinned artifact.

Promote a module to its own distribution when, and only when, a consumer appears
that installs it without kiln.

## Consequences

- Configuration schema, generation and checks version and release together. A
  schema change is one commit, not a coordinated release across distributions.
- Jinja, pydantic, the generation engine and the templates enter every
  repository's development lock, including repositories whose CI only
  verifies. That is the accepted price of one kiln everywhere.
- A checker fix propagates by moving a pin. A change to a generated file also
  needs a regeneration commit in each repository.
- A module is a template set plus its checks and nothing more — the structural
  guard against kiln becoming a god-kit.
- Kiln's own repository stays `python-tool`, because it ships one distribution.

## Alternatives considered

- **Two distributions: `rn-forge-kiln` plus a render-free
  `rn-forge-kiln-checks`.** Bought one thing — a CI environment without the
  generator installed — at the cost of a second version line, a schema-skew
  check, and a CI that still could not run the render-dependent checks.
  Pinning removes the risk it was protecting against ([ADR-0006](ADR-0006.md)).
- **`docs`, `tasks` and `cicd` as separately published libraries.** Four
  independently versioned distributions that must agree on one configuration
  schema, with no consumer that installs one without the others.
- **Unpublished workspace packages under `libs/`.** Buys enforceable boundaries
  that import-linter already supplies, at the cost of one more
  `pyproject.toml` per module.
- **Put the checks in `rn-forge-commons` or `rn-forge-tooling`.** "Every managed
  artifact matches the committed baseline" is repository policy, and policy in
  a runtime-neutral library is how `forge-core` went wrong
  ([ADR-0002](ADR-0002.md)).
- **Framework code generators inside kiln.** The output is application logic,
  not repository shape. They ship as a framework's `[codegen]` extra and
  register as entry points; kiln supplies only the command surface.
- **Kiln owning `src/` and `tests/`.** Narrowed to verification: a kiln that
  *generates* files there has become an application code generator.

## Background

The first decision (D51, before Phase C) split the checks out, because a
generated repository was about to carry **1,454 lines** of committed checker
scripts across eight files, byte-identical between repositories except for list
literals already present in `config.toml`. `rn-forge-kiln-checks` was never
built.

Reopened on F4.1 and settled by
[S4.1.4](../specs/epics/E4-generator/F4.1-checks-by-module.md#s414-the-ci-shape-is-decided)
on 2026-09-13: the original reasoning assumed CI installing kiln meant
installing it *unpinned*. The same spike found `uv lock` failing inside pykit's
workspace with conflicting URLs for `rn-forge-tooling`; one
`override-dependencies` entry in pykit resolves it, and consumer repositories
need no change.

On 2026-09-16 `kiln check` and `kiln doctor` collapsed into one verb — two verbs
for one question asked at two depths — and the docs checkers moved out of
`rn-forge-tooling` into kiln's `docs` module, since only kiln-generated
repositories use them.
