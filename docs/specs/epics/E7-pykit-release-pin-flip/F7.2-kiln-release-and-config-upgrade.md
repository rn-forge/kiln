E7's scope items 1 and 3: tag an `rn-forge-kiln` release, then each repository
moves its kiln pin with `kiln upgrade` ([ADR-0006](../../../adr/ADR-0006.md))
and runs `kiln config upgrade --apply`. Added 2026-10-17 by S6.1.14, so that
E7's `Active` state has a feature to agree with.

Since [F7.4](F7.4-kiln-runs-beside-the-repository.md), a repository's kiln pin
is `[kiln] ref` in `.rn-forge/kiln/config.toml`, not a dev dependency. "Moving
the pin" therefore means:

1. set that ref to the new tag;
1. run `kiln apply`, which re-renders the `KILN` var in `tasks/kiln.yml` and
   `tasks/docs.yml`.

The cut also sets `archetypes.KILN_REF` from `feature/v1` to `v<version>`, so
`kiln new` pins the release.

## Context

**The version (owner decision, 2026-10-31).** The tag is `v0.1.0`, the version
in `pyproject.toml`. "Release 1" names the scope and is not a version number.

**Distribution.** kiln stays on git, through `uvx --from git+…@<ref>`.
Publishing it to PyPI stays the idea `kiln-on-pypi`.

**Order matters.** `KILN_REF` names a tag that does not exist until the commit
that names it reaches `main` and `release` runs, so that commit is the last one
before the merge. Nothing renders from it before the tag exists.

## S7.2.2 — `v0.1.0` is tagged

**State:** New · **Depends on:** S7.2.1

**Build — tests first**, in `tests/test_archetypes.py`:
`test_s7_2_2_1_kiln_ref_is_the_release`: `archetypes.KILN_REF == "v0.1.0"`.

**Build:**

- `archetypes/__init__.py`: `KILN_REF = "v0.1.0"`, and its docstring loses the
  reference to this cut.
- `.rn-forge/kiln/config.toml`: `[kiln] ref = "v0.1.0"`, then
  `uv run kiln apply`.
- `docs/releases/release-1/index.md`: status `shipped (<date>)`.
- The owner merges `feature/v1` to `main`. `release` tags `v0.1.0`.

**Acceptance:**

- `git ls-remote --tags origin v0.1.0` prints the tag.
- `uvx --from git+https://github.com/rn-forge/kiln@v0.1.0 kiln --help` exits
  `0`.
- `kiln new` from that tag writes `ref = "v0.1.0"`, and the new repository
  passes `task setup && task validate`.
