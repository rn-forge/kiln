# ADR-0008 — Only published packages get their own docs site

**Status:** accepted (2026-09-26) · **Scope:** the docs layout of every Python
repository kiln generates

## Decision

In `python-lib`, every package is published on its own, so every package carries
its own docs site: `packages/<pkg>/docs/` and `packages/<pkg>/mkdocs.yml`, built
standalone with `--strict` and included into the root site by
`mkdocs-monorepo-plugin`. The root `docs/` holds only cross-package material.

Every other Python archetype has one root site and nothing else. Its internal
workspace packages have no docs of their own; their reference renders in the
root site.

A `python-lib` repository starts with no packages. `kiln new` writes the empty
workspace, and `kiln generate package` adds packages one at a time, deriving
each package's published URLs from the repository's `origin` remote.

## Consequences

- A standalone strict build fails on any link that leaves the package, so each
  package's docs stand on their own when it is installed alone.
- `docs:build` builds one root site plus one site per package, and `python-lib`
  takes `mkdocs-monorepo-plugin` in its `docs` group.
- The nav and link checks have to learn the layout: an `include` area kind in
  `_areas.yml`, and root links resolved into package sites the way MkDocs
  mounts them.
- A published package also carries a Keep a Changelog `CHANGELOG.md`,
  `[project.urls]` and a README with only absolute links, because its README
  is its page on an index.
- A package's `mkdocs.yml` is seeded once and owned by the repository. It has no
  kiln-managed block, because package navs are curated per package.
- A fresh `python-lib` repository must pass its own gate with zero packages.
- `kiln generate package` is needed in release-1, not after it, because the
  archetype has no other way to gain a package.

## Influences

The work is [E11](../specs/epics/E11-package-docs/index.md). The layout becomes
normative in [the reference](../reference/standard-repo.md) with
[S11.2.1](../specs/epics/E11-package-docs/F11.2-python-lib-package-sites.md#s1121-the-standard-and-the-python-lib-golden).
[F6.1](../specs/epics/E6-rebuild-the-repos/F6.1-pykit-skeleton.md) proves the
archetype can host pykit on this layout.

## Alternatives considered

- **One root site for every archetype, as before.** Packages were published and
  versioned on their own, but their docs were not. A package's guide could
  link into another package without anything failing, and the root `guides/`
  mixed "use this package" with "combine packages".
- **Per-package docs inside one site, with no standalone builds.** The docs
  would sit beside the code, but nothing would catch a cross-package link,
  which is the main reason to split.
- **Per-package sites for every Python monorepo.** This was the first answer on
  2026-09-26, and it was withdrawn the same day. An application's internal
  packages are never installed alone, so a site per package documents a
  boundary that no reader crosses. It would also add a strict build per
  package.
- **`kiln new` takes the package list.** `[project.urls]` would then need a
  repository URL in kiln's config that nothing else reads. The git remote
  already records it, and it exists by the time a package is worth publishing.

## Background

pykit adopted kiln's docs model on 2026-09-26, and kiln's docs-structure checker
was run against its tree. The checker was clean on everything the standard
modeled. All 40 findings were in what it did not model yet: 25 root links into
package sites and 14 links inside pages that pykit excludes from its site. The
measurement, and the options, are in
[the pykit docs alignment plan](../plans/pykit-docs-alignment.md).
