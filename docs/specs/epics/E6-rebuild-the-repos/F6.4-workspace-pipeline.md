Upstream pin met 2026-10-16: `rn-forge-devops-v0.1.0`. Stories written as build
lists on 2026-10-17.

Added 2026-10-13. pykit's E14 replaced its CI with one workflow, driven by
`.github/scripts/workspace_ci.py`, that reads the uv workspace and plans every
job. pykit's `.github/workspace-ci-handoff.md` asks kiln to copy the workflow,
the script, the setup action and `dependabot.yml` verbatim. pykit has since
moved the script into its `rn-forge-devops` package (pykit F16.1), and
`.github/workspace-ci-handoff.md` now points at the package. They cannot be
copied verbatim, for three reasons:

1. **Every step calls a wrapped tool directly**: `uv`, `pytest`, `ruff`,
   `pyright`, `lint-imports`, `mike`, `mkdocs`, and
   `python3 .github/scripts/…`. kiln's `ci-entrypoint` check fails each of
   them. pykit has no `Taskfile.yml`.
1. **`scripts/**` is not a generated path**
   ([ADR-0006](../../../adr/ADR-0006.md)), so kiln has nowhere to put a
   generated `workspace_ci.py`.
1. **Dependabot** conflicts with generated workflows. It is rejected in
   [F6.3](F6.3-hardened-ci.md).

The pipeline's behaviour is what kiln has to keep. If `kiln apply` overwrote
pykit's CI today, after F6.3, pykit would lose the behaviour in this table:

| Behaviour | pykit evidence |
| -- | -- |
| Change-based selection: changed packages and their dependents, measured from the last green push; all packages on dispatch | `main.yml:37-71`; handoff "Assumptions" |
| One `verify` job per selected package (lint, typecheck and test for that member) | `main.yml:75-107` |
| A PostgreSQL service for members that declare `[tool.workspace-ci.postgres]` | `main.yml:109-152` |
| Smoke installs from built wheels, one job per extra (`[tool.workspace-ci.smoke]`) | `main.yml:154-181` |
| Workspace-wide pytest suites (`[tool.workspace-ci.suites]`) | `main.yml:183-202` |
| Release only for packages whose `ok-*` marker exists, in dependency order, with a failed dependency blocking its dependents | `main.yml:73-74, 99-105, 204-263` |
| `external-install`: install the new tag from git, outside the workspace | `main.yml:304-330` |
| Sonar sources and tests passed by CI, not listed in `sonar-project.properties` | `main.yml:297-298` |
| Versioned package sites through `mike`, merged into the Pages artifact | `main.yml:332-392`. This is [S11.5.1](../E11-package-docs/F11.5-deploy-package-sites.md#s1151-ci-deploys-versioned-package-sites), not this feature |

Every step in this feature goes through `task`. A CI-only step is an
**internal** task, declared `internal: true`. It is not a root verb, so the
ten-verb vocabulary does not change ([ADR-0007](../../../adr/ADR-0007.md)).

## Decisions

Answered by the owner on 2026-10-14 (decision 1 revised 2026-10-16), and
recorded in [ADR-0014](../../../adr/ADR-0014.md). The feature moved into
release-1 the same day, so that pykit can adopt kiln before release-1 ships.

1. **The planner is pykit's `rn-forge-devops` package** (revised 2026-10-16;
   pykit's ADR-0012), run only as the console script
   `rn-forge-devops <command>`. kiln's `tasks/ci.yml` runs the version in
   kiln's pin table through `uvx`; in a repository whose uv workspace has a
   member named `rn-forge-devops` (pykit), it runs `uv run rn-forge-devops …`
   instead. It is a CI tool, in no archetype's required or allowed list. This
   adds an [upstream pin](../../index.md#upstream-pins), met 2026-10-16.
   Building and releasing it is pykit's work
   ([ADR-0009](../../../adr/ADR-0009.md)). Rejected: a module of
   `rn-forge-tooling` (`rn_forge.tooling.workspace_ci`, the decision of
   2026-10-14), because tooling depends on commons; a `kiln ci plan` command,
   which breaks E4's module contract; and a seeded or generated
   `.github/scripts/workspace_ci.py`.
1. **Task names** are as proposed: `ci:plan`, `ci:verify -- <package>`,
   `ci:postgres -- <package>`, `ci:smoke -- <package> <extra>`,
   `ci:suite -- <name>`, `ci:release -- <package>…` and
   `ci:external-install -- <package>`. They are internal tasks in a new
   `tasks/ci.yml` that only the `python-lib` cell renders.
1. **`sonar-project.properties` stays kiln's.** It lists sources and tests from
   `[python] packages`, and `doctor` checks it. Rejected: CI passing them, as
   pykit's handoff proposed.

## Design

Settled 2026-10-17 for the build lists below. Everything a builder copies is in
the stories.

How the built pipeline behaves on each event is in
[How a `python-lib` CI run flows](../../../architecture/python-lib-ci.md).

- **The `ci` namespace.** `tasks/ci.yml`, rendered for `python-lib` only and
  included from `Taskfile.yml` as `ci`. Its tasks are **not** `internal`:
  go-task refuses an internal task from the command line, and a workflow step
  calls `task ci:plan`. Only `quality` and `workspace` must be internal
  (`RESERVED_NAMESPACES` in `tasks/checks/layout.py`), so `task-layout`
  accepts it. The root vocabulary does not change
  ([ADR-0007](../../../adr/ADR-0007.md)).
- **The planner command** is the task variable `DEVOPS`:
  `uv run rn-forge-devops` when `"rn-forge-devops"` is one of the config's
  package names (pykit; decided by membership, from committed config only,
  [ADR-0004](../../../adr/ADR-0004.md)), else
  `uvx --from "rn-forge-devops @ git+https://github.com/rn-forge/pykit@rn-forge-devops-v0.1.0#subdirectory=packages/rn-forge-devops" rn-forge-devops`,
  built from `PYKIT_GIT` and `RN_FORGE_TAGS["rn-forge-devops"]`.
- **`python-lib`'s `ci.yml`**, in job order: `validate` (repository-wide:
  `task lint`, `task ci:adapters`, `task docs:build` when docs are on),
  `plan`, `verify`, `postgres`, `smoke`, `suites`, `sonar`, `release`,
  `external-install`, `ci-ok`. Typecheck and tests run per selected member in
  `verify`, never for the whole workspace on every run. `python-app`,
  `python-tool` and the web archetypes keep today's `validate` → `sonar` →
  `release` unchanged.
- **Values reach a task through `env:`** when they are free-form (pytest args,
  suite args, the release list, the extra name), never interpolated into
  `run:` (S6.3.3's rule). A package name from the plan matrix may be passed as
  `-- ${{ matrix.name }}`, as `task build -- ${{ matrix.package }}` already
  is.
- **The plan's outputs** (`rn-forge-devops plan` prints them as `key=value`
  lines): `release-order`, `packages`, `postgres`, `smoke`, `suites`,
  `pytest-args`, `cov-args`, `test-paths`, `sonar-sources`, `sonar-tests`,
  `sonar`, `docs`. Matrix entries: `packages` and `postgres` rows carry `name`
  and `dir` (`postgres` adds `env`); `smoke` rows carry `name`, `extra`,
  `marker`; `suites` rows carry `name`, `args`.
- **Not here:** `sonar-project.properties` stays kiln's (ADR-0014); versioned
  package sites are
  [S11.5.1](../E11-package-docs/F11.5-deploy-package-sites.md#s1151-ci-deploys-versioned-package-sites);
  `docs.yml` does not change.

The reference for every behaviour is pykit's `.github/workflows/main.yml` at
pykit `8cc7b69` (`git -C ../pykit show 8cc7b69:.github/workflows/main.yml`).
Read it before each story; the stories say which job to port.

## S6.4.4 — Ordered release and external install

**State:** Closed (2026-10-17) · **Depends on:** S6.4.3

pykit's release job releases, in dependency order, only the selected packages
whose check markers all exist, and a failed check blocks its dependents. Its
loop already resumes the way F6.3 does (a published release is skipped, a tag
without a release is rebuilt from the tag, a draft is deleted).

**Build — tests first** (`test_s6_4_4_<n>_…`):

1. `verify`, `postgres` and `smoke` each end with pykit's marker steps:
   `run: mkdir ok && touch "ok/<marker>"` (`${{ matrix.name }}.verify`,

1. The `python-lib` `release` job has no `strategy`; needs
   `[validate, plan, verify, postgres, smoke]`;
   `if: ${{ !cancelled() && needs.validate.result == 'success' && needs.plan.outputs.release-order != '[]' }}`;

   `download-artifact` step (`pattern: ok-*`, `merge-multiple: true`,
   `path: ok/`), and `task ci:release` with env `GH_TOKEN`, `PUBLISH` (true
   only on a push to `main`) and
   `SELECTED: ${{ needs.plan.outputs.release-order }}`.
1. `tasks/ci.yml`'s `release` is pykit's "Build and publish releases" script
   with `uv run rn-forge-devops` replaced by `{{.DEVOPS}}`; assert it contains
   `releasable ok`, `--verify-tag` and `gh release delete`.
1. `external-install` needs `[release]`, runs only on a push to `main` after a

   `task ci:external-install` with env

   `{{.DEVOPS}} released`, with the URL from `$REPOSITORY_URL`.

**What the build settled that the story did not say.**

## S6.4.6 — Per-package tasks take the member's directory

## S6.4.7 — Release publishes from the default branch, after the quality gate

**State:** New · **Depends on:** S6.4.4

Also waits on the upstream pin "rn-forge-devops emits a no-extras smoke entry
per selected package", `not yet` on [the board](../../index.md#upstream-pins).

[ADR-0016](../../../adr/ADR-0016.md) decides that publishing happens only from
the default branch, after the quality gate. The generated `python-lib` `release`
job does neither: it runs on pull requests and dispatch (publishing only when
`PUBLISH` is true), and its `needs` omit `sonar`, so a release can ship while
the gate fails. A pull request keeps its packaging proof through `smoke`, which
installs every selected package's wheel with no extras into a clean venv and
imports it, as well as each declared extra.

**Build — tests first** (`test_s6_4_7_<n>_…`, in the files S6.4.2 names):

1. The `python-lib` `release` job's `needs` are
   `[validate, plan, verify, postgres, smoke, sonar]`.
1. Its `if` adds a push to the default branch:
   `github.event_name == 'push' && github.ref == 'refs/heads/main'` (built
   from the configured default branch, as `external-install`'s is), alongside
   the existing `!cancelled()`, `validate` success and non-empty
   `release-order` conditions. It does not run on a pull request or a
   dispatch.
1. `sonar` can be skipped (a fork pull request, which cannot reach `release`
   now) or off. Where the template renders `sonar`, `release`'s `if` needs
   `needs.sonar.result == 'success'`; where `[ci] sonar` is off, `sonar` is
   not in `needs` and the condition is absent.
1. The `release` job's env no longer sets `PUBLISH`, and `tasks/ci.yml`'s
   `release` no longer branches on it: the job only runs when publishing is
   allowed. The test asserts neither contains `PUBLISH`.
1. `smoke`'s matrix is still `fromJSON(needs.plan.outputs.smoke)`, and its step
   is unchanged. The no-extras entry arrives from the plan, with an empty
   `extra`; `ci:smoke` already passes `"${EXTRA:-}"`. A test feeds a plan with
   one empty-`extra` row and asserts the rendered job needs no change.
1. `ci-ok` still needs every job; a skipped `release` on a pull request is not a
   failure.
1. `actionlint` passes on the rendered `python-lib` workflows.

**Build:**

- `src/rn_forge/kiln/modules/cicd/templates/ci.yml.j2`: the `workspace` branch's
  `release` job `needs` and `if` as above; drop `PUBLISH` from its step.
- `src/rn_forge/kiln/modules/tasks/templates/tasks/ci.yml.j2`: remove the
  `PUBLISH` branch from `release`, so it always publishes.
- Nothing else in kiln for `smoke`: the substance is the planner change, which
  is pykit's work (`rn-forge-devops plan` emits a no-extras smoke entry per
  selected package) and releases as a new `rn-forge-devops` tag. Bump
  `RN_FORGE_TAGS["rn-forge-devops"]` to that tag once the pin is met, in this
  story's last commit.
- `docs/architecture/python-lib-ci.md`: when built, change the release job's
  needs, its event row (push to the default branch only), the ordering diagram
  (`sonar ─► release`), the "only a push publishes" bullet, and `smoke`'s
  no-extras entry. Do not change the page before then.
- `docs/reference/standard-repo.md` §8 already states the rule; leave it unless
  the build contradicts it.
