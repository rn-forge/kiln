# ADR-0011 — kiln is one distribution of modules under one contract

**Status:** accepted

## Context

Once the standard is parameterized by organization ([ADR-0005](ADR-0005.md)),
docs, tasks and CI are separable concerns, and the owner asked whether each
should be its own library. At the same time the owner asked for kiln to generate
new library packages, models, APIs, serializers and UI boilerplate — which risks
turning a repository generator into an application code generator.

Two seams already existed and looked alike: kiln's internal module functions
`artifacts()` + `checks()`, and the `ToolProduct` adapter behind the lifecycle
flag. And the archetype had to say which modules a repo gets, which was an
undrafted change to the config schema.

### Alternatives considered

- **docs, tasks and cicd as separately published distributions.** A separate
  distribution is warranted only when something installs it *without* the
  others. `rn-forge-kiln-checks` was the one claimed case (CI installing the
  checks without kiln), and [ADR-0010](ADR-0010.md), as revised, removed it by
  making the pinned kiln what CI installs; docs and tasks have none. Four
  independently versioned distributions that must agree on one config schema
  is a release matrix paid on every schema change for no gained independence.
- **Unpublished workspace packages under `libs/`.** They buy enforceable
  boundaries that import-linter already supplies, at the cost of N more
  `pyproject.toml` files.
- **Publishing `cicd` when ADO lands.** Rejected: no internal module is usable
  outside a kiln-generated repo.
- **Framework code generators in kiln.** Rejected: the output is application
  logic, not repo shape ([ADR-0002](ADR-0002.md)'s codegen extras).
- **kiln "owning its surface" inside `src/` and `tests/`.** Narrowed to
  verification: if kiln *generates* files there it has become an application
  code generator.

## Decision

**docs, tasks and cicd are modules inside the kiln distribution, not separate
libraries or distributions.** Boundaries are enforced by `.importlinter`
contracts per module. Escape hatch: promote a module to a distribution when a
non-kiln consumer appears.

**No internal kiln module is published.** They carry no public API, no separate
version and no compatibility promise.

**The `Generator` protocol is kiln's module contract, and `kiln doctor`
orchestrates it.** Each module registers; `kiln doctor` collects commons
`Finding` rows across all of them and prints one unified report, and a module's
own doctor is the same rows reached by a different entry point. It is
structurally the same as `ToolProduct` — worth collapsing into one protocol with
two registries.

**Each module declares the config it supports, and kiln composes.** A
`KilnModule` owns its config section (a strict pydantic model whose defaults are
kiln's layer), its `kiln new` options, its `artifacts()` and its `checks()`;
kiln owns only composition — the root schema, the union of options (a collision
is a startup error), and module iteration for `apply` and `doctor`.
`archetype.toml` lists the enabled modules alongside the dependency set, and a
section for a disabled module is rejected.

**kiln generates repo structure; frameworks generate their own code.** Adding a
package to a workspace (`kiln generate package`) emits the repo structure kiln
already owns, so it is kiln's to build. Application code generators ship in
`rn-forge-django[codegen]`, register under `rn_forge.kiln.generators`, and kiln
supplies only the command surface. kiln verifies the structure of `src/` and
`tests/` and generates nothing there. Both kinds of generator are backlog
([E10](../specs/epics/E10-kiln-generators/index.md)).

## Consequences

- A module is a template set plus a doctor check, nothing more — the guard
  against kiln becoming a god-kit.
- A module's checks split into the render-free ones CI always runs
  (`kiln doctor`) and the ones that need a render (`kiln doctor --full`)
  ([ADR-0010](ADR-0010.md)).
- The protocol sketch is in
  [E4's design](../specs/epics/E4-generator/design.md#the-module-contract).
