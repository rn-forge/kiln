kiln's standard says what a repository does with the Dependabot pull requests
the generated `dependabot.yml` opens: they are absorbed by the release cut, not
merged into a branch that publishes. The standard states the generic rule and
the release page carries a standing exit criterion; each repository's release
runbook carries the mechanics for its archetype. `dependabot.yml` itself does
not change.

## Context

kiln renders `.github/dependabot.yml` with every update targeting the default
branch (`main`), weekly, with a 7-day cooldown and minor and patch updates
grouped. In a library repository that publishes on push to `main`, such as a
`python-lib` workspace where a merge releases every package whose manifest
changed, merging a Dependabot pull request into `main` would publish packages
with no version bump and no changelog entry. A repository that adopted kiln hit
this in a release cycle: its Dependabot pull requests had to be absorbed on the
release branch by hand, and a new grouped pull request opened as soon as the
release merged.

Decision, owner 2026-11-21: Dependabot stays automatic against `main`, and the
release cut absorbs the open Dependabot updates on the release branch before the
cut. kiln carries only the generic rule; the repository's own runbook says how,
because the mechanics depend on the archetype.

## Design

The two documents to change are rendered from these templates, relative to the
repository root:

- `src/rn_forge/kiln/modules/instructions/templates/standard.md.j2`, which
  renders each repository's `.rn-forge/kiln/standard.md`. The existing
  Dependabot text is in the CI section ("A repository-owned workflow...") and
  in the action-pins paragraph that says Dependabot's `npm` and `uv` pull
  requests are not drift; the new rule sits beside them.
- `src/rn_forge/kiln/modules/docs/templates/docs/releases/_structure.md.j2`,
  which renders `docs/releases/_structure.md`, in the **Exit criteria** bullet
  of the release page's sections.

`src/rn_forge/kiln/modules/cicd/templates/dependabot.yml.j2` (rendered by
`modules/cicd/artifacts.py`) is not edited.

## Considered and rejected

- **`target-branch` in `dependabot.yml`.** It names one fixed branch, so every
  release would need an edit to a generated file, which is drift.
- **Merging Dependabot pull requests into `main` as they come.** In a repository
  that publishes on push to `main`, it releases without a version bump or a
  changelog entry.

## S7.11.1 — The standard and the release page state the rule

**State:** New · **Depends on:** —

**Acceptance:**

- The rendered `standard.md`, near its Dependabot text, states that Dependabot
  pull requests are not merged into a branch that publishes; a release absorbs
  the open Dependabot updates on its release branch before the cut, and the
  repository's release runbook says how.
- The same text names security updates as the exception. They ignore
  `target-branch` and open against the default branch, so they are handled as
  an urgent patch release, not held for the next cut.
- The rendered `docs/releases/_structure.md`, for every docs profile that
  renders it, adds to the Exit criteria guidance a standing criterion: no
  Dependabot pull request is open against the default branch, or each open one
  is listed on the release page as deferred, with its reason.
- The rendered `.github/dependabot.yml` is byte-identical to before for every
  archetype and has no `target-branch`; a test asserts it.
- A test asserts each new sentence in the rendered `standard.md` and
  `docs/releases/_structure.md`, in the archetype cells that render them.
- `task kiln:apply` here leaves kiln's own `standard.md` and
  `docs/releases/_structure.md` as the only generated files that change, and
  `task lint KILN_DOCTOR_FULL=1` passes.
- Consumer impact: after a repository takes the new pin and runs
  `task kiln:apply`, its generated files change only in those two documents.
