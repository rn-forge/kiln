[ADR-0020](../../../adr/ADR-0020.md) splits the instruction files by audience.
`README.md` is for people and carries no agent directive. `AGENTS.md` is the
canonical agent file: a repository-owned body, seeded once, with **kiln's fenced
block moved into it** from `CLAUDE.md`. `CLAUDE.md` is repository-owned, with no
block, seeded as an `@AGENTS.md` import line and a short Claude-only section.
[ADR-0003](../../../adr/ADR-0003.md) holds: one owner per file or block, no
paragraph restated. This replaces the rule "README is the single prose home;
`CLAUDE.md` points at it and carries the block; `AGENTS.md` points at
`CLAUDE.md`" (plan decisions D57 and D58, the owner answer of 2026-11-09, and
[S16.9.9](F16.9-overlay-cutover-findings.md#s1699-docs_structuremd-names-readmemd-as-the-prose-home),
which this feature supersedes). It lands before the `v0.1.0` tag.

## For the owner

The migration needed no choice, and no new code: the apply engine already
removes a block whose state entry the render no longer produces, and inserts a
new one, in one transaction (checked on 2026-11-10 against the engine's `plan`
and `apply`, see S16.10.3). The recommendations below are what the stories
build; change any of them before the build starts.

- **Order inside this feature.** S16.10.1 to S16.10.6 change templates and code
  and leave this repository's generated files stale on purpose; S16.10.7 runs
  `task kiln:apply` here once, for all of them. Until it lands,
  `task lint KILN_DOCTOR_FULL=1` is red here. Commit nothing from S16.10.1 to
  S16.10.6 to a branch that CI sees until S16.10.7 is built. The other order
  (apply here in S16.10.1) would leave `CLAUDE.md` failing `docs-structure`
  between commits.
- **Existing repositories' bodies are not rewritten.** `kiln apply` moves the
  block and leaves both bodies, which are repo-owned. An old `CLAUDE.md` that
  says "read README.md" stays until its repository rewrites it. For an
  `mkdocs` docs profile `docs-structure` flags it (S16.10.4: it neither links
  nor imports `AGENTS.md`); for `docs = none` or `external` nothing flags it.
  Recommended: leave it so, as ADR-0003 says kiln never checks a body.
- **The `@AGENTS.md` import counts as a pointer** for `docs-structure`
  (S16.10.4). The seeded `CLAUDE.md` also carries a Markdown link to
  `AGENTS.md`, so the rule holds either way.
- **`CLAUDE.md` is seeded with no `# <name>` heading**, so `@AGENTS.md` is its
  first line.

## Design

- **Where the block goes.** `render` in
  `src/rn_forge/kiln/modules/instructions/artifacts.py` declares the block
  artifact for `AGENTS.md` instead of `CLAUDE.md`. Its state key becomes
  `AGENTS.md#rn-forge kiln`. The block text (`block.md.j2`) and its content
  hash do not change, so the key moves and nothing else in the entry.
- **Seeded bodies.** `scaffold` still writes `README.md`, `CLAUDE.md` and
  `AGENTS.md` once, each from `templates/<name>.j2`. `AGENTS.md`'s body
  carries no markers, so the apply that follows appends the block beneath it,
  as it did for `CLAUDE.md`.
- **Migration.** On `kiln apply`, `generation.plan` classifies the old entry
  `CLAUDE.md#rn-forge kiln` as `REMOVE` (the block is unedited) and the new
  artifact `AGENTS.md#rn-forge kiln` as `INSERT`; `generation.apply` does both
  in one transaction and rewrites `state.json`. An edited old block classifies
  as `DRIFT`, which blocks the apply until `--force CLAUDE.md`. No function in
  kiln changes for it; S16.10.3 proves it.
- **`metadata.scaffolded`.** `_record_scaffolded` in `commands.py` drops every
  path that has an entry. With the block entry on `AGENTS.md`, `CLAUDE.md` is
  recorded and `AGENTS.md` is not. No code change (S16.10.5).
- **Golden compare.** There are no committed golden repos
  ([S4.4.9](../E4-generator/F4.4-render-matrix.md#s449-the-goldens-leave-the-repository));
  the render is the golden, and no `state.json` is reseeded by hand. After
  the stories, `task self:golden:render` then
  `task self:golden:compare BASE=HEAD` shows, in **every** cell:
  `only in base: CLAUDE.md#rn-forge kiln`,
  `only in ref: AGENTS.md#rn-forge kiln` and
  `differs: .rn-forge/kiln/standard.md`; and in every cell whose docs profile
  is `mkdocs`, `differs: docs/_structure.md`. Nothing else: the three bodies
  are scaffolded, so the compare does not read them.

## Downstream

## S16.10.3 — `kiln apply` moves an existing repository's block from `CLAUDE.md` to `AGENTS.md`

**State:** Closed (2026-11-10) · **Depends on:** S16.10.1

A repository whose `state.json` holds `CLAUDE.md#rn-forge kiln` must end with
the block in `AGENTS.md` after one `kiln apply`.

**Design.** No new code. Apply removes its own fence from `CLAUDE.md`, writes it
into `AGENTS.md` and rewrites the state entry, using what
`rn_forge.commons.generation` already does for a state entry the render no
longer produces: `plan` classifies `CLAUDE.md#rn-forge kiln` as `Action.REMOVE`
(or `Action.DRIFT` if the block was edited) and `AGENTS.md#rn-forge kiln` as
`Action.INSERT`, and `apply` performs both in one transaction, then writes
`state.json` without the old key. Both file bodies are untouched: kiln owns the
fence and nothing else ([ADR-0003](../../../adr/ADR-0003.md)). The block's
`content_hash` is the same before and after, because `block.md.j2` does not
change. An absent `AGENTS.md` is created holding only the block.
`metadata.scaffolded` is not touched (S16.9.6), so a migrated repository's list
is stale; nothing reads it. If a test below fails, the engine does not behave
this way: stop, change no source and report the failure.
