`kiln-devops umbrella` ([F15.5](../E15-ci-standard/F15.5-umbrella-release.md))
creates a GitHub release for every shipped release page that has none. On a
repository that turns the check on after it has shipped several releases, the
first run backfills all of them at the current commit and makes the newest one
it created "Latest". This feature makes the command release only the newest
shipped release and never backfill silently.

## Context

pykit's `umbrella` job runs
`uvx --from "rn-forge-kiln @ git+https://github.com/rn-forge/kiln@feature/v1" kiln-devops umbrella --sha "$GITHUB_SHA"`
(`ci:release:umbrella`, `modules/tasks/templates/tasks/ci.yml.j2:64`), with kiln
built at `84b154c`. Run 43591842240, on pykit `main` at `637a7df` (2026-11-14),
published Release 8's packages. At that commit pykit's spec board listed
Releases 1 to 7 as `shipped` and Release 8 as `planned`. Tags `release-6`
(`ed566a0`) and `release-7` (`63495d8`) existed; `release-1` to `release-5` had
never been tagged.

The step created the tags and GitHub releases `release-1` to `release-5`, all at
`637a7df`, and GitHub now marks "Release 5" as Latest. It did not create
`release-8`, which is still `planned`. The job reported success.

**Cause**, in `src/rn_forge/kiln/devops/umbrella.py`:

- `shipped()` (`:55-66`) returns every `release-<n>/index.md` whose Status is
  `shipped`, with no notion of when it shipped.
- `run()` (`:87-89`) takes all of them as `pending` and drops only those for
  which `github.release_exists(tag)` is true. The check is the GitHub release,
  not the tag, so a repository whose releases 6 and 7 were tagged by hand but
  never released as GitHub releases would be backfilled the same way. Every
  shipped release lacking a release is therefore created at the current
  `--sha`, however old.
- `create_command()` (`:69-76`) passes no `--latest`. `gh release create`
  defaults to `--latest=legacy`, which marks the most recently created release
  as Latest, and `run()` creates in ascending order (`:94-101`), so the lowest
  untagged releases are made first and the highest of them, Release 5, ends
  Latest, below the real newest, Release 7 or 8.
- Nothing is printed for a backfilled release (`:88-102`): the only message is
  the empty case.
- The tests cannot see it: `tests/devops/test_umbrella.py:28-32` (`_repo`)
  builds exactly one release page, so no test has more than one shipped
  release.

## The rule

**`umbrella` creates a release only for the highest-numbered shipped release,
and only when it has no GitHub release.** Every lower shipped release without a
GitHub release is skipped, with a notice on stderr naming it. A backfill is
never silent and never automatic; an owner who wants one creates those releases
by hand.

Why this rule, from the code:

- The command has no history to work from. The job checks out without
  `fetch-depth` and reads only the working tree, and the page carries a
  status, not a date. "Releases whose page changed in this push" would need a
  commit range and `git` in the planner; "the newest" needs only the sorted
  list `shipped()` already returns.
- A release ships in number order (each release page's predecessor is the one
  below it), so the newest shipped release without a GitHub release is the one
  this push shipped, except on the first run in an adopting repository, which
  is exactly the backfill case.
- It keeps the Latest rule trivial: the one release created is the highest
  shipped, so it is the one that gets `--latest`. A lower release never does.

Considered and rejected:

- **An explicit `--backfill` flag.** It adds a mode nobody asked for. The notice
  says what was skipped, and a one-off `gh release create` does the rest.
- **Limit by commit range.** Needs history in the job (`fetch-depth`) and a
  second input to the command, for the same answer in every case that matters.
- **Create all of them, but fix only `--latest`.** Leaves release-1 to release-5
  pointing at a commit that did not ship them, which is the defect.

## S6.12.1 — `umbrella` creates only the newest shipped release

**State:** New

**Build — tests first,** in `tests/devops/test_umbrella.py`. Extend `_repo` to
take a number (it already does) and add a helper that builds several pages in
one `tmp_path` (`_repo` calls `mkdir(parents=True)` without `exist_ok`, so each
page has its own directory and the helper needs nothing more). The fake `gh`
runner answers `gh release view release-<n>` from a set of existing tags. Tests
1 and 2 reproduce pykit's case and fail before the change.

1. `test_s6_12_1_1_old_untagged_releases_are_not_backfilled`: releases 1 to 7
   `shipped` and 8 `planned`, GitHub releases for 6 and 7 present and for 1 to
   5 absent (pykit at `637a7df`): no `gh release create` runs, the exit status
   is `0`, and stderr names `release-1` to `release-5` as skipped.
1. `test_s6_12_1_2_only_the_newest_is_created`: the same repository with release
   8 `shipped`: exactly one `gh release create release-8` runs, with
   `--target <sha>` and `--latest`; nothing is created for 1 to 5, and the
   notice names them.
1. `test_s6_12_1_3_latest_is_never_given_to_an_older_release`: in every test
   above, no `create` command carries `--latest=false`, and none for a release
   lower than the highest shipped number exists. (A lower release is never
   created, so there is no case where `--latest` goes to it.)
1. `test_s6_12_1_4_nothing_to_do_when_newest_exists`: release 7 the highest
   shipped, with its GitHub release present: no `create`, and the existing "No
   shipped release is missing its GitHub release." message.
1. `test_s6_12_1_5_dry_run_prints_only_the_newest`: `--dry-run` on releases 1 to
   3 `shipped` prints one `create`, for `release-3`, runs no `gh`, and adds
   `--latest`.

**Build:** `src/rn_forge/kiln/devops/umbrella.py`:

- `run()` takes `newest = shipped(releases)[-1]` (none shipped: the existing
  message, status `0`). When the release exists, print the existing message
  and return `0`. Otherwise create only `newest`.
- For each lower shipped release with no GitHub release, print
  `kiln-devops: skipped release-<n>: no GitHub release, and only the newest shipped release is created; create it by hand to backfill`
  to stderr, one line each. Under `--dry-run` the existence check does not
  run (the F15.5 rule that dry run calls no `gh`), so every lower shipped
  release is listed as skipped without it.
- `create_command()` appends `--latest`. The one release created is always the
  highest shipped, so the flag is unconditional.
- The module docstring and `run()`'s docstring say "the newest shipped release"
  rather than "each shipped release". The subparser's help in
  `devops/cli.py:139` reads "create a GitHub release for the newest shipped
  release page".

**Acceptance:**

- The five tests pass, and the first two fail on the commit before the change.
- The F15.5 tests in `tests/devops/test_umbrella.py` still pass: they use one
  page.
- `task validate` passes.

## Where the tag lands: `--sha` stays as it is

pykit's open pull request #35 marks Release 8 `shipped`. Once it merges, the
next `main` run creates `release-8` at that docs commit, not at `637a7df`, which
published the packages. This feature does not change that, and does not add a
`--sha` that targets another commit:

- F15.5 defines the release as the commit that marks the page `shipped`
  ("Shipping a release is a docs change"), and the tag follows the page.
- The packages carry their own per-package tags at the publish commit
  (`release-order`); the umbrella tag is the release's, not theirs.
- A different target needs a commit lookup the command has no input for, and the
  caller can already pass `--sha`; `task ci:release:umbrella` passes
  `$GITHUB_SHA` and stays so.

## Not in this feature

- pykit's cleanup: deleting `release-1` to `release-5` (tags and GitHub
  releases), or moving them to the commits that shipped them, and setting
  Latest to `release-7` until `release-8` lands. The pykit owner runs it; kiln
  does not touch pykit.
- A `--backfill` mode.
