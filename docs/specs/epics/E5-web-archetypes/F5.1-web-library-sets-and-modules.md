# F5.1 — Library sets, and the modules gain the web shapes

Epic: [E5](index.md) · **Depends on:**
[S4.3.3, S4.3.4, S4.3.5, S4.3.7](../E4-generator/F4.3-concern-modules.md) (the
templates this feature branches), [S4.5.1, S4.5.2](../E4-generator/F4.5-cli.md)
(`kiln new` and `kiln apply`, so a rendered repo can be synced and gated);
pykit's web pins resolvable ([E5](index.md))

**Build a story by the [board's procedure](../../index.md#building-a-story).**
There is no golden to diff against: each template gains `{% if web %}` and
`{% if web_app %}` branches beside its `python-lib` branch, and the shape below
is what those branches render. [F4.4](../E4-generator/F4.4-render-matrix.md)'s
validate is where the result is proven runnable; until it exists, the feature
block below syncs and gates one rendered repo by hand.

## Design

**The two shapes.** Both are a uv workspace whose root `pyproject.toml` is bare
(`uv init --bare`, `[tool.uv] package = false`) with one member at `api_dir`
(default `apps/api`), exactly as `python-lib` has members under `packages/`. The
member's distribution is `<name>-api` and its module `<name>_api`
(`root_package`). `python-web-app` adds a pnpm-managed Nx workspace whose root
files (`package.json`, `pnpm-workspace.yaml`, `nx.json`, `tsconfig.base.json`,
the eslint and prettier configs) sit at the repo root and whose one application
is the Nx project at `web_dir` (default `apps/web`, project name `web`). Every
file the frontend scaffolder writes is repo-owned; kiln renders nothing under
`web_dir` and nothing the scaffolder wrote.

**Selector contract (2026-09-17).** `--backend` replaces the planned
`--framework`; the config field, `KilnConfig` property, render context and
`[untested]` key are all `backend`. No compatibility alias is needed: the old
selector was never implemented. `--frontend` keeps its name. The archetype
selects the toolchain and which components exist; selectors only choose their
implementations ([ADR-0005](../../../adr/ADR-0005.md)).

F5.1 keeps both options in `PythonModule`, as scoped below. Extract shared
frontend configuration and scaffolding when a second ecosystem needs them,
before implementing another copy. Java archetypes and `--stack`/`--runtime`
selectors are not part of this feature.

**Context, in addition to F4.3's:** `web` (either web archetype); `web_app`
(`python-web-app`); `backend`; `frontend`; `api_dir`; `api_package`
(`<name>-api`); `api_module`; `web_dir`; `web_project` (the basename of
`web_dir`).

**What each module renders differently.** Relative to `python-app`:

| Module | `python-web-api` | `python-web-app` adds |
| -- | -- | -- |
| `python` — `.importlinter` | `root_package = <api_module>`; the forbidden list drops the chosen `backend` (an API imports its framework) and keeps `typer jinja2 click` and the other framework | — |

| `cicd` — `ci.yml` | unchanged | unchanged: every step is already `task …` |
| `cicd` — `sonar-project.properties` | `sonar.sources=<api_dir>/src`, `sonar.tests=<api_dir>/tests` | `sonar.sources` also lists `<web_dir>/src` |

The task vocabulary gains two public namespaces, `api:*` and `web:*`, beside
`docs:*`. The taskgraph rule "inner tasks are internal except `docs:*`" reads
"except `docs:*`, `api:*` and `web:*`" (design, doctor check 5).

## S5.1.1 — Web library sets

**Status:** done (2026-09-17)

`python-web-api`/`python-web-app` take commons → web → `rn-forge-fastapi` or
`rn-forge-django` (+ `rn-forge-cli` for management commands).

**Build:**

- `archetypes/python_web_api/archetype.toml` and
  `archetypes/python_web_app/archetype.toml`, the six modules in the same
  order as `python_app`.
  `[dependencies] required = ["rn-forge-commons", "rn-forge-cli", "rn-forge-web"]`,
  `allowed` the same; `for_config` adds `rn-forge-<backend>` to both, as it
  adds `rn-forge-tooling` for `lifecycle`. `forbidden_tools` and
  `required_validate` per the table above.
- `[untested]` tables: both web archetypes have `backend = ["django"]`;
  `python_web_app` also has `frontend = ["react", "svelte"]`.
  `Archetype.untested: dict[str, list[str]]` and `kiln new`'s refusal already
  exist from S4.5.1; this story fills the tables.
- `modules/python/config.py`: `WebApiConfig` and `WebAppConfig` (`StrictModel`,
  the fields and defaults in the table), and `ArchetypeConfig` gains
  `python_web_api` / `python_web_app` with the same alias pattern.
  `KilnConfig` gains `backend` and `api_dir` for both web archetypes, and
  `frontend` and `web_dir` for `python-web-app` only; each returns `None`
  where its component is absent. `packages` returns `(api_dir,)` for both web
  archetypes so every existing per-member code path applies.
- `PythonModule.options()` gains
  `Option("backend", "archetype.<archetype>.backend", …)` and
  `Option("frontend", "archetype.<archetype>.frontend", …)`; `kiln new`
  substitutes `<archetype>` (S4.5.1).
- Add `backend: str | None = None` and `frontend: str | None = None` to
  `commands.new` and `_FLAG_NAMES` in this story, together with the options
  above. Omit unset selectors from the flags layer so config values and
  archetype defaults survive; retain defaults → config → flags precedence.
- `archetypes.pyproject_paths` already returns the root plus each member.
- `rn_forge_deps`: a `[codegen]` extra of the chosen framework is accepted in a
  dependency group and refused in `[project] dependencies`. Nothing renders
  it.

**Acceptance:**

- For each web archetype and framework, `for_config(...).dependencies.required`
  is commons, cli, web and the framework package, in that order; `allowed`
  equals it (plus `rn-forge-tooling` with `lifecycle`).
- The dependency check refuses a member `pyproject.toml` that lacks
  `rn-forge-web`, one that names the other framework, and one with `[codegen]`
  in runtime dependencies; it accepts `[codegen]` in the dev group (one test
  each).
- A config naming `backend = "flask"` or `frontend = "vue"` fails to load naming
  the key. A `[archetype.python-web-app]` table under a `python-app` config is
  rejected.
- `--backend` is rejected for non-web Python archetypes; `--frontend` is
  rejected for `python-web-api` and non-web Python archetypes. Equivalent
  config keys are rejected too, naming the key; supplied options are never
  silently ignored.
- `backend = "spring-boot"`, `frontend = "none"`, and the old `framework` config
  key are rejected. `--framework` is not a CLI alias. These failures occur
  before scaffolding or writing, including with `--allow-untested`: that
  override admits known untested values, not unsupported values.
- A config-selected backend/frontend survives omitted CLI selectors; explicit
  selectors override it. The live option-union test includes exactly
  `archetype`, `docs`, `backend`, and `frontend` as config-setting flags.

**What the build settled that the story did not say:**

- `WebApiConfig`/`WebAppConfig` fields default to `None` at the
  `ArchetypeConfig` level (same `Optional[Model] = None` pattern as
  `python_lib`'s `PackagesConfig`), not to a populated instance. This means
  the field-level defaults (`backend = "fastapi"`, `frontend = "angular"`, …)
  only take effect once the archetype's `[archetype.<name>]` table exists at
  all — which happens whenever any one of its keys is set, by a CLI flag or a
  `--config` source layer. `kiln new --archetype python-web-api` with **no**
  `--backend` and no config layer leaves `KilnConfig.backend`/`api_dir` as
  `None` (an archetype with no selector at all), rather than silently
  defaulting to `fastapi`. This was chosen over making the field default to a
  populated model because that alternative would inject **every** web
  archetype's table into the defaults layer regardless of which archetype is
  active (the defaults layer is computed generically, once per module, not per
  `[archetype.<name>]` field) — which would then always collide with the new
  "a table belongs to a different archetype" rejection below. Every `kiln new`
  invocation in this feature's own acceptance block passes `--backend`
  explicitly, so this does not block it.
- Added a new rejection to `ConfigManager.validate`: a `[archetype.<name>]`
  table other than the active archetype's own is refused, naming the foreign
  key (e.g. `[archetype.python-web-app]` under a `python-app` config). Nothing
  enforced this before F5.1 since `python_app`/`python_tool`/`python_lib`
  never collided in practice; the acceptance bullet requiring
  `[archetype. python-web-app]` to be rejected under `python-app` needed it as
  a general rule, not a web-specific special case.
- `[codegen]`-in-runtime-dependencies is enforced by a new
  `rn_forge_deps._check_no_codegen_in_runtime` rule, matched by extras syntax
  (`name[..., codegen, ...]`) on `[project] dependencies` only; a
  `dependency-groups` entry is untouched by any existing or new rule, so
  "accepted in a dev group" needed no separate check.
- `Option.key` for `backend`/`frontend` is `"archetype.<archetype>.backend"` /
  `"...frontend"`, substituted by `commands._flag_layer` exactly as S4.5.1's
  `archetype` option already is. Passing `--backend`/`--frontend` for an
  archetype whose `[archetype.<name>]` model has no such field is refused by
  `StrictModel`'s `extra="forbid"` itself (pydantic's "Extra inputs are not
  permitted", naming the dotted key) — no extra rejection logic was needed in
  `commands.py` for that bullet.
- `KilnConfig.packages` now returns `(api_dir,)` whenever `api_dir` is set (i.e.
  for any web archetype with its table present), before falling back to
  `python-lib`'s `packages_for`. A repo cannot be both a web archetype and
  `python-lib`, so the two paths never overlap in practice.

## S5.1.2 — Modules gain the web shapes

**Status:** done (2026-09-17)

Every row of the design table, as template branches and scaffold steps.

**Build:** the `python`, `tasks`, `cicd` and `instructions` modules per the
table; templates `tasks/api.yml.j2` and `tasks/web.yml.j2`; `pins.toml` gains
`pnpm-setup` and `setup-node`. F4.3's five properties apply, with property 4
read as: the `python-app` render is byte-identical before and after this story
(the new branches change nothing outside the web archetypes).

**Tests:** in each module's `tests/modules/<module>/test_artifacts.py`,
`test_s5_1_2_…` names, over `python-web-api` + `fastapi` and `python-web-app` +
`fastapi` + `angular`.

**Acceptance:**

- `python-web-app` renders `tasks/api.yml` and `tasks/web.yml`; `python-web-api`
  renders `tasks/api.yml` and no `tasks/web.yml`. `task --list --json` on each
  shows the ten root verbs, `docs:*` for `mkdocs`, `api:dev` (and
  `api:migrate` for `django`), and `web:lint web:test web:build web:dev` for
  the app only.
- `task-layout` passes on both, and `gate.shrunk` fires on a `python-web-app`
  `Taskfile.yml` whose `lint` no longer calls `web:lint`.
- Only `python-web-app`'s setup action sets up pnpm and node; `ci-pins` and
  `actionlint` pass on both archetypes' workflows.
- A workflow that calls `pnpm`, `npx`, `nx` or `ng` directly fails
  `ci-entrypoint` under `python-web-app`.
- `.importlinter` for `fastapi` forbids `django` and not `fastapi`, and the
  reverse for `django`; `lint-imports` passes on a scaffolded member.
- The three `python-*` archetypes' renders are byte-identical to their renders
  before this story (assert against the goldens, as property 4 already does).

**What the build settled that the story did not say:**

- Context added to every touched module's `render()`, matching the story's list:
  `web`, `web_app`, `backend`, `api_dir`, `api_package` (`<name>-api`),
  `api_module` (`root_package(api_package)`), `web_dir`, `web_project`
  (`Path(web_dir).name`). Each module computes these itself from `KilnConfig`
  rather than sharing one context-building function, matching the existing
  pattern where `tasks`, `cicd` and `instructions` each build their own
  context dict already.
- `.importlinter`'s forbidden-modules list is computed in Python
  (`artifacts.render`) and handed to the template as one pre-joined
  `forbidden_block` string, the same pattern `members_block` already uses —
  looping inside the template with Jinja's whitespace-control markers
  (`{%- for %}`) stripped the block's leading indentation and broke the golden
  byte-match; building the block in Python sidesteps that entirely.
- `python`'s scaffold treats `python-web-api`/`python-web-app` exactly like
  `python-lib`'s workspace branch (bare root `uv init`, one member
  `uv init --package`, the `tool.uv.workspace` table) with one difference: the
  member's `uv init --name` and its `pyproject.toml`'s `module-name` are
  `<repo-name>-api` / `<repo-name>_api`, not the member directory's basename —
  `api_dir`'s basename (`api`) is a directory name, not the distribution name
  the design table specifies. `uvicorn>=0.30` for `fastapi` lands in the
  member's `dependency-groups.dev`, added through a new `extra_dev` parameter
  on the existing `_reconcile` helper (empty for every other archetype/member,
  so no other render changes).
- `tasks/quality.yml.j2`'s five workspace-conditioned task bodies
  (`lint:python`, `format:python`, `typecheck:python`, `test:python`,
  `test:coverage`) gained a third `{% elif web %}` branch beside `workspace`
  and the single-package `else`, each one literal
  `--directory <api_dir> --package <api_package>` command with no `for:` loop,
  exactly as the story specifies. The five repo-wide checkers below them
  (`lint:markdown` through `lint:ci-entrypoint`, plus the docs lints) were
  already written outside that conditional and needed no change.
- `tasks/api.yml.j2` and `tasks/web.yml.j2` are new public namespace files (no
  `internal: true` on any task, unlike every other namespace file) —
  `api:dev`/`api:migrate` and `web:lint`/`web:test`/`web:build`/`web:dev` are
  meant to be run directly, matching the story's "two public namespaces beside
  `docs:*`" framing. `api:migrate` renders only when `backend == "django"`;
  see S5.1.3's note below for the one place this reopens.
- `Taskfile.yml.j2`'s `includes:` gains `api: tasks/api.yml` for both web
  archetypes and `web: tasks/web.yml` for `python-web-app` only; `lint`,
  `test` and `build` each gain one appended `- task: web:*` line, app only,
  right where `extra_refs` would otherwise append — ahead of the `extra_refs`
  loop, so a repo-supplied extra ref still runs last.
- `cicd`'s setup action gets `pnpm/action-setup` and `actions/setup-node`
  (`cache: pnpm`) after `setup-task`, `python-web-app` only. Both pins were
  resolved with `gh api repos/<owner>/<repo>/git/ref/tags/<version>`, then
  (for `pnpm/action-setup`, whose tag is annotated) dereferenced once more
  with `gh api repos/pnpm/action-setup/git/tags/<tag-sha>` to reach the commit
  `ci-pins` requires — `actions/setup-node`'s tag already pointed at a commit
  directly. Chosen versions: `pnpm/action-setup@v4.1.0`
  (`a7487c7e89a18df4991f7f222e4898a00d66ddda`), `actions/setup-node@v4.4.0`
  (`49933ea5288caeca8642d1e84afbd3f7d6820020`) — both current stable majors as
  of 2026-09-17, no compatibility constraint from anything else in the render.
- `sonar-project.properties.j2` gained a `web` branch ahead of the existing
  `workspace`/else branches (web archetypes are never `workspace = true`, so
  the two never collide): `sonar.sources=<api_dir>/src[,<web_dir>/src]`,
  `sonar.tests=<api_dir>/tests`, using the config's own `api_dir`/`web_dir`
  paths rather than the `packages` basename list `python-lib` uses, since a
  web archetype's member directory isn't under `packages/`.
- `instructions`: the **Archetype** bullet in both `CLAUDE.md`'s block and
  `standard.md` names `backend` (and `frontend`, for the app) in parentheses
  rather than folding it into `display_archetype` — `display_archetype` stays
  the `python-tool` alias mechanism only, untouched by this story. The app's
  **Frontend** clause states the frontend, the pnpm+Nx toolchain, and the
  project's directory/name, in both the `CLAUDE.md` block (condensed) and
  `standard.md` (a full paragraph, matching the existing per-archetype prose
  density). The **Entrypoint** bullet's verb list gained `api:dev`
  (`api:migrate` for django) and, for the app,
  `web:lint web:test web:build web:dev`, appended to the existing sentence
  rather than reformatted, to keep the bullet a single flowing sentence like
  the other archetypes'.
- The taskgraph rule "inner tasks are internal except `docs:*`" already read
  "…except `docs:*`, `api:*` and `web:*`" in
  `docs/specs/epics/E4-generator/design.md` before this story (carried over
  from the "F4 - Partial - For F5" commit); no rule enforces it in code today
  (`tasks/checks/layout.py`'s `task-layout` check verifies wrapper-only,
  `desc:`, and the `validate` gate, not namespace-vs-internal), so nothing in
  `src/` needed a change for this bullet — F4.6's `taskgraph.*` doctor check
  is still unimplemented.

## S5.1.3 — `backend` stays a flag

**Status:** done (2026-09-17)

`backend = fastapi|django` changes only `tasks/api.yml`'s primitives, the
`.importlinter` forbidden list, and the scaffold's dependency lines — never
topology or the task graph ([ADR-0005](../../../adr/ADR-0005.md)).

**Acceptance:** for `python-web-app` with `angular`, `django` and `fastapi`
render the same artifact keys and the same public and internal task names. Their
managed artifacts differ only in `tasks/api.yml` and `.importlinter`; every
other artifact's content is byte-identical between the two renders.

**What the build settled that the story did not say — a flagged conflict:**

- Artifact keys are identical between `django` and `fastapi` (verified: both
  render the same fourteen paths). Every managed artifact's content is
  byte-identical apart from `tasks/api.yml` and `.importlinter` (verified by a
  new test that diffs every rendered path between the two backends and asserts
  the differing set is exactly `{"tasks/api.yml"}` — `.importlinter` is not a
  `tasks` artifact, so it is outside that diff and covered separately by
  S5.1.2's own forbidden-list tests).
- **Task names are not identical**, and this is a real tension between two parts
  of the spec, not an oversight: the design table (S5.1.2's own "Build the
  exact table" instruction) attaches `api:migrate` to `django` only
  ("`django`: …, plus `api:migrate`"), so `python-web-app --backend fastapi`
  renders no `api:migrate` task while `--backend django` does. This was
  implemented exactly as the table states, and is covered by an explicit test
  (`test_s5_1_2_django_backend_also_lists_api_migrate` /
  `test_s5_1_2_task_list_json_shows_api_and_web_verbs`'s
  `"api:migrate" not in names` assertion, in
  `tests/modules/tasks/ test_artifacts.py`). The consequence: the feature's
  own acceptance script, below, runs
  `diff "$s/django.tasks" "$s/fastapi.tasks"` under `set -euo pipefail` and
  expects no output — that line **will exit 1** with exactly one diff hunk
  (`api:migrate` present only in `django.tasks`) when run for real (verified
  live, see the feature's acceptance report). Building a no-op `api:migrate`
  for `fastapi` to force the diff empty was rejected: there is no migration
  primitive `rn-forge-fastapi` defines, and rendering a task with no real
  behavior violates "don't add features beyond what the task requires." This
  is left for the owner to resolve — either drop the script's `diff .tasks`
  line's strictness for this one expected line, or amend the design table to
  render `api:migrate` for both backends (with fastapi's body still
  undecided). Everything else in both acceptance bullets passed as specified.

## Acceptance

```bash
set -euo pipefail
cd rn-forge/kiln
kiln_dir=$PWD
kiln() { uv run --project "$kiln_dir" kiln "$@"; }
task test                                                                             # S5.1.1, S5.1.2, S5.1.3
s=$(mktemp -d)
for fw in django fastapi; do
  kiln new "$s/$fw" --archetype python-web-app --backend "$fw" --frontend angular --docs none --yes --json --allow-untested </dev/null \
    | jq -r '.artifacts[].key' | sort >"$s/$fw.keys"
  (cd "$s/$fw" && task --list-all --json) | jq -r '.tasks[].name' | sort >"$s/$fw.tasks"
done
test -s "$s/fastapi.keys"
diff "$s/django.keys" "$s/fastapi.keys"                                               # S5.1.3: same artifacts
diff "$s/django.tasks" "$s/fastapi.tasks"                                             # S5.1.3: same task graph
kiln new "$s/api" --archetype python-web-api --backend fastapi --docs mkdocs --yes </dev/null
(cd "$s/api" && uv sync && task validate && actionlint)                              # S5.1.2: a synced, gated api repo
```

Not scriptable: the `python-web-app` cell's `pnpm install && task validate` is
[F5.2](F5.2-kiln-new-web-end-to-end.md)'s; `--allow-untested` above is only
needed while `django` is untested.
