## S16.6.1 — `init` takes the repository name from git, not the directory

**State:** Closed (2026-11-07) · **Depends on:** —

`_resolve_config` in `src/rn_forge/kiln/commands.py` takes the name from its
first argument, which `init` passes as `root.name` (the directory); only
`--config`'s `[repository] name` overrides it. A worktree named `kiln-cutover`
rendered the Sonar key `rn-forge_kiln-cutover`, `site_name`, the root
`pyproject.toml` `[project].name` and `kiln-cutover.code-workspace`.

Owner decision, 2026-11-07. `init` resolves the name, first match wins:

1. `--config`'s `[repository] name` (as today);
1. the basename of `git remote get-url origin`, `.git` stripped, from the https
   form (`https://github.com/rn-forge/kiln.git`) or the ssh form
   (`git@github.com:rn-forge/kiln.git`);
1. the root `pyproject.toml` `[project].name`, canonicalised (`_project_name`,
   already in `commands.py`);
1. the directory name.

`package.json` is not used: ngkit's is `@ngkit/source`, Nx's default. `kiln new`
is unchanged, since a new directory has no remote.

**Where git runs.** The module contract limits shelling out to a `scaffold`
function, but `commands.py` is the CLI layer and already runs `git status` in
`_require_clean` with `subprocess.run`. The choice: a new
`_git_remote_name(root)` beside it, using the same
`subprocess.run(["git", "remote", "get-url", "origin"], cwd=root, capture_output=True, text=True, check=False)`;
a non-zero status returns `None`. Reading `.git/config` directly was rejected: a
worktree's `.git` is a file, and `url` may come from an `insteadOf` rewrite.

**Build — tests first,** in `tests/test_init.py` (real `git init` repositories
in `tmp_path`, as that file's other tests do):

1. `test_s16_6_1_1_remote_https`: a directory `work-1` whose `origin` is
   `https://github.com/rn-forge/kiln.git`: the resolved `repository.name` is
   `kiln`.
1. `test_s16_6_1_2_remote_ssh`: `git@github.com:rn-forge/kiln.git` gives `kiln`;
   a remote with no `.git` suffix gives the same.
1. `test_s16_6_1_3_config_wins`: `--config` with `repository.name = "other"`
   beats the remote.
1. `test_s16_6_1_4_pyproject_then_directory`: with no `origin`, the root
   `pyproject.toml` `[project].name = "Rn_Thing"` gives `rn-thing`; with no
   `origin` and no `[project].name`, the directory name.
1. `test_s16_6_1_5_package_json_ignored`: a `package.json` named `@ngkit/source`
   does not set the name.
1. `test_s16_6_1_6_logs_source`: the info line names the source used, for each
   of the four: `repository name {} from the origin remote`,
   `... from pyproject.toml`, `... from --config` (the existing line,
   unchanged) and, for the directory, no line.
1. `test_s16_6_1_7_new_unchanged`: `kiln new` of `tmp_path / "x"` names the
   repository `x`.

**Build:** `commands.py`: `_git_remote_name(root: Path) -> str | None` (strips a
trailing `/` and `.git`, takes the part after the last `/` or `:`);
`_init_name(root: Path) -> tuple[str, str]` returning the name and its source
for steps 2 to 4; `init` passes the name to `_resolve_config` in place of
`root.name`, and `_resolve_config` keeps its `--config` override and info line.
Log the source for steps 2 and 3 with `console.info`.

**Acceptance:**

- The seven tests pass, and `task validate` passes.
- Not scriptable here: a worktree named `kiln-cutover` of this repository,
  `init`ed, renders `kiln` everywhere (rerun in the S7.2.4 rehearsal).

**What the build settled that the story did not say:**

- The `git remote get-url origin` call lives in `modules/core/remote.py`
  (`origin_url`, `repository_name`, `github_owner`), not in `commands.py`, so
  S16.6.7's docs module can read the same remote: `.importlinter` lets a
  concern module import `core` but not `commands.py` or a sibling.
  `commands.py` keeps `_git_remote_name(root)` and `_init_name(root)` as the
  Build names them, over that helper.
- `origin_url` returns `None` unless `root` holds its own `.git`. Without that
  `git` walks up to a parent worktree: `kiln new` stages under the current
  directory, and a golden cell under `.goldens/` inside this repository, would
  read this repository's `origin`.
- The sources are logged as `the origin remote` and `pyproject.toml`
  (`repository name kiln from the origin remote`).
- `test_s6_1_16_2_without_a_config_name_the_directory_names_it` changed: the
  rendered fixture has a `[project].name`, which now outranks the directory,
  so the test removes it first.
- `test_s16_6_1_7_new_unchanged` changes directory to `tmp_path`, as
  `tests/test_new.py` does, because `new` stages under the current directory.

## S16.6.2 — The config comment on `[repository] name` stops promising what `apply` does not do

**State:** Closed (2026-11-07) · **Depends on:** —

The docstring of `RepositoryConfig.name` in
`src/rn_forge/kiln/modules/core/config/schema.py` (rendered as the comment above
`name` in `.rn-forge/kiln/config.toml`, line 11 here) says that changing the
name "renames them on `kiln apply`". Generated files follow the name; seeded
files, which `apply` never rewrites (the root `pyproject.toml` `[project].name`,
`<name>.code-workspace`), keep the old one. No behaviour changes.

**Build — tests first,** in `tests/modules/core/test_catalog.py`:

1. `test_s16_6_2_1_name_comment`: the catalog entry `repository.name` has a
   description that contains `generated files follow` and `seeded files keep`,
   and does not contain `renames them`.

**Build:** the docstring becomes: "The repository's name. It names the package
and the project and is written into generated files. Changing it re-renders the
generated files on `kiln apply`; seeded files (the root `pyproject.toml`'s
`[project].name`, `<name>.code-workspace`) keep the name they were created
with." Then `kiln config-update --apply` here, which rewrites
`.rn-forge/kiln/config.toml` (S16.4.7 records that `apply` does not).

**Acceptance:**

- The test passes, and `task validate` passes.
- No generated file other than `config.toml` changes.

**What the build settled that the story did not say:**

- The docstring text is the story's with its sentences reordered so that the
  rendered description contains `generated files follow` and
  `seeded files keep` literally, as the test requires; the story's own wording
  had neither phrase.
- The command run was not `kiln config-update --apply`: only the `task` verbs
  are allowed here and none runs it. `.rn-forge/kiln/config.toml` was edited
  by hand to the comment `config-update` writes, then `task kiln:apply`
  re-recorded its hash in `state.json`; `task validate` checks the comment
  against a fresh write.

## S16.6.3 — The derived nav and doctor keep links inside `docs/`

**State:** Closed (2026-11-07) · **Depends on:** —

`_children_entries` in `src/rn_forge/kiln/modules/docs/nav.py` keeps an index
link when `(docs_root / rel).exists()`, so ngkit's `docs/reference/index.md`
links `../../libs/ng/README.md` became nav entries such as
`reference/../../libs/ng/README.md`, and `task docs:build` (`mkdocs --strict`)
aborted with 22 warnings. `docs-site` did not report them, nor
`guides/development.md`'s links to `../../.github/workflows/ci.yml` and
`../../libs/ng/project.json`, so `task lint` passed what `docs:build` rejects.
(`Site.check_links` in `modules/docs/site.py` resolves such a link, finds the
file, and moves on; only a package site's escape is an error, as
`docs.package-link-escapes`.)

**Build — tests first,** in `tests/modules/docs/test_docs.py` (`TestNav`,
`TestCheckSite`) and `tests/modules/docs/checks/test_site.py`:

1. `test_s16_6_3_1_nav_skips_a_link_outside_docs`: a `docs/reference/index.md`
   linking `[ng](../../libs/ng/README.md)` (the file exists) adds no nav
   entry, and `build_nav` contains no `..`.
1. `test_s16_6_3_2_nav_keeps_a_link_inside_docs`: a link `[a](a.md)` and
   `[b](../guides/b.md)` where `b.md` is under `docs/guides` keeps `a.md`; the
   second is not a child of `reference` and is not added (unchanged
   behaviour).
1. `test_s16_6_3_3_doctor_reports_a_link_outside_docs`: `check_site` on a repo
   whose page links `[ci](../../.github/workflows/ci.yml)` (an existing file)
   returns one finding with code `docs.link-leaves-docs`, severity error, path
   the page, message
   `links outside docs/: ../../.github/workflows/ci.yml; use an absolute URL`.
1. `test_s16_6_3_4_covers_markdown_and_other_files`: the same holds for
   `../../libs/ng/README.md` and `../../libs/ng/project.json`.
1. `test_s16_6_3_5_package_mounts_are_not_flagged`: a root link that resolves
   into a package mount (the existing S11.1.2 case) is not reported; a package
   site's own escape is still `docs.package-link-escapes`, not both.

**Build:** `nav.py`: in `_children_entries`, skip a link when
`(docs_root / rel).resolve()` is not under `docs_root.resolve()`. `site.py`: in
`Site.check_links`, after `resolved` is computed and before the suffix skip,
when `self.package is None` and `resolved` is neither within `docs_dir` nor
within any directory in `self.mounts.values()`, append
`_error("link-leaves-docs", path, f"links outside {docs_dir name}/: {link}; use an absolute URL")`
and `continue`. The code matches the existing `docs.*` kebab codes
(`docs.package-link-escapes`, `docs.broken-link`).

**Acceptance:**

- The five tests pass, and `task validate` passes.
- Not scriptable here: ngkit's `task lint` and `task docs:build` agree after its
  links are made absolute (ngkit's work,
  [ADR-0009](../../../adr/ADR-0009.md)).

**What the build settled that the story did not say:**

- `_children_entries` keeps an index link only when it resolves under the
  **area's** directory, not only under `docs/`. The Build says "under
  `docs_root`", but test 2 needs `../guides/b.md` from `reference/index.md` to
  stay out, and a link inside `docs/` but outside the area would otherwise be
  nav-listed as `reference/../guides/b.md`.
- A package site (`self.package is not None`) never gets `link-leaves-docs`; its
  escape stays `docs.package-link-escapes`. A link into a package mount is
  exempt, including a mount page that does not exist (it is
  `docs.broken-link`).
- Tests 3 and 4 share one parametrized test over the three paths in the story
  (`ci.yml`, `README.md`, `project.json`), plus a second test with two links
  in one page; test 5 is two tests (mount not flagged; package escape reported
  once).

## S16.6.5 — Integration services cover pykit's broker profile, and `broker-profile.yml` retires

**State:** Closed (2026-11-07) · **Depends on:** —

Owner decision, 2026-11-07: after the cutover pykit owns no workflow file. This
revises the "only `broker-profile.yml` stays pykit's" lines in
[F15.7](../E15-ci-standard/F15.7-repo-owned-workflows.md),
[F6.8](../E6-rebuild-the-repos/F6.8-pykit-release-7-ci.md) and
[S7.2.4](../E7-pykit-release-pin-flip/F7.2-kiln-release-and-config-upgrade.md#s724-run-the-cutover-sop-on-pykit-then-ngkit):
each gets a dated note, "*Revised 2026-11-07 (S16.6.5):* pykit's broker profile
is an `integration` service of `rn-forge-auth`; `broker-profile.yml` retires.",
under the line it revises. History is not deleted.

**What the workflow does** (pykit `feature/release-8`,
`.github/workflows/broker-profile.yml` and
`packages/rn-forge-auth/tests/broker/compose.yml`): Keycloak
`quay.io/keycloak/keycloak:26.4.7` with `command: [start-dev, --import-realm]`,
env `KC_HEALTH_ENABLED=true`, port `127.0.0.1:8080:8080`, the read-only volume
`./realms:/opt/keycloak/data/import`, a bash `/dev/tcp` probe of
`127.0.0.1:9000/health/ready` as the healthcheck; then
`pytest packages/rn-forge-auth -m broker -p no:randomly` with
`RN_FORGE_AUTH_KEYCLOAK_URL=http://127.0.0.1:8080`. Triggers: weekly cron, a
pull-request path filter, `workflow_dispatch`; not a required check.

**What kiln's integration stage has** (`devops/ci.py` `Service`, `devops/uv.py`
`load_workspace`, `devops/integration.py`): `image`, `ports`, `health-cmd`,
`env`, `expose`. It `docker run -d`s with `-e`, `-p` and the health flags, then
runs `uv run --directory <dir> --package <name> pytest -q <root pytest-args>`
with `expose` set.

**Missing, exactly:**

| Need | Today | Addition |
| -- | -- | -- |
| Container arguments `start-dev --import-realm` | `start_command` ends at the image | `command`: list of strings, appended after the image |
| Read-only bind of `./realms` | no volumes | `volumes`: list of `src:dst[:ro]`; `src` is relative to the package directory and made absolute by `start_command` |
| `-m broker -p no:randomly` | the leg runs every test with the root `pytest-args` | `pytest-args`: list of strings, added after the root ones for the legs of this service |
| Ports bound to `127.0.0.1` | `-p` is passed through | none |
| Env `KC_HEALTH_ENABLED` | `env` | none |
| The `/dev/tcp` probe | `health-cmd` is passed as `--health-cmd` (shell form) | none; the string is the probe's `exec 3<>…` line |
| Health timing | `--health-interval 2s --health-timeout 5s --health-retries 30`, polled 60 times 2 s | none; see "Not verified" |
| Realm file contents, the URL | in the package | none: the package keeps `tests/broker/realms`, and `expose` sets `RN_FORGE_AUTH_KEYCLOAK_URL` |

**Decisions, recorded here:**

- **Schedule: dropped.** The image is pinned, so a weekly run finds nothing new,
  and the planner's affected-package selection (a change under
  `packages/rn-forge-auth/**` or anything it depends on, or a change outside
  `packages/`) replaces the path filter. `workflow_dispatch` runs every
  declaring package.
- **Gating: integration is gating.** The leg is a `ci-ok` and `checks-ok` need,
  and `release` waits for its `rn-forge-auth.integration` marker. The profile
  was non-required because it lived outside the pipeline; inside it, a failing
  broker test blocks a release of `rn-forge-auth`, which is the point.
- **Marker override** is `pytest-args` on the service, not a root setting: the
  other tests of the package already ran in `test`; the integration leg of
  `rn-forge-auth` should run the broker tests only.

**Build — tests first,** in `tests/devops/test_uv.py` (or `test_ci.py`),
`tests/devops/test_integration.py`:

1. `test_s16_6_5_1_load`: `load_workspace` reads `command`, `volumes` and
   `pytest-args` into `Service.command`, `Service.volumes` and
   `Service.pytest_args` (tuples, default empty).
1. `test_s16_6_5_2_start_command`: for a service with
   `command = ["start-dev", "--import-realm"]` and
   `volumes = ["./realms:/opt/keycloak/data/import:ro"]`, `start_command` ends
   `-v <abs package dir>/realms:/opt/keycloak/data/import:ro <image> start-dev --import-realm`;
   `-v` precedes the image and the command follows it.
1. `test_s16_6_5_3_pytest_args`: `run` passes the root `pytest_args`, then the
   union of the services' `pytest_args`, to the pytest command, in that order.
1. `test_s16_6_5_4_keycloak_declaration`: a fixture package with the Keycloak
   table below loads, and the full `docker run` command it produces is the
   expected one (image, `-e KC_HEALTH_ENABLED=true`, `-p 127.0.0.1:8080:8080`,
   `--health-cmd`, `-v`, command).
1. `test_s16_6_5_5_health_wait`: a service with `health-wait = 300` gives
   `--health-retries 150` in `start_command`, and `run` polls it up to 150
   times; without the key both are `ceil(120 / 2) = 60`; `health-wait = 0`
   raises naming the service.

The declaration pykit adds to `packages/rn-forge-auth/pyproject.toml`:

```toml
[tool.workspace-ci.integration.keycloak]
image = "quay.io/keycloak/keycloak:26.4.7"
command = ["start-dev", "--import-realm"]
ports = ["127.0.0.1:8080:8080"]
volumes = ["tests/broker/realms:/opt/keycloak/data/import:ro"]
health-cmd = "exec 3<>/dev/tcp/127.0.0.1/9000 && printf 'GET /health/ready HTTP/1.1\\r\\nHost: localhost\\r\\nConnection: close\\r\\n\\r\\n' >&3 && grep -q '\"status\": \"UP\"' <&3"
pytest-args = ["-p", "no:randomly"]
health-wait = 300

[tool.workspace-ci.integration.keycloak.env]
KC_HEALTH_ENABLED = "true"

[tool.workspace-ci.integration.keycloak.expose]
RN_FORGE_AUTH_KEYCLOAK_URL = "http://127.0.0.1:8080"
```

**Build:** `devops/ci.py` (`Service.command`, `.volumes`, `.pytest_args`,
`.health_wait`), `devops/uv.py` (`load_workspace`), `devops/integration.py`
(`start_command` resolves each volume's source against the repository root
joined with `package.dir`; `run` appends the services' `pytest_args`), the table
in `docs/architecture/ci.md` ("Integration: services as data") and
`docs/reference/kiln-devops.md` (the declaration table), and the three dated
notes above. Do not change the template: the leg already runs
`task ci:integration`.

*Revised 2026-11-07 (rehearsal run 4):* the declaration drops `-m broker`. A
package's services share one integration run, and `rn-forge-auth` also declares
`redis`; `-m broker` would deselect its Redis tests. The broker tests already
skip unless `RN_FORGE_AUTH_KEYCLOAK_URL` is set, so the leg runs every
`rn-forge-auth` test with both services up. `pytest-args` keeps
`-p no:randomly`.

**pykit's side** (adding the table, deleting `broker-profile.yml` and its
`compose.yml` reference, and its Dependabot `github-actions` pins for it) is
pykit's work, in its cutover pull request
([ADR-0009](../../../adr/ADR-0009.md)); this story does not edit that
repository.

**Acceptance:**

- The five tests pass, and `task validate` passes.
- The three revised lines carry the dated note.
- Not scriptable here: the `rn-forge-auth.integration` leg goes green in pykit's
  cutover pull request.

**Health wait is the repository's (owner decision, 2026-11-07).** The stage

## S16.6.13 — doctor reports a node-lib behind kiln's Nx

Evidence (ngkit, run 4, 2026-11-07): kiln pins `NX_VERSION = "24.0.4"` in
`src/rn_forge/kiln/modules/node/angular.py`, and only `kiln new` uses it. `init`
on ngkit left `package.json`, `nx.json` and the lockfile untouched (Nx 23.1.0,
Angular ~22.1.7), so a newer kiln never reached ngkit, and

**Decisions:**

  registry, not the method, runs checks).

  `dependencies.nx`), strips a leading `^`, `~` or `>=`, and compares the

  `node.nx-behind`, path `package.json`, message

  \<NX_VERSION>` and its migrations`. Equal or newer, a missing `nx`, or a
  non-numeric range (`latest`, a URL) passes.
- kiln does not run `nx migrate`: it edits the repository's own code
  ([ADR-0009](../../../adr/ADR-0009.md)). The cutover runbook gets the step.
- `modules/node/checks` joins the `render-free-checks` contract's
  `source_modules` in `.importlinter`. It may import `NX_VERSION` from
  `node/angular.py` (that module imports no Jinja).
