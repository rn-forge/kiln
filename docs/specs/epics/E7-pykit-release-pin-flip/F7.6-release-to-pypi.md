`[ci] release` gains `pypi`. A library workspace's release job then uploads each
package to pypi.org by trusted publishing, before its GitHub release, and a
dispatched run can upload to TestPyPI instead. Every workspace's per-package
GitHub releases take their notes from the package's changelog and stop claiming
"Latest". A declared job can be granted `contents: write`, so pykit's umbrella
release runs as a `[[ci.jobs]]` entry.

## Context

**Why now, in release 1.** pykit builds PyPI publishing into its hand-written
`main.yml` in its Release 7 (F21.3). Its kiln cutover (F16.3) then deletes
`main.yml`, so the kiln it pins, release 1, must render the same release
behaviour. That is this feature. Taking pykit from PyPI is
[F7.5](F7.5-pykit-from-pypi.md), later.

**pykit's behaviour, which this matches** (pykit F21.3, `main.yml`):

- `workflow_dispatch` takes a boolean input `testpypi`.
- The release job runs in environment `pypi` on a push to `main`, and `testpypi`
  on a dispatch with `testpypi` set. It has `id-token: write`.
- Every build runs `twine check --strict`.
- On a publish run, a package whose GitHub release is not yet published is
  uploaded with `uv publish --trusted-publishing always`, unless
  `https://pypi.org/pypi/<name>/<version>/json` answers. Its GitHub release is
  created after the upload, so a published GitHub release implies the version
  is on PyPI.
- On a TestPyPI run, every package is uploaded to
  `https://test.pypi.org/legacy/` unless TestPyPI has the version. No tags and
  no GitHub releases are created.
- Each `gh release create` drops `--generate-notes` for
  `--latest=false --notes-file`, from the package's `CHANGELOG.md` section.
- `external-install` installs `"$name==$version"` from PyPI, retrying up to 10
  times, 30 seconds apart.
- A failed upload fails the job. A rerun resumes, skipping what PyPI and GitHub
  already have.

**Where pykit and kiln differ.** pykit's umbrella release
(`umbrella-release.yml`, and its `rn-forge-devops umbrella` command) stays in
pykit, called from a `[[ci.jobs]]` entry. kiln's release model does not number
releases. The `notes` command moves into `kiln-devops`, because the release task
that calls it is kiln's.

**Provenance.** The job keeps `actions/attest` over the built files, as today.
`uv publish` does not attach PEP 740 attestations to the upload. pykit made the
same choice.

**What the owner does once per repository.** Not kiln's to automate:

- create GitHub environments `pypi` (deployment branch `main`) and `testpypi`;
- add a trusted publisher per package, naming workflow `ci.yml` and the
  environment, on pypi.org and on test.pypi.org.

pykit's cutover adds the `ci.yml` publishers beside its `main.yml` ones.

## S7.6.1 — ADR-0006 revised: `release = "pypi"`

**State:** New

**Build:** revise [ADR-0006](../../../adr/ADR-0006.md) in place, status
`revision proposed (<date>)`.

- **Decision:** `[ci] release` is `tag-exists | pypi | none`. `pypi` does
  everything `tag-exists` does, and uploads each package to PyPI first. It is
  valid only in a library workspace. Per-package GitHub releases are never
  "Latest".
- **Background:** a dated line naming pykit F21.3 and this feature.

**Acceptance:**

- The owner flips the status to `accepted (<date>)`. Not scriptable.

## S7.6.3 — Per-package releases carry their changelog and are not "Latest"

**State:** New · **Depends on:** S7.6.2, S6.7.5

After
[S6.7.5](../E6-rebuild-the-repos/F6.7-kiln-devops.md#s675-releases-go-through-kiln-devops),
`gh release create` lives in `kiln-devops release-publish`, in
`rn_forge.kiln.devops.github`, and the `python-lib` task calls it. This story
extends that subcommand. It does not put `gh` back in the task.

**Build — tests first** (`test_s7_6_3_<n>_…`):

1. `tests/devops/test_github.py`: `publish_commands(..., notes="n.md")` returns
   `gh release create` with `--notes-file n.md --latest=false` in place of
   `--generate-notes`, for a tag that exists and for one that does not.
   `notes=None` returns today's commands.
1. In the `kiln-devops` CLI tests:
   `release-publish TAG --title T --target S --notes-file n.md FILE` passes
   `notes="n.md"` through.
1. `tests/modules/tasks/test_artifacts.py`, for `python-lib`: `release-publish`
   writes `notes="$(mktemp)"` and
   `{{.DEVOPS}} notes "$dir/CHANGELOG.md" "$version" > "$notes"`, then calls
   `{{.DEVOPS}} release-publish "$name-v$version" --title "$name v$version" --target "$GITHUB_SHA" --notes-file "$notes" dist/"$name"/*`.
   It contains no `--generate-notes`.

**Build:**

- `rn_forge.kiln.devops.github.publish_commands` gains
  `notes: str | None = None`. The CLI's `release-publish` gains
  `--notes-file FILE`.
- `modules/tasks/templates/tasks/ci.yml.j2`'s `release-publish`: the two lines
  from test 3. Take the package's directory from what the task already reads,
  the plan's `dir` or `{{.DEVOPS}} released`.

Single-package archetypes pass no `--notes-file` and keep `--generate-notes`.
Their one release is "Latest" by right.

**Acceptance:**

- `uv run pytest tests/devops tests/modules/tasks/test_artifacts.py` passes.
  Older tests change only where they asserted `--generate-notes` for
  `python-lib`.

## S7.6.4 — `release = "pypi"` uploads before it releases

**State:** New · **Depends on:** S7.6.3

The upload, like the release, is `kiln-devops release-publish`'s job
([ADR-0017](../../../adr/ADR-0017.md): logic, not workflow shell). The
`release-build` additions stay shell, because F6.7 leaves that loop in the task.

**Build — tests first**, in `tests/modules/cicd/test_artifacts.py`, for a
`python-lib` cell with `[ci] release = "pypi"` unless the test says otherwise:

- `test_s7_6_4_1_dispatch_takes_testpypi`:
  `on.workflow_dispatch.inputs.testpypi` is
  `{"type": "boolean", "default": False, "description": "Upload every package to TestPyPI; no tags or releases"}`.
  With `tag-exists`, `workflow_dispatch` is `{}` as today.
- `test_s7_6_4_2_release_job_environment`: `jobs.release.environment` is
  `${{ inputs.testpypi && 'testpypi' || 'pypi' }}`. Its permissions are
  `RELEASE_PERMISSIONS`. Its `if:` is today's, with the push-to-`main` clause
  widened to
  `(github.event_name == 'push' && github.ref == 'refs/heads/main') || (github.event_name == 'workflow_dispatch' && inputs.testpypi)`.
- `test_s7_6_4_3_release_steps_pass_testpypi`: the build and publish steps' env
  has
  `TESTPYPI: ${{ github.event_name == 'workflow_dispatch' && inputs.testpypi }}`.
  The provenance step's `if:` adds `&& env.TESTPYPI != 'true'`.
- `test_s7_6_4_4_pypi_needs_a_workspace`: `release = "pypi"` on a `python-tool`
  cell raises `ValueError` naming `ci.release`.
- `test_s7_6_4_5_pypi_keeps_every_tag_exists_job`: every job and `ci-ok` need
  that renders for `tag-exists` also renders for `pypi`.

In `tests/modules/tasks/test_artifacts.py`, `test_s7_6_4_6_release_tasks_upload`
checks the `pypi` cell's rendered `tasks/ci.yml`:

- `release-build` runs
  `uvx --from twine==6.2.0 twine check --strict dist/"$name"/*.whl dist/"$name"/*.tar.gz`
  after each `uv build`.
- When `TESTPYPI` is `true`, `release-build` builds every releasable package
  from `HEAD`, skipping the published-release and tag checks.
- `release-publish` passes `--upload "$upload"` to
  `{{.DEVOPS}} release-publish`. `upload` is `testpypi` when `TESTPYPI` is
  `true`, and `pypi` otherwise.
- With `tag-exists`, none of these appears.

In `tests/devops/test_github.py`, for
`upload_commands(index, name, version, files, on_index)`, which is pure
(`on_index` is a bool the caller computed):

- `pypi`, not on the index:
  `[["uv", "publish", "--trusted-publishing", "always", *wheels_and_sdists]]`.
- `testpypi`, not on the index: the same with
  `--publish-url https://test.pypi.org/legacy/`.
- On the index: `[]`.
- `files` other than `*.whl` and `*.tar.gz` (the `.cdx.json`) are never
  uploaded.

In the CLI tests, `release-publish ... --upload pypi` runs the upload before
`gh release create`. `--upload testpypi` runs the upload and no `gh` command,
and skips the release-state check. A failed upload exits non-zero before any
`gh` command.

**Build:**

- `modules/cicd/config.py`: `release: Literal["tag-exists", "pypi", "none"]`.
- `modules/cicd/artifacts.py`: raise
  `ValueError("ci.release = 'pypi' needs a library workspace")` when
  `release == "pypi"` and the cell is not a workspace, beside the existing
  `hooks.docs` check (`:69-71`).
- `modules/cicd/templates/ci.yml.j2`:
    - Every `release == "tag-exists"` test becomes `release != "none"`.
    - In the workspace release job, under `release == "pypi"`: add the
      `environment:`, the widened `if:`, the `TESTPYPI` env and the provenance
      `if:`.
    - Render the `inputs` block under `on.workflow_dispatch`.
- `rn_forge.kiln.devops.github`: `upload_commands` as tested, and
  `on_index(host, name, version) -> bool`, a thin `urllib.request` wrapper:
  `GET https://<host>/pypi/<name>/<version>/json`, true on 200, false on 404,
  raising otherwise. `host` is `pypi.org` or `test.pypi.org`. The CLI's
  `release-publish` gains `--upload {pypi,testpypi}` and parses name and
  version from `TAG` (`<name>-v<version>`).
- `modules/tasks/templates/tasks/ci.yml.j2`: the `release-build` additions and
  the `--upload` argument, inside `{% if release == "pypi" %}`. The tasks
  context gains `release` if it does not already carry it.
- Run `uv run kiln apply` and `task self:golden:compare BASE=HEAD`. No golden
  changes, because no cell sets `pypi`.

**Acceptance:**

- `uv run pytest tests/devops tests/modules/cicd tests/modules/tasks` passes.
- `actionlint` passes on a rendered `pypi` cell's `ci.yml`, in the test that
  already runs it for `python-lib`, now parametrized over both release values.
