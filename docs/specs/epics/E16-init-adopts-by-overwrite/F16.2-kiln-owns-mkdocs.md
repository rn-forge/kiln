`mkdocs.yml` becomes a managed artifact with a provenance header, rendered whole
from the docs tree, `_areas.yml` and `config.toml`. Nav additions go in
`_areas.yml`. Other settings go in a `[docs.mkdocs]` table. `site_dir` is
rendered from `[docs] site_dir`; `task docs:build` passes `--site-dir` only for
an explicit output directory (`task docs:build -- <dir>`, which CI's `docs`
stage uses). The Packages section is derived from `packages` for every
`python-lib`.

**One file, two writers, one contract.** `kiln apply` owns the file outside the
`derived nav` fence; `docs-generate` owns the fence's body. So:

- The recorded hash in `state.json` covers the file with the fence's body
  emptied. Every reader of that hash empties the fence the same way before it
  compares: the `generated` check, and `kiln apply`'s classifier for both a
  rendered artifact and a stale entry. A nav rewrite by `docs-generate` is not
  drift; any other edit is.
- The `docs-generate` check (`docs/checks/derived.py`) keeps checking that the
  fence's body is current.
- `kiln apply` renders the fence's body from `build_nav` over the tree as it is,
  never an empty fence, so an apply after `docs-generate` writes nothing.

**A kiln-owned adapter, not an engine change.** The generation engine
(`rn_forge.commons.generation`, from rn-forge-commons) hashes whole files. Its
`classify` compares `ContentHash.of(disk)` with the recorded hash, and so does
its `_stale_action`. Its `Artifact` and `StateEntry` have no field naming a
derived region. Teaching the engine would need a rn-forge-commons release, from
pykit, ahead of kiln's release-1 tag. kiln instead adapts the engine's output,
as `cycle._adopted` already does. The engine, `StateEntry` and the state schema
(`"1"`) stay as they are. Which files have derived regions is a kiln constant,
not a state field, so `generated` reads it without rendering.

## Context

Today `modules/docs/scaffold.py` writes `mkdocs.yml` once, and kiln owns only
the `BEGIN derived nav` fence. mkdocs's `INHERIT:` replaces lists rather than
merging them, so it cannot extend the nav or plugins. First adopters: kiln's own
`mkdocs.yml`, then pykit's and ngkit's.

**Build:**

- `modules/docs/config.py`: `DocsMkdocs(StrictModel)` with the seven keys above,
  each optional, and `DocsConfig.mkdocs: DocsMkdocs`.
- `modules/docs/artifacts.py`: render `mkdocs.yml.j2` as a `DerivedArtifact` of
  kind `MANAGED` (not a seed); merge the table in Python with PyYAML-free text
  emission: put the user entries through the existing YAML writer that
  `nav.py` uses. Pass `build_nav(root / "docs", packages)` into the render.
- `modules/core/derived.py` (new), the adapter:
    - `NAV_BLOCK` moves here from `modules/docs/nav.py`, which imports it from
      here, so `core` does not import `docs`.
    - `DERIVED: Mapping[str, tuple[ManagedBlock, ...]] = {"mkdocs.yml": (NAV_BLOCK,)}`.
    - `managed_digest(path, text)`: `ContentHash.of(text)` after each of
      `DERIVED.get(path, ())`'s blocks has had its body emptied
      (`block.render(text, "")` when `block.extract(text)` is not `None`;
      malformed markers raise, as `ManagedBlock` does).
    - `DerivedArtifact(generation.Artifact)`, a frozen, slotted subclass with no
      new fields, whose `content_hash` property returns
      `managed_digest(self.path, self.content)`. The engine's `to_entry` reads
      `content_hash`, so `state.json` records the normalised hash with no engine
      change.
    - `settle(root, planned, entries) -> Plan`: for each `MANAGED` change whose
      path is in `DERIVED`, re-derive the action from the file on disk. With a
      rendered artifact and an entry whose hash equals `managed_digest(disk)`:
      `UNCHANGED` if the disk text equals `artifact.content`, else `UPDATE`.
      With a hash that does not match, or markers that do not parse: `DRIFT`.
      For a stale entry (no artifact) whose hash matches: action `DELETE`,
      intent `DELETE`; otherwise `DRIFT` with intent `DELETE`. Approval keeps
      the engine's `approved` flag. It leaves `CREATE`, `CONFLICT`, `MISSING`
      and `FORGET` alone.
- `modules/core/cycle.py`: `classify(root, artifacts, entries, *, force=())`
  returns `derived.settle(root, generation.plan(...), entries)`. `plan`,
  `adoption_plan` and `_prepare` call it in place of `generation.plan`, and
  `_adopted` runs after it. `commands._config_change_rows` calls it too.
- `modules/core/checks/generated.py`: `_check_managed` compares
  `managed_digest(relative, text)` with the recorded hash. A malformed derived
  block is an `artifact.drift` finding.
- `mkdocs.yml.j2`: the header, `site_dir`, the extra entries and the nav fence,
  filled with the passed nav; `docs-generate` still rewrites the fence.
- `modules/docs/scaffold.py`: `scaffold` no longer writes `mkdocs.yml`; keep
  `PACKAGE_SEEDS` for packages' own `mkdocs.yml`.
- `modules/tasks/templates/tasks/docs.yml.j2`: the root build passes
  `--site-dir` only when given an argument; drop `MKDOCS_SITE_DIR`. The
  `site_dir` context key stays for `task clean`.
- Run `kiln apply` here: kiln's own `mkdocs.yml` becomes managed, with its
  S16.2.1 extras in `[docs.mkdocs]` and `_areas.yml`. It has no state entry
  today, so this first apply reports it as a `CONFLICT`. Move the extras, then
  run `kiln apply --force mkdocs.yml`, and read its diff: only the header,
  `site_dir` and the order of keys may change. Any other repository on kiln
  takes the same step once. pykit and ngkit do not, since they adopt through
  `init` ([F16.3](F16.3-cutover-sop.md)).

**What the build settled that the story did not say:**

- `DerivedArtifact` and `settle` live in `modules/core/settle.py`, not
  `derived.py`. `tests/test_checks_are_render_free.py` forbids `kiln doctor`
  from importing `rn_forge.commons.generation`, and the `generated` check
  needs `managed_digest`. So `derived.py` holds only the render-free part
  (`NAV_BLOCK`, `DERIVED`, `managed_digest`), and `settle.py` holds the part
  that subclasses the engine's `Artifact`. `cycle.py` and `docs/artifacts.py`
  import from it.
- "Unset renders no `site_dir`" is `[docs] site_dir = ""`. The model's default
  stays `".docs-site"` (so `task docs:build` and `task clean` agree with the
  rendered file), which means a config that never mentions `site_dir` renders
  `site_dir: .docs-site`.
- `[docs.mkdocs] theme` is appended as extra keys under `theme:`; a key kiln
  already sets (`name`, `features`, `palette`) is refused by validation, so no
  key is ever duplicated (reviewer's fix; test 4 covers it). `plugins` and
  `markdown_extensions` accept strings or single-key mappings.
- At render time the nav fence is built from the tree only when
  `docs/_areas.yml` exists; on `kiln new`'s first apply it does not yet, so
  the fence is empty and `docs-generate` (which `new` and `init` already run
  after apply) fills it. The hash ignores the fence either way.
- A page added before `docs-generate` makes `kiln apply` plan `mkdocs.yml` as
  `UPDATE` (the render has the new nav); the settled action is never `DRIFT`.
- `DocsConfig`'s serializer omits an empty `mkdocs` table, so `to_document` and
  the written `config.toml` stay as they were for a repo that sets none.
- `docs/scaffold.py`'s `scaffold` is deleted, not emptied; its callers (`new`,
  `init`'s `_seed`) are removed. `init` no longer seeds `mkdocs.yml`. It keeps
  `_settle_nav`, so an existing unmarked `mkdocs.yml` is still refused or
  marked under `--force`; an existing `mkdocs.yml` is now a `CONFLICT`,
  overwritten only under `--force`. F16.1 reworks this.
- kiln's own conversion changed `mkdocs.yml` by its header and `site_dir` line
  only; its key order already matched the template.
- Existing tests changed: `tests/test_init.py` (`docs_scaffold` leaves
  `_SCAFFOLDS`; `s6_1_6_1` also deletes `mkdocs.yml`, whose nav no longer
  matches the render once `docs/` is gone; the `s9_1_15_2` dry-run row is
  `managed create`; an existing `mkdocs.yml` is a conflict, not kept),
  `tests/test_new.py` (`mkdocs.yml` is now in `state.json`),
  `tests/modules/docs/test_artifacts.py` (the inventory leads with
  `mkdocs.yml`; `_new` no longer scaffolds and passes `packages` to
  `generate`; the header test accepts `#` for `mkdocs.yml`; the new-page test
  expects `mkdocs.yml` `UPDATE`; the `python-lib` strict build drops the
  `!include` nav), `tests/modules/cicd/test_artifacts.py` (`s4_11_4_7` runs
  `docs-generate` after apply), and
  `tests/modules/instructions/test_artifacts.py` (drops the scaffold call).

**What the build settled that the story did not say:**

  retitled or moved one replaces it.

  `python-lib` fixture it needs lives there. `docs.packages-area-missing` and

- `test_s16_2_3_5_seed_header` reads the rendered seed. The header's first line
  is now "nav additions go here; kiln derives the rest", and a `python-lib`
  seed adds two comment lines saying Packages is derived and how to override
  it.
- `_structure.md.j2`'s Package docs paragraph now says Packages is derived from
  `packages`. `tests/modules/docs/test_artifacts.py`'s `s11_2_2_4` stops
  expecting the seeded `packages` area.
- The golden compare shows only `docs/_structure.md` changing in the
  `python-lib` cell, not `_areas.yml` and `mkdocs.yml` as the story says: the

  The seeded `_areas.yml` differs in every cell by its header line, and in
