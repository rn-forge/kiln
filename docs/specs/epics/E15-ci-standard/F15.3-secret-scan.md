A configured check, on by default, for every archetype: gitleaks scans the git
history. It has a `task` verb, `ci:lint:secrets`, and its own job in `ci.yml`
because it needs full history and a fork guard. It is in the pre-release barrier
`checks-ok`'s `needs`
([F15.8](F15.8-one-workflow-contract.md#s1587-one-ci-ok-logic-and-the-pre-release-barrier)),
so a leaked secret stops `release` as well as `ci-ok`. This revises
[F4.11](../E4-generator/F4.11-ci-enhancements.md)'s "Not adopted: gitleaks".

## S15.3.1 — The gitleaks release is pinned

**State:** Closed (2026-11-05)

**Build — tests first,** in `tests/modules/cicd/test_pins.py`:

1. `test_s15_3_1_1_gitleaks_pin_shape`: `load_pins()["gitleaks"]` has `version`
   and, for `linux_x64` and `darwin_arm64`, a `url` ending
   `gitleaks_<version>_<platform>.tar.gz` and a 64-hex `sha256`.

**Build:** `cicd/pins.toml`, a `[gitleaks]` table: `version` is the newest
gitleaks release at build time; each platform table (`[gitleaks.linux_x64]`,
`[gitleaks.darwin_arm64]`) has `url` and `sha256`, taken from the release's
`gitleaks_<version>_checksums.txt`. Check how `checks/pins.py` reads `pins.toml`
and keep it passing: if it requires `uses`/`sha` in every table, exempt
`gitleaks` by name in that one check.

**Acceptance:**

- The test passes, and `task validate` passes.

**What the build settled that the story did not say:**

- The pin is gitleaks v8.30.1, so `version = "8.30.1"` (the release asset names
  carry no `v`; the URLs use `v8.30.1` in the path). Both URLs answered `200`;
  the digests are from `gitleaks_8.30.1_checksums.txt`.
- `checks/pins.py` reads the rendered workflows, not `pins.toml`, so no
  exemption was needed. The test file `tests/modules/cicd/test_pins.py` is new
  (the existing `ci-pins` tests live in `tests/modules/cicd/checks/`).
- `load_pins()` is typed `dict[str, dict[str, str]]` but returns a nested table
  for `gitleaks`; the test casts it and the type is left alone.

## S15.3.2 — `task ci:lint:secrets`

**State:** Closed (2026-11-05) · **Depends on:** S15.3.1

**Build — tests first,** in `tests/modules/tasks/test_artifacts.py`:

1. `test_s15_3_2_1_task_renders_for_every_archetype`: each of the six
   archetypes' `tasks/ci.yml` has `lint:secrets`, which runs
   `.rn-forge/kiln/rendered/bin/gitleaks detect --source . --redact --no-banner --exit-code 1`
   after an internal `secrets:install`.
1. `test_s15_3_2_2_install_verifies_the_sha`: `secrets:install` downloads the
   pinned URL for `uname -s`/`uname -m` with `curl -fsSL`, checks it with
   `shasum -a 256 -c`, extracts only `gitleaks` into
   `.rn-forge/kiln/rendered/bin/`, and fails with `unsupported platform` for
   any other platform. It is skipped when the binary is already there.
1. `test_s15_3_2_3_off`: with `secret-scan = false` neither task renders, and
   the root `lint` is unchanged. The root `lint` never calls
   `ci:lint:secrets`: only the job does, because a local run needs a network
   download.

**Build:** `modules/tasks/templates/tasks/ci.yml.j2` and the context key
`secret_scan_enabled`, URLs and digests from `load_pins()["gitleaks"]`.
`.rn-forge/kiln/rendered/` is already git-ignored.

**Acceptance:**

- The three tests pass, and `task validate` passes.
- On a Linux x64 machine, `task ci:lint:secrets` in a fresh render exits `0`
  (not scriptable here; the CI run in S15.3.3 proves it).

**What the build settled that the story did not say:**

- The tasks are `lint:secrets` (public, so the job can call it) and
  `secrets:install` (internal) in `tasks/ci.yml`; the skip when the binary is
  present is the install task's
  `status: test -x .rn-forge/kiln/rendered/bin/gitleaks`. The context carries
  `secret_scan_enabled` (from the registry's `secret-scan` row) and a
  `gitleaks` list of `uname`/`url`/`sha256` built from `load_pins()`.
- The tests are parametrized over all six archetypes (1 and 3); test 3 also
  compares the root `lint` of an on and an off render.
- `tasks.artifacts` now imports `cicd.artifacts.load_pins`; `.importlinter`'s
  `concern-modules-are-independent` contract gets one `ignore_imports` line
  for it, beside the existing `cicd.config` and `cicd.registry` ones.
- Run once on darwin_arm64: the download verified (`OK`) and `gitleaks detect`
  scanned 293 commits and found no leaks.
- `.rn-forge/kiln/rendered/` is in the generated `.gitignore` of all six golden
  repos, so the binary is never committed.

## S15.3.3 — The `secret-scan` job gates `release` and `ci-ok`

**State:** Closed (2026-11-05) · **Depends on:** S15.1.3, S15.3.2, S15.8.7

**Build — tests first,** in `tests/modules/cicd/test_ci_ok.py`:

1. `test_s15_3_3_1_job_shape`: the job `secret-scan` has
   `runs-on: ubuntu-latest`, `timeout-minutes: 10`,
   `permissions: contents: read`, a checkout with `fetch-depth: 0` and
   `persist-credentials: false`, the setup action, and one step
   `run: task ci:lint:secrets`.
1. `test_s15_3_3_2_fork_guard`: its `if:` is
   `${{ github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository }}`.
1. `test_s15_3_3_3_gates`: `secret-scan` is in `checks-ok`'s `needs` (and so,
   through it, in `ci-ok`'s); a skipped run passes, as `dependency-review`'s
   does.
1. `test_s15_3_3_3b_failed_scan_blocks_release`: for each archetype with a
   release mode other than `none`, `release` needs `checks-ok`, its `if`
   requires `needs.checks-ok.result == 'success'`, and `checks-ok` fails on a
   `failure` result; so a failed `secret-scan` skips `release`.
1. `test_s15_3_3_4_off`: with `secret-scan = false` the job and its `needs`
   entry in `checks-ok` are absent.
1. `test_s15_3_3_5_declared_name`: `GENERATED_JOBS` contains `secret-scan`, so a
   `[[ci.jobs]]` of that name is refused.

**Build:** `ci.yml.j2` (the job, beside `dependency-review`), `GENERATED_JOBS`
in `cicd/config.py`. Run `kiln apply` here, since kiln's own `ci.yml` changes.
F4.11 and F6.8 already carry dated notes pointing here.

**Acceptance:**

- The six tests pass, and `task validate` passes.

- kiln's own pull-request CI shows a green `secret-scan` job.

- S15.1.3's test 3 now asserts the `secret-scan` half (in `checks-ok`'s `needs`,
  not `ci-ok`'s); test 4 compares with `secret-scan = false` minus the job;

## S15.3.4 — A job that never uses uv passes setup-uv's cache save

**State:** Active · **Depends on:** S15.3.3

S15.3.3's last acceptance line did not hold. On kiln's first pull-request runs
after the push (runs 42251333788 and 42296114588), `secret-scan` scanned the
history cleanly, then failed in setup-uv's post step:

```text
##[error]Cache path /home/runner/work/_temp/setup-uv-cache does not exist on disk.
```

The setup action turns on uv's cache for every job. `secret-scan` runs gitleaks
and never touches uv, so the cache directory is never created, and setup-uv
fails the job when there is nothing to save. setup-uv v10.3.0 has an input for
this case, `ignore-nothing-to-cache` (default `false`).

**Build — tests first,** in `tests/modules/cicd/test_artifacts.py`:

1. `test_s15_3_4_1_setup_uv_ignores_nothing_to_cache`: for every archetype
   (`ARCHETYPES`, `node-lib`, and the two web roots, as
   `test_s9_3_7_3_setup_uv_pin_is_v10_3_0` builds them), every step of the
   rendered `.github/actions/setup/action.yml` that uses `astral-sh/setup-uv`
   has `with: ignore-nothing-to-cache: true`, beside `enable-cache: true`.

**Build:** both setup-uv steps in `cicd/templates/action.yml.j2` (the `node_lib`
one and the Python one) gain `ignore-nothing-to-cache: true`. Run
`task kiln:apply` here, since kiln's own `action.yml` changes.

**Acceptance:**

- The test passes, and `task validate` passes.
- `task self:golden:compare BASE=HEAD`: every cell changes in
  `.github/actions/setup/action.yml` only, by that one line per setup-uv step.
- kiln's own pull-request CI shows a green `secret-scan` job.
