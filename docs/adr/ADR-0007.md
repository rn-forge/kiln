# ADR-0007 — Compose a declared public task vocabulary from modules

**Status:** accepted (2026-09-15) · **Scope:** the task surface of every
repository kiln generates

## Decision

A repository exposes a declared public task vocabulary, appropriate to its
archetype and its selected capabilities. `task` is the only entrypoint; nothing
— human, agent or CI — invokes the underlying tools directly.

The implementation is composed from concern-specific task modules. Root tasks
delegate to modules; a module keeps its implementation tasks internal and
exposes only its declared public surface.

A task file belongs to whatever owns its tasks. A language toolchain's file
holds every primitive of that toolchain: install, lint, format, typecheck, test
and build. kiln is a toolchain too, like uv or pnpm: its checks live in its own
file, as one internal task, `kiln:doctor`, that runs `kiln doctor` once, and the
root `lint` calls it. A concern's file (docs, CI) holds that concern's checks
that are not kiln's, such as the workflow linters. A service's file holds only
how to run the service. Formatting checks over the whole tree share one file.

Two surfaces are public. The developer surface is the ten root verbs, the
`docs:` verbs, `kiln:diff`, `kiln:apply`, `api:*` and `web:dev`. The CI surface
is the `ci:` tasks: public only because a workflow step runs them from the
command line, and go-task refuses to run an internal task that way. Each `desc:`
starts `CI only:`, and the standard lists them in a table of their own. Every
other task is `internal: true`.

A supply-chain check, or a check the registry switches, has no
`command_overrides` key: the dependency audits, the licences check, the secret
scan and internal ranges. Their switch and their policy are the only ways to
change them, because overriding one would turn it off without the config saying
so. `command_overrides` keeps replacing a toolchain primitive.

The vocabulary is extended through explicit module or capability configuration,
never by editing a generated task file. Composition is checked: a repository
whose required validation is no longer reachable from the aggregate gate does
not pass.

## Consequences

- Callers get a stable interface while modules change their implementation
  underneath it.
- A new capability adds a namespaced public surface without flattening the task
  architecture into one file.
- An extension must declare its interface, so the public surface is always
  knowable without reading the task files.
- The public vocabulary is a compatibility surface: renaming a verb is a
  breaking change to every caller, agent and workflow.
- Renaming an internal task breaks no caller, but it does rename that task's
  `command_overrides` key. A repository that sets the old key has to update
  its config.
- The gate is derived: `required_validate` includes each registry check folded
  into `task lint` that is enabled for the repository, so `task-layout` fails
  when one stops being reachable from `validate`.
- The standard's task tables are derived from the rendered task files, as the CI
  check matrix is derived from the registry, so they cannot drift from the
  `desc:` lines.
- kiln's checks have one task and no override key. A repository cannot switch
  off a kiln rule through `command_overrides`; it changes the configuration
  the rule reads.
- A new toolchain adds one file, and a new archetype composes the files for its
  stacks rather than splitting a stack's commands across the shared ones.

## Alternatives considered

- **Let every repository invent its own public interface.** A caller then has to
  discover how to build and validate each repository, which is the state
  agents cope with worst.
- **Keep every command in one root task file.** Unrelated concerns become
  coupled, and a capability cannot add tasks without editing shared lines.
- **Freeze every repository to one universal command list.** A new capability
  then cannot expose the operations its users need, so the list gets bypassed.
- **Split the files by verb**, with one quality file for every lint, format,
  typecheck and test primitive. This was the layout until 2026-10-21. It
  spread each toolchain's commands over several files, and no module could add
  a check without editing the shared one.
- **One task per doctor check**, each in its concern's file. This was the layout
  from F4.11 to S4.12.4 (2026-10-21): nine near-identical tasks, nine process
  starts, and nine `command_overrides` keys that let a repository switch off a
  single kiln rule, for nothing doctor's own finding codes do not already say.
- **One file per formatter** (TOML, Markdown). Each would hold two tasks. The
  checks cover the whole tree, so they stay with the other repository-wide
  checks.
- **A dedicated task-running tool of our own.** Built as taskkit and retired
  (D23): go-task already does this, and the wrapper was maintenance without a
  requirement.

## Background

The idea of writing the vocabulary down, rather than leaving it implicit in the
task files, came from a donor repository's task-vocabulary guide. The verbs
themselves were reconciled across two donor repositories that had drifted —
`format-check`, `dev` and `docs` on one side against the set now in the
reference.

- 2026-10-21: revised, by owner decision, twice in the day. The task files are
  split by owner: a file per toolchain (`python`, `node`, and kiln's own
  `kiln`), a file per concern for its checks that are not kiln's (`docs`,
  `ci`), and the tree's formatting checks in `quality`. The frontend's
  lint/test/build leave the public `web:*` surface. The first cut gave each
  doctor check its own task in its concern's file, with a public `docs:lint`
  aggregate. After reading the lint task, the owner replaced that with one
  `kiln:doctor`, and the public docs verbs return to `docs:build`,
  `docs:serve` and `docs:generate`. The layout and the renames are
  [F4.12](../specs/epics/E4-generator/F4.12-task-files-by-owner.md).
- 2026-11-05: revised by owner decision (E17): the CI surface is declared, no
  override key for a registry check, the gate is derived from the checks that
  are on, and the standard's task tables are derived from the task files. The
  naming grammar and where check policy lives follow in F17.2. The page is
  [the task architecture](../architecture/tasks.md).
