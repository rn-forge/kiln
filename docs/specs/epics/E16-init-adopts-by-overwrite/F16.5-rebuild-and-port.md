Existing web applications of several flavours are expected to move onto kiln.
They are rebuilt: `kiln new` renders the target repository, the old repository's
source, tests, configuration and docs are ported into it, and the result lands
as a branch on the **old** repository. kiln's part is a read-only inventory that
is the same for every flavour, and the cutover runbook. The porting itself,
scripts included, is the agent's, following the runbook. No iteration yet. The
owner named the first application on 2026-10-21: apollo, ported to the
`python-web-app --backend fastapi --frontend angular` cell (S16.5.3, formerly
S6.5.3 and kiln's S5.3.4). It is ported by hand from its own build plan, and
what it teaches is what S16.5.1 is written from.

The route is the cutover runbook, not the adopt prompt, which holds judgement
only.

## Design

- **One route, one runbook.** The cutover runbook
  ([S16.3.1](F16.3-cutover-sop.md#s1631-the-runbook-exists), rewritten by
  [S16.8.2](F16.8-retire-kiln-init.md)) is the rebuild and port: a reference
  from `kiln new`, brought onto a branch of the existing repository and
  reviewed as one diff. The `adopt` prompt carries only the judgement.
- **The port's direction keeps the history.** The new repository is built in a
  staging directory and ported into, and its tree then replaces the old
  repository's on a branch. The old repository keeps its history, tags,
  issues, pull requests, remote and deployments; nothing is pushed to a new
  remote.
- **kiln owns only what is the same for every flavour.** kiln knows, for the
  target archetype, which file is managed, seeded, a block or
  repository-owned. Classifying the old repository's files against that is
  deterministic and reusable; mapping one flavour's layout, settings, routes
  and build onto kiln's is not, and is the prompt's.
- **A step becomes kiln code only when two ports repeat it.** The first port
  teaches the prompt; the second shows what is worth automating.

## Considered and rejected

- **A `kiln adopt --path <old repo>` command that brings everything in.** Each
  old repository is ported once, so code that maps one flavour onto kiln runs
  once and is maintained against every later kiln change; a command also makes
  kiln answerable for a port it cannot judge. Rejected 2026-10-16. kiln
  migrating application source stays outside its
  [scope](../E4-generator/design.md#scope-and-ownership).
- **Porting into the new repository's history.** It loses the old repository's
  history, tags and remote. Rejected 2026-10-16.

## S16.5.3 — The first web application is ported: apollo

**State:** New

Moved here from F5.3 (S5.3.4) on 2026-10-21, so that F5.3 could close on its two
shipped cells while the real-application proof runs as long as the rebuild
needs.

**The repository.** apollo (`rn-tools/apollo`, a FastAPI + SvelteKit music
library workstation), rebuilt as
`python-web-app --backend fastapi --frontend angular`. The backend is ported;
the SvelteKit SPA is rewritten in Angular, since kiln has no Svelte frontend
module. The build plan, stories R1–R11, is apollo's own:
`rn-tools/apollo/docs/specs/kiln-rebuild-plan.md`
([ADR-0009](../../../adr/ADR-0009.md): its plan and status are apollo's).

**This is the hand port the prompt is written from.** It follows apollo's plan,
not `kiln prompt --name adopt`; what it records feeds the cutover runbook.

**The owner provides before work starts**, recorded here: the baseline ref, the
kiln ref, and the GitHub repository. apollo's remote is Azure DevOps, and kiln
renders GitHub Actions only ([E8](../E8-ado-provider/index.md) is deferred). So
the old repository moves to GitHub with its history first, and the port then
lands there as a branch, as this feature's design requires.

**Rules carried from S5.3.4.**

- A failure that an empty generated repo also shows is a kiln defect. Reproduce
  it in kiln's tests, fix it in the owning module, and rerun F5.3's S5.3.3
  proof before going on.
- A requirement unique to the application goes through the existing config
  extension points (`[tasks] includes`, `[tasks] extra_refs`,
  `[archetype."python-web-app"]` `api_dir`/`web_dir`, `[ci] sonar`,
  `[ci] jobs`, `[ci.hooks]`), and is recorded here. It does not become an
  archetype special case.
- A web-archetype gap found along the way becomes its own story in this feature.
  apollo's CI dependency on `ffmpeg` needs none: it uses `[ci.hooks] setup`
  (F4.11).
- Set `sonar = false` under `[ci]` unless the repository has a SonarCloud
  project and a `SONAR_TOKEN` secret, and record which.

**Acceptance:**

- This story records the baseline ref, the kiln ref, the GitHub repository and
  the exact `kiln new` command.
- The ported API starts under `task api:dev`, and one real route is exercised
  through the framework's test client. The Angular application builds, and its
  tests pass.
- On the branch, `task setup` (which includes `uv sync` and
  `pnpm install --frozen-lockfile`), `task validate` and `kiln doctor .` pass
  — `kiln doctor . --full` once S4.6.1 ships it.
- The branch's CI run passes and is linked here.
- Every step where apollo's plan was not enough is recorded here, as input to
  the cutover runbook ([S16.8.2](F16.8-retire-kiln-init.md)).
