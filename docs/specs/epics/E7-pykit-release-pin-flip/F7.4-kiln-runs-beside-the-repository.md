A repository pins kiln in `.rn-forge/kiln/config.toml` (`[kiln] ref`), and its
tasks run that kiln with `uvx`, in kiln's own cached environment.
`rn-forge-kiln` leaves every generated repository's dependency groups and lock.
`kiln doctor` gains the `kiln.pin` check that the standard has always listed,
and that was never built: the running kiln is the pinned one.

## Context

**Why.** kiln as a dev dependency shares the repository's `uv.lock`, so every
shared dependency must resolve to one version. uv also refuses two git URLs for
one distribution. That coupling shows up in five places:

- kiln's own pykit pins must equal the ones it renders
  (`test_s7_1_1_2_kiln_takes_pykit_by_tag`);
- kiln cannot take a pykit release until pykit re-tags every package on it;
- pykit's workspace needs `override-dependencies` to install kiln at all;
- every repository carries `pyyaml` only so kiln's checks import;
- Jinja, pydantic and the generator enter every repository's lock.

With kiln in its own environment, its versions and the repository's never meet.

**The precedent.** The rendered `ci.yml` already runs `rn-forge-devops` this
way. Inside pykit's own workspace it uses `uv run`; everywhere else it uses
`uvx --from "<git>@<tag>"` (`modules/tasks/artifacts.py`). kiln follows the same
rule:

- kiln's own repository, whose module is `rn_forge.kiln`, runs its working tree
  with `uv run kiln`;
- every other repository runs the pinned ref.

**What a repository records.** `[kiln] ref` is a kiln release tag, `v<version>`,
the tag kiln's `tag-exists` release creates. Before kiln's first release it may
name a branch, as `KILN_SOURCE` does today (`feature/v1`). A branch pin skips
the version check: it is the interim, and
[F7.2](F7.2-kiln-release-and-config-upgrade.md)'s release-1 cut ends it. Tags
are never moved (ADR-0006's `tag-exists`), so a tag pin is as reproducible as a
lock entry.

**Caching.** `uvx` builds the pinned kiln once into uv's cache. The rendered
setup action already restores that cache (`setup-uv`, `enable-cache: true`), but
its key follows `uv.lock`, which no longer moves with the kiln pin. The cache
key must also follow `config.toml`, so a pin change saves a fresh cache.

**Interaction with F7.3.** Once this lands, kiln's own pykit pins move
independently of `RN_FORGE_TAGS`. [F7.3](F7.3-adopt-pykit-extraction.md) then
bumps kiln's own pins first, and the rendered pins separately.

## Considered and rejected

- **Keep kiln in the lock, and pin the pykit versions it may use as ranges.**
  Ranges loosen the clash, but kiln and the repository would still have to
  agree on every shared package, and Jinja and the generator would still enter
  every lock.
- **A globally installed kiln (`kiln self install`).** It is not pinned per
  repository, and CI would install it unpinned, which ADR-0006 rejects. A
  developer may still use it; `kiln.pin-mismatch` tells them when it is the
  wrong version.
- **Pin a commit SHA instead of a tag.** It is as reproducible, but unreadable
  in review, and kiln's release never moves a tag.
- **A root `KILN` var in `Taskfile.yml`.** The `tasks/*.yml` files are
  self-contained, and the root file stays the ten verbs. Each include that
  runs kiln carries the var, as `ci.yml` carries `DEVOPS`.
