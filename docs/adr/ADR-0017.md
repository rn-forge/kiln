# ADR-0017 — kiln ships the CI planner as `kiln-devops`

**Status:** proposed (2026-10-22) · **Scope:** the generated CI of every
archetype, and kiln's distribution

## Decision

The CI and release logic that [ADR-0016](ADR-0016.md)'s contract needs ships
inside `rn-forge-kiln`, as the subpackage `rn_forge.kiln.devops` and the console
script `kiln-devops`. It replaces pykit's `rn-forge-devops` as the planner
behind `task ci:*`.

- **One distribution.** `rn_forge.kiln.devops` is part of the `rn-forge-kiln`
  wheel and versions with it. It is not a concern module: it has no
  `artifacts()` and no `checks()`, and the module contract
  ([ADR-0001](ADR-0001.md)) does not change.
- **Its own import boundary.** It imports the standard library and `packaging`,
  nothing else from `rn_forge`, and no framework. Nothing else in kiln imports
  it: the generator reaches it only as a command line in a rendered task. Its
  core knows neither the CI platform nor the stack; the uv workspace and
  GitHub Actions are adapters, as in pykit's design.
- **Reached through the kiln pin.** Every repository already pins
  `rn-forge-kiln` as a development dependency ([ADR-0006](ADR-0006.md)), so
  its lock already holds the planner. Generated tasks run
  `uv run kiln-devops …`; there is no `uvx` call and no separate pin.
- **Logic, not workflow shell.** CI and release logic that is more than calling
  a task lives in `kiln-devops`, and a generated workflow step is a `task`
  call. This is pykit's ADR-0012 rule, now kiln's.
- **The rule for kiln's reach.** kiln's code runs at development time and in CI.
  None of it enters a product's wheel or runs in a product's runtime.

This supersedes [ADR-0014](ADR-0014.md)'s choice of pykit's `rn-forge-devops`
and its `uvx` invocation; the rest of ADR-0014 stands. ADR-0016's
"rn-forge-devops is the standard CI planner" now reads `kiln-devops`. pykit
retires its own package in its own specs ([ADR-0009](ADR-0009.md)).

## Consequences

- The workflow kiln renders and the planner it calls change in one pull request
  and release together. Before, a planner change needed a pykit tag, then a
  pin bump in kiln, then a kiln release.
- A planner fix reaches a repository through the kiln pin bump it already takes.
  No generated file changes for it.
- A job that runs `kiln-devops` syncs the repository's development environment,
  kiln's dependencies included. CI jobs already set up uv and sync.
- pykit's CI stops testing a planner it ships, and runs kiln's like every other
  repository.
- `kiln-devops` and `rn-forge-devops` can be installed side by side, so pykit
  can adopt kiln before deleting its package.

## Alternatives considered

- **Keep the planner in pykit.** The contract is kiln's and the planner is its
  implementation, so every change to one needed a coordinated change in two
  repositories. Nothing about the planner belongs to pykit's libraries.
- **A second distribution built from kiln's repository.** It is lighter for a
  planner-only job, but kiln's repository becomes a uv workspace with a second
  release line, and ADR-0001 needs revising. No consumer installs the planner
  without kiln today. Revisit when one does, by ADR-0001's promotion rule.
- **A `kiln ci …` subcommand.** It would load the Typer CLI, commons and tooling
  for every planner call, and put CI code behind the generator's command
  surface.
- **Keep the name `rn-forge-devops`.** pykit's package of the same name would
  collide with it in pykit's environment until pykit deletes its own, so the
  adoption and the deletion would have to land together.

## Background

- 2026-10-21: owner proposal, after pykit's F16.1 moved the planner into a
  package and kiln's ADR-0016 widened it to every archetype.
- 2026-10-22: shape chosen — inside `rn-forge-kiln`, not a second distribution;
  the workflow's remaining inline shell moves into it in the same feature.
