<!-- END derived stories -->

`kiln init` writes starter source into a published package that has no use for
it, and `kiln apply` writes it back when it is deleted. Following the adopt
prompt's advice to delete `[source]` makes the next `kiln config-update --apply`
drop the repository's packages from `config.toml`. pykit's cutover waits on the
first, and takes the second's path.

## Context

pykit's third trial `kiln init` ran on 2026-11-01: ten members, kiln `a8876b8`.
pykit recorded it in its F16.3. On 2026-11-01 kiln repeated it from a fresh
clone of pykit `be50e12` with kiln `224d46a`, on a copy, and read every item in
pykit's S16.3.2 against kiln's source.

What kiln owns:

| Finding | Evidence | Story |
| -- | -- | -- |
| `init` writes `settings.py` and `test_settings.py` into `rn-forge-tooling`. `seedable` reads only `*.py` files directly in the package directory, and that member's code is all in subpackages. After the two files are deleted, `kiln apply --dry-run` plans `seeded create` for both. [ADR-0010](../../../adr/ADR-0010.md) says a starter is written once, at `kiln new`; [F4.9](../E4-generator/F4.9-seeded-starter-source.md)'s "as built" paragraph says `apply` writes one when absent. The code follows the paragraph. | Reproduced. `cycle._artifacts` serves `new`, `init`, `apply` and `config-update` alike, and commons' `classify` creates any absent `SEEDED` artifact. | S6.9.1 |
| With `[source]` deleted, as `prompts/adopt.md` §2 tells an adopter to do, `kiln config-update --apply` rewrites `config.toml` without `[archetype.python-lib]`: `packages`, `modules` and `import_contracts = "own"` all go. `--dry-run` shows `.importlinter` and `sonar-project.properties` changing. | Reproduced. `ConfigManager.reresolve` skips a key recorded in the `source` layer with an unchanged value, expecting that layer to supply it, and with no `[source]` no layer does. | S6.9.2 |

**Why `seedable` is not the fix.** Making it recursive stops `rn-forge-tooling`
being seeded, but `apply` still re-creates a starter deleted from a genuinely
fresh package, so ADR-0010 stays false.

**Why a path prefix, not a flag.** `kiln generate package` seeds through
`cycle.apply` too. A repository-wide "starters on" there would re-create
`rn-forge-tooling`'s files in pykit the first time pykit generates a package, so
only the new package's prefix may seed.

**Why a kept starter stays in the plan.** `kiln new` records its starters in
`state.json`. Dropping them from every later plan would make each `apply` report
`seeded forget`, and `test_s11_3_1_2_…` requires a clean second apply. A starter
file that exists stays an artifact, which `classify` skips; only an absent one
is dropped.

**Rejected on 2026-11-01:**

- *`github-token` defaults to `${{ github.token }}` in the setup action, or a
  doctor check on local action inputs.* pykit reads the three workflows' bad
  calls as failing only when run. They do not: `actionlint`, in `task lint`,
  reports `missing input "github-token"` for all three and
  `input "sync" is not defined` for `umbrella-release.yml`. A default would
  still leave the `sync` error, and pykit changes those workflows anyway.
- *`init` sets `[ci] release` from the repository.* Publishing to PyPI is the
  owner's choice, and pykit's config sets it.
- *`init` reports its change rows before failing on findings.* The rows are
  useful, but nothing in the cutover needs them.
- *`add_task_tools` keeps `pyproject.toml`'s formatting.* It reflows pykit's
  root file, 88 diff lines with no semantic change. That departs from
  [F6.6](F6.6-init-leaves-gate-runnable.md)'s readable `init` commit, but the
  file is reformatted by the adopter's `task format` regardless.
- *`--all-extras` in `python:lint:audit`.* pykit's `dependency-audit` stays
  pykit's ([F6.8](F6.8-pykit-release-7-ci.md)).
- *A `testpypi` dispatch from a branch other than `main`.* `sonar` is skipped
  off `main`, so `release` is too.
  [F7.6](../E7-pykit-release-pin-flip/F7.6-release-to-pypi.md)'s test locks
  that condition and S16.3.2 asks only for a manual dry run.
- *`twine check --strict` on a pull request.* pykit's S16.3.2 states a pull
  request's packaging check is `smoke`.

**Already specified.** S16.3.2's PEP 740 attestations and the planner's Redis
key and `release_order` cycle fix are [F6.8](F6.8-pykit-release-7-ci.md).
Everything else S16.3.2 requires is rendered now, read from source and not yet
run on GitHub: `PACKAGE_DIR`, `release` on the default branch after Sonar, the
`docs` job, the other F21.3 release behaviour, `[[ci.jobs]]` with `uses` and
`events`, `[ci.hooks] docs`, and `[tasks] includes` and `extra_refs`.

*Superseded 2026-11-04 (E16):* the handoff list to pykit that stood here
(umbrella permissions, `notes`, workflow callability, Dependabot pins,
`_areas.yml` and the `mkdocs --strict` warnings) is replaced by
[the cutover SOP](../E16-init-adopts-by-overwrite/F16.3-cutover-sop.md), whose
verdict table carries each such item. `init` now overwrites `_areas.yml` and the
other kiln-shaped files
([F16.1](../E16-init-adopts-by-overwrite/F16.1-opinionated-init.md)). What this
feature decided still holds: `init`, `apply` and `config-update` write no
starter source into an existing package, which F16.1 keeps by never touching
source.

## S6.9.1 — A starter is written only into a repository or package kiln creates

**State:** Closed (2026-11-02)

Only `kiln new`, and `kiln generate package` for the package it adds, create a
starter file. `init`, `apply` and `config-update` never do. Seeded files outside
starter source (docs pages, `.taplo.toml`, `tasks/self.yml`) keep their rule.

**Build — tests first.** In `tests/test_init.py`:

1. `test_s6_9_1_1_init_writes_no_starter_into_a_package_with_subpackages`. On
   `lib_repo`, for `packages/lib-alpha`, delete `settings.py` from the package
   directory and `tests/test_settings.py`, and create `sub/__init__.py` in the
   package directory. `_commit(lib_repo)`, then run `commands.init` as
   `test_s6_1_5_1_…` does. Neither file exists afterwards. `lib-beta`'s
   starter files are unchanged.

In `tests/test_apply.py`, on a repository `commands.new` made as `python-tool`:

1. `test_s6_9_1_2_apply_does_not_recreate_a_deleted_starter`. Delete the
   starter's `product.py`. `commands.apply(dry_run=True, json=True)` reports
   it as `forget`, and no row has the action `create`. After
   `commands.apply()`, the file is absent and a second dry run has no row for
   it.

In `tests/test_generate_package.py`, on a copy of the repository the `generated`
fixture builds:

1. `test_s6_9_1_3_generate_package_seeds_only_the_new_package`. Delete
   `settings.py` from an existing member's package directory, then generate a
   new package. The new package has `settings.py` and
   `tests/test_settings.py`. The existing member's `settings.py` stays absent.

In `tests/modules/python/test_starter.py` and
`tests/modules/node/test_starter.py`:

1. `test_s6_9_1_4_python_starters_are_its_starter_paths`.
   `isinstance(PYTHON, StarterModule)`, and for a fresh `python-tool` package
   `set(PYTHON.starters(config, root))` equals
   `{a.path for a in starter.render(config, root)}`. For a package holding
   product code it is empty.
1. `test_s6_9_1_5_node_starters_include_the_proxy_config`. The same for `NODE`,
   including `<web_dir>/proxy.conf.json`.

**Build:**

- `src/rn_forge/kiln/modules/base.py`: a `@runtime_checkable` protocol
  `StarterModule` with one method,
  `starters(self, config: KilnConfig, root: Path) -> Sequence[str]`, whose
  docstring says it returns the paths in `artifacts()` that are starter
  source. `KilnModule` does not change.

- `PythonModule.starters` and `NodeModule.starters` return
  `[a.path for a in starter.render(config, root)]`, importing `starter` inside
  the method as `artifacts` does. `artifacts` does not change.

- `src/rn_forge/kiln/modules/core/cycle.py`:

    - `_artifacts` gains the keyword `starters: str | None = None`, and becomes:

        ```python
        kept: list[generation.Artifact] = []
        for module in manager.modules_for(config):
            held = (
                set(module.starters(config, root))
                if isinstance(module, StarterModule)
                else set()
            )
            kept += [
                artifact
                for artifact in module.artifacts(config, root)
                if artifact.path not in held
                or (root / artifact.path).exists()
                or (starters is not None and artifact.path.startswith(starters))
            ]
        return kept
        ```

    - `_prepare` and `apply` gain the keyword `starters: str | None = None` and
      pass it on. Its docstring entry on `apply`: "The path prefix under which
      an absent starter file may be created: `""` for the whole repository,
      `None` for nowhere." `plan` and `adoption_plan` do not gain it.

- `src/rn_forge/kiln/commands.py`: `new`'s `cycle.apply` passes `starters=""`.
  `generate_package`'s passes `starters=f"{relative}/"`. No other call passes
  it.

- The docs, in the same change:

    - [ADR-0010](../../../adr/ADR-0010.md) gains a dated `## Background` line:
      `kiln generate package` seeds the package it creates, and `init`, `apply`
      and `config-update` write no starter (F6.9).
    - [F4.9](../E4-generator/F4.9-seeded-starter-source.md)'s "as built" paragraph
      gains a dated sentence saying the same, and its "`apply` writes it only
      when absent" is struck.
    - `docs/reference/standard-repo.md`'s "**Seeded** and **scaffolded**" bullet
      gains: starter source is the exception, and a later `kiln apply` does not
      recreate it.

**Do not:** change `seedable`, change `KilnModule`, add `starters` to any other
module, filter by a path containing `src`, or touch `_preview_rows`. If a test
helper builds a repository with `cycle.apply` and expects starter files, pass
`starters=""` in that helper and record it.

**Acceptance:**

- `init` on a member with only subpackages writes no starter source.
- A deleted starter is never recreated by `apply`, in any repository.
- `kiln generate package` seeds its new package and no other.
- `new`, then `apply --dry-run`, reports only `unchanged` and `skip`.
- `task validate` and `task self:golden:validate` pass with no rendered cell
  changed.

*What the build settled that the story did not say*

- No test helper needed `starters=""`: every existing test that builds a
  repository with `cycle.apply` passed unchanged (1843 passed).
- `StarterModule` is exported from `base.py`'s `__all__`.
- `_artifacts` takes `starters` as a keyword-only parameter. Its `held` set is
  built with `held.update(...)` under an annotation, not the story's
  conditional expression, because pyright strict reports the conditional's
  type as partially unknown.
- `_prepare` takes `starters` positionally as its last parameter, after `adopt`;
  `apply` passes it on.
- `test_s6_9_1_1_…` reads `lib-alpha`'s module directory as `src/lib_alpha/`,
  and `test_s6_9_1_2_…` builds its repository with `commands.new` in
  `tmp_path`, not from the `rendered` fixture.
- `test_s6_9_1_3_…` copies `generated` with `shutil.copytree` and generates
  `golden-gamma`.
- `test_s6_9_1_4_…` also checks `PYTHON.starters` is empty once a package holds
  product code (`service.py`).
- `task format` rewrapped the one line in `cycle.apply`'s call to `_prepare`.
- The feature's own **State** moved from `New` to `Active`, because
  `task docs:generate` refuses a `New` feature with a `Closed` story.
- No departure from the Build list.

## S6.9.2 — `config-update` keeps what `[source]` supplied when `[source]` is gone

**State:** Closed (2026-11-02)

**Build — tests first.** In `tests/test_config_lifecycle.py`, on
`resolved_repo`:

1. `test_s6_9_2_1_deleting_source_keeps_its_values`. Delete the `[source]` table
   from `CONFIG_PATH` and run `commands.config_update` with `--apply`, as
   `test_s4_5_4_apply_writes_the_remerged_config_…` does. Every key the
   `layer` fixture supplied is still in `config.toml` with its value, and
   `commands.config_update(dry_run=True, json=True)` reports no artifact
   change.
1. `test_s6_9_2_2_deleted_source_values_become_overrides`. Delete the table, and
   a `config_update(dry_run=True, json=True)` lists the layer's keys in
   `overrides`.
1. `test_s6_9_2_3_a_missing_source_file_still_refuses`. With `[source]` naming a
   file that no longer exists, `config_update` raises as it does today.

**Build:**

- `ConfigManager.reresolve` in
  `src/rn_forge/kiln/modules/core/config/manager.py`: a recorded
  `source`-layer key is an override when the config has no `[source]`:

    ```python
    orphaned = "source" not in committed
    for path, value in DictUtils.flatten(body).items():
        was = recorded.get(path)
        if (
            was is None
            or was.layer == REPO_LAYER
            or was.value != value
            or (orphaned and was.layer == SOURCE_LAYER)
        ):
    ```

- `reresolve`'s docstring says deleting `[source]` keeps its values as
  repository overrides.

**Do not:** make `init` warn about or refuse a `--config` path, change what it
records as `[source]`, or edit `prompts/adopt.md`, whose advice is correct once
this holds.

**Acceptance:**

- After `[source]` is deleted, `config-update --apply` leaves `packages`,
  `modules` and `import_contracts` in `config.toml`, and changes no rendered
  file.

*What the build settled that the story did not say*

- The three tests share a helper, `_delete_source`, that reads `config.toml`
  with `tomllib`, drops `source` and writes it back with `DocumentUtils`.
- `test_s6_9_2_1_…` asserts the layer's two keys by value (`docs.profile` is
  `"none"`, `ci.sonar` is `False`) and that the dry run after `--apply` has
  `artifacts == []`. `test_s6_9_2_2_…` asserts `docs.profile` and `ci.sonar`
  are each in `overrides`, not that the list equals them.
- `test_s6_9_2_3_…` deletes the layer file; it passed before the fix, as the
  story implies (tests 1 and 2 failed, 3 passed).
- No departure from the Build list.
