`task kiln:upgrade` moves a repository to a new kiln and to that kiln's pykit
floors in one step. It pins kiln, re-renders, rewrites every rn-forge range to
kiln's pin table, prints the release notes in between, and runs `task validate`.
When validation fails it rolls the working tree back to `HEAD`, unless `FORCE=1`
asks to keep the upgrade so the failures can be fixed. `kiln doctor` warns when
a repository's floors are below the pin table.

## Context

**Found 2026-11-18,** after [S7.7.5](F7.7-kiln-installs-as-a-tool.md) raised the
pin table to pykit's Release 9. The pin table (`RN_FORGE_TAGS`) is read only by
`kiln new` and `kiln generate package`. An existing repository's
`pyproject.toml` is its own ([ADR-0018](../../../adr/ADR-0018.md)), so
`kiln apply` never rewrites its ranges, and `rn-forge-deps` checks only their
shape. `uv sync --upgrade` re-resolves inside the declared ranges, so it takes
`rn-forge-tooling` 0.3.3 but never crosses `<0.10` to `rn-forge-commons` 0.10.0.
Release 9 crossed the ceiling of five packages.

`docs/reference/standard-repo.md` says `kiln config upgrade --apply` takes a
breaking pykit release into a repository. It does not: it re-resolves the config
and re-renders, and `pyproject.toml` is not rendered.

**Why the new kiln does the work.** The floors live in the kiln being moved to,
so the step that rewrites them runs at the new ref. `task kiln:pin` already runs
its apply that way, through `uvx` at `$(kiln pin --show)`.

## Design

- `kiln deps-upgrade` rewrites, re-locks with `task setup`, and validates with
  `task validate`. On a failure it restores the working tree to `HEAD`, so it
  refuses to start on an uncommitted tree. `--tree-checked` skips that check
  for a caller that made it already. `--force` keeps a failing upgrade and
  still exits non-zero.
- `task kiln:upgrade [-- <ref>]` checks the tree is clean, runs `kiln pin`, and
  then runs `kiln apply` and `kiln deps-upgrade --tree-checked` at the new
  ref. `FORCE=1` adds `--force`. It is rendered wherever `kiln:pin` is, so
  never in kiln's own repository, which moves the pin table directly.
- Release notes are information, not the gate. For each moved package, kiln
  prints the `CHANGELOG.md` sections after the old floor, up to and including
  the new floor, fetched from pykit at the new tag. When the fetch fails, it
  prints the URL instead.

## S7.8.1 — `kiln deps-upgrade` moves the rn-forge ranges and validates

**State:** New

**Acceptance:**

- Each rn-forge requirement in the root and member `pyproject.toml` files
  becomes `archetypes.requirement(name)`. That covers dependencies, optional
  dependencies and dependency groups, and git-URL pins as well as ranges.
  Extras and markers are kept. A workspace member, a non-rn-forge requirement
  and a floor at or above the table are left unchanged, and nothing else in
  the file changes.
- `task setup` and then `task validate` run. On success, the moves are kept and
  printed.
- On a failure without `--force`, the tree equals `HEAD` again, `task setup`
  re-runs, and the command fails with `deps-upgrade.failed`. With `--force`,
  the moves are kept and it fails with `deps-upgrade.kept`.
- An uncommitted tree is refused with `deps-upgrade.dirty` before anything runs,
  unless `--tree-checked` is passed.
- Each moved package's release notes between the floors are printed, or their
  URL when they cannot be fetched.
- Tests: `tests/modules/python/test_ranges.py`,
  `tests/commands/test_deps_upgrade.py`, and `archetypes.floor` in
  `tests/test_archetypes.py`.

## S7.8.2 — `task kiln:upgrade`

**State:** New · **Depends on:** S7.8.1

**Acceptance:**

- Every generated repository except kiln's own has a public `kiln:upgrade` with
  a clean-tree precondition that runs pin, then apply and
  `deps-upgrade --tree-checked` at the new ref. `FORCE=1` adds `--force`.
- `taskgraph` accepts it, and `task --list` shows `kiln:diff`, `kiln:apply`,
  `kiln:pin` and `kiln:upgrade`.
- The rendered standard and `docs/reference/standard-repo.md` name
  `task kiln:upgrade` as the way to take a new kiln's pykit floors. The
  `kiln config upgrade --apply` claim is gone.
- Tests: `tests/modules/tasks/test_task_doctor.py`,
  `tests/modules/tasks/test_node_tasks.py`.

## S7.8.3 — `kiln doctor` warns when a floor is below the pin table

**State:** New · **Depends on:** S7.8.1, S7.8.2

**Acceptance:**

- `rn-forge-deps` reports `deps.behind`, a warning, for each rn-forge
  requirement outside the workspace whose floor is below the pin table. It
  names the floor, the table's version and `task kiln:upgrade`. A warning does
  not fail `task lint`.
- The check-code table in `docs/reference/standard-repo.md` lists `deps.behind`.
- Tests: `tests/modules/python/checks/test_rn_forge_deps.py`.

passing and rolled back.

## Considered and rejected

- **`uv sync --upgrade` alone.** It stays inside the declared ranges, so it
  never takes a release past a ceiling.
- **Rewrite the ranges in `kiln apply`.** `pyproject.toml` is the repository's
  own (ADR-0018), and a breaking bump needs code fixes, so it must be an
  explicit step.
- **A Python `kiln upgrade` that pins and then continues.** The running kiln is
  the old one, and its pin table is the old table. The new ref has to do the
  rewrite, which the task does through `uvx`.
- **Release notes as the gate.** They are prose, and whether a change breaks a
  repository depends on what it uses. `task validate` answers that.

## Open questions

- Should pykit mark breaking changelog entries in a fixed form, such as a
  `### Breaking` heading, so that kiln can flag them by rule instead of
  printing every section?
- Is an API diff with `griffe`, checked against the repository's imports, worth
  a dependency? It would warn before validation runs.
