A repository that follows a kiln branch pins the commit it last moved to, and
moves forward only when its owner runs `task kiln:pin`. Every machine and CI run
then use the same kiln, and taking kiln's newest work is a one-line config diff.

## Context

Before kiln's first release, `[kiln] ref` names a branch, `feature/v1`, and kiln
keeps changing on it as cutovers and new repositories find improvements. The
rendered tasks run kiln through `uvx` from that branch, with two failures:

- `uvx` keeps the commit it first installed, so a local run can use an older
  kiln than the branch holds, and `task kiln:apply` does not pick up new work.
- CI installs fresh, so a push to kiln's branch can fail another repository's
  drift check when nothing in that repository changed, and the failure does
  not reproduce locally.

## Design

- `[kiln] ref` is a release tag (`v<major>.<minor>.<patch>`, the form
  `modules/core/checks/pin.py` already reads) or a full 40-character commit
  SHA. Anything else is taken as a branch, so config load needs no network.
  A new key, `[kiln] track`,
  names the branch a SHA was taken from; it is present only with a SHA.
- `kiln pin <branch>` resolves the branch's newest commit, writes it as `ref`
  and the branch as `track`. `kiln pin <tag or SHA>` writes `ref` and removes
  `track`. `kiln pin` with no argument moves to the newest commit of `track`,
  and is an error when there is no `track`.
- Every rendered command that installs kiln names `ref`, so the install, the dev
  dependency and the CI install agree, and a cached install is keyed by the
  commit.

## S18.14.1 — The config pins a commit and the branch it follows

**State:** New

**Acceptance:**

- Config load accepts a tag, or a SHA with or without `track`, and refuses a
  branch name in `ref` with a message that says to run `kiln pin <branch>`.
- `track` without a SHA `ref` is refused.
- The rendered `uvx` commands, dev dependency and CI install name the SHA.

## S18.14.2 — `kiln pin` moves to a branch's newest commit

**State:** New · **Depends on:** S18.14.1

**Acceptance:**

- `kiln pin <branch>`, `kiln pin <tag or SHA>` and `kiln pin` with no argument
  write `ref` and `track` as the design says, and each is a test against a
  local git remote.
- `kiln pin` with no argument and no `track` is an error, and so is a branch or
  tag that does not exist; neither writes the config.
- The rendered `kiln:pin` task accepts no argument, and in that form re-renders
  with the newly pinned commit.

## S18.14.3 — kiln's adopters move to a pinned commit

**State:** New · **Depends on:** S18.14.2

kiln's own repository and its golden repositories move from the branch ref to
`kiln pin feature/v1`.

**Acceptance:**

- No config in kiln's repository or its goldens names a branch in `ref`.
- `task kiln:apply` runs on this repository in the same change, and
  `task lint KILN_DOCTOR_FULL=1` passes.

## Acceptance

- S18.14.1: A branch in `ref` is refused at config load, and rendered installs
  name the pinned SHA.
- S18.14.2: `kiln pin` with no argument moves to the newest commit of `track`.
- S18.14.3: No config in this repository or its goldens names a branch in `ref`.
