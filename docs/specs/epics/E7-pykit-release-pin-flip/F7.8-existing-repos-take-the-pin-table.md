`task kiln:upgrade` takes a new kiln pin and its pykit floors in one operation.
The target kiln plans and applies the managed changes, updates dependency ranges
and validates the result. A failed upgrade restores the previous pin, files and
locks by default.

## Context

pykit Release 9 raised the floors for five packages beyond their existing
ceilings. The pin table feeds scaffolding, and repositories own their
`pyproject.toml` files ([ADR-0018](../../../adr/ADR-0018.md)). Re-rendering
managed files leaves those ranges alone, and resolving the lock can only take
versions the ranges already allow.

The earlier upgrade draft pinned and applied before invoking the command that
owned rollback. A failure between those steps could leave a new pin or a
partially applied standard. [S7.8.4](#s784-preview-and-apply-share-a-plan)
consolidates the artifact plan used by upgrade, apply and config preview.

## Design

- A thin launcher reuses pin's branch, tag, SHA and `track` resolution. It
  starts the target kiln at the resolved commit before any repository write.
  The target plans from the candidate config and uses its own templates,
  schema and floor table. Pin keeps its existing behavior.
- The shared apply path owns artifact selection, drift handling and docs
  finalization. Upgrade adds the candidate pin, range edits, setup and the
  full validation gate around it. The target's pin and state are visible to
  validation, and both are covered by rollback.
- After the clean-tree check, upgrade records the original state of the paths it
  will change, including the config, state, generated files, docs files it
  updates, dependency declarations and lockfiles used by setup. It restores
  that footprint on failure, including removing files created within it.
  Unrelated paths and ignored files are preserved. A recovery failure or
  remaining changes outside the footprint are reported explicitly.
- `FORCE=1` keeps a candidate that applied successfully but failed setup or
  validation. It still exits nonzero. It does not authorize drift overwrites
  or keep a partially applied candidate.
- Range changes are printed before writes. Release notes are best-effort
  reporting outside the transaction, with a link as fallback.

## S7.8.1 — Plan and write rn-forge range changes

**State:** Closed (2026-11-18)

**Acceptance:**

- A read-only plan lists moves in the root and member `pyproject.toml` files
  across dependencies, optional dependencies and dependency groups. A governed
  direct Git pin or range below the target floor is eligible.
- Applying those moves preserves extras, markers and unrelated TOML. It leaves
  workspace members, unrelated dependencies and requirements already at or
  above the floor alone.
- The range helpers never run setup, validation or rollback. A reusable floor
  parser supports the warning in S7.8.3.
- Tests cover range selection, exact TOML edits and changelog fallback.

## S7.8.2 — `task kiln:upgrade`

**State:** Closed (2026-11-18) · **Depends on:** S7.8.1, S7.8.4

**Acceptance:**

- `task kiln:upgrade -- <ref>` accepts a branch, tag or commit. With no ref it
  follows `track`. A branch records its resolved SHA and tracking name. A tag
  or SHA records the requested pin and clears `track`. The target kiln
  validates the candidate config before writes.
- A dirty tree, failed ref resolution, failure to load the target or a blocked
  apply plan leaves the repository unchanged. Even with zero range moves, a
  successful apply runs `task setup` and then `task validate`.
- A write, finalization, setup or validation failure restores the upgrade's
  write footprint by default. If setup was attempted, the command attempts to
  restore the old environment with `task setup` and reports any recovery
  failure. Tests cover failures after pin and state writes, after creating or
  removing managed files, and after changing a lockfile.
- `FORCE=1` follows the design above. Tests prove that unrelated files survive
  recovery and the target kiln supplies the ranges and artifacts.
- The task is public wherever `kiln:pin` is rendered. The rendered standard and
  canonical reference describe upgrade and correct the claim about
  `kiln config upgrade --apply`.

Outcome: the task runs `kiln repo-upgrade`, named apart from
`kiln self upgrade`. The launcher writes nothing and runs the target kiln with
`--target-ref`. The target restores a `cycle.Footprint` of the pin, the apply
paths, the moved manifests and the lockfiles.

## S7.8.3 — `kiln doctor` warns when a floor is below the pin table

**State:** New · **Depends on:** S7.8.1, S7.8.2

**Acceptance:**

- `rn-forge-deps` reports `deps.behind`, a warning, for each rn-forge
  requirement outside the workspace whose floor is below the pin table. It
  names the floor, the table's version and `task kiln:upgrade`. A warning does
  not fail `task lint`.
- The check-code table in `docs/reference/standard-repo.md` lists `deps.behind`.
- Tests: `tests/modules/python/checks/test_rn_forge_deps.py`.

## S7.8.4 — Preview and apply share a plan

**State:** Closed (2026-11-18) · **Depends on:** S18.6.3

Carries the apply consolidation from
[S18.10.11](../E18-kiln-simplification/F18.10-review-defects.md#s181011-every-entry-point-runs-the-same-pipeline)
into Release 1 so upgrade can reuse it.

**Acceptance:**

- A single preparation path selects and classifies artifacts against the current
  state. It accepts either the committed config or a validated candidate.
  Plain apply renders once, validates `--force` against that plan, and
  executes the same plan. Diff and dry-run use the same selection and write
  nothing.
- Config update and config upgrade preview the same artifact actions their apply
  would take, including when a starter is missing. Existing repositories keep
  the normal apply starter policy. New repositories and package generation
  retain their explicit starter policy.
- Existing-repo apply finalizes required docs regions when enabling MkDocs. The
  first apply from the `none` profile passes doctor. Finalization and
  ownership-check failures restore the files and state written by apply,
  including a candidate config written by config update or upgrade. Other
  repository quality checks still run through `task validate`.
- The ordinary apply path stays local and requires neither a clean Git tree nor
  a setup run. The clean-tree requirement and full gate belong to the upgrade
  coordinator.

Outcome: `cycle.prepare` and `cycle.execute` share one plan. `execute` snapshots
`Prepared.write_paths()` with `cycle.Footprint`, runs the ownership checks after
`state.json` is written, and restores the snapshot on any failure.

## Acceptance

Run the targeted tests from the story briefs and
`task validate KILN_DOCTOR_FULL=1`. On a real repository behind the floor table,
record a successful upgrade and a failing upgrade that restores the previous
pin, files and locks. Inspect the changes on both runs.

## Considered and rejected

- **Resolve the lock alone.** Resolution stays within the declared ranges.
- **Move dependency ranges during ordinary apply.** They are repository-owned
  inputs and changing them is an explicit upgrade.
- **Chain pin, apply and dependency migration in the task template.** Failures
  before the migration step need the same recovery as a failed validation.

## Open questions

- Should pykit mark breaking changelog entries in a fixed form, such as a
  `### Breaking` heading, so that kiln can flag them by rule instead of
  printing every section?
- Is an API diff with `griffe`, checked against the repository's imports, worth
  a dependency? It would warn before validation runs.
