# ADR-0014 — A library workspace's CI is planned by rn-forge-devops, and its own members are exempt from the rn-forge dependency contract

**Status:** accepted (2026-10-14) · **Scope:** `python-lib` repositories, and
the `rn-forge-deps` check in every Python repository

## Decision

The workspace pipeline that pykit built (change-scoped verify, declared jobs,
ordered release, external install) is rendered by kiln for `python-lib`. Its
planner is pykit's `rn-forge-devops` package
([pykit ADR-0012](https://github.com/rn-forge/pykit/blob/main/docs/adr/ADR-0012.md)),
invoked only as the console script `rn-forge-devops <command>`, never a module
path. pykit owns and releases it. kiln's `tasks/ci.yml` runs the version pinned
in kiln's pin table as
`uvx --from <PYKIT_GIT>@<tag>#subdirectory=packages/rn-forge-devops rn-forge-devops …`.
In a repository whose own uv workspace has a member named `rn-forge-devops`
(pykit), the tasks run `uv run rn-forge-devops …` instead, so its CI tests the
planner it ships — decided by membership, the same rule as the exemption below.
`rn-forge-devops` is a CI tool, not a dependency: it is in no archetype's
required or allowed list. kiln's generated workflow reaches it only through
`task`, as internal `ci:*` tasks in a `tasks/ci.yml` that only the `python-lib`
cell renders: `ci:plan`, `ci:verify`, `ci:postgres`, `ci:smoke`, `ci:suite`,
`ci:release` and `ci:external-install`. They are internal tasks, not root verbs,
so the task vocabulary does not change ([ADR-0007](ADR-0007.md)).

`sonar-project.properties` stays kiln's. It lists sources and tests from
`[python] packages`, as it does today, and `doctor` checks it. CI does not pass
them.

The rn-forge dependency contract
([the reference, §3](../reference/standard-repo.md)) governs dependencies on
rn-forge packages from **outside** the repository. A dependency on a member of
the repository's own uv workspace is outside the archetype's allowed set, and
may add a `{ workspace = true }` source for local development. In `[project]`
dependencies it keeps its pinned direct URL, because that is what a consumer of
the wheel resolves. A dependency group, which never reaches a wheel, may name it
bare. This is how pykit already declares its members.

A `python-lib` repository may set `import_contracts = "own"`. kiln then renders
only the `.importlinter` root packages, and the contracts the repository writes
below the block's END marker are its import boundary. The default, `"kiln"`,
keeps kiln's two contracts.

## Consequences

- pykit can adopt kiln without losing its pipeline. Before this, a `kiln apply`
  would have replaced it with a single validate job.
- A planner fix reaches every library workspace through a devops tag and a kiln
  pin bump. No generated file changes.
- kiln gains an upstream pin: pykit publishes the planner as `rn-forge-devops`;
  met 2026-10-16 with `rn-forge-devops-v0.1.0`.
- Every repo running `task ci:*` needs uv, which generated CI already installs
  ([ADR-0006](ADR-0006.md)).
- A member's release must follow its siblings' tags, because its declared URL
  names them. pykit's ordered release already does this.
- The exemption is decided by membership, not by name. A repository named
  `demo-pkg` with a member called `rn-forge-commons` is a workspace member; a
  repository that depends on pykit's `rn-forge-commons` is not.

## Alternatives considered

- **A module of `rn-forge-tooling` (`rn_forge.tooling.workspace_ci`).** The
  decision of 2026-10-14. Rejected on 2026-10-15: tooling depends on commons,
  so every commons release would drag the planner's audience (CI runners of
  any language) along; pykit's ADR-0012.
- **A `kiln ci plan` command.** It breaks E4's rule that a module is
  `artifacts()` and `checks()` and nothing else, and it couples every CI run
  to kiln's release line rather than the library's.
- **A seeded `.github/scripts/workspace_ci.py`.** Seeded files are never
  updated, so a planner fix would never reach a repository.
- **A generated `.github/scripts/workspace_ci.py`.** kiln would own pykit's
  code, and a fix would need a regeneration commit in each repository.
- **CI passes Sonar sources and tests (pykit's handoff).** Two owners for one
  list. kiln already derives it from `[python] packages`.
- **Keep rejecting `[tool.uv.sources]` for every rn-forge name.** A library
  workspace cannot wire its own members any other way, so pykit could never
  pass `rn-forge-deps`.
- **Exempt members from the direct-URL rule too.** The wheel would then carry a
  bare `Requires-Dist`, which a consumer outside the workspace cannot resolve:
  rn-forge packages are not on an index.
