Phase step: D.7

kiln's own `.importlinter` already holds two contracts and `task lint` runs
`lint-imports` (`tasks/quality.yml`, `lint:imports`). `no-kit-imports` forbids
`typer`, `jinja2`, `click`, `django` and `fastapi` anywhere in `rn_forge.kiln`;
`render-free-checks` forbids `jinja2` in the checks packages
([ADR-0006](../../../adr/ADR-0006.md)). The rn-forge half of the boundary — no
`rn_forge.django`, `rn_forge.fastapi`, `rn_forge.web` — cannot be an
import-linter contract, because import-linter rejects subpackages of external
packages; `kiln doctor`'s rn-forge-deps rule enforces it at the dependency
declaration ([ADR-0005](../../../adr/ADR-0005.md)), and
`tests/test_checks_are_render_free.py` enforces the
`rn_forge.tooling.generation` half of the render-free rule. This feature closes
the two gaps that remain, and settles where a repo's own contracts live once
kiln regenerates its own skeleton.

## S4.7.1 — kiln's contracts

**State:** New

Two gaps. `rn_forge.kiln.modules.instructions.checks` exists but is not a source
module of `render-free-checks`, so nothing stops it importing Jinja. And no
contract keeps a concern module off its siblings: each may import `core` and
kiln's composition layer, not another concern module. Four direct sibling
imports already exist, and this story allows exactly those four:

- `rn_forge.kiln.modules.tasks.artifacts` → `rn_forge.kiln.modules.docs.config`
  (`DocsConfig`)
- `rn_forge.kiln.modules.tasks.artifacts` →
  `rn_forge.kiln.modules.python.artifacts` (`root_package`)
- `rn_forge.kiln.modules.instructions.artifacts` →
  `rn_forge.kiln.modules.cicd.config` (`CiConfig`)
- `rn_forge.kiln.modules.instructions.artifacts` →
  `rn_forge.kiln.modules.docs.config` (`DocsConfig`)

Every module also reaches every other one indirectly, through the composition
layer: each imports `rn_forge.kiln.config`, which imports every module's config,
and `rn_forge.kiln.modules.registry` imports every module. Those paths are not
sibling dependencies, so the contract ignores the composer's edges into the
modules. Without that, the contract breaks on every pair (checked 2026-10-13,
import-linter 2.15).

## S4.7.2 — A repo's own contracts survive `kiln apply` (owner decision)

**State:** New · Must close before [F4.8](F4.8-self-hosting.md)

The `python` module renders `.importlinter` as a whole-file `managed` artifact
from `importlinter.j2`. That template holds only the generic
`frameworks-come-from-rn-forge` contract, plus `packages-are-independent` for a
workspace. When F4.8 runs `kiln apply --force` on kiln itself, it replaces the
hand-authored file. That drops `render-free-checks` and
`concern-modules-are-independent`, and F4.8's acceptance still passes because
`lint-imports` keeps whatever contracts are left. Any generated repo that wants
a contract of its own has the same problem.

The owner picks one. The build is written as its own story once the choice is
recorded here.

- **Recommended: `.importlinter` becomes a `block` artifact.** It uses
  `ManagedBlock("rn-forge kiln")`, the same `#` markers as `.gitignore`;
  `configparser` reads `#` lines as comments. kiln's block holds
  `[importlinter]` and the generic contracts, and the repo adds its own
  `[importlinter:contract:…]` sections below the end marker. The cost: every
  golden's `.importlinter` and its `state.json` entry change, and an existing
  repo whose `.importlinter` has no markers needs a defined first apply.
- **A config key listing extra contracts.** Rejected: a schema addition with one
  consumer.
- **A second, repo-owned config run by a second task.** Rejected: `lint-imports`
  reads one config per run, and the generated `lint:imports` task would change
  for every repo.

**Acceptance:**

- The choice and the reason are recorded on this story, and the build story it
  implies is written with a Build list.
