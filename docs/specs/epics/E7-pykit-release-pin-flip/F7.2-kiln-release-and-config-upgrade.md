E7's scope items 1 and 3: tag an `rn-forge-kiln` release, then each repository
moves its kiln pin with `task kiln:pin -- <ref>`
([S7.2.5](#s725-task-kilnpin-moves-a-repository-to-another-kiln-ref),
[ADR-0006](../../../adr/ADR-0006.md)) and runs `kiln config upgrade --apply`.
Added 2026-10-17 by S6.1.14, so that E7's `Active` state has a feature to agree
with.

Since [F7.4](F7.4-kiln-runs-beside-the-repository.md), a repository's kiln pin
is `[kiln] ref` in `.rn-forge/kiln/config.toml`, not a dev dependency. "Moving
the pin" therefore means:

1. set that ref to the new tag;
1. run `kiln apply` **from the new ref**, which re-renders the `KILN` var in
   `tasks/kiln.yml` and `tasks/docs.yml`.

Step 2 is the catch S7.2.5 closes. Running `task kiln:apply` after editing the
ref by hand runs the *old* kiln, because `KILN` still names the old ref. The old
templates render and only `KILN` moves, and a second apply is needed to get the
new render.

The cut also sets `archetypes.KILN_REF` from `feature/v1` to `v<version>`, so
`kiln new` pins the release.

## Context

**The version (owner decision, 2026-10-31).** The tag is `v0.1.0`, the version
in `pyproject.toml`. "Release 1" names the scope and is not a version number.

**Distribution.** kiln stays on git, through `uvx --from git+…@<ref>`.
Publishing it to PyPI stays the idea `kiln-on-pypi`.

**Repository-owned cleanup.** The 2026-11-03 rehearsal's finding #13 was stale
comments in pykit's `.importlinter`. This is pykit's cutover cleanup, with no
kiln implementation required.

**Order matters.** `KILN_REF` names a tag that does not exist until the commit
that names it reaches `main` and `release` runs, so that commit is the last one
before the merge. Nothing renders from it before the tag exists.

## S7.2.5 — `task kiln:pin` moves a repository to another kiln ref

**State:** New

One verb moves a repository's kiln pin to any ref (a tag, a branch or a SHA,
higher or lower) and re-renders with the kiln at that ref, so the move is one
command and one reviewable diff. It is named `pin`, not `upgrade`, because the
move can go in either direction; the docs already say kiln is *pinned* by
`[kiln] ref` (owner decision, 2026-11-13).

**Build — tests first:**

- `tests/test_pin.py`: the `kiln pin` command, against a scaffolded repository.
- `tests/modules/tasks/test_artifacts.py`: the rendered task.

**Build:**

- `commands.py`: `pin(ref: str) -> None`, registered in `cli.toml` as `pin`. It
  reads the committed config with `ConfigManager`, sets `[kiln] ref` to *ref*,
  writes it with `_write_config`, and prints `kiln ref <old> → <new>`. It
  writes nothing else and does not apply. An empty or whitespace *ref* raises
  `AppException`. It does not check that the ref exists; the task does.

- `modules/tasks/templates/tasks/kiln.yml.j2`: a public `pin` task, reached as
  `kiln:pin`. A `precondition` fails with `pass a kiln ref after --` when
  `CLI_ARGS` is empty. Its `desc:` is "Move kiln to another ref (tag, branch
  or SHA) and re-render with it. Pass the ref after `--`." Its commands, in
  order:

    1. `kiln_command(<ref>)` with `version`, so a ref that does not resolve fails
       before anything is written;
    1. `{{.KILN}} pin <ref>`, the current kiln writing the ref;
    1. `kiln_command(<ref>)` with `apply`, the new kiln rendering.

    `<ref>` is `{{.CLI_ARGS}}`. The `kiln_command` prefix needs a new context key,
    `kiln_git` (`archetypes.KILN_GIT`), so the template builds the `uvx --from`
    string for a ref known only at run time.

- Not rendered in kiln's own repository (`config.module == "rn_forge.kiln"`),
  which runs its working tree.

- `docs/adr/ADR-0007.md`: the developer surface gains `kiln:pin`, with a dated
  line under `## Background`.

- `docs/adr/ADR-0006.md`, *Consequences*: "a one-line `config.toml` change
  followed by `kiln apply`" becomes `task kiln:pin -- <ref>`, with a dated
  line.

- `modules/instructions/templates/standard.md.j2` and the tasks architecture
  page: how to move the pin. The standard's task table picks up the task from
  the rendered file.

- The goldens are re-seeded.

**Not in scope.** If the target kiln wants another `schema_version`, step 3
fails with the existing message that names `kiln config-upgrade`, and the
developer runs it from the new ref. Moving to a ref older than the config's
schema fails the same way. Neither is automated. A ref from before this story
renders no `kiln:pin` and has no `kiln pin`, so the way back from it is the hand
edit and two applies described above.

**Acceptance:**

- `test_s7_2_5_1_writes_only_the_ref`: `kiln pin v9.9.9` changes only
  `[kiln] ref` in `config.toml` and no generated file.
- `test_s7_2_5_2_empty_ref`: `kiln pin ""` exits non-zero and writes nothing.
- `test_s7_2_5_3_task_order`: a rendered `tasks/kiln.yml` has a public `pin`
  task whose commands are `version`, `pin` and `apply`, in that order. The
  first and last run
  `uvx --from "rn-forge-kiln @ git+https://github.com/rn-forge/kiln@{{.CLI_ARGS}}"`,
  and the second runs `{{.KILN}}`.
- `test_s7_2_5_4_precondition`: the task has the empty-`CLI_ARGS` precondition.
- `test_s7_2_5_5_not_in_kiln`: kiln's own render has no `pin` task.
- `task validate` and `task self:golden:validate` pass.
- Not scriptable, judged by the owner: on pykit, `task kiln:pin -- feature/v1`
  is a no-op diff, and `task kiln:pin -- <an older SHA>` leaves `KILN` and
  every generated file as that SHA renders them, after a single run.
