A developer can run the workspace's coverage tests and scan the checked-out
branch on SonarCloud, awaiting the quality gate, before pushing: one `task`
verb, backed by a `kiln-devops` subcommand. Today only pykit can, with its own
`.github/scripts/sonar_local.py`, which kiln neither renders nor tests.

## Context

pykit's script reads the planner's `cov-args`, `test-paths`, `sonar-sources` and
`sonar-tests`, runs `pytest` with them, then runs `sonar-scanner` with the
branch name and `-Dsonar.qualitygate.wait=true`. It prints the target and the
commands under `--dry-run`, refuses `main` and a `--branch` that differs from
the checked-out branch, strips `CI` and `GITHUB_*` from the scanner's
environment, needs `SONAR_TOKEN` and `sonar-scanner` on `PATH`, and exits with
the gate's status. Its tests mock the subprocess calls.

Those four plan outputs are forwarded by the generated `ci.yml` plan job but
read by no job: the scan job takes its sources from `sonar-project.properties`
([kiln-devops reference](../../../reference/kiln-devops.md)). `sonar` is read by
nothing. Their only reader is pykit's script, so kiln emits them for a consumer
it does not own. This feature gives them a reader of kiln's, or removes them;
S6.10.1 decides which.

SonarCloud's plan may refuse to read a non-`main` branch's data, so awaiting a
branch's gate can fail even when the scan uploads. The verb passes the scanner's
failure through and says so in its guide; it does not work around the plan.

The scan is not CI evidence: it uploads the working tree, which may differ from
every commit.

pykit retires its script once it adopts the kiln release that carries this. That
is pykit's work and does not gate this feature.

## S6.10.1 — Decide the verb's name, and where its scope comes from

**State:** Closed (2026-11-13)

Choose, by comparing the options, and record the result on this feature under
*Considered and rejected*:

- **Name.** `task sonar:local` is proposed. It adds a developer-surface task, so
  it needs [ADR-0007](../../../adr/ADR-0007.md)'s vocabulary amended, and a
  namespace that is not under `ci:`.
- **Scope.** Either the subcommand reads `cov-args`, `test-paths`,
  `sonar-sources` and `sonar-tests` from the plan, which keeps them, or it
  computes its scope itself, or runs `task test:coverage` and takes the
  sources from `sonar-project.properties`, which lets the four outputs and
  `sonar` be retired from `plan()`, `_PLAN_KEYS` and the reference.

**Acceptance:**

- The decision is written on the feature, with the options rejected, and the
  open question below is removed.
- If the vocabulary changes, ADR-0007 carries the amendment.

**Decided (owner, 2026-11-13).** The verb is `task sonar:local`, rendered only
when Sonar is on, and ADR-0007's developer surface names it. The subcommand
takes no scope from the plan: it runs `task test:coverage` (the root verb, which
already writes `coverage.xml` for Sonar), and the scanner reads its sources,
tests and report path from `sonar-project.properties`, as the CI scan does. So
`cov-args`, `test-paths`, `sonar-sources`, `sonar-tests` and `sonar` are retired
from `plan()`, `_PLAN_KEYS`, the generated `ci.yml` and the kiln-devops
reference, in S6.10.3 (which re-seeds the goldens anyway). pykit's
`sonar_local.py` reads them; it retires with them when pykit adopts the release
that carries this.

## S6.10.2 — `kiln-devops sonar-local` scans the checked-out branch

**State:** New · **Depends on:** S6.10.1

A `sonar-local` subcommand, in `devops/` beside `sonar-target`:

- `--dry-run` prints the target branch and the coverage and scanner commands,
  and runs nothing, needing no token or scanner.
- The target is the checked-out branch. `--branch` must equal it, or name the
  branch on a detached HEAD. `main` is refused. An uncommitted tree is
  scanned, with a note that the scan is not CI evidence.
- Without `--dry-run` it checks `SONAR_TOKEN` and `sonar-scanner` first, runs
  the coverage tests (`task test:coverage`, S6.10.1), stops on their failure,
  then runs the scanner with `-Dsonar.qualitygate.wait=true` and the branch
  name, with `CI` and `GITHUB_*` removed from its environment, and exits with
  the scanner's status. The token is never in the arguments or the output.
- A usage error exits `2`, as the other subcommands do.

**Acceptance:**

- `tests/devops/test_sonar_local.py` covers each rule above with the subprocess
  calls faked: dry run, missing token, missing scanner, `main`, detached HEAD,
  mismatched `--branch`, dirty tree, scrubbed environment, token absent from
  output, failing tests stop before the scan, and the scanner's status
  propagates.
- `uv run pytest tests/devops` passes.

## S6.10.3 — Sonar-on repositories render the verb, and the docs say how to use it

**State:** New · **Depends on:** S6.10.2

The tasks module renders the verb, calling `{{.DEVOPS}} sonar-local`, only when
Sonar is on, with a `desc:` that names the prerequisites. The kiln-devops
reference, the standard's task tables (derived from the rendered files), the
tasks architecture page and the development guide document it: `SONAR_TOKEN`,
`sonar-scanner` on `PATH` with no dependency added, `--dry-run`, the plan
restriction above, and that an uncommitted scan is not CI evidence. The plan
outputs S6.10.1 retires (`cov-args`, `test-paths`, `sonar-sources`,
`sonar-tests`, `sonar`) leave `plan()` in `devops/ci.py`, `_PLAN_KEYS` in
`modules/cicd/artifacts.py`, the rendered `ci.yml` plan job's outputs and the
reference's outputs table, with their tests.

**Acceptance:**

- A cell with Sonar on renders the task and one with Sonar off does not; the
  golden compare shows no other change.
- `task kiln:apply` here leaves `task lint KILN_DOCTOR_FULL=1` passing, and
  `task docs:build` passes.
- `task sonar:local -- --dry-run` in kiln prints the target and both commands.

## Acceptance

```bash
set -euo pipefail
cd rn-forge/kiln
uv run pytest -q tests/devops tests/modules/tasks tests/modules/cicd   # S6.10.2, S6.10.3
task sonar:local -- --dry-run                                          # S6.10.3
task validate
task self:golden:validate
```

Not scriptable: a full scan with a real `SONAR_TOKEN` (S6.10.2).

## Considered and rejected

- **Read the four plan outputs** (as pykit's script does). It keeps five outputs
  alive for one local reader and a second way to compute coverage scope, which
  can drift from `task test:coverage` and `sonar-project.properties`, the two
  things CI actually uses.
- **Compute the scope inside the subcommand.** The same drift, in new code.
- **A name under `ci:`.** The verb is run by a developer, never by a workflow;
  `ci:` is the CI surface ([ADR-0007](../../../adr/ADR-0007.md)).
