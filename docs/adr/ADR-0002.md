# ADR-0002 — Build on the rn-forge platform; keep repository policy in kiln

**Status:** accepted (2026-09-15) · **Scope:** the rn-forge workspace — every
product in it, kiln included

## Decision

An rn-forge product consumes shared mechanisms from pykit's library APIs rather
than reimplementing them: `rn-forge-commons` for runtime-neutral Python, data,
filesystem and integration protocols and the console; `rn-forge-cli` for the
Typer layer, the declared command surface and the error-to-exit-code mapping;
`rn-forge-tooling` for local state, the template engine and the generation
engine.

A product never imports a peer product. Reuse travels through libraries.

Repository policy — archetypes, managed artifacts and their checks — lives in
kiln. Pykit owns its own package layout, internal dependency graph and library
APIs; kiln records the contracts it consumes, not how pykit implements them.

Every Python repository in the fleet uses the same toolchain: **uv** for
packaging and resolution, **task** as the only entrypoint, **ruff** for
formatting and linting, **pyright in strict mode at zero errors** for types,
**pytest** for tests, **import-linter** for internal boundaries, and **MkDocs**
for the documentation site. mypy is not configured, not installed and not a
permitted alternative; a repository that wants it needs its own decision record.

Declared dependencies and Python imports are two boundaries. Each has its own
executable check.

## Consequences

- A library upgrade can force product changes. Duplicating the library is not
  the fallback.
- One type checker, one configuration shape and one failure format across the
  fleet. Strict mode makes untyped third-party libraries visible where they
  enter, which is the intended pressure: the value is typed once at the
  boundary rather than by lowering the gate.
- Published packages carry `py.typed`; strict checking inside a repository says
  nothing to a consumer installing the wheel.
- Peer tools stay independently implemented products. A shared need becomes a
  library, never a cross-import.
- Policy changes belong in kiln; mechanism changes belong in the library that
  provides the mechanism.

## Alternatives considered

- **Copy shared mechanisms into each product.** Two kits already did: each built
  its own Typer app factory, its own `--json` / `--dry-run` / `--yes` set, its
  own console wrapper and its own error-to-exit-code map, then drifted to
  `typer>=0.26.8` and `typer>=0.12`, and both grew a
  `core/{state,config,paths,io}.py` over the same ground.
- **Import peer tools.** Their commands and policy become the importer's
  implementation API, and a fix in one becomes a release in all.
- **Put kiln's rules into the shared libraries.** Every consumer then inherits
  repository policy it did not request.
- **mypy**, as several original specs named. Diverges from what every repository
  actually runs, for no gain in these codebases.
- **pyright at `basic`.** Would have accepted the 84 errors strict found in the
  first repository converted — and those errors are exactly where the untyped
  libraries (`tomlkit`, `ruamel.yaml`, Jinja) enter, which is where the types
  are worth having.
- **Both checkers.** Two type checkers disagreeing is a standing tax on every
  repository.

## Background

The toolchain was a fleet decision in practice long before it was written down:
no repository in `rn-forge` or `rn-tools` runs mypy, and every Python template
already generated a `pyright` task. It was promoted from a donor kit's own
record on 2026-09-15, because a standard that lives only in the repositories
already following it is not a standard.

The library seam moved once, after the Phase C review: the Typer helpers to
`rn-forge-cli`, and `StateStore`, `TemplateEngine` and the generation engine to
`rn-forge-tooling`. A later pass moved `AppConsole` on to `rn-forge-commons` —
console output is a property of the process, Rich was already a commons
dependency for the log handler, and the framework packages are forbidden from
importing `rn_forge.cli`, so a console living there was unreachable from the
packages that wanted one.
