A repository owned outside `rn-forge` gets a SonarCloud organisation and project
key from its own config. After `[repository] owner` changes in `config.toml`,
`kiln apply` records the new owner in `state.json`.

## Context

apollo moved from `rn-tools` to `rn-apps` on 2026-11-15, and agentkit lives
under `rn-tools`. Both found two defects:

- `SONAR_ORGANIZATION = "rn-forge"` in
  `src/rn_forge/kiln/modules/cicd/artifacts.py` and the literal `rn-forge_`
  prefix in `sonar-project.properties.j2` render `sonar.organization=rn-forge`
  and `sonar.projectKey=rn-forge_<name>` for every repository. A SonarCloud
  organisation is bound to one GitHub organisation, so a repository owned
  elsewhere cannot analyse.
- `kiln new` records its flags as the `flags` layer in `state.json`
  `metadata.config_provenance`. A later `kiln apply` copies that metadata
  forward unchanged, so after `owner` is edited, every rendered file shows the
  new owner and `state.json` still shows the old one, under `flags`.
  `kiln config-update` then treats the edit as a repository override, which is
  right, but nothing else records it.

## Design

- **The organisation is config.** `[ci] sonar_organization` names the SonarCloud
  organisation. When it is unset, the organisation is `[repository] owner`.
  The project key is `<organisation>_<name>`, SonarCloud's own default for a
  GitHub import. Repositories owned by `rn-forge` render the same bytes as
  before.
- **apply records what the config says.** On every apply that writes state, a
  provenance entry whose recorded value differs from the committed value is
  re-recorded as the `repo` layer with the committed value. This is the same
  rule `reresolve` already uses to find an override, applied when the state is
  written. Keys with no entry are left alone, as today.

## S16.11.1 — The Sonar organisation and project key come from the config

**State:** Closed (2026-11-19) · **Depends on:** —

**Acceptance:**

- `CiConfig` gains `sonar_organization: str | None = None`, documented in its
  docstring, the config schema and the `[ci]` block of
  `docs/reference/standard-repo.md`. An empty string is refused.
- `SONAR_ORGANIZATION` is removed. `cicd/artifacts.py` passes the resolved
  organisation, `ci.sonar_organization` or else `repository.owner`, to the
  template. `sonar-project.properties.j2` renders
  `sonar.projectKey=[[ organization ]]_[[ name ]]`.
- Tests, written first:
    - a repository with `owner = "rn-apps"` and no `sonar_organization` renders
      `sonar.organization=rn-apps` and `sonar.projectKey=rn-apps_<name>`;
    - `sonar_organization = "acme"` overrides the owner in both lines;
    - an `rn-forge` repository's `sonar-project.properties` is byte-identical to
      before. The goldens do not change.
- `task kiln:apply` on this repository changes nothing, and
  `task lint KILN_DOCTOR_FULL=1` passes.

Outcome: an empty or whitespace-only `sonar_organization` is refused, and the
six golden cells are unchanged.

## S16.11.2 — `kiln apply` records an edited key's new value and layer

**State:** Closed (2026-11-19) · **Depends on:** —

**Acceptance:**

- Wherever apply writes `state.json` (the `cycle.prepare` and `execute` path)
  without a fresh `provenance` from its caller, it rewrites each
  carried-forward `metadata.config_provenance` entry whose `value` differs
  from the committed config to
  `{"layer": "repo", "value": <committed value>}`. Entries that match, and
  callers that pass `provenance` (`kiln new`, `config-update`,
  `config-upgrade`), behave as today.
- Tests, written first:
    - render a repository with `owner = "rn-tools"` as a flag, edit `config.toml`
      to `owner = "rn-apps"`, apply: `state.json` records `repository.owner` as
      `{"layer": "repo", "value": "rn-apps"}`;
    - a second apply with no config change leaves `state.json` byte-identical;
    - an untouched flag key keeps its `flags` layer;
    - after the edit and apply, `kiln config-update --dry-run` still lists
      `repository.owner` as an override.
- `task kiln:apply` on this repository changes only `state.json`'s provenance,
  and `task lint KILN_DOCTOR_FULL=1` passes.

Outcome: kiln's own `state.json` had stale recorded values for `cli.commands`
and `ci.jobs`, both already under `repo`. The first apply refreshed them.

## Acceptance

Run the stories' tests and `task validate KILN_DOCTOR_FULL=1`. Then, on apollo
(`rn-apps`), after it pins the kiln that carries both stories, run
`task kiln:upgrade`. `sonar-project.properties` names `rn-apps`, and
`state.json` records `repository.owner = "rn-apps"`.

## Considered and rejected

- **Derive the organisation from the owner only, with no key.** A SonarCloud
  organisation key can differ from its GitHub organisation, so the key is
  needed. The default covers the usual case.
- **Re-resolve the whole config on every apply.** That is `config-update`'s job.
  It fetches `[source]` and can change values. apply only records what is
  already committed.
