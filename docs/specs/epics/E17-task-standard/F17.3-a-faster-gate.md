`task validate` is the gate every story, every cutover and every pull request
runs, and it has become slow enough to be skipped. Measured at `dacff72` on a
10-core machine:

| What | Time | Why |
| -- | -- | -- |
| `task test` | 154 s for 2508 tests | one process, one of ten cores |
| `kiln:doctor` | 22.7 s | the docs checks parse the same Markdown page again and again (S17.3.3) |
| `quality:lint:markdown`, `quality:format:markdown` | 11 to 14 s each | one mdformat process over 171 files |
| the rest of `task lint` | about 5 s |  |
| slowest tests | 12.5 s, 12.1 s, 9.3 s | the two Nx workspace builds, and the docs-policy test (it is the doctor's docs check) |

The feature spends the time in this order: the doctor first (it is also the
slowest test and runs in every later story's `task lint`), then parallel tests,
then the shared Nx build that parallel tests would otherwise repeat, then
parallel mdformat, then a separator in `task validate`'s output, then the board
rule that keeps acceptance scripts out of the specs. **Build order is S17.3.3,
S17.3.1, S17.3.2, S17.3.4, S17.3.5, S17.3.6.** Every story leaves
`task validate` and `task lint KILN_DOCTOR_FULL=1` green on its own; a story
that changes a template runs `task kiln:apply` here in the same story, so none
of them leaves this repository stale (`AGENTS.md`, Guardrails).

Read [the board's "Building a story"](../../index.md#building-a-story) first.
For every story: tests first, named after the story ID and shown failing; only
`task` verbs (never `uv`, `pytest`, `ruff` or `kiln`); commit nothing. When the
story is built, paste the tail of `task validate` into its *What the build
settled* block.

## Design

**Where `-n auto` goes (S17.3.1).** The repository's `pyproject.toml` is
repository-owned: it has no entry in `.rn-forge/kiln/state.json`, so
[ADR-0003](../../../adr/ADR-0003.md) leaves it to the repository.
`tasks/python.yml` is kiln's (its first line says so), and its `test` task is
`uv run pytest -q`. The flag therefore goes in
`[tool.pytest.ini_options] addopts`, and the generated test task does not
change. That scopes it to this repository. It is not a template change for
`python-app`, `python-tool` and `python-lib`: a `python-lib` runs one `pytest`
per package from the package directory, and a new repository's suite is a
handful of tests, where starting workers costs more than it saves. Whether the
template should carry `-n auto` for archetypes whose suites are large is a
question for after this repository has run with it; it is not decided here.

**Why the shared Nx build is per run, not per worker (S17.3.2).** The owner's
brief says each of the two 12-second tests builds its own Nx workspace. They do
not: `rendered` in `tests/conftest.py` is already session-scoped and builds each
archetype once, so the 12 s are charged to whichever test asks first. Under
xdist, though, a session fixture is built once per worker, so ten workers would
each run `pnpm` and Nx for `node-lib` and for `python-web-app`, twenty heavy
builds at once. S17.3.2 makes the two Nx archetypes build once per run across
all workers.

**Doctor (S17.3.3).** The profile, taken with `cProfile` around `kiln doctor .`
(70 s profiled, 22.7 s unprofiled), puts 97 percent of the time in `markdown_it`
parsing: 2639 parses, 1820 of them `MarkdownUtils.headings` (from `anchors`) and
632 `MarkdownUtils.links`, for 215 distinct page texts. The cause is
`structure._check_links` and `site.check_links` (the same link check, run by two
doctor checks) calling `MarkdownUtils.anchors(target page)` once for every link
that has an anchor, so a page that many stories link to, such as a feature page,
is parsed again for each link. `docs/generate.stale` and `work.load_work` parse
every page again. The simplest fix is a cache keyed by the page text: no page is
parsed twice, and nothing has to be threaded through the checks. Verified with a
throwaway script that wrapped `MarkdownUtils.headings` and `.links` in
`functools.lru_cache` before calling the doctor: 22.7 s became 3.8 s (215 and
169 misses; 1605 and 463 hits), with the same findings. The remaining 3.8 s is
start-up, YAML and the other checks.

**Group output was measured and rejected (S17.3.5).** go-task 3.54's
`output: group` wraps each *command's* output, not each task's: with a task of
two commands, `begin` and `end` print twice. go-task's own `task: [x] cmd` line
stays outside the group. The setting is global: a top-level `output:` or
`--output`; the `TASK_OUTPUT` environment variable has no effect, and no task
can opt out. Group mode buffers a command until it exits, so `uv run pytest -q`
(about 30 s once S17.3.1 is built) prints nothing until it ends,
`task docs:serve` never prints at all, and a hung doctor shows no sign of life.
Not acceptable for `test`, and a global switch cannot exclude it. `{{now}}` is
not used: it renders once for both templates, so it gives no duration. The
decision is the `interleaved` default plus a one-line banner printed between the
steps of `validate`. The banner is the same on a developer machine and under
GitHub Actions: a `::group::` pair needs group mode to be closed, and the CI
workflows run `task ci:*` steps that GitHub already folds per step.
`ci:validate` is not changed.

## S17.3.4 — mdformat runs in parallel batches

**State:** New · **Depends on:** —

A template change: `quality.yml.j2` renders the Markdown lint and format tasks
for every archetype. It uses `xargs -0 -r -n 20 -P 4`:

- `-P 4`: four processes. It is the core count of a GitHub-hosted runner and
  well under a developer machine's; a literal keeps the rendered file the same
  on every machine (`nproc` does not exist on macOS, and the golden compare
  needs one output).
- `-n 20`: twenty files per process. Each batch pays about 0.5 s to start
  `uv run` and import mdformat's plugins, against about 0.07 s per file, so a
  batch of twenty spends under a third of its time on start-up, and today's
  171 files make nine batches, enough to keep four slots busy.
- `-P`, `-n`, `-0` and `-r` are accepted by macOS (BSD) `xargs` and by GNU
  `xargs`. (BSD takes `-r` as a no-op because it never runs on empty input;
  the task already used it.) `xargs` exits 123 if any batch fails, which fails
  the task, so `--check` still fails the gate.
- Only the Markdown tasks change: `taplo` has few files and is fast.

## Considered and rejected

- **`output: group` in the root Taskfile.** Buffers `pytest`, hides
  `docs:serve`, wraps per command rather than per task, and cannot be scoped.
  See [Design](#design).
- **`-n auto` in the generated `test` task.** It would change every Python
  archetype's rendered file for a measured gain on one repository.
- **`pytest-xdist` `--dist loadfile`.** `tests/modules/cicd/test_artifacts.py`
  and `tests/modules/tasks/test_artifacts.py` hold 428 test functions between
  them (more once parametrized), so two workers would carry them and the run
  would end when they do.
- **A timestamp in the banner.** `{{now}}` renders once, so it shows no
  duration.
