Existing web applications of several flavours are expected to move onto kiln.
They are rebuilt: `kiln new` renders the target repository, the old repository's
source, tests, configuration and docs are ported into it, and the result lands
as a branch on the **old** repository. kiln's part is a read-only inventory that
is the same for every flavour, and the cutover runbook. The porting itself,
scripts included, is the agent's, following the runbook. The owner named the
first application on 2026-10-21: apollo, ported to the
`python-web-app --backend fastapi --frontend angular` cell (S16.5.3, formerly
S6.5.3 and kiln's S5.3.4). It is ported by hand from its own build plan, and
what it teaches is what S16.5.1 is written from.

The route is the cutover runbook, not the adopt prompt, which holds judgement
only.

## Design

- **One route, one runbook.** The cutover runbook
  ([S16.3.1](F16.3-cutover-sop.md#s1631-the-runbook-exists), rewritten by
  [S16.8.2](F16.8-retire-kiln-init.md)) is the rebuild and port: a reference
  from `kiln new`, brought onto a branch of the existing repository and
  reviewed as one diff. The `adopt` prompt carries only the judgement.
- **The port's direction keeps the history.** The new repository is built in a
  staging directory and ported into, and its tree then replaces the old
  repository's on a branch. The old repository keeps its history, tags,
  issues, pull requests, remote and deployments; nothing is pushed to a new
  remote.
- **kiln owns only what is the same for every flavour.** kiln knows, for the
  target archetype, which file is managed, seeded, a block or
  repository-owned. Classifying the old repository's files against that is
  deterministic and reusable; mapping one flavour's layout, settings, routes
  and build onto kiln's is not, and is the prompt's.
- **A step becomes kiln code only when two ports repeat it.** The first port
  teaches the prompt; the second shows what is worth automating.

## Considered and rejected

- **A `kiln adopt --path <old repo>` command that brings everything in.** Each
  old repository is ported once, so code that maps one flavour onto kiln runs
  once and is maintained against every later kiln change; a command also makes
  kiln answerable for a port it cannot judge. Rejected 2026-10-16. kiln
  migrating application source stays outside its
  [scope](../E4-generator/design.md#scope-and-ownership).
- **Porting into the new repository's history.** It loses the old repository's
  history, tags and remote. Rejected 2026-10-16.

## S16.5.6 — A web API member has no console script

**State:** Closed (2026-11-16) · **Depends on:** —

**Why.** `_uv_init` (`src/rn_forge/kiln/modules/python/scaffold.py:409-441`)
runs `uv init --package` for a web archetype's API member. uv then writes two
things:

- a `main()` stub into `src/<module>/__init__.py`;
- `[project.scripts] <name>-api = "<module>:main"`.

kiln then empties `__init__.py`. The comment says the starter's `main:app`
script never uses that stub. That holds for `python-tool` and `python-app`,
because `_reconcile_pyproject` (`:386-391`) rewrites their scripts. Nothing
rewrites the web member's, so a fresh `python-web-api` or `python-web-app`
declares a console script whose target does not exist. `uv sync` installs it,
and running it fails with `ImportError`.

**Design.** The API member gets no console script. `task api:dev` already serves
it (`uvicorn <module>.app:app`), and a served entry point is the application's
decision, so it stays repo-owned. In `_reconcile_pyproject`, when
`web and is_member`, delete `project.scripts` if it is present. Then rewrite the
file with `_tidy`, using the same document read and write that `_tidy` itself
uses. Keep the stub removal in `_uv_init`.

**Rejected.**

- **Seed a `main()` that runs uvicorn.** It writes the application's production
  entry point for it, and apollo already plans its own (`apollo-api serve`,
  apollo S1.1.2).
- **`uv init --lib` for the member.** It changes the member's layout and its
  `__init__.py` stub for every web repository, only to drop a single table.

**Tests first**, in `tests/modules/python/test_scaffold.py`:

1. `test_s16_5_6_1_web_api_member_has_no_console_script`, parametrised over
   `python-web-api` with `fastapi`, `python-web-api` with `django`, and
   `python-web-app` with `fastapi`. For each cell:
    - scaffold it, then read `config.packages[0]/pyproject.toml`;
    - assert `"scripts" not in document["project"]`;
    - assert the member's `__init__.py` is empty.
1. `test_s4_9_1_7_scaffold_points_project_scripts_at_the_app` is unchanged and
   still passes.

**Acceptance:**

- `task test` passes, and so does `task lint KILN_DOCTOR_FULL=1`.
- After `task self:golden:render`, no
  `.goldens/working/python-web-*/apps/api/pyproject.toml` has a
  `[project.scripts]` table.

**What the build settled that the story did not say:**

- `_reconcile_pyproject` pops `project.scripts` from a web member and re-runs
  `_tidy`; no deviation from the story.

## S16.5.7 — A web application starts both dev servers with `task dev`

**State:** Closed (2026-11-19) · **Depends on:** —

**Why.** A `python-web-app` exposes `api:dev` and `web:dev`, but no task starts
both. Running the application locally takes two terminals, and the frontend's
proxy to the API fails until the second one is up. apollo's owner found it on
2026-11-19.

**Design.** The root Taskfile of a `python-web-app` gains an eleventh root verb,
`dev`, that calls `api:dev` and `web:dev` as `deps:`. go-task runs `deps:` in
parallel; a dev server never returns, so `cmds:` would never reach the second.
`WEB_APP_VERBS = ("dev",)` in `modules/tasks/config.py` names it, and the
`task-layout` surface check expects `ROOT_VERBS + WEB_APP_VERBS` for a web app
and `ROOT_VERBS` elsewhere. `tasks.extra_refs` cannot extend `dev`. The
AGENTS.md entrypoint bullet, the standard and
[ADR-0007](../../../adr/ADR-0007.md)'s developer surface say so.

**Rejected.**

- **A namespaced `web:dev:all`.** It keeps the root at ten verbs, as ADR-0007
  prefers for a new capability, but the owner wants the root task.
- **`web:dev` depends on `api:dev`.** The surface does not change, but the
  frontend can no longer run on its own.

**Tests.**

1. `test_task_list_json_shows_api_and_web_verbs` (`test_task_archetypes.py`)
   also asserts `dev` is listed and its `deps:` are `api:dev`, `web:dev`.
1. `test_only_a_web_app_has_the_dev_verb`: a `python-web-api` has no `dev`.
1. `test_the_wrappers_call_node` (`test_task_ci.py`) exempts `dev` from "no root
   verb calls `web:`"; `test_the_wrappers_call_python_in_place` reads `deps:`
   where a verb has no `cmds:`.
1. The instructions tests assert the bullet's "`dev` runs both" and the
   standard's `task dev` row.

**Acceptance:**

- `task test` passes, and so does `task lint KILN_DOCTOR_FULL=1`.
- A scratch Taskfile with the same `dev` task, over apollo's own `tasks/api.yml`
  and `tasks/web.yml`, served `/livez` on 8000 and `<app-root>` on 4200 at
  once.

**What the build settled that the story did not say:**

- `deps:` refs are not walked by `task_refs`, so `taskgraph` does not resolve
  `dev`'s calls; the rendered-task tests cover them instead.
- apollo receives `dev` when it moves its `[kiln] ref` past this change and runs
  `task kiln:apply`.

## S16.5.8 — The dependency table matches pykit and ngkit as they stand

**State:** Closed (2026-11-20) · **Depends on:** —

**Why.** apollo's S1.1.1 adds `rn-forge-sqlalchemy`, which kiln pins at v0.2.4,
and `kiln doctor` rejects it: no archetype allows it. The archetype sets were
last widened by S7.5.6 (`rn-forge-auth` for web apps) and have not followed
pykit since. apollo's owner found it on 2026-11-19 and asked for the whole table
to be reviewed rather than one entry added.

**Review (2026-11-19).** pykit `release-10` and ngkit's published releases,
against kiln's pin table (`archetypes/__init__.py`), the `[dependencies]` of
each `archetype.toml`, `NGKIT_URL` (`modules/node/angular.py`) and
[the reference, §3](../../../reference/standard-repo.md#3-the-dependency-set):

| Package | Released | Pinned in kiln | Allowed by | Finding |
| -- | -- | -- | -- | -- |
| `rn-forge-commons` | 0.10.0 | 0.10.0 | every python archetype | current |
| `rn-forge-cli` | 0.2.0 | 0.2.0 | app, tool, web-api, web-app | current |
| `rn-forge-tooling` | 0.3.3 | 0.3.3 | lib, tool (and `lifecycle = true`) | current |
| `rn-forge-web` | 0.3.2 | 0.3.2 | web-api, web-app | current |
| `rn-forge-auth` | 0.2.0 | 0.2.0 | web-api, web-app | current |
| `rn-forge-django` | 0.7.0 | 0.7.0 | web, `backend = "django"` | current |
| `rn-forge-fastapi` | 0.5.1 | 0.5.0 | web, `backend = "fastapi"` | pin one patch behind |
| `rn-forge-sqlalchemy` | 0.2.4 | 0.2.4 | none | pinned but never allowed |
| `rn-forge-data` | 0.1.5 | — | none | not pinned; reached only through the `transfer` extras of django and fastapi |
| `rn-forge-devops` | 0.5.0 | (run by `uvx` in `tasks/ci.yml`) | none | correct: a subprocess, never a dependency |
| `@rn-forge/ng` | v0.5.0 | v0.4.0 | `frontend = "angular"` (seeded) | pin one release behind; v0.6.0 is cut on ngkit's `chore/release-5-cut`, not yet published |
| `@rn-forge/ng-tailwind`, `@rn-forge/ng-bootstrap` | v0.5.0 | — | not governed (no Node dependency check) | the reference does not mention them |

The reference's table is also stale: it shows only required runtime packages,
omits `rn-forge-auth`, still says `rn-forge-fastapi` "when that package exists",
and lists `rn-forge-django[codegen]` and `rn-forge-fastapi[codegen]` as dev
dependencies, though neither package declares a `codegen` extra today. The
rendered `.importlinter` header also says `rn-forge-commons` and
`rn-forge-tooling` are the *only* rn-forge packages a repo may depend on, which
has not been true since the web archetypes took `rn-forge-web`.

**Design.**

1. **Pin table** (`RN_FORGE_TAGS`), read from pykit `release-10`:
   `rn-forge-fastapi` → `rn-forge-fastapi-v0.5.1`; add `rn-forge-data` →
   `rn-forge-data-v0.1.5`. The docstring names `release-10` and the date.
1. **Allowed sets**, each package allowed and not required:
    - `python-web-api`, `python-web-app`: add `rn-forge-sqlalchemy` and
      `rn-forge-data`, after `rn-forge-auth`.
    - `python-app`, `python-tool`: add `rn-forge-data`.
    - `python-lib` is unchanged; `rn-forge-devops` stays out of every set.
1. **ngkit pin.** `NGKIT_URL` moves to the v0.5.0 tarball. The move to v0.6.0
   waits for its release to be published.
1. **The reference, §3** becomes one table with **Required**, **Allowed** and
   **Dev** columns per archetype (and per backend for the web archetypes). It

## S16.5.9 — A single-member repository's CI test job runs its tests

**State:** New · **Depends on:** —

**Why.** In a single-member Python repository (apollo: `python-web-app`, one
member `apollo-api`) the rendered `ci.yml` test job runs
`task ci:test -- apollo-api` (`modules/cicd/templates/ci.yml.j2`, the matrix
`name`). The rendered `tasks/ci.yml` `test` task for a non-workspace repository
(`modules/tasks/templates/tasks/ci.yml.j2`, "CI only: Run the repository's tests
(the plan's one member).") calls `task: :test`. go-task forwards the global
`CLI_ARGS` to a called task, so `python:test`
(`uv run --directory apps/api --package apollo-api pytest -q {{.CLI_ARGS}}`)
runs `pytest -q apollo-api`, which exits 4 with
`ERROR: file or directory not found: apollo-api`. No test runs in CI for any
single-member repository. apollo's owner found it on 2026-11-20 (apollo PR #4,
CI run 44812529197).

**Design.** The single-member `ci:test` calls `:test` with `CLI_ARGS` cleared:

```yaml
  test:
    cmds:
      - task: :test
        vars: {CLI_ARGS: ""}
```

The matrix still passes the member name, as the workspace `test` needs it and
`ci.yml` stays one shape for both. Confirmed against go-task 3.54.0 with a
scratch Taskfile: `task a -- m`, where `a` calls `test` plainly, echoes `m` in
the callee; `task b -- m`, where `b` calls `test` with `vars: {CLI_ARGS: ""}`,
echoes nothing. The build must keep that as the test below, since it is go-task
behaviour kiln does not own.

**Rejected.**

- **`ci.yml` omits the member when the plan has one member.** It needs a
  conditional on the plan's size in the workflow (the plan is a runtime value,
  so a `if:` or a second step), and the task would still break when run by
  hand as `task ci:test -- <member>`, the form its description implies.
- **`python:test` ignores `CLI_ARGS`.** `task test -- -k name` is how a
  developer passes pytest arguments; removing it breaks that for everyone.

**Tests.**

1. `test_single_member_ci_test_does_not_forward_cli_args` (`test_task_ci.py`):
   for every non-workspace cell, the rendered `tasks/ci.yml` `test` task has
   one `task: :test` command whose `vars` is `{"CLI_ARGS": ""}`; the workspace
   `test` task is unchanged.
1. `test_single_member_ci_test_runs_pytest_without_the_member`
   (`test_task_ci.py`, `@requires("task")`, beside the `--dry` precedent in
   `test_node_tasks.py`): render the `python-web-app` fastapi/angular cell and
   run `task --dry ci:test -- apollo-api`; the output holds `pytest -q` and
   does not hold `apollo-api` after it. A `python-app` cell does the same.

**Acceptance:**

- `task test` passes, and so does `task lint KILN_DOCTOR_FULL=1`.
- apollo, with its `[kiln] ref` moved past this change and `task kiln:apply`
  run, shows its API tests running in the PR CI `test` job.
