# S7.8.2 — `task kiln:upgrade`

Brief for
[S7.8.2](../F7.8-existing-repos-take-the-pin-table.md#s782-task-kilnupgrade), at
`ad061c9`, after S7.8.1 and S7.8.4. Line references are at `ad061c9`.

## Goal

Add one `kiln upgrade` operation. The running kiln resolves the ref and hands
off to the kiln at that ref. That target kiln does five things:

1. Writes the new pin.
1. Applies its own templates through the shared plan from S7.8.4.
1. Moves the rn-forge ranges with S7.8.1's helpers.
1. Runs `task setup` and then `task validate`.
1. On any failure, restores everything it wrote, unless `--force` keeps a fully
   applied candidate.

## Settled

Settled by the reviewer on 2026-11-18, within the feature's `## Design`.

- **Shared pin helpers.** Move pin's ref logic out of `pin` in
  `commands/config.py` into `src/rn_forge/kiln/modules/core/kiln_ref.py`, and
  export both:

    - `target(ref: str, track: str | None) -> tuple[str, str | None]` holds the
      branch, tag, SHA and `track` rules exactly as `pin` has them now. It
      returns `(new_ref, new_track)` and raises the same `kiln.track-missing`
      and unknown-ref errors.
    - `write_pin(config_path: Path, ref: str, track: str | None) -> str` writes
      the `[kiln]` table the way `pin` does and returns the old ref.

    `pin` calls both. Its CLI, output and tests stay as they are.

- **`process.run` streams on request.** Add `capture_output: bool = True` to
  `run` in `modules/core/process.py`, pass it to `Process.execute`, and
  document it.

- **The command.** Add a new `src/rn_forge/kiln/commands/upgrade.py` with
  `upgrade(ref: str = "", force: bool = False, target_ref: str = "", target_track: str = "") -> None`.

    - Register it in `.rn-forge/kiln/config.toml`'s `[cli]` table as
      `name = "upgrade"`, `target = "rn_forge.kiln.commands.upgrade:upgrade"`,
      after `pin`.
    - Export it from `commands/__init__.py`.
    - Render `cli.toml` with `task kiln:apply`; never edit it by hand.
    - The docstring says that `--target-ref` and `--target-track` are internal,
      set by the launcher.
    - Command modules import no sibling command module except `output`
      (`tests/suite/test_commands_modules.py`). Shared code goes in
      `modules/core`.

- **The launcher**, when `target_ref` is empty:

    1. `root = umbrella.find_root(Path.cwd())`. Read the `[kiln]` table, as `pin`
       does, and run `new, track = kiln_ref.target(ref, table.get("track"))`.
    1. Run
       `process.run("kiln-upgrade", "uvx", "--from", f"rn-forge-kiln @ {archetypes.KILN_GIT}@{new}", "kiln", "upgrade", "--target-ref", new, *(("--target-track", track) if track else ()), *(("--force",) if force else ()), cwd=root, check=False, capture_output=False)`.
    1. If it exits non-zero, raise
       `AppException("upgrade.target-failed: the kiln at {} exited {}", new, rc)`.

    The launcher writes nothing. A target kiln older than this story has no
    `upgrade` command, so it fails before any write.

- **The target**, when `target_ref` is set. Here `CONFIG_PATH` is the config
  file and `STATE_PATH` is `umbrella.STATE_PATH`.

    1. **Clean tree.** If `git status --porcelain --untracked-files=all` prints
       anything, raise
       `AppException("upgrade.dirty: the working tree has uncommitted or untracked changes — commit or stash them, so a failed upgrade can be restored")`.

    1. **Pin.** Take `pinned = cycle.Footprint(root, {CONFIG_PATH})`, then call
       `old = kiln_ref.write_pin(root / CONFIG_PATH, target_ref, target_track or None)`.

    1. **Plan.** Inside a `try`:

        - Run `prepared = cycle.prepare(root)`, which loads and validates the
          candidate config, then `prepared.plan.check()`, which refuses a blocked
          plan.
        - Run `moves = ranges.plan(prepared.config, root)`.
        - Take
          `footprint = cycle.Footprint(root, prepared.write_paths() | {Path(m.path) for m in moves} | {Path("uv.lock"), Path("pnpm-lock.yaml")})`.
        - Print `kiln ref {old} → {target_ref}`, the artifact rows through
          `output.change_rows` / `output.emit_rows`, and one line per move,
          `{path}: {old} → {new}`, with ` (breaking range)` appended when the
          move is breaking.

    1. **Apply.** Run
       `cycle.execute(root, prepared, finalize=finalizer(root, prepared.config), post=lambda: output.fail_on_errors(root))`
       (`finalizer` is from `modules.docs.generate`), then
       `ranges.write(root, moves)`.

        If any of steps 3–4 raises, restore `footprint` (if it was taken) and
        `pinned`, then re-raise. `--force` never keeps a candidate that failed
        here.

    1. **Release notes**, which are information, not the gate: for each move,
       print `{distribution}:` and `ranges.release_notes(move)`.

    1. **Gate.** Run `task setup`, then `task validate` only if setup exited 0.
       Use
       `process.run(f"task-{verb}", "task", verb, cwd=root, check=False, capture_output=False).return_code`.
       Both run even with zero moves. If both exit 0, return.

    1. **Failure with `force`:** raise
       `AppException("upgrade.kept: task {} failed; the upgrade is kept because of --force — fix what it reports", verb)`.

    1. **Failure without `force`:**

        - Restore `footprint`, then `pinned`.
        - Run `task setup` again with `check=False, capture_output=False`.
        - Read `git status --porcelain --untracked-files=all`.
        - Raise
          `AppException("upgrade.failed: task {} failed; the previous pin, files and locks are restored{}{}", verb, recovery, residual)`.
          `recovery` is `""`, or
          `"; recovery task setup also failed — run it again"` when the re-run
          setup exited non-zero. `residual` is `""`, or
          `"; still changed: <paths>"` when the status is not empty.

- **The task.** Add it to
  `src/rn_forge/kiln/modules/tasks/templates/tasks/kiln.yml.j2`, inside the
  `{% if not kiln_own %}` block, after `pin`. It has no preconditions, because
  the command checks the tree:

    ```yaml
      upgrade:
        desc: Pin kiln to a ref after `--` (or follow `track`), apply the new kiln's standard, move the rn-forge ranges to its pin table and run `task validate`. A failure restores the previous pin, files and locks unless FORCE=1.
        cmds:
          - '{{.KILN}} upgrade{{if .CLI_ARGS}} --ref {{.CLI_ARGS}}{{end}}{{if .FORCE}} --force{{end}}'
    ```

    Extend the template's comment at line 8 with: "`upgrade` pins, applies the new
    kiln's standard and pykit floors, and validates
    (`task kiln:upgrade -- <ref>`, `FORCE=1` to keep a failing upgrade)." Add
    `"upgrade"` to `PUBLIC_KILN_TASKS` in `modules/tasks/checks/layout.py`.

- **The rendered standard.** In `modules/instructions/templates/standard.md.j2`,
  after the paragraph ending "Do not edit the ref by hand: `task kiln:apply`
  would then run the old kiln.", add this paragraph, under the same condition:

    > A new kiln can raise the rn-forge floors, which `task kiln:pin` does not
    > take, because `pyproject.toml` is this repository's own. Run
    > `task kiln:upgrade -- <ref>` instead. The kiln at that ref pins itself,
    > applies its standard, rewrites every rn-forge range to its pin table, prints
    > the release notes in between, and runs `task setup` and `task validate`. It
    > needs a clean working tree. A failure restores the previous pin, files and
    > locks; `task kiln:upgrade FORCE=1 -- <ref>` keeps an applied upgrade so you
    > can fix what `task validate` reports.

- **`docs/reference/standard-repo.md`.** Replace "A breaking pykit release moves
  kiln's pin table; `kiln config upgrade --apply` takes it into a repository.
  An additive release needs only `uv lock --upgrade`." with:

    > A breaking pykit release moves kiln's pin table. A repository takes it with
    > `task kiln:upgrade`, which applies the new kiln's standard, rewrites its
    > rn-forge ranges to that kiln's table and validates, restoring the previous
    > pin, files and locks on a failure unless `FORCE=1`. An additive release
    > needs only `uv lock --upgrade`.

    Add `kiln:upgrade` wherever the page lists the public `kiln:` tasks next to
    `kiln:pin`.

- **Test names** describe behaviour, `test_<subject>_<behaviour>`, and carry no
  spec ID.
