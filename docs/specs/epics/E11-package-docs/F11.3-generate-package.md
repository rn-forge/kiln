## S11.3.1 — `kiln generate package <name>` for `python-lib`

**State:** Closed (2026-10-01)

**Build:**

- The CLI is `kiln generate package <name> [path]`, with `path` defaulting to
  `.`, wired in `main.py` and `commands.py` the way `apply` is. It takes
  `--json`, which lists the paths written and the apply result.
- Preflight runs before anything is written, and each failure exits non-zero:
    - The archetype is not `python-lib`: `generate.unsupported-archetype`.
    - `<name>` is not a kebab-case distribution name, is already in
      `config.packages`, or `packages/<name>` exists: `generate.package-exists`
      or `generate.invalid-name`.
    - `git remote get-url origin` fails or is not a GitHub remote:
      `generate.no-remote`, with the message
      `a published package needs the repository's GitHub remote: git remote add origin https://github.com/<owner>/<repo>`.
      Both `https://github.com/<owner>/<repo>[.git]` and
      `git@github.com:<owner>/<repo>[.git]` are accepted.
- Once preflight passes, the command runs these steps in order:
    1. It appends `packages/<name>` to `[archetype.python-lib] packages` in
       `.rn-forge/kiln/config.toml`. The file is edited in place with its
       comments kept, the way S4.5.4's `config update` writes it.
    1. It runs
       `modules/python/scaffold.py:add_package(root, config, name, remote)`. This
       runs `uv init` and `_reconcile` for the member, exactly as `scaffold`
       does per member today. It then appends the member to the root
       `[tool.uv.workspace] members`, adds `<name> = { workspace = true }` to
       `[tool.uv.sources]`, and adds `<name>` to the `workspace` dependency
       group. Last, it writes the member's `[project.urls]` from *remote*, using
       the [E11 design](index.md#design)'s table. The remote is read only here,
       which is a scaffold function.
    1. It runs `modules/docs/scaffold.py:add_package(root, config, name)`, which
       renders these seeds once each, skipping any that exist, from
       `modules/docs/templates/package/`: `mkdocs.yml`, `docs/index.md`,
       `docs/guides/usage.md`, `docs/reference/api.md`, `docs/changelog.md`,
       `CHANGELOG.md` and `README.md`.
    1. It runs the apply cycle in-process, so the managed files that depend on
       `config.packages` are updated. These include `tasks/docs.yml`, the task
       files and the workflows. It then runs
       `generate.generate(root, packages)`, so the nav gains the package's
       `!include` entry.
- `kiln new --archetype python-lib` also seeds
  `docs/runbooks/adding-a-package.md`, which is added to `SEEDS` for
  `python-lib` only. The runbook says to set `origin`, run
  `kiln generate package <name>`, then fill the package's guides. Add it to
  the golden first.

**Tests:** a new `tests/test_generate_package.py`. It uses
`tests/modules/python/test_scaffold.py`'s `uv` fixture pattern for the scaffold
steps.

**Acceptance:**

- In a fresh `kiln new` `python-lib` repository whose `origin` is
  `https://github.com/rn-forge/golden-lib`, the command runs
  `generate package golden-alpha`, then `generate package golden-beta`. The
  resulting files equal the S11.2.1 golden's, apart from name and
  provenance-version lines. Seeded pages that the golden extended by hand must
  contain the seed's lines in order, as in S4.3.2.
- `uv sync`, `task validate` and `kiln doctor` pass in that repository, and a
  second `kiln apply --dry-run --json` is all `unchanged`.
- An `ssh` remote and an `https` remote for the same repository write the same
  `[project.urls]`.
- With no `origin`, the command fails with `generate.no-remote`, and
  `git status --porcelain` is unchanged.
- A repeated name fails with `generate.package-exists`, and a `python-app`
  repository fails with `generate.unsupported-archetype`. Neither writes
  anything.

*What the build settled that the story did not say:*

- **Golden equality means what the command writes or edits.** The test compares
  these against the S11.2.1 golden, for `golden-alpha` then `golden-beta` with
  `origin` `https://github.com/rn-forge/golden-lib`, in a `kiln new`
  repository named `golden-lib`:
    - Every managed file in both `state.json` baselines is byte-equal, apart from
      the provenance line's kiln version. That covers `tasks/docs.yml`,
      `tasks/quality.yml` and `tasks/workspace.yml`.
    - `config.toml` is compared as a loaded config, since the golden's file is
      hand-minimal and `kiln new` writes the defaults too. Both list the same
      packages, and the comments survive the edit.
    - The root `mkdocs.yml` body, with the nav emptied and `site_description`
      normalized, is equal. The generated nav is the golden's lines in order,
      and holds the `Packages` `!include` entries.
    - A package seed that the golden did not extend by hand is equal, with
      `site_description` normalized: `mkdocs.yml`, `docs/changelog.md` and
      `docs/reference/api.md`. Every seed's lines are contained in the golden's
      file, in order, as in S4.3.2. The golden's `CHANGELOG.md`, `README.md`,
      `docs/index.md` and `docs/guides/usage.md` carry hand-written text, so the
      seeds hold only lines the golden also holds.
    - Each member `pyproject.toml` is compared by table, not by line: `uv init`
      writes a `description`, `authors` and `[project.scripts]` that the golden
      replaced by hand, and a `uv_build` floor that follows the installed uv.
      Equal are `[project.urls]`, `name`, `requires-python`, `dependencies`, the
      build backend, `[tool.uv]`, pytest's options, pyright's four keys and the
      ruff test ignores. The golden's `src/` modules and `test_add.py` and
      `test_double.py` are not compared; `tests/test_package.py` is equal.
    - The root `pyproject.toml` is compared for `[tool.uv.workspace]`, each
      member's `[tool.uv.sources]` entry, and the `workspace` and `docs`
      dependency groups. The golden's `dev` group names the kiln checkout by
      path where a fresh one pins the git URL, so only its first entry, the
      `include-group` for `workspace`, is compared.
- **`kiln generate package` is a `generate` namespace.** `cli.toml` and
  `config.toml` declare `generate` with target `commands:generate_app`, a
  `CliApp` with one command, `package`. A namespace needs a Typer app, and
  `.importlinter` forbids importing `typer`, so `generate_app` is a `CliApp`
  from `rn_forge.cli`, which is a Typer subclass and passes the contract. Its
  own root callback also takes `--log-level` and `--json`, so a `--log-level`
  given before `generate` is reset by the namespace's default.
- **`[path]` is `--path`.** A parameter with a default is always an option in
  this framework, as `new` and `diff` already note.
  `kiln generate package <name> --path <dir>` defaults to `.`, and the root is
  the nearest ancestor holding a kiln config, as `apply` finds it.
- **The preflight order** is archetype, name syntax, existing name, then the
  remote, so a `python-app` fails with `generate.unsupported-archetype`
  without a remote. A name is valid when it matches
  `^[a-z][a-z0-9]*(-[a-z0-9]+)*$`; the leading letter keeps the module name
  importable. `generate.package-exists` covers both a name in
  `config.packages` and an existing `packages/<name>`. Each message is
  `<code>: <text>`; `generate.no-remote`'s text is the story's, exactly.
- **Where git runs.** `python/scaffold.py:github_remote(root)` is the one
  `git remote get-url origin` call, a scaffold function. It returns
  `https://github.com/<owner>/<repo>`, or `None` for a failed call or a
  non-GitHub remote, whichever of the two accepted forms was given. The
  command calls it in the preflight, and passes the result to `add_package` as
  *remote*, so `[project.urls]` is written from the same value that was
  checked.
- **`add_package` reconciles the one member.** `_reconcile_pyprojects` is split
  so that `add_package` reconciles only the new `pyproject.toml`; the
  per-member logic is otherwise `scaffold`'s. It also writes the package's
  `tests/test_package.py`, which `scaffold` writes for every member.
- **The root edits.** `[tool.uv.sources]` gains `<name>` as a sub-table,
  `[tool.uv.sources.<name>]` with `workspace = true`, not as an inline table,
  because the config library writes a nested mapping as a table; the two parse
  identically. The first package also adds `{ include-group = "workspace" }`
  to the front of the `dev` group, as the golden has, so that `uv sync`
  installs the members. Without it the `workspace` group the story asks for
  would be unused.
- **`docs/scaffold.py:add_package` reads the URLs from the member's
  `pyproject.toml`**, which step 2 has just written, since it takes no remote.
  It pre-wraps the README's links line to 80 columns with `textwrap`, the
  width `.mdformat.toml` sets, so that `mdformat --check` accepts it for any
  name or URL length. It returns the files it wrote, and writes nothing unless
  the docs profile is `mkdocs`.
- **The seeds' wording** is the least that is also in the golden, so that a
  fresh package passes its own gate and the golden contains it: the README is
  its title and links line, `usage.md` is its title and the API-reference
  sentence, `index.md` is the title and the three bullets, and `CHANGELOG.md`
  is Keep a Changelog's header and `## [Unreleased]`. `site_description` is
  `<name> — package documentation.`
- **The runbook.** `docs/runbooks/adding-a-package.md` is added to the golden
  first, with its nav entry, a bullet in the golden's runbooks index, and a
  `seeded` entry in its `state.json`. `SEEDS` carries it, and `render` drops
  it for every archetype except `python-lib` through `_PYTHON_LIB_ONLY`. The
  template is byte-equal to the golden's page. The seeded `runbooks/index.md`
  stays `# Runbooks`, so a fresh repository's index does not list it; the nav
  does. `_seeds()` in `tests/modules/docs/test_artifacts.py` now drops it for
  the other archetypes.
- **The `--json` payload** is `root`, `written` and `artifacts`. `written` is
  `config.toml`, the root `pyproject.toml`, and every file under
  `packages/<name>/` (uv's `.python-version` included); `artifacts` is the
  apply result's `{key, path, kind, action}` rows.
- **No rollback and no doctor run.** Preflight is the only guard. A `uv init` or
  apply failure after step 1 leaves the earlier steps' writes in place. The
  command runs steps 1-4 and nothing else, so unlike `kiln apply` it does not
  run `kiln doctor`'s checks.
- **`uv init`'s own files stay.** A member keeps its `.python-version`, which
  the golden's members do not have, and `[project.scripts]`, exactly as the
  per-member scaffold leaves them today.
- **The second `apply --dry-run --json` is `unchanged` or `skip`.** The
  feature's acceptance `jq` requires every row `unchanged`, but a seeded file
  already on disk always reports `skip`, as `tests/test_apply.py` and S4.5.2
  settle. The test and the hand run accept both, and check that nothing but a
  seeded file is `skip`. The literal `jq` is false on any repository that has
  seeds.
- **Not in `pytest`:** `uv sync`, `task validate` and `kiln doctor` in the
  generated repository need the network, so the feature's acceptance block
  runs them. They were run by hand against this checkout:
  `task setup && uv pip install -e <kiln> && UV_NO_SYNC=1 task validate`.
- **Fixed in review: the generated repository's own gate.** `mdformat --check`
  scanned trees that are not this repository's prose, so `task validate`
  failed after the command. `kiln generate package` applies in process, and
  the engine backs up each managed file it replaces under
  `.rn-forge/kiln/backups/<stamp>/`; any `kiln apply` that updates a managed
  file does the same. And a task run with `--directory packages/<pkg>` runs
  its tool there, so each member grows its own `.uv-cache/` and
  `.pytest_cache/`, whose READMEs fail the check from the second run on. The
  seeded `.mdformat.toml` now excludes `.rn-forge/kiln/backups/**`, and the
  four tool caches as `**/<cache>/**` in place of root-only patterns. The change
  is in `modules/core/templates/mdformat.toml.j2`, the three goldens' copies
  and kiln's own. A planted unformatted page in a member cache and in the
  backups passes, and one in `docs/` still fails.
- **Acceptance block, corrected in review.** The `jq` line accepts `skip` as
  well as `unchanged`, for the reason above. `kiln new` runs from `$s`: S4.5.9
  keeps `.staging/<name>/` under the invocation directory and refuses to reuse
  it, so a second run from kiln's root fails.

## Acceptance

```bash
set -euo pipefail
fails_with() { local out rc=0; out=$("${@:2}" 2>&1) || rc=$?; [ "$rc" -ne 0 ] && grep -qF -- "$1" <<<"$out"; }
cd rn-forge/kiln
kiln_dir=$PWD
kiln() { uv run --project "$kiln_dir" kiln "$@"; }
uv run pytest -q tests/test_generate_package.py                                       # S11.3.1
s=$(mktemp -d)
(cd "$s" && kiln new "$s/lib" --archetype python-lib --docs mkdocs --yes </dev/null)
cd "$s/lib"
git init -q
before=$(git status --porcelain)
fails_with generate.no-remote kiln generate package alpha                            # S11.3.1
[ "$(git status --porcelain)" = "$before" ]                                           # S11.3.1
git remote add origin git@github.com:rn-forge/f11-proof.git
kiln generate package alpha                                                           # S11.3.1
rg -q 'Documentation = "https://rn-forge.github.io/f11-proof/packages/alpha/latest/"' packages/alpha/pyproject.toml
test -f docs/runbooks/adding-a-package.md                                             # S11.3.1
fails_with generate.package-exists kiln generate package alpha                       # S11.3.1
uv sync && task validate                                                              # S11.3.1
kiln apply --dry-run --json | jq -e 'all(.artifacts[]; .action == "unchanged" or .action == "skip")'  # S11.3.1
```
