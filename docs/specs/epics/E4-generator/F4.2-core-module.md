# F4.2 — The `core` module, the config manager and the module contract

Epic: [E4](index.md) · Phase step: D.2 · Decisions:
[ADR-0004](../../../adr/ADR-0004.md), [ADR-0011](../../../adr/ADR-0011.md) ·
Design: [module contract](design.md#the-module-contract),
[config lifecycle](design.md#the-config-lifecycle) · **Depends on:**
[F4.1](F4.1-checks-by-module.md); pykit's `rn-forge-commons[pydantic]` extra
(its commons plan, Part G — done)

The CLI does not exist until [F4.5](F4.5-cli.md), so this feature's behaviour is
proven through the Python API. Each acceptance bullet below is at least one test
whose name says which bullet it proves.

## S4.2.1 — The module contract and archetype manifest

**Status:** done (2026-09-16)

`modules/base.py` — `KilnModule` and the registry; `archetypes/*/archetype.toml`
lists `modules`, the dependency set, `forbidden_tools`, `required_validate`.

**Acceptance:**

- A stub module that implements `KilnModule` registers. One missing a member
  fails `task typecheck`.
- Two modules declaring the same option make registry startup fail, and the
  error names both modules and the option.
- Every Python archetype's `archetype.toml` loads, with `modules`, the
  dependency set, `forbidden_tools` and `required_validate`. A manifest naming
  an unregistered module is refused, and the error names it.

What the build settled that the story did not say:

- **The contract gains `section`.** A module's name and the table it owns differ
  twice: `cicd` owns `[ci]`, and `python` owns `[archetype.<name>]`. `core`
  and `instructions` own no section; core's config is the root `[repository]`
  table.
- **Module objects never import their checks or templates at import time.**
  `checks()` and `artifacts()` import them when called, so the registry is as
  cheap to load as the render-free checks, and
  `tests/test_checks_are_render_free.py` still holds.
- **The manifest keeps the dependency set as a `[dependencies]` table** with
  `required` and `allowed`; `lifecycle = true` and `docs.profile = "mkdocs"`
  still adjust it in code, as they did before the manifests existed.

## S4.2.2 — The config manager

**Status:** done (2026-09-16)

`core/config/` — the composed schema (`schema_version`, `[repository]`,
`[source]`, one section per enabled module); layered resolution from a path or
git URL; list-replace deep merge; per-key provenance recorded in state; schema
compatibility on every load; override preservation on re-resolution. Built on
commons `DictUtils.merge_layers` and documents, not reimplemented.

**Acceptance:**

- An invalid config fails with an error naming each failing key by its dotted
  path. This is tested for a missing key, a wrong type and an unknown key.
- A layer that sets a list replaces the lower layer's list, while tables and
  scalars deep-merge.
- A config whose `schema_version` is newer than the running kiln is refused, and
  the error names the version it needs.
- A section for a module the archetype does not enable is rejected, not ignored.
- A path source and a `git-url@ref` source both resolve. The git source records
  location, ref and resolved commit in `[source]` (tested against a local bare
  repo).
- Re-resolution keeps a key whose committed value differs from what its layer
  last supplied, and lists it as an override.
- The manager contains no merge implementation of its own; it calls
  `DictUtils.merge_layers`.

What the build settled that the story did not say:

- **Strict models come from commons.** They are `rn-forge-commons[pydantic]`'s
  `StrictModel`, which reports every failing key by dotted path
  ([ADR-0004](../../../adr/ADR-0004.md), History).
- **`[cli]` is carried, not validated.** rn-forge-cli owns that table and
  validates it when it builds the app; kiln's schema accepts it as written.
- **One source layer.** `[source]` is a single table, so a config resolves from
  kiln's defaults, at most one source, then flags. A source is a
  `config.toml`, a directory holding one, or a `git+` URL whose repository
  holds one at its root. A `git+…@ref` is cloned and checked out; the commit
  is recorded.
- **Per-key provenance** is recorded in `state.json` metadata as
  `config_provenance`: each leaf's dotted path, its layer and the value it
  supplied. The defaults layer includes `[repository]`'s own defaults, so an
  unedited `lifecycle = false` is not mistaken for an override.
- **The manager does not write `config.toml`.** Writing it is `kiln new` and
  `kiln config update` ([F4.5](F4.5-cli.md)).

## S4.2.3 — `core` artifacts and the cycle adapter

**Status:** done (2026-09-16)

`core/` artifacts — `.rn-forge/kiln/` umbrella, `find_root`, the `.gitignore`
block, `.editorconfig`, `.rn-forge/kiln/standard.md`, `legacy.kiln-state`
detection (the retired predecessor's trees are never overwritten implicitly,
[ADR-0004](../../../adr/ADR-0004.md)). `core/cycle.py` — the thin adapter over
tooling `generation`. Core's `checks()` wraps `modules/core/checks`
([S4.1.2](F4.1-checks-by-module.md)).

**Acceptance:**

- Applying `core` into an empty directory classifies only `CREATE` and `INSERT`,
  and every core artifact exists afterwards.
- A second apply classifies every artifact `UNCHANGED` and leaves `state.json`
  byte-identical.
- A hand-edited managed core artifact classifies `DRIFT`, and nothing is
  written: every artifact and `state.json` keep their bytes. Forcing that path
  rewrites only it.
- A pre-existing `.rn-forge/kiln/` tree without `schema_version` reports
  `legacy.kiln-state` and nothing is written.
- `find_root` from a nested directory returns the repo root.
- A write failure injected mid-transaction restores backups, removes created
  files, and leaves `state.json` with its previous bytes.
- Core's `checks()` reports the same findings as `kiln doctor --only generated`
  on the same fixture.

What the build settled that the story did not say:

- **`standard.md` is the `instructions` module's**, as the apply sequence in the
  design and [S4.3.5](F4.3-concern-modules.md) already say. It is the whole
  canon templated per archetype, so it lands with that template set. `core`
  renders `.editorconfig` and the `.gitignore` block.
- **`state.json` is in the engine's format.** tooling's `StateStore` writes
  `schema_version` as `"1"`, `content_hash` as a bare SHA-256 hex digest — of
  a block's body as the engine reads it, trailing newline included — and keys
  a block `<path>#<block name>`. The committed baselines used `1`,
  `sha256:<hex>`, a body without its last newline and `<path>::kiln`, so a
  real apply would have been reported as drift. The `generated` check now
  reads blocks and hashes exactly as the engine does, and kiln's and each
  golden's `state.json` were re-seeded from the bytes on disk after
  `kiln doctor --only generated` passed on each.
- **`.rn-forge/kiln/state.lock` is gitignored.** The engine holds it while
  writing state; kiln's and the goldens' `.gitignore` blocks gained the line
  first, and the template follows them.
- **`legacy.kiln-state` looks at both trees** ADR-0004 names: the repo's
  `.rn-forge/kiln/` and `$RNF_HOME/kiln/`. A tree is legacy when it is
  non-empty and neither its `config.toml` nor its `state.json` declares
  `schema_version`.
- **Until every module renders, apply is not safe on an existing repo.** A state
  entry no module renders plans as `DELETE`, so applying today's core-only
  render over kiln or a golden would remove their other managed files. Nothing
  exposes `apply` before [F4.5](F4.5-cli.md), which follows
  [F4.3](F4.3-concern-modules.md).
