# ADR-0016 — Every archetype's CI follows one contract, planned by rn-forge-devops

**Status:** accepted (2026-10-18) · **Scope:** the generated CI of every
archetype

## Decision

The flow and logic of CI are the same in every kiln-managed repository, whatever
the stack. Only what runs under each `task` differs.

- **Triggers:** pull request into the default branch, push to it, and manual
  dispatch. A newer push to a pull request cancels its run; default-branch
  runs queue.
- **`validate`** (repository-wide checks, through `task`) gates everything.
- **Nine stages, in this order, for every archetype:** `validate`, `test`,
  `integration`, `smoke`, `suites`, `sonar`, `release`, `verify-release`,
  `docs`, then `ci-ok`. Each archetype maps each stage to a stack-specific
  `task`, or marks it n/a. There are no exceptions: docs, release and the
  post-release install are stages of `ci.yml`, never a separate workflow.
- **A plan** selects changed units plus their dependents. A single-package
  archetype is a plan of one unit. An empty, invalid or non-ancestor base, or
  a change outside every unit and outside docs, selects all; docs-only selects
  none. A pull request diffs against its base, a push against the last green
  run, a dispatch selects all.
- **Per selected unit:** `test`, then the stages a unit declares: `integration`
  (tests against service containers the unit declares as data: image,
  environment, ports; one matrix leg per unit, no database named in kiln) and
  `smoke` (the built artifact installs and starts or imports), then
  workspace-wide `suites`.
- **Sonar** with `sonar.qualitygate.wait=true`, skipped for fork pull requests
  and Dependabot's, with one guard for every archetype.
- **Publishing** happens only from the default branch, only for units whose
  every check passed and whose selected prerequisites are releasable, after
  the quality gate; never from a pull request. Release is idempotent and
  follows version bumps: the release, not the tag, is the record. `node-lib`'s
  release is a job of `ci.yml` under the same rule ([ADR-0015](ADR-0015.md)'s
  steps).
- **After release:** `verify-release` installs each new release from its
  registry, outside the workspace; then `docs` deploys once.
- **One workflow, one required check.** `ci.yml` is kiln's and a repository
  never edits it. `ci-ok` is the single required check, with one logic for
  every archetype; a skipped job is not a failure. kiln may split a stage into
  a reusable workflow, `.github/workflows/_<stage>.yml` called from `ci.yml`,
  when the stage is large or shared. It renders those files and a repository
  never edits them; `ci.yml` stays the one entry and `ci-ok` the one required
  check.
- **Every step goes through `task`.** An exemption needs an ADR; ADR-0015's Nx
  calls are the existing one. A check is a `task` verb first and a job second:
  it gets its own job only when it needs full history, extra permissions,
  services, a schedule or a fork guard, and otherwise folds into
  `task validate` or `task lint`.
- **Check switches.** Every check is *standard* (always on), *derived* (on when
  the tree calls for it, with no key) or *configured* (a key in `[ci.checks]`,
  default on or off). The configured defaults: `licenses` on (denying GPL,
  AGPL and UNKNOWN, with its policy as an inline table), `secret-scan` on,
  `umbrella-release` off, `scorecard` off. No switch removes `validate` or
  `ci-ok`. The keys are the same for every archetype; each names a different
  tool per stack.
- **A repository extends the generated CI by reference to files it owns**, never
  by kiln templating their content and never by hand-editing a generated file.
  Four tiers, all declared in `.rn-forge/kiln/config.toml` and naming
  repository-owned `task` verbs or files. There is no separate hook file.
    1. `[ci.checks]` switches a kiln check or sets its policy.
    1. `[ci.hooks]` runs steps inside kiln's jobs at named anchors, never by step
       number (`setup` and `docs` exist; a new anchor is added by revising this
       ADR when a repository needs it).
    1. `[[ci.jobs]]` declares a repository job, rendered as a reusable-workflow
       call (`uses: ./.github/workflows/<file>`) that needs `validate`. A
       boolean `required` says whether `ci-ok` needs it.
    1. A repository-owned workflow file is allowed for non-gating or scheduled
       runs only. Dependabot's `github-actions` ecosystem keeps its pins current
       and ignores every action in kiln's `pins.toml`.
- The repository's own files are held to the same standard: `ci-pins` reads
  every file under `.github/workflows/` and `.github/actions/`,
  `ci-entrypoint` every workflow under `.github/workflows/`, and `ci-hooks`
  checks that every hook and declared job names a file that exists and, for a
  job, can be called.
- The ownership CI checks (`ci-entrypoint`, `ci-pins`, `ci-hooks`) run in every
  repository's `task lint`, so a pull request enforces them, not only a
  default-branch push.
- **Security and supply-chain checks are part of the contract.** Workflow
  security linting, dependency update automation, a dependency vulnerability
  audit and release provenance are standard. The secret scan and the licence
  check are configured, on by default. The audit's ignore list records
  accepted vulnerabilities, each with a reason.
- **The check matrix is derived.** One check registry in kiln code (check,
  archetypes, switch, default, verb, job) renders `ci.yml`, validates
  `[ci.checks]`, and fills the derived regions of
  [the CI page](../architecture/ci.md) and the rendered `standard.md`. The
  registry is planned work in [E15](../specs/epics/E15-ci-standard/index.md).

**rn-forge-devops is the standard CI planner for every archetype**, as MkDocs is
the standard docs tool ([ADR-0012](ADR-0012.md)). It holds the planning and
orchestration behind `task ci:*`. `node-lib` may keep its Nx-native affected CI
while it meets the contract. A future archetype (Java, Maven) meets it by
rn-forge-devops gaining a planner for that ecosystem, not by hand-written logic.

## Consequences

- `python-lib`'s `release` runs only on a push to the default branch and waits
  on `sonar`; before, it also ran on pull requests and dispatch, and could
  ship while the gate failed.
- A pull request still proves packaging: `smoke` installs every selected
  package's wheel with no extras, plus each declared extra. That needs an
  upstream change, pykit's: `plan` emits a no-extras smoke entry per package.
- `node-lib` carries an audit against this contract
  ([F9.1](../specs/epics/E9-node-archetypes/F9.1-node-lib-hosts-ngkit-ci.md)).
- Logic that lives in a repository's workflow, not in `task`, is drift.

## Alternatives considered

- **Each archetype's CI as its stack's tooling prefers.** Three pipelines would
  hold three sets of selection and release rules, and a fix to one would not
  reach the others.
- **Hand-written planning logic per stack.** It would sit in the repository's
  workflow, outside `task`, and drift per repository.
- **Move `node-lib` onto rn-forge-devops now.** It would discard Nx's own
  affected graph for no gain while ngkit's CI meets the contract.
- **Insert a repository's steps by position.** Step numbers shift silently when
  kiln's template changes, so an extension would land in the wrong place with
  nothing to detect it.
- **Per-step enable and disable flags on every step.** They would let a
  repository opt out of the contract, and multiply the render matrix by every
  flag. The configured checks are a closed, registered set instead.
- **A separate hook file.** `config.toml` is already the one place a repository
  talks to kiln; a second file would split it.
- **A hand-written check matrix.** It would drift from the workflow; the
  registry renders both.
- **Security jobs left in each repository's own workflow.** pykit's `main.yml`
  carried them, so a swap to `ci.yml` silently dropped them from `ci-ok`, and
  a second workflow shares the concurrency group and cancels the first.
- **`[ci] node` as a built-in toggle.** A repository's Node needs (versions,
  caching) are its own, and kiln would have to guess them; kiln has no
  `package.json` or lockfile to read them from. S4.8.3 shipped the key and
  [S4.11.1](../specs/epics/E4-generator/F4.11-ci-enhancements.md#s4111-repositories-extend-the-generated-ci-by-reference)
  removes it.
- **A `[[ci.jobs]] task =` field.** It made kiln render the job body, checkout
  and setup included, which is the templating of repository content this
  decision rules out.

## Background

- 2026-10-18: owner decision. [ADR-0014](ADR-0014.md) chose rn-forge-devops for
  `python-lib` only; this widens it. The release rule (default branch only,
  after Sonar) corrects `python-lib`'s generated `release` job, which did not
  match the standard's "`release` depends on `sonar`".
- 2026-10-19: revised, from S4.8.3's build. Giving kiln's own CI Node needed a
  pnpm and Node version that kiln cannot know, and `[ci] node` plus a
  task-running `[[ci.jobs]]` had kiln render the repository's content. The
  decision now extends the generated CI by reference to repository-owned files
  (hooks at named anchors, declared jobs that call reusable workflows) and
  rules out per-step flags.
- 2026-10-28: the planner is now `kiln-devops` ([ADR-0017](ADR-0017.md)); the
  contract above is unchanged.
- 2026-11-04: revised by owner decision, from the pykit cutover review
  ([findings R5 to R7](../specs/ideas/pykit-cutover-findings.md#r6-the-ci-model-everything-pykit-runs-in-kiln)).
  Adds the check switches, the four hook tiers, `required` on `[[ci.jobs]]`
  and the derived matrix, and drops "no flags to switch checks off": security
  checks the repository can configure are now declared, not forbidden. It
  revises three feature decisions, which stay as written:
  [F4.11](../specs/epics/E4-generator/F4.11-ci-enhancements.md#not-adopted)
  (no gitleaks: the secret scan is now a configured check),
  [F6.8](../specs/epics/E6-rebuild-the-repos/F6.8-pykit-release-7-ci.md) (the
  security jobs stay pykit's: they move into kiln) and
  [F7.6](../specs/epics/E7-pykit-release-pin-flip/F7.6-release-to-pypi.md)
  (the umbrella release stays pykit's: it becomes the configured
  `umbrella-release` check, off by default). All of it ships in release 1.
- 2026-11-04: revised again by owner decision, from the review of the CI pages
  ([finding R8](../specs/ideas/pykit-cutover-findings.md)). Adds the
  nine-stage vocabulary for every archetype; `verify` is renamed `test`, the
  `postgres` and `redis` jobs become the `integration` stage with services
  declared as data, and `external-install` and `node-lib`'s
  `published-install` become `verify-release`. The five gaps between the
  templates and this contract (the single-package archetypes' `docs.yml`,
  `node-lib`'s `release.yml`, `plan` and install checks only in `python-lib`,
  two `ci-ok` logics, a Sonar guard only `node-lib` had) are all folded into
  `ci.yml`, with no exception recorded. `node-lib`'s release is therefore no
  longer a dispatched workflow, which revises [ADR-0015](ADR-0015.md)'s
  dispatch and its own gate; its steps are unchanged. Reusable stage workflows
  are allowed. Job names other than `ci-ok` are not required checks, so the
  renames break no branch protection. Built by
  [F15.8](../specs/epics/E15-ci-standard/F15.8-one-workflow-contract.md); the
  built state is in [the CI architecture](../architecture/ci.md).
