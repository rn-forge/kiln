## S4.1.1 — The repo becomes a workspace

**Status:** planned

Convert the repo to a uv workspace: `packages/rn-forge-kiln/`,
`packages/rn-forge-kiln-checks/`. kiln's own `config.toml` stays `python-tool`
until [F4.8](F4.8-self-hosting.md).

**Acceptance:**

- The root `pyproject.toml` declares both packages as workspace members, and
  there is no root `src/`.
- Both `rn_forge.kiln` and `rn_forge.kiln.checks` import after `uv sync`.
- `task build` produces one wheel per distribution.
- `task validate` passes, and kiln's config still records `python-tool`.

## S4.1.2 — Port the policy checkers into their modules

**Status:** planned

Port the four policy checkers from the goldens' `scripts/` into the module that
owns each rule, replacing each `# BEGIN kiln config` header with a read of
`.rn-forge/kiln/config.toml`: `checks/core/generated.py` (`check-generated`),
`checks/python/rn_forge_deps.py` (`check-rn-forge-deps`),
`checks/tasks/layout.py` (`check-task-layout`), `checks/cicd/entrypoint.py`
(`check-ci-entrypoint`), plus `checks/docs/policy.py` — the docs policy object
tooling's docs checkers take (A2). One console script per check and an aggregate
`kiln-checks`. **No import of the generator, no Jinja** — an `.importlinter`
contract holds it. Refuse an unknown `state.json` `schema_version` loudly.

**Acceptance:**

- Each console script exits 0 on each golden.
- Each script exits non-zero and names the offending path on a fixture that
  breaks one of its rules. There is one test per rule the original script
  enforced, and the script's existing tests are ported with it.
- `kiln-checks` runs all four and exits non-zero if any fails.
- A `state.json` with an unknown `schema_version` makes `check-generated` exit
  non-zero with a message naming that version.
- No `# BEGIN kiln config` header remains in the package.
- `lint-imports` keeps a contract that `rn_forge.kiln.checks` imports neither
  the generator (`rn_forge.kiln` outside `checks`) nor `jinja2`.
- tooling's docs checkers pass on kiln's docs when given `checks.docs.policy`.

## Open questions

### 1. Does CI install a checks package, or kiln itself?

**Raised:** revision 14 as D74 (*proposed*); reopened by the owner on 2026-09-12
with option B and the regression-pipeline idea. Answered by S4.1.4.

**The constraint underneath.** A check that needs only committed files
(`state.json` hashes, the task graph, workflow entrypoints, the dependency set)
can run anywhere. A check that needs a fresh render (`artifact.stale`,
`block.stale`) needs kiln installed. The question is which of those CI runs, and
what it installs to run them.

**Option A — D74 as proposed.** `rn-forge-kiln-checks` is the render-free half
of each module's checks, organized by module, and a `core` module owns what
every module shares: the umbrella, config manager, state baseline,
`standard.md`, the gitignore block and `check-generated`; `scaffold` becomes
`python`. Each module's `checks()` = its functions in
`rn_forge.kiln.checks.<module>` + its render-dependent checks — one
implementation of each rule, reachable from `kiln doctor` locally and from
console scripts in CI.

- For: ADR-0003 and ADR-0010 stand unchanged; CI's environment holds no Jinja,
  generation engine, pydantic or template sets.
- Against: two distributions to version; CI cannot see that kiln has moved on,
  so a kiln upgrade reaches a repo only when a developer runs it locally.

**Option B — kiln is a dev dependency, and CI runs the module doctors.** The
checks package dissolves into the modules; CI runs `kiln doctor`, which includes
the render-dependent checks, so the gate is a full rendered drift check.

- For: one distribution and one implementation path; kiln's version is pinned in
  each repo's `uv.lock`, so which kiln rendered a repo is recorded rather than
  implied; a kiln upgrade becomes a dependency bump a bot can propose, and CI
  on that pull request shows exactly what the new kiln would change.
- Against, as D74 recorded it: Jinja, the generation engine, pydantic and every
  template set enter every repo's lock and CI environment; a kiln upgrade is a
  dependency bump in every repo whether or not an artifact changed; supersedes
  ADR-0003 and ADR-0010 for no check CI can run that the split cannot.
- Weakened by pinning: ADR-0003's "a generator bug becomes a build failure in
  ten repos at once" assumed CI installs kiln *unpinned*. With a locked
  version, a kiln release changes nothing until a repo's lock moves.
- **Unverified, and possibly blocking:** pykit is a `python-lib` whose workspace
  *contains* `rn-forge-tooling`, while kiln depends on `rn-forge-tooling` by
  pinned direct URL. Putting kiln in pykit's dev group may not resolve (one
  package name, a workspace source and a URL source). Needs a spike.
- Also unverified: Dependabot's support for bumping a git-sourced uv dependency
  (kiln is not on PyPI, ADR-0005). Renovate handles git refs; whether
  Dependabot does is not established.

**Option C — A for the gate, plus a non-gating regression workflow.** Keep A's
required gate. Add a generated workflow that is not a required check — on a
schedule, on `workflow_dispatch` with a kiln ref, and on bot pull requests —
which installs kiln at that ref, runs `kiln config upgrade --dry-run`,
`kiln apply` and `kiln doctor` on a branch, and opens or updates a pull request
with the rendered diff: Dependabot for the standard. It tests a kiln upgrade on
a branch with no local environment.

- For: gets B's main benefit — upgrades proposed and exercised in CI — without
  kiln in every lock or on the required path.
- Against: kiln installs in a CI job, so ADR-0003's "CI never installs kiln"
  needs rewording to "the gate never does"; the workflow can only reach kiln
  through `task`, which needs either a new public verb (a fifteenth verb needs
  an ADR under [ADR-0007](../../../adr/0007-task-vocabulary.md)) or a
  repo-owned `self:` namespace; opening pull requests needs a token with write
  scope.

**Recommendation.** C, with B's pykit-resolution spike run first. If the spike
shows B resolves cleanly in pykit and the lock weight is acceptable, B is the
simpler end state and C's workflow becomes its upgrade channel. Whichever wins
is folded into ADR-0010 (and ADR-0003 if the regression workflow is adopted);
the losing options move to its *Alternatives considered*, and D74's text is then
either accepted there or recorded as rejected.
