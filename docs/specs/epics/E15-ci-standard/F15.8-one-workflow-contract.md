Every archetype runs the same nine stages in `ci.yml`: `validate`, `test`,
`integration`, `smoke`, `suites`, `sonar`, `release`, `verify-release`, `docs`,
then `ci-ok`, with one pre-release barrier, `checks-ok`, before anything
publishes ([the design](design.md#stage-vocabulary),
[ADR-0016](../../../adr/ADR-0016.md)). This feature builds it, folding the five
gaps found by the 2026-11-04 audit into `ci.yml` with no exception:

| Gap | Today | Built by |
| -- | -- | -- |
| Docs deploy | the single-package Python archetypes render a separate `docs.yml`, outside `ci-ok` and not gated on release | S15.8.6 |
| `node-lib` release | `release.yml` runs its own gate and `published-install` | S15.8.5 |
| `plan` and `external-install` | only `python-lib` has them | S15.8.3, S15.8.4 |
| `ci-ok` | `node-lib`'s uses a `jq` script; the others use `contains(needs.*.result)` | S15.8.7 |
| Release barrier | `release` waits on some checks only (not `secret-scan` or required declared jobs), and `node-lib`'s would need a test job that is always skipped | S15.8.7 |
| Sonar and Dependabot | Sonar skips Dependabot's pull requests only on `node-lib` | S15.8.8 |

The `postgres` and `redis` jobs become data (S15.8.2), and the stages may be
split into reusable workflow files (S15.8.9).

## Context

- **The cutover.** pykit declares `[tool.workspace-ci.postgres]` and
  `[tool.workspace-ci.redis]`. `kiln-devops` stops reading them (S15.8.2) and
  names the new table in its error, and pykit's declarations are converted by
  the cutover SOP in its cutover pull request. No backward reading is kept:
  the pull request that bumps the `[kiln] ref` is the one that converts.
- **Job names.** Only `ci-ok` is a required check, so renaming a job breaks no
  branch protection.
- **Order.** S15.8.1 first writes the job lookup helper, so that no test of
  S15.8.2 to S15.8.8 changes when S15.8.9 moves a job into a reusable file.

## S15.8.1 — Stage names: `verify` becomes `test`

**State:** Closed (2026-11-05) · **Depends on:** S15.1.1

Renames only; nothing changes behaviour.

**Build — tests first.** First write the helper
`tests/modules/cicd/workflows.py`,
`jobs(files: dict[str, str]) -> dict[str, dict]`: it parses `ci.yml` and every
`_*.yml` in `files` (the rendered file map) with `YamlUtils` and returns the
merged `jobs` mappings. Every test of this feature looks a job up through it.
Then, in `tests/modules/cicd/test_stages.py`:

1. `test_s15_8_1_1_lib_jobs`: a two-package `python-lib` render's job names are

1. `test_s15_8_1_2_marker_kind`: in `tests/devops/test_ci.py`,
   `Package.checks()` starts with `{"kind": "test", "marker": "<name>.test"}`,
   and `releasable` finds a package releasable only when `<name>.test` exists.
1. `test_s15_8_1_3_test_task`: `tasks/ci.yml` has `test` (running what `verify`
   ran) and no `verify`; the `test` job runs `task ci:test`.
1. `test_s15_8_1_4_node_jobs`: a `node-lib` render has `test-cloud` and
   `test-local` in place of `ci-cloud` and `ci-local`, and `smoke` in place of

1. `test_s15_8_1_5_no_old_name`: no template mentions `ci:verify`, `ci-cloud`,
   `ci-local` or a `package` job.

**Build:** `ci.yml.j2`, `tasks/ci.yml.j2`, `devops/ci.py` (`checks()`, and the
marker names `release` reads), `docs/architecture/ci.md` (the names in "Stages"
and in the `python-lib` event table and diagram). Run `kiln apply` here.

**Acceptance:**

- The five tests pass, and `task validate` passes.
- `task self:golden:compare BASE=HEAD`: only job and task names change.

**What the build settled that the story did not say:**

- The helper `tests/modules/cicd/workflows.py` is not a package module

  by path with `importlib.util`. Later F15.8 tests do the same.
- `test_s15_8_1_2_marker_kind` is in `tests/devops/test_ci.py` and also checks
  that a stale `<name>.verify` marker no longer counts. The `release` job
  reads markers only through `Package.checks()`, so no other reader changed.
- `GENERATED_JOBS` (`cicd/config.py`) takes `test` in place of `verify`, so a
  declared `[[ci.jobs]]` may not be named `test`. The registry cells for
  `pyright strict` and `pytest` (`python-lib` column) say `test`.
- The `node-lib` `package` job is now `smoke`; its artifact name
  `package-tarballs`, its task `ci:package` and the registry row "Package
  tarballs" are unchanged (tasks are not renamed). The older tests in
  `tests/modules/cicd/test_artifacts.py` and
  `tests/modules/tasks/test_artifacts.py` were updated to the new names.
- `ci.md` keeps `external-install` until S15.8.4; its job table lists the
  `node-lib` `smoke` row separately from the Python `smoke` row.
- Also renamed: the prose in `standard.md.j2` and
  `docs/reference/standard-repo.md` (`ci:verify`, `ci-cloud`, `ci-local`);
  `docs/guides/` names none of them.

## S15.8.2 — The `integration` stage: services as data

**State:** Closed (2026-11-05) · **Depends on:** S15.8.1

**Build — tests first,** in `tests/devops/test_integration.py` and
`tests/devops/test_ci.py`. The declaration is
[the design's](design.md#integration-services-as-data)
`[tool.workspace-ci.integration.<service>]` table (`image`, `ports`,
`health-cmd`, `env`, `expose`):

1. `test_s15_8_2_1_load`: `load_workspace` reads a package declaring `postgres`
   and `redis` into `Package.services`, a tuple of `Service` (`name`, `image`,
   `ports`, `health_cmd`, `env`, `expose`); `image` is required, the others
   default to empty.
1. `test_s15_8_2_2_plan`: `plan(...)["integration"]` has one entry per selected
   package with services, `{"name", "dir", "services": [...], "marker"}`; the
   keys `postgres` and `redis` are gone; a package with none has no entry.
1. `test_s15_8_2_3_marker`: `Package.checks()` lists
   `{"kind": "integration", "marker": "<name>.integration"}` exactly when the
   package has services, and the old `postgres` and `redis` kinds are gone.
1. `test_s15_8_2_4_old_table_is_refused`: a package with
   `[tool.workspace-ci.postgres]` makes `load_workspace` raise, with the
   message
   `[tool.workspace-ci.postgres] was replaced by [tool.workspace-ci.integration.postgres]`.
1. `test_s15_8_2_5_run`: `integration.run(package, runner)`, with a fake
   `runner`, issues for each service
   `docker run -d --name <id> -e K=V -p <port> --health-cmd <cmd> <image>`,
   waits until `docker inspect` reports `healthy` (or `running` with no
   `health-cmd`), runs the package's pytest with every `expose` variable in
   the environment, and always ends with `docker rm -f` of each container,
   also when pytest fails; its return value is pytest's exit code.
1. `test_s15_8_2_6_cli`: `main(["integration", "<name>"])` runs it.
1. In `tests/modules/cicd/test_stages.py`, `test_s15_8_2_7_job`: a `python-lib`
   render has one job `integration` (no `postgres`, no `redis`), with
   `matrix.include: ${{ fromJSON(needs.plan.outputs.integration) }}`, running
   `task ci:integration -- ${{ matrix.name }}`, uploading
   `ok-${{ matrix.marker }}`, `if` skipping it when the list is `[]`; `sonar`,
   `release` and `ci-ok` need `integration` and not `postgres` or `redis`.
1. `test_s15_8_2_8_task`: `tasks/ci.yml` has `integration` running
   `{{.KILN_DEVOPS}} integration "$@"`; `postgres` and `redis` are gone.

**Build:** `devops/uv.py` and `devops/ci.py` (`Service`, `Package.services`,
`plan`, `checks`), new `devops/integration.py`, a subparser in `devops/cli.py`,
`ci.yml.j2` and `tasks/ci.yml.j2`. The containers are started by the task, not
by a `services:` block, because a job's `services` cannot vary with the matrix
leg. Update the marker list `release` reads. Update `docs/architecture/ci.md`
and `docs/reference/standard-repo.md` where they name `postgres` and `redis`.

**Acceptance:**

- The eight tests pass, and `task validate` passes.
- `task self:golden:compare BASE=HEAD`: only the `python-lib` cell changes.
- Not scriptable here: pykit's declarations are converted in its cutover pull
  request, by the SOP, and its `integration` legs go green there.

**What the build settled that the story did not say:**

- `Service` is a frozen dataclass in `devops/ci.py`; `plan`'s `services` is the
  list of service names, since the leg reloads the workspace and reads the
  rest from `Package.services`. `Package.postgres_env` and `redis_env` are
  gone.
- A service table without `image` raises `ValueError` too, and the CLI turns
  both `ValueError`s from `load_workspace` into an exit message, like a
  missing workspace. The refusal names the package:
  `<name>: [tool.workspace-ci.postgres] was replaced by [tool.workspace-ci.integration.postgres]`.
- `integration.run(package, runner, pytest_args, sleep=, attempts=)`: the runner
  is `runner(command, env=None, capture=False)` returning a
  `CompletedProcess`; `subprocess_runner` is the default. Containers are named
  `kiln-ci-<package>-<service>`. A service with a `health-cmd` also gets
  `--health-interval 2s --health-timeout 5s --health-retries 30` (Docker's 30
  s default interval would stall every leg). Readiness is polled every 2 s, 60
  times. A failed `docker run` or a service that never gets ready ends the run
  (status of the `docker run`, or 1) after the cleanup. `pytest_args` is the
  root `pytest-args`, which the CLI reads from the workspace, so the job no
  longer passes `PYTEST_ARGS`.
- The task is `{{.DEVOPS}} integration {{.CLI_ARGS}}`, the form every other
  devops task uses (the story said `{{.KILN_DEVOPS}} ... "$@"`).
- The leg records and uploads the plan's `marker` (`<name>.integration`) instead
  of building the name from `matrix.name`. `integration` replaces `postgres`
  and `redis` in `GENERATED_JOBS` and in the plan keys.
- No fixture declared the old tables; the old per-job tests of
  `test_artifacts.py` and the `postgres`/`redis` task tests were removed,
  their contract now covered by tests 2 to 8. `docs/reference/kiln-devops.md`
  (the declaration table, the subcommand table and the plan keys) was updated
  too.

## S15.8.3 — Single-package Python archetypes get a plan of one

**State:** Closed (2026-11-05) · **Depends on:** S15.8.1, S15.8.2, S15.8.7

A single-package Python repository is a workspace of one member, so it runs the
same `plan`, `test`, `integration`, `smoke` and `suites` jobs as `python-lib`.

**Build — tests first,** in `tests/devops/test_uv.py` and
`tests/modules/cicd/test_stages.py`:

1. `test_s15_8_3_1_root_is_the_member`: `load_workspace` on a root
   `pyproject.toml` with no `[tool.uv.workspace]` returns one package, named
   from `[project] name`, `dir` `.`, with `module` from the `src/` layout.
1. `test_s15_8_3_2_plan_of_one`: `plan(...)` selects it for a change under
   `src/` and for a dispatch, and selects nothing for a change only under
   `docs/`.
1. `test_s15_8_3_3_jobs`: for each of `python-tool`, `python-app`,
   `python-web-api` and `python-web-app`, the render has `plan`, `test`,
   `integration`, `smoke` and `suites` with the same bodies as `python-lib`'s,
   and `validate` runs `task ci:validate`.
1. `test_s15_8_3_4_validate_task`: `tasks/ci.yml` `validate` runs `task lint`,
   `task typecheck` and, with docs, `task docs:build`; `test` runs
   `task test`, which for `python-web-app` includes the frontend.
1. `test_s15_8_3_5_needs`: `sonar` needs `validate`, `test`, `integration`,
   `smoke`; `checks-ok` needs the same plus `plan`, `suites` and `sonar`;
   `release` needs `plan` and `checks-ok`; `ci-ok` needs `checks-ok` and the
   release stages.
1. `test_s15_8_3_6_suites_are_declared`: with no `[tool.workspace-ci.suites]`
   the `suites` job's matrix is empty and the job is skipped.

**Build:** `devops/uv.py` (the root-as-member fallback), `ci.yml.j2` (the
`workspace` flag no longer gates `plan`, `test`, `integration`, `smoke`,
`suites`; it keeps gating the per-package `release` and `docs` bodies),
`tasks/ci.yml.j2` (`validate` for single-package Python). The single-package
`release` job keeps its own steps (S15.8.4 adds what follows it).

**Acceptance:**

- The six tests pass, and `task validate` passes.
- `task self:golden:render`, then `task self:golden:validate`: every Python cell
  passes its own gate in a clean clone.

**What the build settled that the story did not say:**

- `workspace` (the template flag for `python-lib`) still gates the per-package
  `release` and `docs` bodies, the `adapters`, `requirements` and
  `release-build` family of tasks, and `validate`'s `task lint` form. The
  stages `plan`, `test`, `integration`, `smoke` and `suites`, and the matching
  `prerelease_needs()` entries, are gated on `not node_lib`.
- `ci:validate` for a single-package repository runs `:lint`, `:typecheck`,
  `:docs:build` (with docs) and the `validate` extras of other modules; it
  does not run `test`, which is the `test` job's. `ci:test` is `task: :test`
  and ignores its `-- <name>` argument, so the job body stays the one
  `python-lib` has. `python-web-app`'s root `test` already ran `node:test`; no
  change there.
- `find_root` falls back to the nearest `pyproject.toml` when no directory at or
  above declares `[tool.uv.workspace]`. `load_workspace` then returns the root
  project as the one member (`dir` `.`). The member's `module` is now read the
  same way for every member: `[tool.uv.build-backend] module-name`, else the
  one package directory under `src/`, else the project name. A root-member
  repository's `select` gives every file outside `docs/` to the root package,
  and the plan's `sonar-sources` and `sonar-tests` read `src` and `tests`, not
  `./src`. `python-web-api` and `python-web-app` are real uv workspaces (the
  API under `api_dir`), so their one member is the API, as before.
- The single-package `release` job needs `[plan, checks-ok]` and gains no
  `release-order` term: it keeps its own steps and its own released-state
  check.
- The `plan` job's "Check internal ranges" step is absent from single-package
  renders (one member has no ranges), the one difference from `python-lib`'s
  stage bodies; `test_s15_8_3_3_jobs` compares everything else.
- Tests of earlier stories that listed the single-package jobs, the `Validate`
  step (`task validate`), the `release` job's `needs` or the absence of
  `ci:validate`/pipeline tasks outside `python-lib` were updated.

## S15.8.4 — `verify-release` for every Python archetype

**State:** Closed (2026-11-05) · **Depends on:** S15.8.3

`external-install` becomes `verify-release`: install the published release from
the registry it went to, and import it.

**Build — tests first,** in `tests/devops/test_verify_release.py` and
`tests/modules/cicd/test_stages.py`:

1. `test_s15_8_4_1_pypi`: `verify_release.run(spec, runner)` with
   `[ci] release = "pypi"` runs `uv pip install --no-cache <name>==<version>`
   into a clean venv and imports the package's module; the install source is
   PyPI.
1. `test_s15_8_4_2_tag`: with `tag-exists` the install source is
   `git+<repo-url>@<tag>`, as `external-install` does today.
1. `test_s15_8_4_3_task`: `tasks/ci.yml` has `verify-release`, and
   `external-install` is gone.
1. `test_s15_8_4_4_lib_job`: the `python-lib` job `verify-release` replaces
   `external-install`, with the same `needs` and `if`.
1. `test_s15_8_4_5_single_package_job`: a single-package archetype's `release`
   job has an output `tag` (empty when nothing was published); the job
   `verify-release` needs `release`, is skipped when `tag` is empty, and runs
   `task ci:verify-release -- ${{ needs.release.outputs.tag }}`.
1. `test_s15_8_4_6_none`: with `[ci] release = "none"`, neither archetype
   renders `verify-release`.
1. `test_s15_8_4_7_ci_ok`: `ci-ok` needs `verify-release` wherever it is
   rendered.

**Build:** rename `devops/` `external-install` to `verify-release` and add the
PyPI source; `ci.yml.j2`, `tasks/ci.yml.j2`, and the single-package `release`
job's output. Update `docs/architecture/ci.md`.

**Acceptance:**

- The seven tests pass, and `task validate` passes.
- Not scriptable here: `verify-release` is green on the first release a Python
  repository publishes after the cutover.

**What the build settled that the story did not say:**

- `external-install` was a shell loop in `tasks/ci.yml`, not a `devops/`
  subcommand. The new `devops/verify_release.py` (`Spec`, `requirement`,
  `run(spec, runner)`, reusing `integration.Runner`) and the subcommand
  `kiln-devops verify-release --source {pypi,git} [TAG]` replace it; the task
  is `{{.DEVOPS}} verify-release --source <pypi|git> {{.CLI_ARGS}}`. The PyPI
  install keeps the old 10 attempts 30 s apart and `--no-config`, and takes
  `--no-cache` in place of `--refresh`. The git source still fetches the tag
  first; a root-member repository has no `#subdirectory`.
- Without `TAG` the subcommand verifies each tag at `HEAD` (`python-lib`); with
  `TAG` it verifies the workspace's one member at that tag, the version being
  the tag without its leading `v`. The `git` source reads `REPOSITORY_URL`.
- `[ci] release = "pypi"` is valid only for `python-lib` (S7.6), so the
  single-package job always uses the git source.
- The single-package job passes the tag through `env: TAG` and runs
  `task ci:verify-release -- "$TAG"`, not the story's inline
  `${{ needs.release.outputs.tag }}`, so no expression is interpolated into a
  script (zizmor). `test_s15_8_4_5` asserts that form.
- The `release` output is
  `steps.check.outputs.should-release == 'true' && steps.check.outputs.tag || ''`,
  from the `release-state` step. The job's `if` also requires
  `needs.release.result == 'success'`.
- `ci-ok` gets `verify-release` through `postrelease_needs()` for every
  non-`node-lib` archetype. The registry row, `GENERATED_JOBS` and the
  `ci:verify-release` task are renamed; the row now covers all Python
  archetypes. The task renders for every Python archetype, whatever `release`.
- `test_s15_8_1_5` matches `ci:verify` with a regex, since `ci:verify-release`
  begins with the old name. kiln's own `ci.yml` gains `verify-release`.

## S15.8.5 — `node-lib` releases from `ci.yml`

**State:** New · **Depends on:** S15.8.1, S15.8.7

`release.yml` and its `published-install` become `ci.yml`'s `release` and
`verify-release` jobs. The dispatch inputs go: the version is bumped in a pull
request, and the rest is derived
([the design](design.md#node-lib-versions-in-the-pull-request), owner decision
2026-11-04). CI never commits; it tags.

**Build — tests first,** in `tests/modules/cicd/test_stages.py` and
`tests/modules/tasks/test_node_release.py` (new; the shell tests run the
rendered task's script with `bash` in a temporary git repository, with a fake
`gh` on `PATH`, and skip when `bash` or `git` is missing):

1. `test_s15_8_5_1_no_release_yml`: a `node-lib` render with
   `[ci] release = "nx-dispatch"` has no `.github/workflows/release.yml`.
1. `test_s15_8_5_2_release_job`: `ci.yml` has a `release` job for `node-lib`,
   `needs: [checks-ok]`,
   `if: ${{ !cancelled() && needs.checks-ok.result == 'success' && github.event_name == 'push' && github.ref == 'refs/heads/main' }}`,
   `concurrency` group `release` with `cancel-in-progress: false`, the
   permissions `release.yml` had except `actions: read`, an output `tag`, and
   steps running `task ci:release:state`, `ci:release:author`,
   `ci:release:tag`, `ci:release:verify`, `ci:release:push`,
   `ci:release:github`, `ci:release:publish`, `ci:release:finalize` and
   `ci:release:latest` in that order. No step reads `inputs.`; none runs
   `ci:release:gate` or `ci:release:version`.
1. `test_s15_8_5_3_state`: `release:state` reads `V` from the release group's
   `package.json` files and fails when they differ; it writes `tag=vV` and
   `mode`: `new` with no `vV` tag, `resume` with the tag and a draft (or no)
   GitHub Release, `released` with a published one. It also writes
   `first-release=true` exactly when the repository has no `v*` tag other than
   `vV` (so a resumed first release is still a first release), and `dist-tag`:
   `latest` for `1.2.3`, `rc` for `1.3.0-rc.1`, `beta` for `2.0.0-beta.0`.
1. `test_s15_8_5_4_new_mode_steps`: in `new` mode `release:tag` creates `vV` at
   `HEAD`, and `release:push` pushes that tag and no branch; in `resume` mode
   neither creates nor pushes; in `released` mode only the `Already released`
   notice runs and the job's `tag` output is empty.
1. `test_s15_8_5_5_verify_rebuilds`: `release:verify` always rebuilds `dist/`
   from the tagged source (today's `MODE=resume` path), since no versioning
   step runs in CI; the `MODE` variable is gone.
1. `test_s15_8_5_6_publish_flags`: the `Publish` step passes `DIST_TAG` and
   `FIRST_RELEASE_FLAG` from `release:state`'s outputs; `DRY_RUN_FLAG` is
   gone.
