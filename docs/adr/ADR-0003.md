# ADR-0003 — Ownership is complete or absent

**Status:** accepted (2026-09-15) · **Scope:** every repository kiln generates

## Decision

Kiln owns a managed file completely, or an explicitly fenced block completely.
It renders, updates and checks every byte inside that boundary. Bytes outside a
managed boundary belong to the repository, and doctor ignores them.

A **derived region** is kiln's too, but kiln computes it from the repository's
own inputs rather than rendering it from kiln's configuration. Those inputs are
its docs tree, `docs/_areas.yml`, its spec and release pages, and its configured
packages. kiln regenerates the region and compares it with what is on disk; it
stores no hash for it, and the region has no `state.json` entry. Its fence names
start with `derived`. A repository changes a derived region by changing its
inputs; an edit inside the fence is reported as stale, and the next
`task docs:generate` overwrites it.

Kiln's own namespace is `.rn-forge/kiln/`. It neither manages nor checks sibling
directories under `.rn-forge/`, and requires no umbrella-level manifest.

Scaffolding may seed repository-owned files once. After scaffolding, kiln does
not enforce their content, their structure or their continued presence. A seeded
file is not an artifact kiln continues to own.

Doctor may read declared configuration and any input it needs to check a managed
artifact; reading an input confers no ownership over it.

Doctor may also check repository-owned content against a rule the standard
defines, when kiln supplies the means to meet it: the docs area model, met by
`docs/_areas.yml` and `task docs:generate`, and the rn-forge dependency
contract, met by the scaffold and `kiln config upgrade`. Such a check is a gate
rule, not advice, and its finding says how to meet the rule. Doctor never checks
seeded content's presence or wording, and never checks an unowned file against
anything else.

## Consequences

- A managed change is applied through kiln. Repository customization lives
  outside managed boundaries, or in declared configuration.
- Seeded content may diverge or be deleted without a doctor finding.
- Adding a page never makes kiln's baseline stale: a derived region is checked
  against its inputs, so nothing needs re-seeding when they change.
- Kiln guarantees nothing about repository-owned content beyond the rules the
  standard defines for it. The repository's own validation tasks provide every
  other check.
- Other tools may use sibling namespaces under `.rn-forge/` without coordinating
  with kiln.
- A check of repository-owned content needs a rule in the standard and a kiln
  mechanism that meets it. A rule kiln cannot help a repository meet is not
  added.
- `kiln new` and `kiln apply` fail only on ownership checks, so a repository's
  own content never blocks a regeneration.

## Alternatives considered

- **Advisory checks on repository-owned files.** Constrains content kiln has no
  way to fix, which imposes a standard without supplying a means to meet it.
  The docs-structure, docs-site and rn-forge-deps checks differ on both
  counts: each enforces a rule the standard defines, so a failure fails the
  build rather than advises, and each has a kiln mechanism that meets the rule
  (`task docs:generate` and the area model; `kiln config upgrade` and the
  scaffold). A check without such a mechanism stays rejected.
- **Shared ownership of the same bytes.** Neither writer can then distinguish an
  intended change from drift, so every check becomes a judgement call. The
  rule applies to prose too: `README.md` and `CLAUDE.md` opened with the same
  sentence and repeated the same pointers until one of them stopped.
- **Own the whole `.rn-forge/` umbrella.** Couples kiln to unrelated tools and
  forces a manifest schema no tool asked for.
- **Keep enforcing seeded files.** Makes every scaffold default a permanent
  constraint, so a repository cannot adapt its own documentation without
  fighting doctor.
- **Hash the docs nav as a managed block.** This was the rule until 2026-10-01.
  The block's bytes depend on the repository's pages, so every new page made
  the stored hash stale. Every feature that added a page carried a "re-seed
  `state.json`" step, and any repository that added pages without one would
  drift.
- **A hand-curated nav, checked for reachability.** Nothing would drift, but
  titles, order and package entries would become one more thing each
  repository maintains by hand. Repositories' navs would diverge in shape, and
  a check could only report a problem, not fix it.

## Background

Promoted on 2026-09-15 from a donor kit's ownership record, which had one owner
per file. Per-block ownership was added because three artifact kinds were needed
in practice: agentkit, the repository and seeded files all own paths, and
"everything is kiln-owned" was considered and not adopted. A formatter rewriting
a kiln-owned file is the shared-ownership failure in miniature, which is why
`.rn-forge/kiln/standard.md` is excluded from Markdown formatting.

Revised on 2026-10-01 to add derived regions, for the docs nav, the spec board
and release Scope tables (E13). The revision is proposed until the owner accepts
it, and [F13.1](../specs/epics/E13-docs-work-model/F13.1-derived-regions.md)
depends on that acceptance.

- 2026-10-21: revised, by owner decision, to let doctor check repository-owned
  content against a rule the standard defines when kiln supplies the means to
  meet it. The registry already did, with `docs-structure`, `docs-site` and
  `rn-forge-deps`; the contract changed rather than the checks, and bare
  `kiln doctor` now runs them. The work is
  [F4.12](../specs/epics/E4-generator/F4.12-task-files-by-owner.md).
