## S16.4.2 — The dependency group is re-sorted on every write (R4)

**State:** Closed (2026-11-04)

**Build — tests first,** in `tests/modules/python/test_scaffold.py`:

1. `test_s16_4_2_1_add_task_tools_sorts_the_group`: a `dev` group
   `["pytest", "aiosqlite", "zebra"]` with `taplo` missing becomes, after
   `add_task_tools`, every entry sorted by normalized name (`aiosqlite`,
   `pytest`, `taplo`, `zebra`).
1. `test_s16_4_2_2_normalization`: `Foo_Bar` sorts as `foo-bar`; a version
   specifier does not change the order; entries keep their text.
1. `test_s16_4_2_3_include_group_tables_stay_last`: `{ include-group = "x" }`
   entries stay after the strings.
1. `test_s16_4_2_4_no_write_when_nothing_changes`: a sorted group with every
   tool present is byte-identical after the call.
1. `test_s16_4_2_5_comments_survive`: a comment on an entry stays with it.

**Build:** `modules/python/scaffold.py`: `add_task_tools` and the scaffold
writer sort each group they touch, by `rn_forge_deps.distribution(entry)`
(`canonicalize_name`). This is the owner's choice (2026-11-04) over uv's rule of
appending when a list is unsorted. `new` writes sorted groups already.

**Acceptance:**

- The five tests pass, and `task validate` passes.

**What the build settled that the story did not say:**

- The import contracts allow `scaffold.py` to import `distribution` from
  `python.checks.rn_forge_deps`: it already did (same module, `python`), so no
  helper moved. `distribution` lowercases and maps `_` to `-`; it is not
  `packaging`'s `canonicalize_name` (no `.` or run collapsing), and
  `packaging` is not a declared dependency, so the key is `distribution` as
  the Build says.
- `.importlinter` forbids importing `tomlkit` anywhere in kiln, so `_sort_group`
  works on the round-trip array through its `_value` groups, with no `tomlkit`
  import: strings sorted by `distribution`, then inline tables in their
  original order, then any trailing standalone comment. A comment on lines of
  its own travels with the entry below it; a trailing comment stays on its
  entry. It uses tomlkit's private `_value` and `_reindex`, since the array
  has no public reorder.
- `add_task_tools` sorts only the `dev` and `docs` groups, and only when a tool
  is missing (it returns before reading otherwise), so a sorted group is never
  rewritten (test 4). An unsorted group with nothing missing is left alone.
- The scaffold writer is `_reconcile`: it sorts every dependency group of the
  `pyproject.toml` it writes, root or member. `_join_workspace` still puts the
  `include-group` table first in `dev`; `add_task_tools` moves it last later.
- `new` did not write sorted groups already: `_DOCS_GROUP` had `mdformat-gfm`
  before `mdformat-front-matters`. It is swapped, and this repository's own
  `pyproject.toml` `docs` group with it.
- Tests that pinned the old order changed: `test_s6_6_2_2` (sorted, not
  appended), `test_s11_2_2_2`, `test_s4_9_2_3` (`httpx` before `uvicorn`),
  `test_s9_1_15_3` (pinned entries are present, no longer the first two), and
  the docs-group order in `tests/test_generate_package.py` and
  `tests/test_init.py`.

## S16.4.7 — `config.toml` explains every option

**State:** New

Owner decision, 2026-11-04. `new`, `init`, `config-update` and `config-upgrade`
write `config.toml` as a bare `model_dump`: no word on what a key means, which
values it takes, or what `kiln apply` does when it changes; and keys whose
default is `None` (`[ci] release`, `[archetype.<name>] module`) are dropped.
This story makes the schema describe itself, and the writer print that
description above every key. `kiln configure` (idea `kiln-configure`) and a
generated reference page later read the same catalog.

**Design, fixed:**

- The pydantic models stay the single source. Each module still owns its
  section's model; nothing is declared twice.
- kiln's config models derive from a new `ConfigModel(StrictModel)` in
  `modules/core/config/schema.py`, whose `model_config` adds
  `use_attribute_docstrings=True`, so each field's existing attribute
  docstring becomes its `description`. Every field's docstring says what the
  key means and what `kiln apply` changes when it is changed.
- A new `modules/core/config/catalog.py` walks the model `RootConfig.compose`
  builds for an archetype and returns `OptionSpec` entries — `path` (dotted),
  `module` (owning module name, `core` for root keys), `description`,
  `choices` (from a `Literal`, else `None`), `default` (JSON value, or
  `None`), `default_note` (text for a `None` default resolved elsewhere, e.g.
  `"tag-exists; nx-dispatch for node-lib"`, taken from the docstring's last
  sentence starting `Default:`). `[cli]` and `[lifecycle]` are untyped and
  owned by rn-forge-cli and rn-forge-tooling: one entry each, described as
  such, and not walked.
- `_write_config` builds a `tomlkit` document from the catalog and the resolved
  values: above each key, its description as `#` lines, then
  `# One of: "a", "b".` when it has choices, then `# Default: <value>.`; a key
  whose resolved value is `None` is written commented out
  (`# release = "tag-exists"`), so it keeps following the archetype's default.
  An empty table carries its description and nothing else. The file header is
  unchanged. Other archetypes' `[archetype.<name>]` subtables are not written.

**Build — tests first,** in `tests/modules/core/test_catalog.py` and
`tests/test_new.py`:

1. `test_s16_4_7_1_every_field_described`: for every archetype in the builtin
   registry, every `OptionSpec` from `catalog.for_archetype(name)` has a
   non-empty `description`. A field added without a docstring fails here.
1. `test_s16_4_7_2_choices_and_defaults`: for `python-tool`, the
   `ci.doctor_full` entry has `choices == ("default-branch", "every-run")`,
   `default == "default-branch"`, `module == "cicd"`; `ci.release` has
   `default is None` and a non-empty `default_note`; `docs.profile` has
   `module == "docs"`.
1. `test_s16_4_7_3_commented_render`: `_write_config` for a `python-tool` config
   writes, directly above `doctor_full = "default-branch"`, the docstring's
   lines as comments followed by `# One of: "default-branch", "every-run".`
   and `# Default: "default-branch".`
1. `test_s16_4_7_4_none_default_commented`: the same render has the line
   `# release = "tag-exists"` in `[ci]` and no live `release =` line; with
   `[ci] release = "pypi"` resolved it has `release = "pypi"` live.
1. `test_s16_4_7_5_round_trip`: loading the written file gives a `KilnConfig`
   equal to the one written; writing it again is byte-identical.
1. `test_s16_4_7_6_one_writer`: `new`, `init`, `config-update` and
   `config-upgrade` each produce the commented form (assert the `# One of:`
   line is present after each).

**Build:** `ConfigModel` and the base-class switch for every model under
`modules/*/config.py` and `core/config/schema.py`; docstrings written or
rewritten for every field the first test names; `catalog.py`; `_write_config` in
`commands.py`. Run `kiln apply` (kiln's own `config.toml` is rewritten by
`task self:golden:validate`'s goldens only if they compare it; regenerate them).

**Docs:** [ADR-0004](../../../adr/ADR-0004.md) gains a line: the written
`config.toml` is generated from the schema catalog, comments included, and is
still the one input a developer edits. E15 stories that add keys (`[ci.checks]`,
`[[ci.jobs]] required`) document them in their docstrings; test 1 holds them to
it. For `[ci.checks]`, a mapping validated from the check registry (S15.1.2),
the catalog takes one entry per configurable check from the registry, with the
registry's description.

**Acceptance:**

- The six tests pass, and `task validate` and `task self:golden:validate` pass.
