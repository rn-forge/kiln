# F4.5 — CLI

Epic: [E4](index.md) · Phase step: D.5 · Design: [commands](design.md#commands)
· **Depends on:** [F4.3](F4.3-concern-modules.md); S4.5.5 also depended on
pykit's lifecycle surface

`cli.py` is declared on `build_tool_app` (kiln's own `[cli]` table), never
written
([shared CLI design](../E3-realign-goldens-and-canon/index.md#shared-cli-design)).
S4.5.1 declares the app, and each later story adds its commands to the table.
`doctor` is [F4.6](F4.6-doctor.md).

**Across every story:** each command accepts `--json`, and its output parses
with `jq`. Every value that would be prompted for has a flag, and with stdin
closed a missing required value exits non-zero naming the flag rather than
blocking.

**Order.** S4.5.1 and S4.5.2 are the thin slice
[E5](../E5-web-archetypes/index.md) needs — a repo can be created, synced and
gated — and are built right after F4.3. S4.5.3–S4.5.8 follow E5's first two
features; S4.5.9 follows S5.2.4's frontend-module split. **Build a story by the
[board's procedure](../../index.md#building-a-story).** A command is a function
in `commands.py` plus a `[[cli.commands]]` row in `cli.toml` *and* in
`.rn-forge/kiln/config.toml` (`tests/test_cli_surface.py` holds them equal);
`build_tool_app` builds everything else. Before the first command, read
`rn-forge-cli`'s README in pykit (`packages/rn-forge-cli/README.md`) for how a
command receives the standard `--json`, `--dry-run` and `--yes` options and how
it prints JSON — declare `options = ["json", "dry-run", "yes", "log-level"]`
under `[cli]`, as the reference's §9 shows.

## S4.5.1 — `kiln new`: creation

**Status:** done (2026-09-16)

`new <dir> --archetype A [--docs P] [--backend F] [--frontend W] [--config <path>] [--allow-untested] [--dry-run] [--yes] [--json]`:
collect config in memory, preview, and with `--yes` write `config.toml` and run
scaffold + apply ([ADR-0004](../../../adr/ADR-0004.md)). A git-URL `--config` is
[S4.5.7](#s457-config-from-a-git-source).

**Build:**

- `commands.py:new(directory: Path, archetype: str, docs: str = "mkdocs", backend: str | None = None, frontend: str | None = None, config: str | None = None, allow_untested: bool = False)`
  plus the standard options. The set of flags is fixed in the signature; a
  test asserts it equals the union of every registered module's `Option.flag`,
  so the modules stay the source of truth. An `Option.key` may contain
  `<archetype>`; `new` substitutes the `--archetype` value
  (`archetype.<archetype>.backend`).
- The flag layer is a mapping of dotted keys to values, `None` flags omitted;
  `ConfigManager.resolve` merges defaults → the `--config` layer → flags (read
  its signature first; it exists). Validation errors surface as they do on
  load.
- **Preview** (no `--yes`): print the resolved config as TOML and one line per
  artifact — `key`, `kind`, and `create`/`insert`/`skip` by kind, since an
  empty directory classifies no other way — from
  `module.artifacts(config, directory)` over `manager.modules_for(config)`. It
  runs no scaffold and writes nothing, so `directory` need not exist.
- **`--yes`**: `directory.mkdir(parents=True, exist_ok=True)`; refuse it if it
  holds any entry; write `.rn-forge/kiln/config.toml` from
  `config.to_document()` with the goldens' two-line header comment; run
  `python.scaffold`, `docs.scaffold`, `instructions.scaffold` in that order;
  `cycle.apply(directory)`; then `checks.run(directory)` and fail on an error
  finding — apply's step 7.
- **JSON**:
  `{"root": "<abs path>", "config": {...}, "artifacts": [{"key", "path", "kind", "action"}]}`;
  the artifact rows come from `ApplyResult` (read
  `rn_forge.tooling.generation.ApplyResult` for the field names), or from the
  preview's rows without `--yes`.
- **Untested values.** `Archetype` gains `untested: dict[str, list[str]] = {}`,
  read from an optional `[untested]` table in `archetype.toml`
  (`frontend = ["react", "svelte"]`). `new` refuses a flag whose value is
  listed, naming the flag and the value, unless `--allow-untested`. The python
  manifests have no such table; the test uses a fixture manifest written to
  `tmp_path` and loaded through `Archetype.parse`.
- `--config <path>` is a `config.toml` or a directory holding one, resolved by
  the existing `sources.fetch`; `[source]` records location and ref (`path`
  sources record no commit).

**Tests:** `tests/test_new.py`, `test_s4_5_1_…`. The end-to-end test runs
`uv init` through the python scaffold and is therefore slow; mark it with the
same marker `tests/modules/python/test_scaffold.py` uses, if any.

**Acceptance:**

- With every flag and `--yes`, stdin closed, it exits 0. It writes
  `.rn-forge/kiln/config.toml`, and its JSON lists artifacts whose `action` is
  only `create`, `insert` or `skip`.
- Without `--yes` it prints the plan, and `<dir>` gains no `.rn-forge/`.
- A non-empty `<dir>` is refused with a non-zero exit that names the directory,
  and nothing is written.
- `--config <path>` merges beneath the flags: a layer setting `ci.sonar = false`
  with no `--sonar` flag yields `sonar = false` in the written config, and
  `[source]` records the path.
- An `untested` flag value is refused without `--allow-untested`, naming the
  flag and value, and accepted with it.
- The resulting repo passes `uv sync && task validate` for each Python archetype
  with `--docs mkdocs` and with `--docs none`. This is the feature block
  below, run by hand and recorded on this story. **Not scriptable in the unit
  suite** — needs network and a real `uv sync`; left for the owner to run by
  hand from the `## Acceptance` block.

**What the build settled that the story did not say:**

- The pinned `rn-forge-cli` (`231a68e`, `feature/upgrade`) has no per-command
  `options = [...]` declaration and no README §9 describing one —
  `CommandSurface` only carries `name`/`target`/`help`. Declaring `options` in
  `cli.toml` would be silently ignored (`DataclassMixin.from_dict` drops
  unknown keys), so it is not written. Instead `--dry-run`, `--yes` and
  `--json` are plain typed parameters on `new`/`apply`, exactly as `doctor`'s
  own `only` parameter already works ("nothing here imports Typer"): a bare
  `bool = False` parameter becomes a `--flag/--no-flag` pair. `--json` on a
  command calls `console.set_mode(OutputMode.JSON)` directly; the root's own
  `--json` (before the subcommand) already does this via `CliOptions`, so
  either spelling works.
- `archetype: str` with no default (as the Build list writes it) would be a
  *positional* argument under this same convention, not `--archetype` as the
  usage line and the acceptance block both show. `new` instead gives it a
  default of `""` (like `docs`'s own default) and raises, naming
  `--archetype`, when it is empty — the "missing required value" framing
  paragraph above S4.5.1 describes exactly this shape, not Typer's
  `prompt`-based required option (which `commands.py` cannot use without
  importing Typer).
- `new`'s config-setting flags are `("archetype", "docs")`
  (`commands._FLAG_NAMES`), not the four the Build list's signature names.
  `backend`/`frontend` have no backing `Option` yet — no module declares one —
  and `tests/test_new.py::test_s4_5_1_flags_match_module_union` checks the
  flag set against the *live* union of every registered module's
  `Option.flag`, so an unclaimed flag would break the very invariant the test
  exists to hold ("the modules stay the source of truth"). F5.1 adds
  `backend`/`frontend` to both the signature and this constant together with
  the module that declares the matching `Option`.
- The 2026-09-17 selector decision names the planned option `backend` rather
  than `framework` (ADR-0005). F5.1 adds it without an old-name alias and
  validates selector applicability before any writes; F5.2 supplies the
  frontend scaffold.
- `Option.key` substitution only ever needs `<archetype>` today (no module
  declares a key containing it yet); the substitution is still implemented
  generically (`key.replace("<archetype>", archetype)`) so a later module's
  `Option` needs no CLI change.
- The repo name (`[repository].name`, required by `RootConfig`) is not a CLI
  flag anywhere in the Build list; `new` sets it from `directory.name`, always
  at the highest-precedence (flags) layer.
- `--dry-run` on `new` is treated as forcing preview even with `--yes` — "report
  what would change without writing anything" (`DryRunOption`'s own
  docstring), consistent with `apply`'s `--dry-run`. The acceptance block does
  not exercise this combination.
- The header written above `config.toml` is the two lines the goldens'
  `config.toml` files already start with (see e.g.
  `tests/fixtures/golden/python-tool/.rn-forge/kiln/config.toml`); kiln's own
  `.rn-forge/kiln/config.toml` has a longer, kiln-specific header, so that one
  was not reused as the template.
- Preview classifies each artifact with the same
  `rn_forge.tooling.generation.classify(root, artifact, None)` the engine
  itself uses for a never-applied artifact, rather than a hand-rolled rule —
  it already implements exactly "create/insert, or skip for a seeded artifact
  already on disk" and stays correct if that function's rules ever change.
- `kiln new`'s two new CLI commands (`new`, `apply`) are added to both
  `src/rn_forge/kiln/cli.toml` and `.rn-forge/kiln/config.toml`, identically,
  per `tests/test_cli_surface.py`.

## S4.5.2 — `kiln apply`: reconciliation

**Status:** done (2026-09-16)

`apply [--dry-run] [--json] [--force <artifact>]…` — the full apply sequence,
idempotent and non-interactive.

**Build:**

- `commands.py:apply(force: list[str] | None = None)` plus the standard options;
  the root is `umbrella.find_root(Path.cwd())`.
- Plan first: `cycle.plan(root, force=force)`. Every `--force` value must be the
  key of a change whose action is blocking (`DRIFT`, `CONFLICT`, `MISSING`);
  one that is not is refused before anything runs, naming it and listing the
  reported keys. Then `cycle.apply(root, force=force, dry_run=dry_run)`, then
  `checks.run(root)` — an error finding fails the command after the apply has
  committed, as apply's step 7 says.
- An unforced blocking change is the engine's `AppException`; check that its
  message names every blocking key, and add the listing in `apply` if it does
  not.
- JSON: `{"root", "artifacts": [{"key", "path", "kind", "action"}]}`, from
  `ApplyResult` (or the plan under `--dry-run`).

**Tests:** `tests/test_apply.py`, `test_s4_5_2_…`, over a repo built by
`cycle.apply` directly (no `uv init` needed).

**Acceptance:**

- On a clean repo, `apply --dry-run --json` lists at least one artifact, all
  `unchanged`, and `apply` writes nothing.
- After a config edit, `--dry-run` lists the updates and writes nothing. `apply`
  writes them, and the next `--dry-run` is all `unchanged`.
- An unforced conflict, drift or missing artifact exits non-zero, names each
  path, and writes nothing — no artifact and not `state.json`.
- `--force <path>` rewrites only that path. A `--force` naming a path that was
  not reported is refused, naming it. `--yes` never implies force.

**What the build settled that the story did not say:**

- `apply` has no `--yes` option at all
  (`tests/test_apply.py::test_s4_5_2_apply_has_no_yes_option` asserts it by
  introspecting the signature) — confirming the acceptance bullet's premise
  rather than adding a no-op flag.
- `--force` is validated against a lookup keyed by both `Change.key` and
  `Change.path` (matching how `rn_forge.tooling.generation.plan.plan` already
  accepts either for its own `force` parameter), so a plain file path — the
  only form the acceptance block ever passes — always resolves.
- The unforced-blocking-change message is entirely the engine's own
  (`Plan.check`'s `AppException`, raised from inside `cycle.apply` by way of
  `generation.apply`): it already names every blocking path and its action, so
  `apply` adds nothing further, per the Build list's own "if it does not"
  proviso.
- `checks.run(root)` runs after every non-dry-run `apply`, matching the Build
  list's literal sequence; it is skipped when `--dry-run` is set, since a dry
  run commits nothing for the checks to verify and the Build list's step
  numbering ("after the apply has already committed") only makes sense for a
  real apply.
- Tests build their repo by copying the `python-tool` golden fixture (skipping
  `.venv` and tool caches) and running `cycle.apply` on the copy once before
  each test, rather than assembling a config from scratch — the golden is
  already a complete, passing repo, and this needs no `uv init`. The one-time
  `cycle.apply` resyncs any drift between the checked-in golden and the
  templates as currently uncommitted on this branch (the golden is hand-kept
  in step per `README.md`, not regenerated automatically); it never touches
  `pyproject.toml` or `src/`, which the `python` module's `artifacts()` does
  not render.
- A "clean" repo's `apply --dry-run` lists every artifact as `unchanged` *or*
  `skip` — a seeded artifact (a docs stub page) classifies as `skip` forever
  once it exists on disk, never `unchanged` (`ArtifactKind.SEEDED`'s own
  contract), so a repo with any docs pages already seeded cannot be "all
  unchanged" the way the feature's `## Acceptance` block below assumes for a
  freshly-`kiln new`-created repo. Not something S4.5.2's own build can
  resolve — flagged here rather than silently narrowing the test.

## S4.5.3 — `kiln diff` and `kiln version`: inspection

**Status:** done (2026-09-19)

`diff [<artifact>]` — unified diff of on-disk vs fresh render. `version`.

**Acceptance:**

- On a clean repo, `kiln diff` prints nothing and exits 0.
- After a managed artifact is edited, `kiln diff` exits 1, as `diff(1)` does,
  and prints a unified diff whose headers name that path.
  `kiln diff <artifact>` limits the output to it.
- `kiln diff <unknown>` exits non-zero and names the artifact.
- `kiln version --json` has a `.version` equal to the installed distribution's.

**What the build settled that the story did not say:**

- `diff`'s artifact selector is `--artifact`, not a bare positional: a defaulted
  parameter is always an option in this framework without a `typer.Argument`
  marker, which `commands.py` never imports (same reasoning S4.5.1 recorded
  for `--archetype`). `tests/test_diff.py` exercises it as
  `commands.diff("Taskfile.yml")` at the Python level, where the distinction
  is invisible; the CLI surface only ever sees `--artifact`.
- A change's disk content is compared to `Change.artifact.content` (the block
  body, for a block artifact) via `difflib.unified_diff`, keyed by artifact
  path for both `fromfile`/`tofile` headers; seeded artifacts are skipped
  entirely (their content is never inspected, per `ArtifactKind.SEEDED`'s own
  contract) and a stale state entry with no current artifact
  (`change.artifact is None`) is skipped too — not exercised by the acceptance
  block, and `kiln diff`'s job here is comparing renders, not the deletion
  `kiln apply` already reports.
- A difference found raises `AppException` (exit 1) after the diff text is
  printed via `console.print(..., markup=False)` — not through
  `console.error`, so the diff body lands on stdout like real `diff(1)`
  output, and is skipped entirely in `--json` mode (`console.print` is a no-op
  there); JSON instead gets `{"diffs": [{"path", "diff"}]}` from
  `console.json`.
- `version` reads `importlib.metadata.version("rn-forge-kiln")` — the
  *installed* distribution, per the acceptance bullet's own wording — rather
  than the hand-kept `rn_forge.kiln.__version__` constant `cycle.py` already
  uses for `state.json`'s `kiln_version` metadata; the two happen to agree
  today but nothing enforces it, and reusing `__version__` would not have
  satisfied "equal to the installed distribution's" as a meaningful check.

## S4.5.4 — `kiln config update` and `kiln config upgrade`

**Status:** done (2026-09-19)

Both `[--dry-run] [--apply]`, per the
[config lifecycle](design.md#the-config-lifecycle).

**Acceptance:**

- `config update --dry-run` re-resolves the recorded `[source]` with the running
  kiln's defaults, prints the artifacts that would change, and writes nothing.
- A key the repo overrode survives both `update` and `upgrade`, and is listed as
  an override.
- `--apply` writes the re-merged `config.toml` and runs `apply`, after which
  `apply --dry-run` is all `unchanged`.
- A config written for the previous `schema_version` is migrated by
  `config upgrade`. `config update` refuses it and names `config upgrade`.

**What the build settled that the story did not say:**

- **Flat command names, not a `config` namespace.** `[cli.commands]` can mount a
  `typer.Typer` as a namespace (`CommandSurface.target`, per
  `rn_forge.cli.surface`), which is how a literal `kiln config update` would
  be built — but `.importlinter`'s own
  `kiln imports no framework or CLI toolkit directly` contract (which
  `commands.py`'s own docstring already explains) forbids `rn_forge.kiln` from
  importing `typer` anywhere, including a small wrapper module built only to
  hold that namespace. The commands are instead `kiln config-update` and
  `kiln config-upgrade`, flat entries in `cli.toml` pointing straight at
  `commands.py` functions, matching every other command's shape.
  `src/rn_forge/kiln/modules/instructions/templates/standard.md.j2` (and the
  three golden repos' already-rendered `standard.md`) still say
  `kiln config update`/`kiln config upgrade` — written ahead of this story,
  before the contract was checked against a real implementation. Left
  unchanged here rather than cascading a doc-text fix through three golden
  repos' state baselines and rehashes; the owner should re-word those four
  instances to the flat names (or reopen whether the contract should carry a
  narrow exception) before this ships.
- **`state.json`'s `config_provenance` was never actually written.** The
  manager's `reresolve` (S4.2.2) and a test helper already assumed `kiln new`
  populates it, but `commands.new` discarded its `Resolution`'s provenance
  after resolving, and `cycle._prepare` only ever carried an *existing* value
  forward — so every repo's provenance was permanently empty and `reresolve`
  would treat every committed key as an override forever. Without this, "a key
  the repo overrode survives... and is listed as an override" has nothing to
  test against. Closed by giving `cycle.plan`/`cycle.apply` an optional
  `provenance` parameter (seeding `state.json`'s metadata when given, instead
  of the carry-forward default) and having `commands.new` pass its
  `Resolution.provenance_metadata()` through on the first apply. `kiln init`
  (S4.5.8) will need the same wiring when it is built.
- **`ConfigManager.validate`/`reresolve` gained `allow_schema_upgrade`.**
  `validate` already refused any `schema_version` other than the running
  kiln's, naming `config-upgrade` for an older one — exactly what
  `config update`'s refusal bullet needed, with no new code, by just calling
  `reresolve` and letting the exception propagate. `config upgrade` needed a
  way to bypass only that refusal (never the "needs a newer kiln" one — there
  is no downgrading), so `reresolve(root, allow_schema_upgrade=True)` skips it
  and lets the rest of the merge proceed; the final merged document always
  carries the *current* `SCHEMA_VERSION` (`_defaults()`), so "migration" here
  is exactly a normal re-resolve once the stale-version refusal is out of the
  way — there is no field-level migration framework, and `SCHEMA_VERSION` has
  only ever been `1`, so nothing exercises one yet.
- **"The artifacts that would change"** (the config lifecycle table's own
  phrase) means rendered files, not config keys — matching `diff`/`apply`'s
  vocabulary. `commands._config_change_rows` renders the re-resolved config's
  artifacts and classifies them against the *current* `state.json` via
  `generation.plan`, the same engine `cycle.apply` uses, then reports every
  artifact whose action is not `unchanged` or `skip`. `--apply` reuses this
  same re-resolution to write `config.toml` and calls `cycle.apply` with the
  new `Resolution`'s provenance, so a later `config-update`/`config-upgrade`
  keeps working from an accurate baseline.
- **Tested against two repo shapes**, in `tests/test_config_lifecycle.py`: a
  repo built from a real local `--config` source (exercises the `[source]`
  re-fetch and a genuine `Resolution`'s provenance, but is not a full
  scaffold, so `--apply`'s post-apply checks are not exercised on it), and the
  `python-tool` golden `tests/test_apply.py` already builds on (passes every
  check, but — being hand-authored — carries no recorded provenance of its
  own, so the test seeds `state.json`'s `config_provenance` the way `kiln new`
  now would have left it, attributing every committed key to the flags layer).

## S4.5.5 — Lifecycle wiring

**Status:** done (2026-09-26) · **Unblocked 2026-09-25:** pykit
`feature/upgrade` at `1a8241b` or later has the `[lifecycle]` table, its
`namespace` key and `build_tool_app` (pykit ADR-0005).

The lifecycle verbs mounted under `kiln self` (`kiln self upgrade`,
`kiln self doctor`, …) by `rn-forge-tooling`'s `build_tool_app`, so they read as
managing the installed tool and `kiln doctor` keeps meaning the repository check
([tool lifecycle spec](../E3-realign-goldens-and-canon/F3.3-python-tool-is-a-tool.md)).

**Acceptance:**

1. `kiln --help` lists `self`; `kiln self --help` lists all six verbs
   (`install`, `upgrade`, `uninstall`, `cleanup`, `status`, `doctor`); a bare
   `kiln status` is a usage error.
1. `kiln --json self status` prints JSON with a `.version`.
1. After an upgrade, loading a committed config *warns* when it loads but a
   newer schema exists, and *errors* when it no longer validates. Both
   messages name `kiln config-upgrade`. One fixture config for each case.
   *(Built 2026-09-19; its two tests stay as they are.)*
1. `kiln doctor PATH` (the repository) and `kiln self doctor` (the install) both
   run and reach different targets.
1. The `python-tool` golden declares `[lifecycle]` and builds its app with
   `build_tool_app`; its own `task validate` passes.

### What pykit changed, and why the old plan is void

The plan written on 2026-09-21 added a `namespace` key to `[cli.lifecycle]`.
pykit instead **retired `[cli.lifecycle]` and its `target` key**
([pykit ADR-0005](https://github.com/rn-forge/pykit/blob/feature/upgrade/docs/adr/ADR-0005.md)).
Before building, read pykit's
`packages/rn-forge-tooling/docs/guides/lifecycle.md`, section *Exposing the
verbs on a command line*, and
`packages/rn-forge-tooling/tests/cli/test_lifecycle_commands.py` (the
`namespace` tests are the shape to copy). The contract kiln builds against:

- Lifecycle verbs are declared in a **top-level** `[lifecycle]` table, a sibling
  of `[cli]`, with keys `product` (required), `verbs` (optional, default all
  six) and `namespace` (optional).
- The app is built by `rn_forge.tooling.cli.lifecycle.build_tool_app(source)`,
  where `source` is a path or an already-parsed mapping of the whole document.
  It returns a `rn_forge.cli.CliApp`. `CliApp.from_config` no longer mounts
  any lifecycle verbs.
- With `namespace = "self"`, only `self` occupies the root, so a root
  `[[cli.commands]]` named `doctor` may sit beside `self doctor`.

## S4.5.8 — `kiln init`: bring an existing standard repository under kiln

**Status:** planned · **Depends on:** S4.5.2

`init --archetype A [--docs P] [--backend F] [--frontend W] [--config <path|git-url[@ref]>] [--force] [--dry-run] [--yes] [--json]`
is `new`'s configuration and first-apply flow for an existing repository. It is
not `adopt`: it accepts only a repository that already has kiln's standard
topology, and it does not infer an archetype, transform application source, or
run a third-party scaffold.

**Build:**

- Resolve the repository root from the current directory. Refuse when it is not
  a Git worktree root, is kiln's own source checkout, or lacks this
  standard-repository preflight set: `pyproject.toml`, `Taskfile.yml`,
  `tasks/`, `.github/`, `docs/`, `README.md`, `CLAUDE.md`, `AGENTS.md` and
  `.gitignore`. Name every failed condition. `init` never creates these
  preflight paths merely to satisfy the check.
- Accept the same selector and config-source flags as `new`; derive the
  repository name from the existing root directory. Require `--archetype` —
  `init` does not guess it from existing files. Preview resolves the config
  and reports the complete artifact plan, but writes nothing.
- With `--yes`, write the resolved config and run the normal artifact cycle,
  including the generated-state baseline and checks. Do not run `python`,
  frontend, docs, or instructions scaffolds: `init` operates on an existing
  repository and must not invoke `uv init`, `pnpm create`, or `nx g`.
- Without `--force`, a full-file collision whose bytes differ from its rendered
  managed artifact, or a pre-existing kiln block that has no state entry, is a
  conflict. Byte-identical managed files are recorded in the initial baseline
  without rewriting them. Abort before writing the config, state, or any
  artifact; report every conflicting path. A block absent from a repo-owned
  file is inserted normally and leaves the surrounding body intact.
- `--force` is an all-conflicts approval for this one-time command, not
  `apply`'s repeated per-artifact option. Warn before writes, copy every
  conflicting target — including `.rn-forge/kiln/config.toml` and `state.json`
  on a re-init — to `.rn-forge/kiln/backups/<UTC timestamp>/`, then overwrite
  managed files or replace the managed body of blocks. `--force` never implies
  `--yes`.
- Refuse if `.rn-forge/kiln/state.json` already exists. `--force` is the sole
  exception: archive the prior kiln state and targets, discard that state for
  planning, and execute the same initialisation flow against the supplied
  config. The archive is preserved if the new run fails.

**Tests:** `tests/test_init.py`, named `test_s4_5_8_…`; reuse the existing
standard-repository fixture shape from `tests/test_apply.py` rather than
creating a second synthetic topology.

**Acceptance:**

- From a valid existing standard repository whose managed files already equal
  their rendered outputs, `init --archetype python-app --docs mkdocs --yes`
  writes config and state without rewriting them. With differences, the same
  command plus `--force` produces the managed files and blocks of a fresh
  `new` repository with those selectors.
- A directory outside a Git worktree, kiln's own checkout, and a worktree
  missing each preflight path fail non-zero and leave no `.rn-forge/` entry.
- A conflicting managed file or an already-present managed block fails without
  `--force`, names all conflicts, and leaves every file, config and state byte
  unchanged.
- `init --force --yes` warns, archives every overwritten target beneath
  `.rn-forge/kiln/backups/<UTC timestamp>/`, then writes the selected
  standard; non-conflicting repo-owned bodies around inserted blocks remain
  unchanged.
- A second unforced `init` fails naming the existing state. A forced re-init
  archives the prior state and applies the new selectors as a first init.
- Neither initialisation path invokes `uv init`, `pnpm create`, or `nx g`.

## S4.5.9 — `kiln new` assembles in persistent staging

**Status:** done (2026-09-26) · **Depends on:** S4.5.1, S5.2.4

`kiln new` builds and reviews each generator's raw output before publishing a
finished repository. For this development phase the staging tree is persistent;
moving it beneath `${RNF_HOME}` and adding a cleanup command are separate work
for the tool release.

**Build:**

- Use `.staging/`, resolved from the invocation's current working directory, as
  the staging root. One invocation for repository `<name>` owns exactly this
  shape:

    ```text
    .staging/<name>/
      backend/
      frontend/
      workspace/
    ```

    Resolve `<name>` from the requested target directory's basename. Create
    `.staging/.gitignore` containing `*` so the staging root ignores itself and
    every retained scaffold when the invocation directory is inside any Git
    worktree; do not edit that worktree's own `.gitignore`.

- Refuse an existing `.staging/<name>/` before any scaffold or target write. Do
  not delete, replace or reuse it: retained staging output is review state.

- Write each third-party generator's completed output beneath its owning raw
  directory. Python's `uv init` output lands in `backend/`; the selected
  frontend generator's output lands in `frontend/`. Create both directories
  for every archetype, including when one remains empty, so the staging shape
  is stable.

- Reconcile `backend/` and then `frontend/` into `workspace/`, with the existing
  collision rules. Reconcile by copying: it must not move from or rewrite a
  raw tree, including when applying `web_dir` path rewrites. Write the
  resolved config to `workspace/`, then run docs and instructions scaffolds,
  `apply`, and kiln's post-apply checks there. No scaffold writes directly to
  the requested target.

- After the staged workspace passes, copy its complete contents into the
  requested empty target. Preserve all three staging directories after both
  success and failure; a failed run must leave the requested target empty.

- Add no `--keep-scaffold` flag and perform no automatic cleanup. Do not add
  `kiln clear` or `kiln staging clear`; one of those commands will own cleanup
  in a later story. Do not read `${RNF_HOME}` yet; relocation of the staging
  root is release work.

**Tests:** `tests/test_new.py`, named `test_s4_5_9_…`; subprocesses are stubbed
unless a pre-existing slow scaffold test already covers the path.

**Acceptance:**

- A successful `kiln new <target> --yes` retains
  `.staging/<name>/{backend,frontend,workspace}` and the target is
  byte-for-byte equal to the staged workspace.
- Backend and frontend raw outputs remain separately inspectable; files in the
  assembled workspace appear only after their owning reconcile runs, and the
  raw trees are byte-identical before and after reconcile.
- In a Git worktree, `git check-ignore .staging/<name>/workspace` succeeds
  without changing the worktree's existing `.gitignore`.
- A backend, frontend, reconcile, apply or post-apply-check failure retains the
  staging tree and makes no target write: an absent target remains absent and
  a supplied empty target remains empty.
- An existing `.staging/<name>/` is refused without changing staging or target.
- CLI help and `new`'s signature contain no scaffold-retention or cleanup flag;
  the implementation does not access `${RNF_HOME}`.

**What the build settled that the story did not say:**

- `python/scaffold.py` splits into `scaffold_backend(raw, config)` (the
  `uv init` calls) and `reconcile_backend(raw, workspace, config)` (copy, then

  remains as the two composed in place, for its existing tests.

  failed run leaves an absent target absent. A non-empty existing target is

- `_fail_on_errors` runs before the final report, so a failed post-apply check
