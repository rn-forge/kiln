E7's scope items 1 and 3: tag an `rn-forge-kiln` release, then each repository
moves its kiln pin with `task kiln:pin -- <ref>`
([S7.2.5](#s725-task-kilnpin-moves-a-repository-to-another-kiln-ref),
[ADR-0006](../../../adr/ADR-0006.md)) and runs `kiln config upgrade --apply`.
Added 2026-10-17 by S6.1.14, so that E7's `Active` state has a feature to agree
with.

Since [F7.4](F7.4-kiln-runs-beside-the-repository.md), a repository's kiln pin
is `[kiln] ref` in `.rn-forge/kiln/config.toml`, not a dev dependency. It is a
release tag or a commit SHA; a branch is refused, and a SHA taken from a branch
records that branch as `[kiln] track`. A repository moves its pin with
`task kiln:pin -- <ref>`
([S7.2.5](#s725-task-kilnpin-moves-a-repository-to-another-kiln-ref),
[S7.2.6](#s726-the-pin-task-passes-its-ref-as-an-option)), which writes the ref
and re-renders with the kiln at that ref in one run.

**What the tag is for, now that pins are SHAs (owner decision, 2026-11-19).** A
SHA pin already makes every repository reproducible, so the tag no longer exists
to get repositories off a moving branch. It still does three things: it merges
release 1 to kiln's `main`; it moves `archetypes.KILN_REF`, the ref `kiln new`
pins, off `feature/v1`, which stops moving once it is merged; and it gives
release 1 a name a repository can pin and a spec can wait on (S7.2.3, pykit's
F21.5).

## Context

**The version (owner decision, 2026-10-31).** The tag is `v0.1.0`, the version
in `pyproject.toml`. "Release 1" names the scope and is not a version number.

**Distribution.** kiln stays on git, through `uvx --from git+…@<ref>`.
Publishing it to PyPI stays the idea `kiln-on-pypi`.

**Repository-owned cleanup.** The 2026-11-03 rehearsal's finding #13 was stale
comments in pykit's `.importlinter`. This is pykit's cutover cleanup, with no
kiln implementation required.

**Order matters.** `KILN_REF` names a tag that does not exist until the commit
that names it reaches `main` and `release` runs, so that commit is the last one
before the merge. Nothing renders from it before the tag exists.

## S7.2.5 — `task kiln:pin` moves a repository to another kiln ref

**State:** Closed (2026-11-13)

One verb moves a repository's kiln pin to any ref (a tag, a branch or a SHA,
higher or lower) and re-renders with the kiln at that ref, so the move is one
command and one reviewable diff. It is named `pin`, not `upgrade`, because the
move can go in either direction; the docs already say kiln is *pinned* by
`[kiln] ref` (owner decision, 2026-11-13).

**Build — tests first:**

- `tests/test_pin.py`: the `kiln pin` command, against a scaffolded repository.
- `tests/modules/tasks/test_artifacts.py`: the rendered task.

**Build:**

- `commands.py`: `pin(ref: str) -> None`, registered in `cli.toml` as `pin`. It
  reads the committed config with `ConfigManager`, sets `[kiln] ref` to *ref*,
  writes it with `_write_config`, and prints `kiln ref <old> → <new>`. It
  writes nothing else and does not apply. An empty or whitespace *ref* raises
  `AppException`. It does not check that the ref exists; the task does.

- `modules/tasks/templates/tasks/kiln.yml.j2`: a public `pin` task, reached as
  `kiln:pin`. A `precondition` fails with `pass a kiln ref after --` when
  `CLI_ARGS` is empty. Its `desc:` is "Move kiln to another ref (tag, branch
  or SHA) and re-render with it. Pass the ref after `--`." Its commands, in
  order:

    1. `kiln_command(<ref>)` with `version`, so a ref that does not resolve fails
       before anything is written;
    1. `{{.KILN}} pin <ref>`, the current kiln writing the ref;
    1. `kiln_command(<ref>)` with `apply`, the new kiln rendering.

    `<ref>` is `{{.CLI_ARGS}}`. The `kiln_command` prefix needs a new context key,
    `kiln_git` (`archetypes.KILN_GIT`), so the template builds the `uvx --from`
    string for a ref known only at run time.

- Not rendered in kiln's own repository (`config.module == "rn_forge.kiln"`),
  which runs its working tree.

- `docs/adr/ADR-0007.md`: the developer surface gains `kiln:pin`, with a dated
  line under `## Background`.

- `docs/adr/ADR-0006.md`, *Consequences*: "a one-line `config.toml` change
  followed by `kiln apply`" becomes `task kiln:pin -- <ref>`, with a dated
  line.

- `modules/instructions/templates/standard.md.j2` and the tasks architecture
  page: how to move the pin. The standard's task table picks up the task from
  the rendered file.

- The goldens are re-seeded.

**Not in scope.** If the target kiln wants another `schema_version`, step 3
fails with the existing message that names `kiln config-upgrade`, and the
developer runs it from the new ref. Moving to a ref older than the config's
schema fails the same way. Neither is automated. A ref from before this story
renders no `kiln:pin` and has no `kiln pin`, so the way back from it is the hand
edit and two applies described above.

**Acceptance:**

- `test_s7_2_5_1_writes_only_the_ref`: `kiln pin v9.9.9` changes only
  `[kiln] ref` in `config.toml` and no generated file.
- `test_s7_2_5_2_empty_ref`: `kiln pin ""` exits non-zero and writes nothing.
- `test_s7_2_5_3_task_order`: a rendered `tasks/kiln.yml` has a public `pin`
  task whose commands are `version`, `pin` and `apply`, in that order. The
  first and last run
  `uvx --from "rn-forge-kiln @ git+https://github.com/rn-forge/kiln@{{.CLI_ARGS}}"`,
  and the second runs `{{.KILN}}`.
- `test_s7_2_5_4_precondition`: the task has the empty-`CLI_ARGS` precondition.
- `test_s7_2_5_5_not_in_kiln`: kiln's own render has no `pin` task.
- `task validate` and `task self:golden:validate` pass.
- Not scriptable, judged by the owner: on pykit, `task kiln:pin -- feature/v1`

## S7.2.6 — The pin task passes its ref as an option

**State:** Closed (2026-11-17)

`kiln pin`'s `ref` has a default since S18.14.2, so the CLI exposes it as the
option `--ref`, not as a positional argument. The rendered task still passes
`{{.CLI_ARGS}}` positionally, so `task kiln:pin -- <ref>` fails with a usage
error and writes nothing. `task kiln:pin --ref <ref>` is no way round it:
go-task reads `--ref` as its own flag and prints its help. A positional optional
argument is not open to kiln, because its import contract keeps `typer` out of
product code, so the task passes the flag. Found by the owner, 2026-11-17.

**Build:**

- `modules/tasks/templates/tasks/kiln.yml.j2`: the `pin` task's first command
  becomes `{{.KILN}} pin{{if .CLI_ARGS}} --ref {{.CLI_ARGS}}{{end}}`, so no
  argument still follows `track`. The second command and the task's `desc:` do
  not change.
- `commands/config.py`, `pin`'s docstring: name the option `--ref` where it says
  REF.
- The tests that pinned the old string expect the new one, and one test proves
  the rendered command parses: with `CLI_ARGS` set,
  `task --dry kiln:pin -- <sha>` prints `pin --ref <sha>`, and kiln's CLI,
  given those arguments, pins the ref.

**Not in scope.** The CLI surface does not change. The `[kiln]` that `--help`
drops from the docstring is the pykit F23.1 pin
([F7.7](F7.7-kiln-installs-as-a-tool.md)).

**A repository whose rendered task predates this story** passes the flag itself,
once: `task kiln:pin -- --ref <ref>`. That run renders the fixed task.

**Acceptance:**

- A rendered `tasks/kiln.yml`'s `pin` task runs
  `{{.KILN}} pin{{if .CLI_ARGS}} --ref {{.CLI_ARGS}}{{end}}` first.
- `task --dry kiln:pin -- <sha>` on a rendered repository prints
  `pin --ref <sha>`; `task --dry kiln:pin` prints `pin` with no `--ref`.
- kiln's CLI run as `pin --ref <sha>` in a scaffolded repository exits `0` and
  sets `[kiln] ref`.
- `task validate` passes. Tests: `test_task_order`,
  `test_the_pin_task_passes_the_ref_as_an_option`,
  `test_the_pin_task_with_no_ref_runs_bare_pin` and
  `test_the_cli_takes_the_ref_as_an_option`, which also proves the positional
  form is refused.
- Not scriptable, judged by the owner: ngkit, whose `[kiln] ref` is still the
  branch `feature/v1`, moves to a SHA with
  `task kiln:pin -- --ref feature/v1`, and a second `task kiln:pin` with no
  argument is a no-op diff.

## S7.2.2 — `v0.1.0` is tagged

**State:** New · **Depends on:** S7.2.1, S7.2.4

Held by the owner (2026-11-02) until S7.2.4 is done.

*Rewritten 2026-11-19 (owner decision).* Pins are SHAs now, so this story is no
longer what makes repositories reproducible. It merges release 1 to `main`,
moves the ref `kiln new` pins off `feature/v1`, and names the release (see the
feature's opening). Dropping the tag and setting `KILN_REF = "main"` was
rejected: S7.2.3 and pykit's F21.5 wait on a named release.

**The catch.** `kiln new` resolves `KILN_REF` to a SHA and records `KILN_REF` as
`[kiln] track` (`commands/new.py`). That is right for a branch and wrong for a
tag: a tag is pinned as itself, with no `track`, as `kiln pin` already does
through `kiln_ref.target`.

**Build — tests first:**

- `tests/test_archetypes.py`, `test_s7_2_2_1_kiln_ref_is_the_release`:
  `archetypes.KILN_REF == "v0.1.0"`.
- `tests/commands/test_new_flags.py`: the two assertions that expect
  `{"ref": <sha>, "track": archetypes.KILN_REF}` expect `{"ref": "v0.1.0"}`,
  and `test_s7_2_2_2_new_pins_a_tag_without_track` proves `kiln new` writes no
  `track` when `KILN_REF` is a tag.

**Build:**

- `commands/new.py`: the `kiln.ref` and `kiln.track` flags come from
  `kiln_ref.target(archetypes.KILN_REF, None)`; `kiln.track` is set only when
  `target` returns one.
- `archetypes/__init__.py`: `KILN_REF = "v0.1.0"`, and its docstring loses
  "until a kiln release is tagged".
- kiln's own `.rn-forge/kiln/config.toml` has no `[kiln]` table and runs its
  working tree, so it does not change. Run `task kiln:apply`, which re-renders
  every file that names `KILN_REF`, then `task lint KILN_DOCTOR_FULL=1`.
- The goldens are re-seeded.
- `docs/releases/release-1/index.md`: status `shipped (<date>)`.
- The owner merges `feature/v1` to `main`. `release` tags `v0.1.0`.

**Acceptance:**

- `git ls-remote --tags origin v0.1.0` prints the tag.
- `uvx --from git+https://github.com/rn-forge/kiln@v0.1.0 kiln --help` exits
  `0`.
- `kiln new` from that tag writes `[kiln] ref = "v0.1.0"` with no `track`, and
  the new repository passes `task setup && task validate`.
- `task validate` and `task self:golden:validate` pass.

**No branch-ref check.** Finding #6 of the 2026-11-03 rehearsal proposed a
