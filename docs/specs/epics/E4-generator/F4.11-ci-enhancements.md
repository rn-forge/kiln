kiln's generated CI keeps improving after it matches the upstream CI
([F6.3](../E6-rebuild-the-repos/F6.3-hardened-ci.md)): what a repository may add
to it, and what the checks enforce on it, under one CI contract
([ADR-0016](../../../adr/ADR-0016.md)). Each story here is one such change.

[S4.11.1](#s4111-repositories-extend-the-generated-ci-by-reference) lets a
repository extend the generated CI only through files it owns: hooks at named
anchors, and declared jobs that call reusable workflows. kiln never guesses a
repository's needs and no repository hand-maintains its CI. kiln's own
self-hosting ([S4.8.1](F4.8-self-hosting.md#s481-kiln-generates-itself)) is the
first consumer; pykit retiring its hand-written `main.yml` is a likely next one.

## Design

### Extension by reference (S4.11.1)

- **`[ci.hooks]`.** A closed set of anchors; this story ships `setup`, a list of
  local composite actions the generated setup action runs as its last steps.
  Each entry matches `^\./\.github/actions/[a-z0-9][a-z0-9-]*$`, is not
  `./.github/actions/setup` (kiln's own), and is unique. Default: none, and
  the setup action is then byte-identical to before.
- **`[[ci.jobs]]`.** `uses` replaces `task`: a path
  `./.github/workflows/<file>.yml` (or `.yaml`), not `ci.yml`. The job renders
  as a reusable-workflow call after `validate`, and `ci-ok` needs it. `name`
  and `events` are as S4.8.3 settled them.
- **No `runs-on`, `timeout-minutes` or `steps`** on a call: GitHub refuses them.
  The called workflow's jobs carry their own timeouts, and S6.3.1's rule
  applies to them as authored. No `secrets:`: a job that needs secrets is a
  later ADR revision.
- **`ci.node` is removed.** `python-web-app` keeps its Node steps, gated on the
  archetype alone as before S4.8.3.
- **The repository's files are held to the same standard.** `ci-pins` reads what
  the repository owns under `.github/`, and `ci-entrypoint` its workflows (not
  its composite actions); the new `ci-hooks` checks that each hook and
  declared job names a file that exists and that a declared job's workflow can
  be called.

## S4.11.1 — Repositories extend the generated CI by reference

**State:** New · **Depends on:** S4.8.3

S4.8.3's build recorded the risk: the setup action's Node steps carry no pnpm
`version:` and no `node-version:`, because `python-web-app` has `packageManager`
and a lockfile to supply them, and kiln has neither a `package.json` nor a
lockfile. The hand-copied `golden-render` job passes `version: 12` and
`node-version: 24`; no key in `[ci] node` can say that, and a key that did would
have kiln guess a repository's Node needs. [ADR-0016](../../../adr/ADR-0016.md)
is revised (2026-10-19) to extend the generated CI by reference to files the
repository owns: hooks at named anchors, and declared jobs that call reusable
workflows. This story builds that, and supersedes S4.8.3's `ci.node` and the
`task` field of `[[ci.jobs]]`. Nothing here changes kiln's own `ci.yml`, which
stays hand-copied until S4.8.1.

## S4.11.2 — Pull requests run `ci-pins` and `ci-hooks`

**State:** New · **Depends on:** S4.11.1

`task validate` reaches `kiln doctor` only through `lint`'s internal tasks, each
of which runs `kiln doctor . --only <check>`: `generated`, `rn-forge-deps`,
`task-layout`, `ci-entrypoint` and the docs checks. `ci-pins` has no lint task,
and `ci-hooks` (S4.11.1) will have none. Both are `ownership` checks in
`CHECKS`, so a bare `kiln doctor` runs them, and `lint:generated` runs a bare
`kiln doctor . --full` only when `KILN_DOCTOR_FULL` is set; the generated
`ci.yml` sets it only for a push to the default branch and for
`workflow_dispatch`. So an unpinned action, a job without `permissions:`, or a
hook or declared job whose file is missing passes a pull request and fails only
after the merge. [ADR-0016](../../../adr/ADR-0016.md) holds a repository's own
files to these checks; this story makes a pull request enforce them, by giving
each its own lint task, shaped as `lint:ci-entrypoint` is, that `lint` runs.
