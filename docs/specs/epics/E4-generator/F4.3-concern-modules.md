# F4.3 — The concern modules, with templates

Epic: [E4](index.md) · Phase step: D.3 · Design:
[template inventory](design.md#template-inventory),
[apply sequence](design.md#apply-sequence) · **Depends on:**
[F4.2](F4.2-core-module.md); the [E3](../E3-realign-goldens-and-canon/index.md)
goldens, which the templates are written from

In apply order, one at a time, each with its config model, options, Jinja
templates written from the E3 goldens, and `checks()` = its checks functions +
its render-dependent checks (`artifact.stale`, `block.stale`).

**Every story in this feature is done only when, for its module, tests show
that:**

1. Rendering a small config for each Python archetype produces exactly the
   module's rows of the template inventory.
1. Into an empty directory, the module's artifacts classify only `CREATE`,
   `INSERT` or `SKIP`.
1. A second apply is all `UNCHANGED`.
1. Each rendered file equals its counterpart in the E3 goldens, apart from name
   and provenance-version lines.
1. Each of the module's checks fails on a fixture that breaks its rule, and
   passes on the rendered output.

The story-specific acceptance below is in addition to these. Property 4
normalizes exactly one thing: the version in a `Generated by kiln <version>`
provenance line. Every other byte — names, package lists, paths — comes from the
golden's own `config.toml`, which the test loads.

**Build a story by the [board's procedure](../../index.md#building-a-story).**
Each story below carries a **Build** list naming the files, functions and
template context it expects; a build that departs from it records why under
*What the build settled*, as S4.3.1 and S4.3.2 do.

## S4.3.1 — `python`

**Status:** done (2026-09-16)

`uv init` + reconcile, `.importlinter`, pyproject check 8a including `[project]`
identity ([ADR-0005](../../../adr/ADR-0005.md)), rn-forge dependency set incl.
`lifecycle`.

**Acceptance:**

- The scaffold step runs `uv init` into an empty directory, and the reconcile
  leaves a `pyproject.toml` that check 8a passes.
- Check 8a *warns*, and does not error, when a `[tool.ruff]` value or
  `[project] name` differs from the expected value. kiln never writes either.
- `lint-imports` passes on the rendered `.importlinter` in each archetype.
- The dependency check refuses a render missing a required rn-forge package.
  `lifecycle = true` adds `rn-forge-tooling` to the required set.

What the build settled that the story did not say:

- **`lifecycle` already reached the dependency set before this story.**
  `archetypes.for_config` (built in F4.2) adds `rn-forge-tooling` to both the
  required and allowed sets when `config.lifecycle` is true, and
  `rn_forge_deps.check` already reads through it. S4.3.1 needed no change here
  — only the tests in `tests/modules/python/checks/test_rn_forge_deps.py`
  already covered it.
- **Check 8a's expected values live as module-level constants in
  `modules/python/checks/pyproject.py`**, not in `archetype.toml` or a data
  template: `REQUIRES_PYTHON`, `PYRIGHT_EXPECTED`, `PYTEST_ADDOPTS`,
  `RUFF_TEST_IGNORES` and `DEV_GROUP_TOOLS`. They are read back by
  `modules/python/scaffold.py`'s reconcile step, so the two halves of check 8a
  — what it verifies, and what the scaffold writes — cannot drift apart.
- **Check 8a's scope is a defined subset, not every key in the named tables.**
  It compares: `[project].name` and `.requires-python` (root `pyproject.toml`
  only); `[tool.pyright].typeCheckingMode` and `.reportMissingTypeStubs`;
  `[tool.pytest.ini_options].addopts`; `[tool.ruff.lint.per-file-ignores]` for
  a `tests/*`-suffixed key covering at least `S101 D ANN PLR2004`; and
  `[dependency-groups].dev` (root only) for the five base distribution names
  `import-linter pyright pytest ruff rn-forge-kiln`, ignoring version pins.
  Fields no template varies by archetype (`venvPath`, `include`, `testpaths`,
  coverage settings) are left unchecked — the goldens differ on them per
  archetype shape, and the story only asks for a *defined* subset, not a
  full-table diff.
- **The scaffold function is
  `modules/python/scaffold.py:scaffold(root, config) -> None`.** It shells out
  to `uv init` (`Process.execute`, the same `rn-forge-commons` subprocess
  wrapper `rn_forge_deps` and other kits use), once per package — the repo
  itself for `python-app`/`python-tool`, the workspace root plus each
  `config.packages` entry for `python-lib` — with `--vcs none --no-readme` so
  it never fights `instructions`' seeded `README.md` or creates a nested
  `.git`. It then reconciles every `pyproject.toml` in
  `archetypes.pyproject_paths(config)` via
  `rn_forge.commons.fs.documents.DocumentUtils.update`, which deep-merges into
  the tomlkit document `uv init` wrote and preserves its comments. It does not
  add rn-forge dependencies: that is `rn_forge_deps`'s concern, is business
  logic the scaffold cannot infer, and check 8a never tests for it. Not yet
  wired into a CLI — [F4.5](F4.5-cli.md) does that. *Revised by
  [S4.3.7](#s437-the-scaffold-completes-pyprojecttoml): the required set is
  config, so the scaffold writes it after all.*
- **`.importlinter` is one template with an `is workspace` branch**, not two
  templates, since `python-app` and `python-tool` render byte-identical text
  apart from the package name and `python-lib` only differs by the workspace
  clauses (`root_packages` vs `root_package`, the independence contract). The
  per-package list lines are pre-joined in `artifacts.py` before being handed
  to Jinja (`members_block`), rather than looped in the template: Jinja's
  `-%}` whitespace control strips leading indentation along with the newline,
  which silently de-indented the `source_modules`/`modules` entries when a
  `{% for %}` tag tried to do it inline.

## S4.3.2 — `docs`

**Status:** done (2026-09-16)

Tree, `_areas.yml`, `_structure.md`, `mkdocs.yml` nav block.

**Acceptance:**

- `docs.profile = "none"` and `"external"` render no docs artifacts. `"mkdocs"`
  renders the tree, and `mkdocs build --strict` passes on it.
- An edited `_areas.yml` survives apply (`SKIP`), and the docs structure check
  validates against the edited copy.
- Adding a page and re-applying updates only the nav block. The body of
  `mkdocs.yml` keeps its bytes.

What the build settled that the story did not say:

- **The module contract is now `artifacts(config, root)`**, matching
  `checks(config, root)`. The nav block is rendered from the docs tree on
  disk, which `artifacts(config)` could not reach. Every module takes `root`,
  and every module but `docs` ignores it.
- **The nav is rendered from the tree as it will be after apply.** Rendering
  writes nothing, so when a seed is absent — always, on a new repo —
  `modules/docs/artifacts.py` copies `docs/` into a scratch directory, writes
  the absent seeds there and builds the nav from that copy. When every seed is
  present it reads `docs/` directly.
- **The body of `mkdocs.yml` comes from a scaffold step**, not a seeded
  artifact: `modules/docs/scaffold.py:scaffold(root, config)` writes it from
  `templates/mkdocs.yml.j2` when it is absent. Like `python`'s scaffold, it
  runs once, from `kiln new`, and is not wired to a CLI until
  [F4.5](F4.5-cli.md). A seeded body with a block would not work: tooling's
  engine refuses a whole-file write and a block write to the same path in one
  apply, and the goldens' `state.json` has no `mkdocs.yml` entry.
- **`nav:` is the last key of `mkdocs.yml`**, followed by a blank line and then
  the block. `ManagedBlock.render` appends an absent block at the end of the
  file, after a blank line, so this is the only layout that a fresh `INSERT`
  produces. The three goldens and kiln's own `mkdocs.yml` were changed to it,
  and the comment explaining the block moved above `nav:`. The block bodies,
  and therefore the `state.json` hashes, did not change.
- **Seeded index pages are the goldens' pages without the repo's own entries.**
  `docs/index.md` and the `architecture`, `guides`, `runbooks` and `adr` index
  pages in a golden list pages that the golden wrote. The seed cannot link
  pages that do not exist, and `mkdocs build --strict` would fail if it did.
  It also omits the `reference/` link, because that area is generated and
  absent in a new repo. Property 4 checks these five pages by requiring that
  the seed's lines appear in the golden's lines, in order. Every other seed
  must equal its golden byte for byte. The nav block must equal the golden's,
  and the scaffolded body plus the block must equal the golden's `mkdocs.yml`,
  apart from `site_name` and `site_description`.
- **Property 3 reads `SKIP` for seeds, not `UNCHANGED`.** The engine never
  inspects a seed that is present. Every other artifact is `UNCHANGED`.
- **Property 5 needs an instruction file.** The `docs-structure` check needs
  `CLAUDE.md` or `AGENTS.md` to point at the docs rules, and `instructions`
  (S4.3.5) does not render one yet. The tests write a minimal `CLAUDE.md`.
- **The python-lib golden said `golden-cli`** in `docs/architecture/index.md`.
  The repo is `golden-lib`, and the golden was corrected.

## S4.3.3 — `tasks`

**Status:** done (2026-09-16)

`Taskfile.yml`, `tasks/*.yml`, repo-owned includes, `extra_refs`,
`command_overrides`.

**Renders** (property 1, in this order):

| Artifact | Kind | When |
| -- | -- | -- |
| `Taskfile.yml` | managed | always |
| `tasks/workspace.yml` | managed | always |
| `tasks/quality.yml` | managed | always |
| `tasks/docs.yml` | managed | `docs.profile = "mkdocs"` |
| `<include.taskfile>`, one per `[tasks].includes` entry | seeded | config order |

**Build:**

- `modules/tasks/artifacts.py` exposes `render(config) -> list[Artifact]`, and
  `TasksModule.artifacts` calls it through the same late import
  `modules/python/__init__.py` uses. Templates live in
  `modules/tasks/templates/`: `Taskfile.yml.j2`, `tasks/workspace.yml.j2`,
  `tasks/quality.yml.j2`, `tasks/docs.yml.j2`, `tasks/include.yml.j2`. One
  template per artifact, branching on the context — never one template per
  archetype.
- The context is exactly: `kiln_version`; `name`; `package`
  (`python.artifacts.root_package(name)`, the `--cov=` target); `workspace`
  (`config.archetype == "python-lib"`); `packages` (the basename of each
  `config.packages` entry, in order — `golden-alpha golden-beta`); `docs`
  (`config.docs_profile == "mkdocs"`); `site_dir` (`[docs].site_dir`);
  `includes`; `extra_refs`; `overrides` (see below).
- **Write each template by diffing the three goldens.** `python-app` and
  `python-tool` differ only in `name` and `package`. `python-lib` differs in:
  the `PACKAGES` var and the `for:` loops in `quality.yml`'s `lint:python`,
  `format:python`, `typecheck:python`, `test:python` and `test:coverage`;
  `workspace.yml`'s `install`, `version` and `build`; the `desc:` of
  `Taskfile.yml`'s `build` and `version`; and the explanatory comment blocks
  at the top of `quality.yml` and `workspace.yml`. Every one of those hunks is
  `{% if workspace %}`. The goldens assume members live at `packages/<name>`;
  `render` raises `AppException` naming the entry for any other layout.
- **Without `mkdocs`** the `docs:` include line, `validate`'s `docs:build` call,
  `lint`'s `quality:lint:docs`, `quality:lint:docs-structure` and
  `quality:lint:docs-nav` calls, and `quality.yml`'s `lint:docs`,
  `lint:docs-structure` and `lint:docs-nav` tasks are absent. Nothing else
  changes: `lint:markdown` and `workspace:install` keep their `--group docs`,
  because the `docs` dependency group exists in every archetype
  ([S4.3.7](#s437-the-scaffold-completes-pyprojecttoml)).
- **Includes.** Each `[tasks].includes` entry adds `<namespace>: <taskfile>` to
  `Taskfile.yml`'s `includes:` after the generated ones, and one seeded
  artifact at `<taskfile>` whose content is `tasks/include.yml.j2`: a
  `# Seeded by kiln — this file is yours.` comment, `version: "3"`, and
  `tasks: {}`. A seeded file is never rendered again.
- **`extra_refs`** appends `- task: <ref>` to the named root verb's `cmds:`,
  after the generated calls, in list order. A key that is not one of the ten
  root verbs is a config error: add a `field_validator` to `TasksConfig` that
  raises `ValueError` naming the key, so the failure carries its dotted path
  like every other config error.
- **`command_overrides`** replaces the whole `cmds:` list of the named inner
  task with the one override string. The key is fully qualified
  (`quality:test:python`). `render` raises `AppException` naming an unknown
  key and listing the tasks the archetype renders. Pass the overrides to the
  templates as `overrides`, a `dict[str, str]`, and look each task up with
  `overrides.get("quality:test:python")` at the point it renders its `cmds:`.
- The only check is the existing `task-layout`
  (`modules/tasks/checks/layout.py`). Do not add one.

**Tests:** `tests/modules/tasks/test_artifacts.py`, named
`test_s4_3_3_property<n>_…` and `test_s4_3_3_<bullet>_…`, copied in shape from
`tests/modules/docs/test_artifacts.py`. Property 4 loads each golden's own
config, so `name`, `package` and `PACKAGES` match without normalizing; only the
provenance line's version is normalized.

**Acceptance:**

- `task --list --json`, run in a rendered repo, lists exactly the ten root
  verbs; in an `mkdocs` repo it also lists exactly
  `docs:build docs:serve docs:nav docs:structure`. Run `task` as a subprocess
  in the test; go-task is on `PATH` wherever kiln's tests run.
- A repo-owned include is seeded once, `task --list-all` succeeds with it
  present, and an edit to it survives apply (`SKIP`).
- An `extra_refs` entry is reachable from `validate` (assert with
  `layout.reachable_from`), and `task-layout` passes on the result. An
  `extra_refs` key that is not a root verb fails config load naming
  `tasks.extra_refs.<key>`.
- A `command_overrides` entry replaces that task's `cmds:` and nothing else; an
  unknown key raises naming it.
- Without `mkdocs`, the rendered `Taskfile.yml` and `quality.yml` contain no
  `docs` reference, and `task-layout` passes on them.

What the build settled that the story did not say:

- **The Jinja variable delimiters are `[[ ]]`, not `{{ }}`, for every template
  in this module.** `TemplateEngine` forwards `**environment_kwargs` to
  `jinja2.Environment`, so `artifacts.py` passes
  `variable_start_string="[[", variable_end_string="]]"`. The goldens'
  `tasks/*.yml` carry go-task's own `{{.CLI_ARGS}}`, `{{.PACKAGES}}`,
  `{{.ROOT_DIR}}` and `{{.ITEM}}` verbatim (`python-lib`'s `version`, `build`
  and `test:coverage`); with Jinja's default delimiters those collide and
  raise a template syntax error. Changing the delimiter, once, for the whole
  engine instance was simpler than `{% raw %}`-fencing every go-task
  reference.
- **`config.document.tasks` and `config.document.docs.site_dir` are read with
  the same defensive `getattr` + `isinstance` pattern
  `KilnConfig.docs_profile` and `KilnConfig.packages` already use** — inline
  in `modules/tasks/artifacts.py` as `_tasks_config` and `_site_dir` — rather
  than adding new properties to `KilnConfig` itself or to the `docs` module,
  since neither story asked for that and the pattern already exists for
  exactly this purpose.
- **`workspace.yml`'s `UV_CACHE_DIR` is `/tmp/{{ name }}-uv-cache`.** The three
  goldens differ only in the repo name embedded in that path
  (`/tmp/golden-tool-uv-cache`, `golden-app`, `golden-lib`); `name` is already
  in the fixed context list, so no new key was needed.
- **`workspace.yml`'s `clean` task removes `{{ site_dir }}`, not a literal
  `.docs-site`.** Every golden happens to use the default, so the two render
  identically, but `site_dir` is already in the fixed context and `clean`
  removing the *configured* docs output directory is the simpler, more correct
  reading — there is nothing to write down as a divergence if the config is
  ever changed.
- **A `python-lib` package not laid out at `packages/<name>` is a render-time
  `AppException`, not a config error**, since the layout rule is about what
  the `tasks` templates can express (`vars: PACKAGES`, the `for:` loops), not
  about the shape of `[archetype."python-lib"].packages` in isolation;
  `render` checks `Path(package).parts[:-1] == ("packages",)` before building
  context.
- **`overrides.get(...)` is checked in every inner task of `workspace.yml`,
  `quality.yml` and `docs.yml`**, not only `quality:test:python` (the story's
  one example) — `workspace:install`, `workspace:version`, `workspace:build`,
  `workspace:clean`, every `quality:*` task, and every `docs:*` task all
  accept an override at the same `cmds:` site. Restricting it to one
  hard-coded key would have made the feature accidentally partial.
- **`extra_refs`' vocabulary check lives in `TasksConfig` as a
  `field_validator`** (static — the ten root verbs never change), while
  **`command_overrides`' vocabulary check lives in `render()`** (the archetype
  and `docs.profile` decide which tasks exist, and only `render` has both), as
  the Build list already distinguishes.
- **`tests/modules/core/test_cycle.py`'s S4.2.3 test now expects `Taskfile.yml`,
  `tasks/workspace.yml` and `tasks/quality.yml`** among a fresh apply's
  created files, alongside `.importlinter` (added there by S4.3.1). That test
  exercises the full default module registry, so it necessarily grows with
  every module that gains real artifacts; no other test outside
  `tests/modules/tasks/` needed a change.

## S4.3.4 — `cicd`

**Status:** done (2026-09-16) · **Depends on:** the defaults recorded in
[S4.3.6](#s436-the-sonar-decisions) — the build proceeds on them; the owner's
confirmation is that story's, not this one's

Workflows, `.github/actions/setup`, `sonar-project.properties`, the pin set
([ADR-0006](../../../adr/ADR-0006.md)).

**Renders** (property 1, in this order):

| Artifact | Kind | When |
| -- | -- | -- |
| `.github/actions/setup/action.yml` | managed | always |
| `.github/workflows/ci.yml` | managed | always |
| `.github/workflows/docs.yml` | managed | `docs.profile = "mkdocs"` |
| `sonar-project.properties` | managed | `ci.sonar = true` |

`ci.provider = "ado"` is reserved: `render` raises `AppException` naming
[E8](../E8-ado-provider/index.md).

**Build:**

- `modules/cicd/artifacts.py` exposes `render(config) -> list[Artifact]`;
  templates in `modules/cicd/templates/`: `action.yml.j2`, `ci.yml.j2`,
  `docs.yml.j2`, `sonar-project.properties.j2`.

- **The pin set is `modules/cicd/pins.toml`**, read with `tomllib` through
  `importlib.resources.files("rn_forge.kiln.modules.cicd")`, one table per
  action, copied from the goldens:

    ```toml
    [checkout]
    uses = "actions/checkout"
    sha = "3d3c42e5aac5ba805825da76410c181273ba90b1"
    version = "v7.0.1"
    ```

    Tables: `checkout`, `setup-uv`, `setup-task`, `sonarqube-scan`, `gh-release`,
    `upload-pages-artifact`, `deploy-pages`. A template writes
    `uses: {{ p.uses }}@{{ p.sha }} # {{ p.version }}` and never a literal SHA.
    The design's `archetypes/_shared/pins.toml` location is superseded by this.

- The context is: `kiln_version`; `name`; `workspace`; `packages` (basenames,
  the release matrix); `docs`; `sonar`; `release` (`"tag-exists"` or
  `"none"`); `pins`.

- **Write each template by diffing the goldens.** `python-app` and `python-tool`
  render byte-identical CI apart from `sonar-project.properties`' two name
  lines. `python-lib` differs in `ci.yml`'s header comment, the `release`
  job's `strategy.matrix.package`, and the four `matrix.package` substitutions
  in its steps; and in `sonar-project.properties`' `sonar.sources` and
  `sonar.tests`, which are the comma-joined `packages/<name>/src` and
  `packages/<name>/tests`.

- **`ci.sonar = false`**: the `sonar` job is absent and `release.needs` is
  `[validate]`. **`ci.release = "none"`**: the `release` job is absent.
  Everything else keeps its bytes.

- `sonar.projectKey` is `rn-forge_{{ name }}`, `sonar.projectName` is
  `{{ name }}`, and `sonar.organization` is the constant
  `SONAR_ORGANIZATION = "rn-forge"` in `artifacts.py`. Making the organization
  a config key is not this story.

- **A second check, `ci-pins`**, in `modules/cicd/checks/pins.py`:
  `NAME = "ci-pins"`; `ci.unpinned` (error) for a `uses:` whose ref after `@`
  is not 40 hex characters or that lacks a trailing `# <version>` comment —
  `uses: ./…` is exempt; `ci.permissions` (error) for a job under `jobs:` with
  no `permissions:` key. It reads every `*.yml` under `.github/workflows/` and
  `.github/actions/` with `yaml.safe_load` plus a line scan for the comment.
  Register it in `CicdModule.checks` and in `checks.py`'s `CHECKS` right after
  `entrypoint`. No task wiring: [F4.6](F4.6-doctor.md) folds every check into
  `task lint`.

- `KILN_DOCTOR_FULL` is not rendered here; [S4.6.4](F4.6-doctor.md) adds it.

**Tests:** `tests/modules/cicd/test_artifacts.py` and
`tests/modules/cicd/checks/test_pins.py`, `test_s4_3_4_…` names.

**Acceptance:**

- `actionlint` passes on every rendered workflow, for each archetype, with
  `sonar` on and off. The test runs `actionlint` as a subprocess and calls
  `pytest.skip` with a reason when it is not on `PATH`; the feature block
  below runs it unconditionally.
- `ci-pins` passes on the rendered output, reports `ci.unpinned` on a fixture
  whose `uses:` names a tag, and `ci.permissions` on a job without the key
  (one test each).
- `ci.sonar = false` renders neither the Sonar job nor
  `sonar-project.properties`, and `release` needs only `validate`.
- `ci-entrypoint` passes on the rendered workflows, and fails on a fixture
  workflow that calls `uv` directly.
- For `python-lib`, `ci.yml`'s matrix lists every `config.packages` basename.

What the build settled that the story did not say:

- **The Jinja variable delimiters are `[[ ]]`**, as in `tasks`: every workflow
  carries GitHub's own `${{ }}` expressions verbatim. A pin is written
  `[[ pins["setup-uv"].uses ]]@[[ pins["setup-uv"].sha ]] # [[ pins["setup-uv"].version ]]`,
  because the table names carry hyphens.
- **The context gains `organization`**, which is `SONAR_ORGANIZATION` passed
  through, so the properties template names no literal organization.
  `artifacts.py` also exposes `load_pins()`, which reads `pins.toml`.
- **`ci.release = "none"` leaves `ci.yml`'s header comment alone.** The comment
  still reads `validate → sonar → release.`, as it does with Sonar off. That
  follows "everything else keeps its bytes".
- **`ci-pins` needs a `# <version>` comment containing at least one non-space
  character after the `#`.** It reads `*.yml` only, not `*.yaml`, as the story
  says. It checks `.github/actions/setup/action.yml` for pins too, but that
  file has no `jobs:`, so it can never report `ci.permissions`.
- **`tests/test_checks_registry.py` and `tests/modules/core/test_cycle.py`
  changed.** The registry test lists `ci-pins` after `ci-entrypoint`. A fresh
  default apply now also creates the setup action, `ci.yml` and
  `sonar-project.properties`.
- **The feature's acceptance block runs bare `actionlint`.** Without a `.git`
  directory, that exits with "no project was found". The tests pass the
  workflow paths explicitly (`actionlint .github/workflows/*.yml`), and that
  form passes for all three rendered repos. The block is the owner's, so it
  was left unchanged.

## S4.3.5 — `instructions`

**Status:** done (2026-09-16)

`README.md`, `CLAUDE.md` and `AGENTS.md` bodies, the kiln block in `CLAUDE.md`,
`.rn-forge/kiln/standard.md`.

**Renders** (property 1, in this order):

| Artifact | Kind | When |
| -- | -- | -- |
| `CLAUDE.md#rn-forge kiln` — `ManagedBlock("rn-forge kiln", comment="<!--")` | block | always |
| `.rn-forge/kiln/standard.md` | managed | always |

**The three bodies are a scaffold step, not artifacts.** The engine refuses a
whole-file write and a block write to the same path in one apply (learned in
S4.3.2), and the goldens' `state.json` records no entry for any of the three.
`modules/instructions/scaffold.py:scaffold(root, config)` writes `README.md`,
`CLAUDE.md` and `AGENTS.md` from `README.md.j2`, `CLAUDE.md.j2` and
`AGENTS.md.j2` when each is absent, and never otherwise — the shape of
`modules/docs/scaffold.py`. The kiln block lives in `CLAUDE.md` only;
`AGENTS.md` is a pointer to it, as every golden shows. (The design and the
reference said "the latter two"; the goldens are the source of truth, and both
now say this.)

**Build:**

- `modules/instructions/artifacts.py` exposes `render(config) -> list[Artifact]`

## S4.3.6 — The Sonar decisions

**Status:** planned · **Owner's story:** a decision, not code

The two questions below were parked on `cicd`. They are answered as an ADR or as
a rejected option recorded here; until then, S4.3.4 builds on the proposed
defaults, which are already what `CiConfig` and the goldens encode.

1. **Is Sonar on by default (`ci.sonar = true`) for every archetype, or
   opt-in?** Proposed: on by default. `CiConfig.sonar` defaults to `True`, the
   goldens assume it, and a repo that cannot have a `SONAR_TOKEN` sets
   `sonar = false` in one line. Opt-in would make every rendered cell pass
   without the gate the standard calls required.
1. **Are these repos public or private, and does it change anything?** Proposed:
   nothing generated differs. SHA pins and `permissions:` are generated
   regardless; the fork-PR skip on the Sonar job is the only visibility-aware
   line and it is harmless on a private repo. SonarCloud's `rn-forge`
   organization hosts both.

**Acceptance:**

- The answers are recorded: an ADR, or the questions above rewritten as
  *Considered and rejected* on this story, with the date.
- If the answer to 1 is opt-in, `CiConfig.sonar` defaults to `False` and the
  goldens' `config.toml` set it explicitly; S4.3.4's tests are unchanged.
