pykit's `rn-forge-devops` planner moves into `rn-forge-kiln` as
`rn_forge.kiln.devops`, with the console script `kiln-devops`. Generated tasks
call it through the `[kiln] ref` pin every repository already has, run with
`uvx` outside the repository's lock
([F7.4](../E7-pykit-release-pin-flip/F7.4-kiln-runs-beside-the-repository.md)),
and the pykit pin for it goes. The generated workflow's remaining inline shell,
which resolves the Sonar target and runs the single-package release, moves into
`kiln-devops` subcommands, so every one of those steps becomes a `task` call.

## Context

[ADR-0016](../../../adr/ADR-0016.md) made the CI contract kiln's, but its
implementation lived in pykit. A change to one needed a pykit tag, a pin bump in
`RN_FORGE_TAGS` and a kiln release. [ADR-0017](../../../adr/ADR-0017.md) puts
both in kiln. pykit takes the planner when it adopts kiln, in its own F16.3, and
then deletes its `rn-forge-devops` package in its own specs
([ADR-0009](../../../adr/ADR-0009.md)). Nothing in this feature waits on pykit.
The two console scripts have different names, so they can be installed side by
side.

**The source.** The code is pykit's `packages/rn-forge-devops` at pykit commit
`9eac94b` (branch `feature/release-6`), version 0.2.0: `ci.py`, `uv.py`,
`github.py`, `cli.py` and `__init__.py`, and 32 tests in `test_ci.py`,
`test_cli.py`, `test_github.py` and `test_uv.py`. Read it with
`git -C ../pykit show 9eac94b:packages/rn-forge-devops/<path>`. It is not on
pykit's `main`.

**Out of scope.** The workspace `release-build` task's loop (which builds in a
worktree, writes the SBOM and counts), `docs-publish` and `external-install`
stay as shell in `tasks/ci.yml`; moving them is a later feature.
[F7.6](../E7-pykit-release-pin-flip/F7.6-release-to-pypi.md) later extends
`release-publish` with changelog notes and a PyPI upload; nothing here changes
for it. The planner for non-Python workspaces stays an idea
(`rn-forge-devops-non-python`, renamed in S6.7.6).

## S6.7.5 — Releases go through `kiln-devops`

**State:** New · **Depends on:** S6.7.3

The single-package `release` job carries the release-state check, the tagged
checkout, the draft delete and the publish as inline shell. The workspace
`release-publish` task repeats the same `gh` logic. Three subcommands hold it
once, and both paths call them.

### The subcommands

All three live in `rn_forge.kiln.devops.github`. They load no workspace, so they
run in any repository. Every `git` or `gh` command they run writes its own
stdout to stderr, so a subcommand's stdout carries only its output lines. A
command that fails ends the subcommand with that command's exit status.

| Subcommand | Does | Prints |
| -- | -- | -- |
| `release-state TAG` | Reads the release with `gh release view TAG --json isDraft --jq .isDraft` (a failure means no release), and whether `git ls-remote --tags origin refs/tags/TAG` prints anything | `tag=TAG`, `should-release=`, `draft=`, `tagged=`, in that order, each `true` or `false`. A published release gives `should-release=false` and writes `Release TAG already published; nothing to do.` to stderr |
| `release-source TAG` | If the tag exists on `origin`: `git fetch --no-tags origin refs/tags/TAG:refs/tags/TAG`, then `git checkout --detach TAG` | `sha=<git rev-parse HEAD>` |
| `release-publish TAG --title TITLE --target SHA FILE...` | Reads the state as `release-state` does. Published: writes the same message and exits 0. Draft: `gh release delete TAG --yes`. Then `gh release create TAG FILE... --verify-tag --title TITLE --generate-notes` if the tag exists, otherwise `… --target SHA --title TITLE --generate-notes` | nothing |

Split each subcommand into a pure function and thin `subprocess` wrappers:

- `release_draft(tag) -> str | None`: `"true"`, `"false"`, or `None` when there
  is no release.
- `remote_tag_exists(tag) -> bool`.
- `release_state(tag, draft, tagged) -> dict[str, str]`: pure.
- `publish_commands(tag, title, target, files, draft, tagged) -> list[list[str]]`:
  pure. Returns `[]` when published.

The comments that explain why now live in their docstrings, copied from the
template's step comments: the release, not the tag, is the record; a tag without
a release means a failed release, which must rebuild from the tag; and
`gh release create` makes the tag at `--target`.

## Considered and rejected

- **Port the tests under their pykit names.** The board's procedure names every
  test after its story. The `test_s6_7_2_` prefix keeps pykit's name readable
  after it.
- **Keep the membership rule, so a workspace with an `rn-forge-devops` member
  runs its own.** pykit is the only such workspace, and it deletes the
  package. The rule would keep a second planner alive in kiln's generated
  tasks.

  on.** The tasks module would have to read the `cicd` config, which is a new
  sibling import. An unused task costs nothing.
