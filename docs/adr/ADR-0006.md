# ADR-0006 — Commit generated CI, and run the pinned kiln read-only

**Status:** accepted (2026-09-13) · **Scope:** CI in every repository kiln
generates

## Decision

Kiln generates and commits the workflows and the local composite actions. CI
executes the committed `task` entrypoints with locked dependencies, and never
applies a generated change.

CI runs the repository's pinned kiln ([ADR-0001](ADR-0001.md)) read-only,
through `task`. `task validate` runs `kiln doctor` on every run — the
render-free checks over committed files. A fuller gate runs where the workflow
asks for it: it renders for comparison, and still never replaces a repository
artifact.

A kiln upgrade, and any generated change that follows from it, is reviewed as a
repository change. Nothing is adopted implicitly during a build.

## Consequences

- A kiln release changes a repository's build only when that repository's pin
  moves, and it does so in the pull request that moves it.
- A bad release breaks no repository until someone moves its pin, and then it
  fails that pull request's CI rather than ten builds at once.
- Checker fixes arrive as a dependency update. Workflow fixes additionally need
  a regeneration commit in each repository — the propagation the committed-CI
  rule deliberately gives up.
- CI installs the generator's dependencies even on runs that only verify.
- Which kiln rendered a repository is recorded in that repository's lock, and a
  check asserts the running kiln is the locked one.
- A cold clone builds with `uv sync` and nothing else: no bootstrap script, no
  environment variable.

## Alternatives considered

- **Generate during CI, or install kiln unpinned.** A change released anywhere
  can then change a build with no repository change — a generator bug becomes
  a build failure in ten repositories at once.
- **Shared remote workflows from a devops repository.** Examined and rejected
  (D45): pinned reusable workflows cost the same per-repository churn as
  generation *and* add an external CI dependency, while floating them means
  unpinned CI. The reviewability they promised was bought instead with a
  committed composite action, `.github/actions/setup`.
- **Commit the checker implementations.** A checker fix becomes ten commits
  instead of a version bump, and the byte-identical copies need a test to
  guard them.
- **Publish a separate checks package.** Adds a second version line and a
  schema-skew check, and still cannot run the render-dependent checks
  ([ADR-0001](ADR-0001.md)).

## Background

The rule started stricter — CI runs committed code and never installs kiln —
which is why a generated repository was about to carry its checkers as committed
scripts. S4.1.4 narrowed it on 2026-09-13 to what the objection actually
protected: *CI never writes a generated file, and never runs an unpinned kiln*.
Pinning was the missing distinction; with the pin, a release is inert until a
repository's lock moves.

What stays committed is what CI must trust without re-deriving it: `state.json`,
`config.toml` and `standard.md`. The checker logic does not, and `scripts/` left
generated repositories with it — it now holds only a repository's own lints,
wired through `[tasks.extra_refs]`.
