# S7.8.2 — `task kiln:upgrade`

Brief for
[S7.8.2](../F7.8-existing-repos-take-the-pin-table.md#s782-task-kilnupgrade), at
`871e2b1`, after S7.8.1 and S7.8.4.

## Goal

Expose one upgrade operation that uses the target kiln's templates and
dependency floors, then validates the candidate repository. The operation owns
recovery from the first repository write.

## Current behaviour

`commands/config.py:97` resolves the pin and writes `config.toml`.
`modules/core/kiln_ref.py` resolves a branch or tag to its commit.
`modules/tasks/templates/tasks/kiln.yml.j2` runs pin and apply in separate
processes. The original upgrade draft added another process for dependency
migration, leaving the first two commands outside its recovery boundary.

## Change

- Add an upgrade command invoked by the generated task. Share the read-only ref
  and tracking resolution with pin. Preserve pin's existing CLI and behavior.
  The launcher dispatches once to kiln at the resolved commit. Pass the
  candidate pin and tracking information to the target entry point without
  writing them to the repository. A target without upgrade support fails
  before writes.
- In the target process, validate the candidate config, prepare the shared
  artifact plan from S7.8.4, and plan range moves from S7.8.1. Preserve other
  repository config. Report the candidate pin, artifact changes and range
  moves. Refuse blocked plans before writes.
- The coordinator checks for a clean tree, including untracked files, before
  writes. Record the original bytes and existence of affected paths before
  each write stage. Include the config, state, managed creations and removals,
  docs finalization, changed manifests and lockfiles used by setup. Use this
  footprint for restoration. Preserve unrelated paths and report residual
  changes. Do not use a repository-wide reset or clean.
- Execute the prepared plan through the shared apply path and write the
  candidate state before running the candidate's `task setup` and
  `task validate`. Reuse the process wrapper, extending it for streamed task
  output if needed. Both tasks run in sequence even when no range moves are
  planned. A setup failure skips validation.
- Recover from any failed write, finalization or gate step. Once setup has been
  attempted, run setup again with the old config and locks restored. Verify
  the restored files and report any failure to recover the tree or environment
  alongside the original error. With `FORCE=1`, keep a fully applied candidate
  on setup or validation failure and return nonzero. Refusal and partial apply
  still leave the old revision in place.
- Keep release notes outside the write and recovery path. Use the helpers in
  S7.8.1 and report a link if a fetch fails.
- Render `kiln:upgrade` next to `kiln:pin` for the same repositories. Forward
  the optional ref and map `FORCE=1` to the command's force option. Add
  `upgrade` to the allowed public kiln tasks. Update the canonical reference
  and generated standard template with the task, its clean-tree requirement
  and recovery behavior. Re-render generated files through `task kiln:apply`.

## Tests first

- Cover branch, tag, SHA and tracked-branch resolution, and assert the launcher
  selects the resolved commit without touching the checkout. Cover dirty
  trees, unavailable targets and blocked plans.
- At the target entry point, use throwaway repositories and fake only the
  external tasks. Make old and target floors and artifacts different. Assert
  that setup and validation see the candidate pin, artifacts and state.
- Inject apply, finalization, setup and validation failures. Verify the old pin,
  state, changed manifests and lockfile are restored, new managed files
  disappear, removed ones return and unrelated paths survive. Test recovery
  setup failure, and test the successful and failing force paths.
- Check the generated task surface, flag forwarding and canonical and rendered
  docs. Test one upgrade with zero range moves.

## Validation

- Run the focused command and task tests through `task test -- <paths>`.
- Run `task kiln:apply`, review the render-matrix diff and run
  `task validate KILN_DOCTOR_FULL=1`.
- Record the two adopter runs in the feature's acceptance.
